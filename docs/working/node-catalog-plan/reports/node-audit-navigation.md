## Findings recorded during inspection

- The catalog already defines `web.browser.tab` and `web.browser.download` in addition to navigate (`domain/src/actions/schemas.ts:349,355`); the working plan's catalog list omits them. Extend these owners rather than propose duplicate nodes.
- `runtime/navigation-target.ts` already preserves FluxIQ/browser pages and drives the active ordinary page, with a fallback to the last automation/new tab. Earlier wrong-tab live failures motivated this landed code; they are not proof the current implementation still has the defect.
- `runtime/navigation-outcome.ts` compares destination plus document/URL movement; missing movement evidence is marked unknown, not failed. Current action-level success cannot independently certify a user outcome.
- `runtime/browser-download.ts` admits missing/invalid completion timestamps and uses a 15-second lookback without initiating-action correlation: a source-confirmed false attribution risk requiring a regression.

## Existing contracts and execution path

The public action IDs are `web.browser.navigate`, `web.browser.tab`, and `web.browser.download`; registered output-node IDs use `web.output.browser-*`. Definitions, schemas and gateway mapping already own these capabilities. `domain/src/actions/schemas.ts:221` requires navigate's URL and permits `newTab`; `actions/types.ts:293` defines tab open/switch/close and `types.ts:303` defines download filename/timeout. Definitions expose the structured tab/download parameters at `output-nodes/definitions.ts:310`. These are executable registered outputs, not passive evidence inputs.

Trace: `domain/src/output-nodes/native-runtime.ts:77` -> policy output dispatch -> `domain/src/client/gateway-mapping.ts` and `gateway-action-parameters.ts` -> `background/connection/server-command-channel.ts` -> `apps/extension/src/runtime/action-runner.ts` -> browser APIs for tab/download/navigation or frame-addressed content execution. Parameter normalization lifts `tabId`, `frameId`, `frameUrlPath`, `newTab`, structured tab/download options and check-wait policy. Preserve that seam when changing contracts; synchronize action types, schemas, definitions, gateway normalization, protocol, runtime and tests.

Output/route contract: native implementation initially returns `status: success`, `route: success`, `outputs.success: true` **for preparing a dispatch**, not for completing the browser action. Actual command outcomes are promoted by `domain/src/io/gateway-output-dispatcher.ts:25..52` and runtime adapter. Browser results include command/action IDs, succeeded/failed/timed_out status, bounded expected/actual validation, message, timestamps, optional structured failure and URL/title; `action-runner` adds target tab/frame. Browser-family nodes have no custom `ended` route (that is next_page's contract). Gateway mapping carries result evidence/checkWait; workers do not have a DOM snapshot unless they explicitly request one. Navigate/tab successes generally carry URL, navigate can carry title/checkWait, and download success carries only basename in message/validation. Download wait defaults to 30 s, clamped to 1..120 s. Preserve failure categories and avoid treating the prepared-dispatch success as task completion.

## Outcome, consent and challenge rules

Preserve existing supported-page guards and explicit ordinary-page target selection. `navigation-target.ts` already handles the earlier wrong-tab failure; do not replace it with a new convenient active-tab fallback. Served status comes from the page navigation performance entry and can be unread, especially with browser differences; unread status is not a known 200. Soft-error pages returning 200 need an expected page/outcome check rather than a fabricated HTTP error.

`landed-challenge.ts` recognizes robot landings; person-needed checks return handoff, and `landed-check-wait.ts` only waits for self-clearing checks within budget. Credential/code challenges need explicit handoff evidence, not generic retry/click. Consent/interference handling already prefers Reject/close, does not automatically accept marketing, and avoids disabled/outbound controls. Preserve those choices. Page waits must express the requested predicate; generic network idle is not available from DOM and must not silently enable requests.

An action transport receipt and independent task completion remain distinct. Unknown movement/challenge/coverage should be represented explicitly and block claims needing it; this report does not propose failing every DOM action merely because optional performance status is absent. Requests remain OFF by default. JS is last resort after approximately three failed typed approaches, with scope/reason/result recorded; no debugger for JS.

## Proposed public additions, after fixing existing owners

1. `web.browser.back`: `{tabRef?, steps: 1, expected?: {urlPath?, origin?, pageMarker?}, timeoutMs}` -> movement/document receipt plus landed gates; absence of history is distinct from success. This reduces repeated list/detail/tab constructions. Regression: BFCache restoration, no history, unexpected foreign history entry, same-URL SPA popstate, challenge after back. Existing internal goBack recovery is reused only where its contract matches.
2. `web.browser.wait_for_navigation`: `{tabRef?, afterActionId, expected?, timeoutMs}` -> correlated URL/document transition and landed receipt; arms before triggering dispatch or consumes a retained event receipt. A post-hoc listener must not miss a fast transition. Tests: instantaneous transition, same-document history update, timeout, wrong-origin transition, child frame versus top frame.
3. Extend `browser.tab` with provenance-bound tab references/list evidence and extend `browser.download` with trigger-correlated receipt. Do not create duplicate open_tab/download nodes. A new node is justified only if a distinct contract cannot be expressed through the existing registration.
