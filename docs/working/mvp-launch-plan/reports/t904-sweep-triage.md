## Open questions or contradictions found

- **Coordinator's question: why is a cleared check met again after Continue? (rows 5-6)** On dev it is not. In the failing tests the check was never cleared: `nativeNodeExecutor` returned `CHECK_RESULT` for the `check` node on every call. Since 806a3004e, Continue runs the step again (`person-cleared.ts`: no floor, so `automationStudioNodeRepeatCannotAct` gives a rerun). The rerun calls the executor afresh, with no cached result. The failure's three distinct ask ids (`opened.1..3`) show three fresh executions. The engine then read the stub's answer as a check still on the page, as documented in `person-needed.ts`. With a stub that clears the check once the person completes it, unchanged dev code finishes with one ask: ask-activity 7/7, step-count 4/4. On t902's tree, which removed the three-ask ending, the same stub loops to the step ceiling; the stub fix removes that too, since the check is gone after Continue. No dev product code is implicated, and nothing here depends on t902.
- **Coordinator's follow-up: should a cleared check with no recorded action effect go on rather than re-run?** No, and I did not change product code. The test's `check` node has no floor and no metadata, so `automationStudioNodeSideEffectClass` is `none` and `automationStudioNodeRepeatCannotAct` is true (`engine/automation/defensive/node-side-effect.ts:77-79`). That is the class of a read, look or wait. 806a3004e runs such a step again after Continue on purpose: the attempt that met the check never saw the page's content. Going on without the step is the defect 806a3004e fixed, a step walked past and a list read over the wrong rows (`run-mwapfy0i-d64b26db`). In the product every web step has a floor from the domain, and a plain press with a floor still goes on (`person-cleared.ts`).
- **How each ask-activity and step-count case ends now (on its own merits, with no step cap, ask limit or timeout involved):** Continue in place: the person completes the check (`checkCleared = true` as they answer), the step re-runs on a cleared page and succeeds, `read` and `End` follow, 1 ask, `succeeded`. Parked then resumed with Continue: same, 1 ask, `succeeded`. Stop: `failed` route, run ends, 1 ask. Nobody answering: `timed_out`, `failed` route, 1 ask. Cancelled while waiting: abort, `cancelled`. Thread unreadable: the port throws and the run ends. Mismatched answer: `refused`. Refused resume: `refused` with no rows. None of these reaches a second ask, so t902's removal of the three-ask ending and of rechecks from the step count cannot make them run on.

- **Step card said twice on a rerun (row 6).** Since 806a3004e, a step whose check a person cleared runs again and posts its card again ("Running step 2 of 3" twice). The count stays right, so I made the test expect it. If the chat should say a rerun differently (for example "Doing the step again" alone), that is a product decision. `person-cleared.ts` already emits a "Doing the step again" thought.
- **Other harnesses.** Other scenario harnesses (everything-store `browser-kit.ts`, social-network-feed, auction-marketplace, company-website `site-driver.ts`) also treat a click as done when Playwright returns. They have not failed in this sweep. `requestsAnswered` is shared so they can adopt it if they show the same race; I did not change them.
- **Recurring cause.** Rows 1-4 broke because four fixtures each copied Core's library list. The lease fixture now derives from `CORE_PACKAGES`. The other three keep explicit literals because they are assertions, so the next change to Core's list will fail them again, visibly, as intended.
