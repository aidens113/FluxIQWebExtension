# W-4 verification verbs: report

Brief: `w2-w4-verification-verbs` (design `reports/w2-back-half-design.md`,
section 2.2 and section 8 row W-4). Worker report; not supervisor-verified.

## Outcome

Done. The web domain's `web.dom.assert`, `web.dom.wait_for_text` and
`web.dom.wait_for_selector` output node definitions now carry
`metadata.verifiesState: true`. Core's change verdict can therefore count a
later one of these nodes that succeeded as a `downstream_assertion`. No other
definition carries the key, not even set to `false`.

## What changed and why

- `domain/src/output-nodes/definitions.ts`
  - New private constant `VERIFIES_STATE_METADATA_KEY = "verifiesState"`.
    Core's constant `AUTOMATION_STUDIO_NODE_VERIFIES_STATE_METADATA_KEY` exists
    in Core source at `aab40c1`
    (`AS/runtime/flow-change/contracts.ts:173`), but Core's **built** output
    does not include it yet: `packages/fluxiq/dist/programs/automation-studio/runtime/flow-change/`
    does not exist, and `dist` contains no `VERIFIES_STATE`. The domain
    resolves `fluxiq/automation-studio` through `dist`
    (`packages/fluxiq/package.json` exports), so the literal is used for now.
  - New private set `stateVerifyingOutputs`, holding the three action types.
    In `createWebAutomationOutputNodeDefinition`, the metadata spreads
    `{ [VERIFIES_STATE_METADATA_KEY]: true }` only for those three. It is a
    fixed list, not derived from the schema: the design names these verbs
    explicitly, and nothing in the action schema distinguishes "proves state"
    from "changes state".
  - A doc comment explains why these three count and why reads
    (`extract`, `extract_list`, `capture_snapshot`) and actions do not.
- `domain/src/output-nodes/tests/definitions.test.ts`: one new test,
  "exactly the verbs that prove the page's state tell Core their success
  verifies a change". It checks that:
  - the set of nodes with `metadata.verifiesState === true` is exactly the three
    verbs, sorted;
  - each of the three still passes Core's `validateAutomationStudioNodeDefinition`
    (the existing first test also validates every node);
  - every other node does not have `verifiesState` as an own key at all.
  The key is spelled out in the test as a literal rather than imported from the
  domain, so a misspelt constant fails the test.
- `domain/src/tests/domain.test.ts`: **not changed**. It does not pin
  output-node definition metadata. Its only `metadata` assertions are about the
  action capability, at lines 302-303.
- `domain/.test-build/**`: regenerated by `pnpm test` in `domain`, which is the
  unlabeled run and writes the tracked directory. The run rebuilt every bundle,
  so the tracked directory now also reflects other workers' in-progress domain
  sources as they stood at that moment (see "Open questions").

**The one-line switch** once Core's built output exports the name: in
`domain/src/output-nodes/definitions.ts`, replace

```ts
const VERIFIES_STATE_METADATA_KEY = "verifiesState";
```

with an import of `AUTOMATION_STUDIO_NODE_VERIFIES_STATE_METADATA_KEY` from
`fluxiq/automation-studio` (aliased or with the use site renamed), and delete
the "literal stands in" paragraph of its comment. The test needs no change.

## Not verified

  run against these definitions, and no Lab or live run was made, as the brief
  required ("No live calls").
- I did not rebuild Core's `dist`, because `F:\!FluxIQ` is outside this brief.
  So the switch to Core's exported constant is untested.

  known load failure, which is deterministic and has a real assertion diff.

## Open questions or contradictions found

- The brief describes `domain.test.ts` as failing "to load because of a Core
  catalog problem". What I observed matches: the file fails at load time
  because Core's catalog selection leaves out the required term `end`.
- The unlabeled `pnpm test` rewrote every file in `domain/.test-build`. If
  W-1, W-2 or W-3 had uncommitted source edits at that moment, those edits are
  now in the tracked bundles. The supervisor should regenerate
  `domain/.test-build` once more, after all the domain workers land and before
  committing.
- `web.dom.wait_for_selector` takes a `wait` condition. If that condition can
  mean "hidden" or "detached", success still proves a stated page condition, so
  it fits the design's rule. I did not read the wait condition's schema to
  confirm this.
