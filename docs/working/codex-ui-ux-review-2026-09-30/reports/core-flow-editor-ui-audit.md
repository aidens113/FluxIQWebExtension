## Source-confirmed local behavior

FlowGraphToolbar delegates selection operations to NodeSelectionActions with canEdit=isFlowMode. Add node is disabled outside Flow mode; its palette and outline IDs/expanded states are passed explicitly. Fit graph remains enabled and optional-chains flowInstance.fitView; a null instance therefore produces a no-op. Whether a null instance is reachable in the actual mounted toolbar requires its controller/canvas contract. No keyboard handler exists in these three files; declared F/A shortcuts do not prove a keyboard defect because controller/canvas implementations were deliberately excluded. Toolbar arrow navigation, text-input shortcut isolation, selection eligibility and graph-library focus behavior are unverified.

FlowEditorActionsProvider intentionally preserves one stable context value and forwards each action through the latest actionsRef. This correctly accommodates ordinary callback replacement; function identity cannot serve as graph/project authority. The provider has no explicit graph/project/actor owner or mounted lifetime guard. Consequently a retained public action function continues invoking its last actions after provider unmount, and while mounted it forwards any supplied node/edge ID to the newest implementation. This is a source-confirmed bridge behavior, not proof a real stale graph event reaches it or that the callee lacks its own guards. Protected execution/persistence ownership remains opaque.

FlowEditorView has explicit detail-load-error/retry, summary-loading, absent-graph start-pane, and lazy hydrated-canvas branches. Detail load error is visible with role=alert; summary loading exposes aria-busy and polite live feedback. The lazy Suspense fallback and the start-pane readiness spinner provide visible text but have no corresponding local busy/live semantics. An outer live region could change actual announcement behavior; no AT/browser assertion is made. An undefined onReloadGraph would produce an enabled no-op retry, but whether this prop is optional/absent requires the excluded direct props contract.

The start pane keeps readiness in local state and advances generation only when its effect starts a new load. Older settled requests are correctly rejected after a later effect advances that generation. There is no effect cleanup invalidation or result owner stored with readiness. On a project/flow props change, the render still evaluates prior readiness against the new props until the next effect resets it. Thus the local code has an owner-change/render window and may pass old readiness into current authoring/improvement eligibility; a pending old result can also call its setter after unmount because the generation remains unchanged. React retirement may ignore that latter publication, so it alone is not a demonstrated visible defect. Whether the former can enable a wrong action depends on the two named eligibility helpers, which were not read. Do not infer command mutation ownership from their names.
