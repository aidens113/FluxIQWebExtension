## Concrete findings

1. **Rejected list/detail requests leave busy states set.** `loadActionPage` (line79), `loadRunDetail` (101) and `loadEventPage` (115) await commands without catch/finally. A rejected promise bypasses the loading reset. Effect/button callers use `void`, so they also leave an unhandled rejection. Existing failure-envelope handling only covers fulfilled `{ ok: false }` responses.
2. **Malformed fulfilled responses can throw or corrupt pagination.** These loaders dereference `result.ok` without an envelope check, accept truthy compact detail without a structural check, and accept action/event arrays and page fields without runtime validation. Non-array event payloads fail at the spread; null rows fail during merge/render. Non-array actions fail at rendering. Invalid offsets/limits/cursors/high-water sequences can reach pagination. Treat absent optional fields according to the existing contract, but reject invalid supplied shapes and conflicting run identity rather than silently claiming an empty successful page.
3. **Compact-detail failure has no useful retry when detail is absent.** The empty-detail render branch (269) displays the error in header text but only offers action-list retry. Compact-detail Retry exists in the hydrated branch (297), which is unavailable for an initial compact-detail failure. When supplied detail exists, `loadRunDetail` returns immediately; that button cannot repair an external parent error by itself. The bounded fix should expose retry for the local failed compact read, without inventing a parent refresh contract.
4. **Command owner changes are not scoped.** The reset effect (193) depends only on projectId/runId. `useRuntimeDetailCommands` creates a new command object when transport changes, but the view neither aborts old requests nor resets/refetches for this change. Owner identity must include project, run and commands. Existing request counters handle replacement requests and passive project/run resets, not a changed command owner by themselves.
5. **Retained callbacks mutate state before checking current owner.** `selectAttempt`/`selectEvent` synchronously abort existing work, increment counters and set selection before issuing a request. A callback captured under an old owner can therefore cancel a new owner's request or show an old row after navigation. List, pager, retry, close and export handlers need a current-owner check before any mutation or request. Completion guards must also include owner/mount generation, not only per-request counters.
6. **Old local data can appear on the first new-scope render.** State is cleared in a passive effect. `props.runDetail ?? loadedRunDetail`, action/event pages and selected detail can display the preceding owner until that effect runs. Tag local results with their owner and mask mismatched results during render. Supplied parent detail must retain its established compatibility contract; do not change backend shapes to solve this frontend problem. Reset omissions also include actionError, exportPreparing and eventScrollTop.
7. **Action pager commits navigation before request success.** Next/Previous (185–191) change index/cursor history before loading succeeds. A failed next page leaves old page data and offset with a new cursor index; Retry then combines the old offset and new cursor. Keep the last confirmed page/index/history together and retain the failed requested query for retry, committing navigation only when that request succeeds.
8. **Audit export lacks request recovery and scope ownership.** `exportAudit` (239) has no catch/finally, request generation, abort or synchronous duplicate lock. Command rejection, null envelope, malformed audit, serialization failure or download failure can leave Preparing set. Late export results can download an old run and overwrite feedback after project/run/commands changes or unmount. An obsolete finally must not unlock a newer export. Check current owner before requesting, after each await and before download; keep the request-owned lock separate from React's asynchronously rendered disabled state.
9. **Download cleanup has an exceptional-path leak.** The download object URL is revoked only after anchor creation/click and timeout scheduling succeed. If any of those operations throws, revocation is never scheduled. Acquire/release the URL through an explicit cleanup boundary, preserving deferred revocation after a successful click.
10. **Serialization worker cleanup is incomplete.** `runtimeAuditBlob` (366) revokes its script URL in finally and terminates on message/error. A throwing `postMessage` rejects without terminating the constructed worker. Worker responses are cast to Blob without checking shape; there is no messageerror handler or cancellation on owner change/unmount. The fallback JSON stringify can reject for cyclic/BigInt input; export must surface that as retryable feedback and clear busy state. A worker that never responds is a separate liveness concern: do not claim rejection handling proves recovery from an indefinitely pending transport/worker. Cancellation should terminate the worker and release the script URL.

## Required meaningful regressions

- Deferred rejection followed by successful retry independently for actions, compact detail, events and export; verify visible error, released busy control and no unhandled rejection. Initial compact failure must offer its own usable Retry.
- Null/malformed envelopes, non-array pages, null rows, invalid supplied pagination fields and conflicting returned run identity recover safely; legitimate empty pages remain valid.
- Fail Next Actions, then retry: request parameters and displayed range/cursor history follow the intended page, with previous confirmed data retained truthfully until success.
- Switch project/run and separately commands while each request is pending. Late success/rejection must not publish data, error, busy state, cursor state or a download into the new owner. Unmount must similarly fence completion and release local serialization resources.
- Invoke retained old select/retry/pager/close/export callbacks after switching owner: no request, no mutation and no cancellation of current-owner work. Exercise render-before-passive-effect masking explicitly rather than relying on `act` flushing effects before assertions.
- Start a new export after owner change while the old one remains pending; settling the old export cannot clear the new busy state. Two same-owner export activations before React renders issue one request.
- Reject serialization and anchor/download setup; show retryable export error and release busy state. Verify worker termination and script/download URL revocation on success, error, messageerror, throwing constructor/postMessage, invalid worker result and owner/unmount cancellation. Preserve a successful large audit export and existing detail/refresh tests.
