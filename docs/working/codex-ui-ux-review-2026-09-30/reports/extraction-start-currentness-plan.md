## Source-confirmed boundaries

control.startPick captures activeTabId/list/newId, stores via sessions.start but discards the returned object, awaits ensureContentScript, sends pickStart, and only inspects transport reply. Current failure/refusal cleanup clears by ID and successful acknowledgement returns sessionId/tabId/form without checking that stored object survived. Store start returns a NEW ExtractionSession object, first clears the same tab, stores that object under its ID and updates legacy latest pointer. get(id) can establish exact object identity. clear/clearTab also synchronously retire preview reads and erase rows. State mutates on the same object: picked sets picked/proposal, refused stays picking, markRecorded sets recorded. These are enough for local object fences; no store API/edit or generation field is needed.

cancelPick captures and clears its selected session synchronously before awaiting the exact-ID content cancel. A later start may therefore create B while A's ensure or send is pending. clearTab/navigation, same-tab replacement, intentional synthetic same-ID replacement and recording transition are likewise visible through get(capturedId) and captured.state. Existing cancellation/Confirm behavior must remain unchanged by this unit.

acceptPick writes real refusal state through sessions.refuse then immediately invokes rearmPick; rearm currently sends captured ID/form without a current-object/state guard and ignores transport rejection. After that await acceptPick still acknowledges the original ID or original value refusal even if that session disappeared/replaced. There is no normal await between refuse and rearm dispatch, so the pre-rearm guard is a defensive reentrancy boundary; the post-await acknowledgement boundary is an actual asynchronous retirement schedule. Do not pretend a pre-rearm race was reproduced in a real browser.

Held dispatch evidence from the earlier bounded plan remains relevant but was not reread here: actual sendToTab invokes chrome.tabs.sendMessage synchronously inside its Promise executor. With the current production implementation, a check immediately before deps.sendToTab fences work not yet issued. A dependency wrapper that itself delays real dispatch would need its own contract; this two-path unit does not add one.

## Exact implementation decisions

1. Capture const session = deps.sessions.start(sessionId,tabId,form). Define a local predicate/closure for stored exact object, not ID equality alone. Do not reread manager.activeTabId to silently retarget an already-started operation; its originally captured tab/frame0 stay fixed while that stored object is current.
2. After ensureContentScript resolves, and immediately before constructing/issuing pickStart, require deps.sessions.get(sessionId)===session AND session.state==="picking". If retired, replaced, cleared or already transitioned, return existing no_session refusal without sending. No extra await, microtask, provider call or generation allocation between guard and deps.sendToTab.
3. After send settles successfully, require the same stored object and an active state (picking OR picked) before returning usable acknowledgement. A genuine fast user pick can arrive while transport acknowledgement is pending, so requiring picking at this boundary would reject valid current picked data. Recorded is no longer an active picking attempt and can return no_session. Preserve actual sessionId/tabId/form acknowledgement exactly.
4. For a transport refusal/rejection or ensure failure, cleanup ONLY if the same captured object is STILL stored AND still picking. Old catch/refusal must never clear another object under the same ID; late transport uncertainty must not erase actual fast-picked evidence. Current still-picking failure clears as before and returns page_refused with existing error handling. Current picked data is retained even when transport fails, so the already-built frontend uncertain-start Retry can verify that real session instead of losing it. Do not silently return successful start from a failed transport.
5. If the attempt is retired/replaced when a failure arrives, return no_session rather than a misleading successful acknowledgement; do not clear or mutate replacement. Existing transport/page refusal contract remains for a still-current failed attempt. Exact precedence should be pinned in NEW tests for both rejected ensure and rejected/refused send.
6. rearmPick checks exact stored object AND picking state before issuing its original captured pickStart to captured tab/frame0. It keeps current refusal state on rejection as before. No store write or extra retry is added. After await in acceptPick, check that captured session remains exactly stored and active before its original success/value refusal acknowledgement. Preserve current original refusal branch; a fast second successful pick on the same object remains accepted. Retired/replaced/recorded old acknowledgement returns no_session. No new record/cancel dispatch fencing is claimed here.

Existing no_session/page_refused codes suffice. For the new inactive-picking branches, recommend calling existing refuse("no_session", "That picking attempt is no longer active. Try again.") so the authored sentence truthfully addresses this captured attempt even if B or already-picked A exists. The existing default Confirm no_session sentence and every established vocabulary/count/Define response remain unchanged. This uses the existing error override, not a shared refusal union/name or new wire field. It must not quote page data or transport internals.
