### Workspace owner and lifecycle

Keep IdentityAccessLive public export and pure visibleIdentityUsers/isLastEnabledAdmin exports. Public wrapper derives a render-owned token from api identity and actual currentUser.id and renders a private keyed workspace. Same API/actor plus changed displayName does not remount or discard edits. Old wrapper tokens fail identity equality during render before effect cleanup; private workspace combines that predicate with a mounted ref cleared by layout teardown. Layout cleanup aborts the current explicit read and invalidates request/dialog epochs. No shared helper/OperationGate/Modal/transport change is needed.

Configured authorization factors are distinct from actor identity: preserve the existing snapshot-derived actor PIN rule and currentUser TOTP rule. Current actor role/factor policy changes must invalidate retained submit callbacks and old proof-bearing dialog epochs before POST; do not infer new actor identity from cosmetic names. Keep policy state in the view, with actual policy primitives compared during render. Mask or clear proof-bearing dialogs on a policy transition rather than leaving stale credentials eligible for a new authorization policy. Same-owner profile/query/selection drafts need not be reset by a harmless name update.

A latest-actions ref updated during render checks retained entry callbacks against the current named function. Entry guards precede operation.run and any POST. Async response/finally guards use captured workspace token, request/dialog epoch and bound subject, rather than function equality that could be broken merely by a busy-state render. All operation labels keep the existing synchronous gate and busy-modal contract. Each operation catches an unexpected API rejection into fixed local feedback; ordinary transport refusal still uses the returned response and existing requiresRecheck guidance. No automatic replay, additional operation gate or promise-as-cancelled-server claim.

### Subject-bound dialogs

Add userId to CredentialEdit and construct it in beginCredential from the explicitly selected user. The credential modal description, save validation and POST use that id, not a reconciled selectedUser. Enrollment state becomes a subject-bound setup record carrying userId plus validated material and the captured authorization factors; confirm uses setup.userId. Its displayed subject resolves that id in current confirmed users. No change to begin-totp/confirm-totp wire field names or retained-factors-between-calls policy.

Profile/role/enabled/disable already carry ids; every privileged submit verifies its captured id still belongs to current confirmed users, and last-enabled-admin disable/role guards continue to follow the current list. Missing subject masks that dialog during render and invalidates its epoch; passive state cleanup may follow but cannot be the fence. Changing the detail list's selected row is never interpreted as permission to retarget an open credential or enrollment flow. TOTP ClipboardButton keys and displayed material follow the bound setup userId and value; existing clipboard acknowledgement remains intact.

Local per-kind dialog epochs increment synchronously on open/close/replacement and render-invalidated subject/policy changes. Captured old input/change, close and submit handlers require the exact epoch and workspace. Old success/refusal cannot clear, reopen, populate or attach feedback to a newer same-kind dialog. Authorization proof is dropped when a dialog closes/finishes or becomes invalid; create cancellation continues to clear the whole new-user form, while same-owner refusal retains current editable draft. Existing Modal disables normal close/Escape while busy and stays unchanged; tests distinguish retained/programmatic callback races from an unavailable user gesture. Any optional draft revision guard must protect changed drafts from old completion without making ordinary busy rerenders suppress valid acknowledgement.

### Explicit snapshot recovery

Separate last confirmed IdentityAccessSnapshotResponse from loading/read error and acknowledged mutation status. A scoped read captures monotonically increasing request id and AbortController, invalidates/aborts the old read and checks mounted workspace owner/id/signal before request, completion and finally. Initial read and direct Retry/Refresh use the same lifecycle. Replacing API/actor masks old snapshot/dialogs immediately through keyed ownership. No periodic sensitive-store polling and no transport/coordinator edits.

Validate minimal fields actually consumed by the UI: object payload; users array of id/username/displayName/roleId strings and expected boolean flags; roles array of id and string permissions; sessions array with userId; vault object with boolean initialized/unlocked and optional safely typed display fields. Preserve optional contract fields and genuine empty arrays. Malformed ok success becomes a fixed recoverable read error, not empty-ready data or a map/filter crash. Exact optional checks will follow actual exported frontend contract and existing source consumption when released; no invented backend schema semantics.

Initial/no-confirmed-data failure shows the unavailable screen with direct Retry. Same-owner failure after data exists keeps confirmed users/roles/policy visibly stale with fixed error and direct Retry, while preserving current drafts. Add manual Refresh to current workspace if needed to support explicit external metadata confirmation; reads remain user-triggered only. Initial and refreshed loading states stay distinct. Mutation acknowledgement is shown independently of any failed reconciliation read; a successful write is never relabelled failed or automatically repeated because the read failed. The existing operation lock can continue through reconciliation while its acknowledged receipt remains visible; unmount/current-owner invalidates UI publication only, not an already issued server action.
