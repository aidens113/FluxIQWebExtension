## Findings

The real backend already has extraction session identity. Production frontend discards its typed representation and routes read/Confirm/cancel implicitly to the latest background session. Control-page authorization and top-frame sender checks exist, but neither proves that an open draft still belongs to the session those implicit commands select. Findings below are source-confirmed paths and adversarial schedules, not executed reproductions.

Progress checkpoint: source confirms backend view really includes sessionId/tabId/form, while frontend view omits those typed fields and client sends no sessionId for read/Confirm/cancel. Backend omitted-ID lookup uses latest-started session globally, not current active tab; trusted control-page sender is enforced independently. Content picks/Escape validate real sessionId + sender tab + frame0. Recorded host is mounted once and intentionally reparented between recording bar and automation entry; frozen HEAD shell inspected rather than active shell worker changes. Continuing asynchronous replacement and host teardown boundary review. No gates or source edits.

## S1 ? Replacement draft can address the wrong production session (high priority)

Concrete source schedule: panel A restores picked extraction A, retaining draft A. Another trusted surface starts extraction B (same or different tab), setting store.latestId=B. Panel A Confirm or cancel carries no ID, so control.ts:295/273 chooses B through sessionIdOf(undefined)/sessions.get(). Cancel forgets B; Confirm uses B proposal.item with A submitted columns/labels because recordedListExtraction uses the held proposal item and independently submitted fields (definition.ts:57,142). confirmRequest.item is not an ownership check. Backend validation may refuse some mismatches, but does not prove A/B equality. A new read similarly discovers B, and panel.applySession initializes a proposal only when draft is absent (panel.ts:202), permitting old draft retention across replacement.

This is not a finding that arbitrary page code can drive extraction: exact control-page origin checks remain enforced. It is a same-extension multi-surface/user-context correctness defect. Source-confirmed real IDs in the backend mean a frontend extraction-ID fix need not invent wire fields; runtime already accepts optional message.sessionId (control.ts:350). Fixture extra fields are not the evidence; actual backend reply/store are.

Existing extraction-control/confirm tests normally send explicit sessionId, while production client does not. Boundary tests cover hostile origins, no storage writes and frame/tab mismatch, not implicit-client replacement. Their passing status from earlier units does not certify this adverse schedule; no test was run here.

## S2 ? In-flight operations lack post-await session/current-owner checks

- readSession captures session before await refreshPreview, then serializes that same object even if clearTab/navigation/cancel/replacement deleted it (control.ts:224?239). Store.setPreview safely no-ops for missing IDs, but that does not invalidate the captured reply object. A restored response can therefore represent a discarded session; current UI epoch fencing only helps when the UI itself changed epoch.
- startPick stores A, awaits ensureContentScript then sends A pickStart without rechecking A is still current (control.ts:125?144). Replacement B or top-frame navigation during that wait can leave a stale A overlay command after A was removed.
- cancelPick clears A before awaiting content delivery. Another start B can replace the content picker meanwhile; content pickCancel for A calls stopPick unconditionally (picker/messages.ts:70). Typed IDs are carried but not enforced at this receiver.
- Confirm checks recordingState once, captures selected session, records definition then reads asynchronously (control.ts:294?319; confirm.ts:66?98). Replacement/navigation/recording owner changes during awaits are not rechecked at dispatch boundaries. markRecorded(A) after removal is a no-op, yet old success counts can return to a same-local-epoch panel. Issued recording/action work cannot be retroactively cancelled by a UI fence.

A fix must distinguish operations not yet dispatched, replies not yet published, and already-issued mutations. Do not reject an old completion while claiming its recorded definition/action never happened. Domain recording-first semantics and count-only replies must remain truthful.

## S3 ? Preview ordering and privacy ownership is also missing in backend

refreshPreview concurrent requests have no request object/revision guard. An older broad read can finish after a newer narrow read and overwrite store.preview/previewKey; an old refusal can clear newer success (control.ts:246?268; session-store.ts:131/148). New UI helper correctly suppresses obsolete panel publication, but does not repair that backend cache ordering. readSession reads session.preview at reply time, rather than returning an operation-specific committed preview. Replacement/deletion can also leave the captured old object's preview in a reply.

Additionally extractionPreviewRequest returns undefined when every field is excluded (definition.ts:108?109), and refreshPreview then returns without clearing a previous stored broad preview (control.ts:248). The panel drops excluded values immediately, but the worker still holding the old rows violates the stated two-sided D12 erasure policy. This is source inspection, not executed reproduction, and should receive its own bounded backend preview regression unit before any claim of end-to-end privacy completion. The comma-joined cache key also deserves collision assessment if actual production field-key grammar permits commas; no grammar claim was established here and no invented counterexample is asserted.

## S4 ? Project/pairing/recording owner is not an extraction capability

ExtractionSessions stores tab/form/ID only. startPick consults activeTabId once; read/cancel do not consult manager context; Confirm checks recordingState but not an extraction owner's project/client/paired identity (control.ts:125,224,272,294). A trusted old surface can retain an extraction across owner transitions because recording.render merely disables/relabels the entry and preserves the already-open draft. Availability is UI advice, not backend authorization.

The inspected sources establish absence of proof here, not which wider protected connection/recording ownership checks may reject a later event. Full project/recording authorization needs a separately released investigation of the manager's real recording owner/public status lifecycle. Do not bolt automation's local ownerRevision onto extraction, reuse pairing tokens, or invent recording IDs. Existing extension-only session-ID partition can fix S1 without claiming S4 is resolved.

## Host lifetime ? E7 remains conditional; normal reparenting must survive

Actual caller createRecordingControls mounts one host once (recording-controls.ts:59?60). render moves that same host between extractSlot and barExtract as recording status changes (143?144); its handle exposes only setAvailable. Frozen HEAD shell creates controls once (mount-panel.ts:64), installs root shell once (118), toggles screen.hidden (155?170), and pagehide/pageshow only activate screen clients (206?213). The active shell lane was not used as stable evidence.

Dialog focus intentionally portals an open sheet into document.body, retaining original parent/next and restoring inert state/listeners on close (dialog-focus.ts:48?77). Its MutationObserver isolates new body children; it does not infer permanent host disposal. Consequently a late initial restore after an externally removed host could portal an orphan sheet and isolate the document, and a detached active picker could keep polling. That path is possible from the API, but no production permanent-removal caller was found in this bounded discovery. Normal temporary reparenting is demonstrated source behavior and must not trigger disposal.

Firefox popup entry mounts a fresh panel document; source explicitly restores from background because clicking the page destroys/closes popup (client.ts:69?73; popup/index.ts:7). Whole-document destruction removes local UI/timers with the document; background memory session survives while the worker lives. Do not cancel background pick on blur, pagehide, navigation between extension screens, or popup disappearance. A pagehide persisted/reuse case or repeated mountPanel on the same root would require explicit caller teardown design/tests; no existing destroy/dispose extraction method was found. No disposal API is proposed for immediate implementation on this evidence alone.
