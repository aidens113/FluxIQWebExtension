# Extension connection and recording recovery audit

Status: Complete — read-only audit; frozen for supervisor review
Owner: wait_gaps
Date: 2026-10-01
Scope: Read-only inspection of the six source owners in the written brief and their directly owning tests. Product, tests, shared documentation and earlier naming/extraction fixes are unchanged.

## Source-confirmed findings

1. **Settings status refresh releases a pending Disconnect.** `settings/settings-view.ts:134–139` disables the button until the request completes, but `render():164` derives its disabled state solely from connection status. A connected status update during the pending request therefore enables another native activation. There is no pending-operation guard in the handler. Regression: defer Disconnect, publish still-connected status, attempt a second activation, verify one request and a disabled pending control; then refuse and verify usable retry.

2. **Settings connection mutations can overlap and overwrite feedback.** Save releases its busy state at `settings-view.ts:121`, before the optional reconnect at `:131`. Disconnect and Forget have separate busy state and share the same outcome notice. A pending reconnect can consequently report an older failure after a later Disconnect/Forget result. This confirms UI interleaving and stale feedback; it does not establish backend data corruption. Prefer one connection-mutation operation owner through the entire Save/reconnect sequence, with an internal duplicate guard and render-derived busy controls. Preserve editable form inputs, the submitted edit-revision guard and persistent unsaved drafts. Regression: defer reconnect, attempt another mutation, resolve/refuse in both orders, and verify current feedback plus newer draft/selection preservation.

3. **Forget closes even after refusal and restores focus without ownership checks.** `settings-view.ts:142–147` resolves `Promise<void>` for both success and fulfilled failure. `settings/forget-confirmation.ts:39` closes after either result. Retry thus requires reopening the confirmation; the failure remains in the settings outcome notice. Separately, `setOpen():29–33` always calls focus, including after delayed completion. There is no visible/active-document/current-focus check. The unconditional DOM focus call is source-confirmed; actual browser focus transfer is untested. A minimal success result from the existing callback can retain confirmation on failure and permit retry. Async success should restore the opener only while focus still belongs to the initiating confirmation in a visible active document. Explicit opening should continue to focus Cancel so stray Enter does not forget pairing. Regression: failed/successful/deferred result, repeat activation, Cancel before confirmation, focus moved to another field or browser page, hidden settings, and retry after refusal.

4. **Paused recording exposes Start recording.** `recording/record-control.ts:25` treats only `recording` as ongoing. Connected, supported, non-working `paused` status falls through to an enabled visible Start control. The owning review model test explicitly describes pausing as still recording (`recording/review/tests/review-model.test.ts:31–34`). No record-control test covers paused status. Treat paused like recording in this helper; test connected/unsupported/disconnected/working paused combinations while retaining all idle behavior and the exact Start recording name. No claim about backend consequences of a duplicate Start is made.

5. **Review phase changes replace action controls, including Done.** `recording/review/recording-review.ts:114` replaces every button whenever a phase changes. Activating Generate/Test/Save synchronously dispatches a busy phase before issuing its request (`:70–85`), removing the activated button. The analyzing-to-building timer also replaces Done even when Done is still present and may have acquired focus. There is no focus restoration. Node replacement is confirmed; browser keyboard impact needs component/browser validation. Reconcile controls by ReviewAction with current handlers/labels/busy state, preserving shared actions across phases. If a focused action genuinely disappears, use an explicitly owned visible remaining action or local named status fallback without stealing focus from another field/page. Dismiss hides the card; an external fallback cannot be introduced through an unowned caller without a new brief. Regression: stable Done across timer/completion, current Generate/Test/Save handlers and ids, removed-action fallback, passive redraw/external-document focus, and dismissed/old-review late replies.

6. **Getting Started can install a stale failure after the goal status already arrived.** `getting-started/start-view.ts:69–78` installs a result failure only after awaiting the request. Its recovery predicate is observed during `render():115–118`. If a render reaches the requested connected/disconnected goal before the failed result arrives, that observation happens before the error exists; the late failure is displayed until another status render observes it. There is no immediate observation of the latest status after installing the error. Confirm with a mounted deferred-request regression before implementing: publish the goal status during a pending Cancel, then deliver failure without another status push. Preserve real failures while the requested goal remains unmet, subsequent retries and both buttons' current pending guard. Do not redesign cancellation while a Connect acknowledgement is pending without tracing the background contract in a separately authorized brief.

## Preserved protections and limits

- Save's submitted `editRevision` protects edits made while the request is pending. Dirty status refreshes do not refill the form. Existing six settings-draft scenarios cover unchanged/address/toggle/retyped/save-failed/reconnect-failed behavior and must remain unchanged and passing.
- `address-form.ts` retains field nodes and synchronously focuses invalid input after explicit Save. Reassigning clean field values on refresh alone does not prove a browser selection defect; no form rewrite is justified by this audit.
- Getting Started disables both Connect and Cancel until its request acknowledgement; ordinary status renders do not re-enable them. This differs from the confirmed Settings Disconnect race.
- Review dispatch guards unchanged phases before requesting, snapshots preview ids, fences late replies by review epoch, and clears the analyzing timer when leaving that phase. Existing pure model tests cover retry preview retention, unsupported replies, paused recording lifecycle and stale model events. Done dismisses review presentation; this audit does not authorize cancellation of background work.
- These six owners have no popup-versus-side-panel branching. Shared rendering can preserve both contracts, but popup teardown, focus behavior and live browser appearance have not been exercised.
- Inspection establishes fulfilled refusal/failure paths. No production transport rejection or backend corruption was reproduced; missing raw Promise catches alone are not reported as a confirmed production defect. Unexpected rejection should only be added to an implementation brief with an explicit contract/recovery decision.
