## Recommended bounded frontend policy

Introduce one program-owned hook, mounted only by these operational views. No root/global poll and no backend/runtime contract changes.

1. One snapshot request on mount; while document.visibilityState is visible, schedule the next read **10s after prior completion**. Only one automatic request per owner at a time. A pending manual/mutation refresh coalesces or supersedes the snapshot read with explicit generation/abort; it must not stack timer requests or abort a mutation. Polling does not call run/start/advance/cancel/set-enabled/control.
2. Hidden tab cancels scheduled reads/local clock timers and aborts this view's read controllers only. Retain DOM/data/drafts with "Updates paused while this tab is hidden". Visibility return updates nowMs and requests one immediate fresh read, coalescing repeat events. Continue bounded visible polling after completion. Do not replay missed interval ticks or launch many requests on resume.
3. Failure backoff20s ->40s ->60s maximum while visible; permission403 stops automatic retry until manual Retry or a later visibility return, with explicit fixed permission feedback. Successful response resets normal10s cadence. Program API already owns request retries/deadlines/auth recovery; the hook owns only view-level cadence, no second retry loop inside one read.
4. Track lastSuccessfulAt, loading/refreshing, lastError/permission and paused. Show "Snapshot loaded at ...", not Live/current-time-as-refresh. Mark displayed snapshot stale immediately after failed refresh and when last success is older than30s. Retain last good payload and surrounding controls/drafts on transient failure. Initial failure has no fabricated empty-good state and shows Retry. Fixed error messages avoid raw server content.
5. Compute heartbeat age and Background countdown are explicitly estimates from the last successful snapshot. Preserve pure computeNodeHealth/formatCountdown math; stale/paused banner makes uncertainty visible. Timer1s for Background and10s for Compute is local display only, paused hidden and reset on visibility return. Production needs no independent local clock. Reported node/scheduler/workload status is only renewed by server response.
6. Owner is API/scope identity; request generations invalidate immediately on scope/unmount and manual replacement. Render old-owner snapshots/details as loading/unconfirmed before passive cleanup. Captured old refresh/retry callbacks cannot read or publish into a new owner. Prevent unexpected rejected read promises from escaping.
7. Background successful snapshot refresh additionally refreshes only the visible task's current50-row history page (same task/filter/offset), not every task. Independent page identity `{api,taskId,filter,offset}` and signal/generation fence; read errors retain explicitly stale rows with Retry history. Scope/filter/page/render guard prevents old list/detail under new controls. Matching selected run is replaced by the new returned object; removed/filtered run clears selection. Successful history may clamp offset if total shrinks, preserving current existing behavior.
8. Preserve keyed rows and selected ids wherever visible; no automatic focus placement. Compute detail/activity follow visible filtered node. Background task selection follows visible filtered task; same task keeps filter/page, changed task resets page/detail. Production same target preserves draft and operation states, removed target follows existing scoped fallback. Poll-driven re-render must not clear edited parameter input or create mutation requests.

Cadence/stale thresholds above are proposed bounded defaults, not measured responsiveness.10s balances operational visibility with the existing120s/300s health horizons;30s marks missed reads without asserting node failure. Supervisor may choose slower values in the written implementation brief, but tests must assert the chosen policy, not indefinite fake-clock churn. Scope is frontend data freshness; do not change server scheduler/heartbeats or health contracts.

New server command/lease/capability/node appears on successful tick. Health/search/capability selection still matches detail/activity after refresh/removal. Failure marks stale retained row, not asserted currently offline; successful retry restores confirmation.
- Background: task nextRunAt advances and scheduler state changes server-side; periodic snapshot updates countdown rather than staying Due now/100%. Current-task page alone refreshes at limit50; task/filter/page/scope/unmount old page ignored; updated same-id run becomes completed in selected detail. Existing independent launch/run locks continue to issue at most one mutation per activation; no poll-driven start/advance/cancel.
