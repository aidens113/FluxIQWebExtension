## Findings (what triggered the read, its shape, why it lost a clause)

- **Trigger and timing.** `AutomationStudioActionPermissionGate.instructedFor()` derives the read the first time an
  action *declares* a lasting class. That happens inside the domain's permission check, which runs while the domain is
  already executing the call. In run musp8nz1, Get coupons (0021/0023) declared nothing lasting, so no read happened
  then. Add to cart (0029) declared `["create_new"]`, so the read (0031, 18:05:43.97-44.68) ran inside press 0030's
  permission check and against that press's clock. `instructedLastingActs` (the 1002-M fix) only *forces* the read at
  the first test if it has not happened yet; here it already had.
- **Request shape.** The read was an `evidence_tool_decision` with `tools: []`, so it got the full page-decision system
  prompt: the domain text "You operate a real website...", the evidence-loop prose, and "Write summary as ... what you do
  next". That is why its summary read "Reading the Farbazaar page to find the ... listing". The completion asked
  "which lasting consequences" as a list capped at 5 (one per class). The class descriptions frame it per class.
- **Why it lost a clause.** The question was per class, not per clause. Once `create_new` was given for the cart,
  nothing asked the model about the coupon. Even if it had answered the coupon as `create_new` as well,
  `readAutomationStudioInstructedConsequences` kept one entry per class ("first grounded claim wins") and would have
  dropped it. The lasting-act test then matched quotes, found none for a2, and so treated Get coupons as repeatable.

## What changed and why

- `action-permissions/instructed.ts`:
  - New `automationStudioInstructedConsequencesSchema(acts)`. For an instruction with acts, it asks first for `acts`:
    one required key per act id, described as `The act "<person's words>"`, answered with a class array or `["none"]`.
    The old free `instructed` list follows unchanged. With no acts it returns the old schema object unchanged.
  - New `readAutomationStudioInstructedRead`. It adds one grounded entry per class per answered act (quote = the act's
    words), so two acts of one class become two entries. It skips an act entry whose class matches a free entry with an
    overlapping quote. It records each act's answer (`consequences: [...] | [] | null`) as a non-enumerable `acts`
    property. Stored entries stay exactly four fields (tested with a JSON round trip through
    `currentAutomationStudioInstructedConsequences`).
  - New `automationStudioInstructedReadUnanswered` and `automationStudioInstructedActReads`.
  - The free list keeps its per-class first-claim-wins behaviour, so the existing tests are unchanged.
- `service/instruction-authority.ts`:
  - It computes the acts with `automationStudioInstructedActs` from the same `title\nbody` join the service uses for
    the checklist, so the ids match.
  - It poses the per-act schema. The decision schema now carries a description: "This call reads the person's
    instructions alone: there is no page here and nothing to do next, so complete at once. Write summary as one plain
    sentence saying what the instructions ask for, act by act."
  - A failed or non-complete answer returns every act as unanswered instead of `[]`.
- `flow-bootstrap/action-permissions.ts`:
  - (b) `executeTool` now makes the read *before* handing the domain a call whose `value.consequences` declares
    something lasting. The gate's check then finds the read already made.
  - (c) `instructedLastingActs` now names an act as lasting when its quote matches as before, or the read answered it
    with a class, or the read gave it **no answer** (lasting-unknown). Only an act answered `none` replays. A plain list
    of entries with no per-act answers, or a reader that threw, keeps the old quote-only rule.
  - Unanswered acts are said once in the Flow's thread through the existing `say`: "Reading your instruction gave no
    answer for "...", so the build's tests check the step that does it rather than do it again." This is
    best-effort.
  - `crossCheck` uses the same read.
- `flow-draft/verify-only.ts`: exported the existing private `declaresLasting` as
  `automationStudioFlowDraftDeclaresLasting`, so the gate and the dry run read a declaration by one rule. The doc comment
  on unanswered acts is updated. Replay-mode behaviour is unchanged.
- `llm/node-tools/dry-run-gate.ts`, `service/flow-bootstrap-commands/permission-outcome.ts`: comments only.
- Tests:
  - New `service/tests/instruction-authority.test.ts` (10 tests, wired as the service wires it).
  - 6 new tests in `action-permissions/tests/instructed.test.ts`.
- Docs:
  - `docs/architecture/automation-studio/llm-flow-bootstrap.md`: a new paragraph in "Permission on the authoring path".
  - `docs/architecture/automation-studio/flow-authoring.md`: two sentences in "Lasting Acts And Excusal".
  - Both files already had other workers' uncommitted hunks in other regions (lines ~60 and ~766-830). I edited only my
    own regions.
- `llm/deepseek/system-prompt.ts` was **not** edited. The cause was the question's shape and the per-class dedupe, both
  fixable in owned files. Giving the read its own system message would need either a new task kind or a
  metadata-keyed branch in the provider adapter. It would also lose the read's cached system prefix (1,536 of 2,260
  tokens were cache hits in 0031). The read's framing now travels in its own user-message schema instead. The page-
  decision system text still precedes it.
