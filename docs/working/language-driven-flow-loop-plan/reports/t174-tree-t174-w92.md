## What changed and why

Nothing changed. Findings for each string follow.

### (a) `Doing "Create an automation here".`

- **Where it comes from:** `runtime/conversations/instructions/respond.ts:65`
  `` `${lead}Doing "${invocation.title}"${target}.${readingNotes(invocation)}` ``. `invocation.title` is the capability title
  (`commands/create-here.ts:16` `TITLE = "Create an automation here"`). `lead` is the model's optional `say`
  (`instructions/parse.ts:47`), which was empty in the live run. `target` is ` for the Flow "<name>"` only when the call has a `flowId`.
- **Call path:** extension relay → `api/handlers/conversations.ts:192-203` (append-turn with capabilities) →
  `AutomationStudioConversations.respondToPersonTurn` (`runtime/conversations/conversations.ts:328-357`) →
  `respondToAutomationStudioConversationTurn` (respond.ts:52), on the `!asksFirst` branch. That reply goes into the thread
  before the command starts. The `execution.summary` from `commands/execute.ts:40`
  (`Started "<title>". I will say here when it has finished.`) is not rendered by the extension. `git grep execution` in
  `apps/extension/src/panel/chat` and `background/panel` finds nothing.
- **Proposed wording.** Each Core command gets its own announcement, written for the person:
  - `flow.createHere`: `I'll make you a new automation for this, working out its steps by trying them on <site | "this page">. I'll say here when it is ready.`
  - `flow.explore`: `I'll work out the steps for "<Flow name>" (or: the Flow's steps) by trying them on <site | "the website">, and say here when they are in.`
  - `flow.improve`: `I'll work out the change by trying it on the website, then ask you here whether to apply it.`
  - `run.execute`: `Running "<Flow name>" (or: the Flow) now. I'll say here how it went.`
  - A capability without an announcement, which means one the client runs itself, keeps today's `Doing "<title>"` (see Open questions).
    `lead`, `readingNotes` and `withProblem` stay as they are. The Lab matches `/I read your message without the model/u`
    (downstream `packages/test-runner/src/flow-lane/creation/chat/build-from-chat.ts:69`), so that text must not change.
- **How to implement it:** add an optional `announce?(view: { args; flowName: string | null; site: string | null }): string` to
  `AutomationStudioConversationCommand` (`commands/command.ts`). Add a new file `commands/announcement.ts` that exports
  `automationStudioConversationCommandAnnouncement(invocation, flows, pageUrl): string | null` and looks the command up in
  `AUTOMATION_STUDIO_CONVERSATION_COMMANDS`. respond.ts would import it directly, not through the `commands/index.ts` barrel.
  The barrel pulls in `execute.ts`, which imports `instructions/index.ts`. `prompt.ts` already has this edge, but importing the
  direct file keeps the cycle out of respond.ts. `respond.ts` also needs `pageUrl` in its input, which `conversations.ts:346`
  passes as `onScreen.pageUrl`.

### (b) Full loopback URL as "where"

- **Where it comes from:** `commands/create-here.ts:59` and `commands/explore.ts:52` set
  `where = automationStudioConversationPageShown(context.startLocation) ?? "the site"`. `commands/page.ts:8-19` returns
  `origin + pathname`, for example `http://127.0.0.1:NNNN/scenarios/...`. `where` is used in `progress.landed("explored ${where} ...")`,
  which also appears in a failure's "Before that I ..." line, and in the success summary (create-here.ts:65, explore.ts:58).
- **Where `startLocation` comes from:** `api/handlers/conversations.ts:202` sets `startLocation: onScreen.pageUrl`. That value
  is checked by `requestedOnScreen` (conversations.ts:324-337). Downstream sends it from
  `apps/extension/src/background/panel/conversation-relay.ts:158`, which takes the active tab's URL via `chat-page.ts`. No page
  title is sent anywhere: `AutomationStudioConversationOnScreen` (`instructions/decision.ts:22-34`) has only `pageUrl`.
- **Proposed wording:** use the site's name, meaning the hostname without a leading `www.`, for example `shop.example.com`.
  For an IP literal or `localhost`, which covers every Lab scenario, say `the page you had open`. Leave `page.ts` unchanged:
  the prompt (`instructions/prompt.ts:61`) and the handler's validator (`conversations.ts:336`) depend on its contract.
- **Option, not recommended for this task:** have the extension send the tab title as `onScreen.pageTitle`. That is a cross-repo
  wire change touching the extension's `shared/protocol.ts:214`, `background/panel/chat-page.ts` (`ChatPageTab` gains `title`),
  `relay-context.ts`, `conversation-relay.ts`, Core's handler `requestedOnScreen`, `decision.ts` and `command.ts`. It is also
  untrusted page text that would go into the thread.

### (c) `Say "run it" to try it.` while the Flow is already running

- **Where it comes from:** `commands/create-here.ts:65` (`Created the Flow "<name>", explored <where>, and put the steps it
  worked out into the Flow. Say "run it" to try it.`) and `commands/explore.ts:58` (`Explored <where> and put the steps that
  worked into the Flow. Say "run it" to try it.`). Both go through `progress.succeeded` → `execute.ts:62` `settle`, which writes
  them as an automation turn with attachment `panel-capability-result` / the capability id.
- **Who starts the playback:** the Lab, not the product. In Core, no conversation command starts a run after a build: create-here
  goes create → save instruction → `generate-flow-bootstrap-adaptation` → apply, and stops there. Downstream,
  `packages/test-runner/src/flow-lane/creation/lane.ts` `buildRunAndJudge` waits for the chat result turn (`startChatBuild` →
  `chat/build-from-chat.ts`, which matches the turn by attachment `panel-capability-result` + `flow.createHere`, lines 66-67),
  then reads the nodes, resets the scenario lab (`lane.ts:399`), and calls `prepareFlowPage("playback")`.
  It then starts the run with `executeRecordedFlowRun` (`lane.ts:407`, which reaches
  `existing-fluxiq-control.ts:382` `start-runtime-session`). The run starts right after the summary is written, so Core cannot
  know at that moment that a run will follow. During the build, Core tests the Flow once from its start, with lasting acts
  checked rather than done (`runtime/result-verification/build-test/`). So "try it" is also loose for a real person.
- **Proposed wording:** drop the instruction to say "run it", and state something that stays true whether or not a run follows:
  - create-here: `Your automation "<name>" is ready: I tried its steps on <site | "the page you had open"> and put the ones that worked into it.`
  - explore: `The Flow's steps are in: I tried them on <site | "the page you had open"> and kept the ones that worked.`
  - The failure step becomes `tried the steps on <site | ...> and worked out which ones work`. Today it reads `explored <url> and worked out the steps`.
