## What changed and why

### What I found before changing anything

The brief said the six closed reasons "are flattened away before anything
downstream can see them". That is right, but the flattening was not where the
line numbers suggested, so it is worth recording precisely.

`WebLlmToolRejectionDetail` already existed and already carried `reason` and
`target`, and the retired `web.press_control` and `web.detect_repeating_structure`
tools already produced the specific reasons (`handle_not_in_packet`,
`page_moved_since_packet`, `handle_no_longer_on_page`, …). But the only path the
model uses now is `core.run_node`, and on that path every handle failure came
back as one reason:

```
domain/src/runtime/llm-evidence/node-run/run.ts:402
function handleRefusal(parameters, issueCodes) {
  return rejectionDetail({ reason: "parameters_not_resolved", … });
}
```

The plan resolver's own codes — `web.handle.unknown`, `web.handle.stale`,
`web.handle.not_unique`, `web.handle.malformed`, and six more — were passed in
`instead`, mixed in with the shape hints (`target: {"handle": "target.N"}`) and
the `<code>:<position>` entries. So the codes were technically present, and the
*reason*, which is the field a consumer reads, was the single word
`parameters_not_resolved` for all ten. The existing test asserted exactly that,
three times over, under a title claiming they were different.

### The change

`domain/src/runtime/llm-evidence/tool-rejection.ts`:

1. **A closed table from the resolver's codes to the reason each implies**
   (`HANDLE_ISSUE_REASONS`), and `webLlmHandleRejectionReason(issueCodes)` which
   returns the first reason the codes name:

   | resolver code | reason |
   | --- | --- |
   | `web.handle.malformed` | `malformed_handle` |
   | `web.handle.misplaced` | `handle_in_wrong_parameter` *(new)* |
   | `web.handle.unknown` | `handle_not_in_packet` |
   | `web.handle.stale` | `page_moved_since_packet` |
   | `web.handle.ambiguous` | `handle_names_several_now` |
   | `web.handle.not_unique` | `handle_names_several_now` |
   | `web.handle.frame_mismatch` | `handle_in_another_frame` *(new)* |
   | `web.handle.unknown_field` | `column_not_in_detected_list` *(new)* |
   | `web.handle.extraction_required` | `extraction_handle_required` *(new)* |
   | `web.handle.wrong_control` | `handle_wrong_kind_of_control` *(new)* |

   The two `web.handle.expected.*` entries are deliberately not in the table:
   they are the shape a handle is accepted in, not a statement of what went
   wrong, and reading one as the reason would answer "what did I do wrong" with
   "here is the shape" — which the model was already told.

   First match wins, which is the resolver's own priority: `refusal()` in
   `plan-resolution/resolve-plan-node.ts:402` emits its reasons in
   `WEB_PLAN_HANDLE_ISSUE_CODES` declaration order ahead of the positions and
   shapes, so reading the list in order is reading that order.

2. **Five new reasons** added to `WEB_LLM_TOOL_REJECTION_REASONS`, one per
   resolver code that previously had no reason it could be told apart by:
   `handle_in_wrong_parameter`, `handle_in_another_frame`,
   `handle_wrong_kind_of_control`, `extraction_handle_required`,
   `column_not_in_detected_list`. Each is documented with the different next move
   it implies, which is the standing bar in this file for adding one. The set
   stays closed and enumerable — the type is still derived from the value — and
   nothing in the set is free text, page content or a selector.

3. **The sharpening is applied in `rejectionDetail`**, not at the call site, so
   no caller can hold the resolver's codes and forget it. It fires only when the
   caller said `parameters_not_resolved` *and* passed an `instead`, and it is
   idempotent: a reason that has already been sharpened is not
   `parameters_not_resolved`, so the branch does not fire a second time. That
   idempotence is what lets `node-run/run.ts` later call
   `webLlmHandleRejectionReason` itself without this becoming a second,
   disagreeing copy of the table.

The handle (`detail.target`) was already carried and still is; it is the model's
own input echoed back, which the file's redaction note already permits.

Nothing about redaction changed. The table's keys and values are both this
domain's closed vocabulary, so nothing a page said can cross it — and the
existing test "no refusal carries a word of the page, whatever it refused" still
passes unchanged.

### Tests (`domain/src/runtime/llm-evidence/tests/tool-rejection-detail.test.ts`)

Updated the four assertions that pinned the old flattened reason, and added
three tests:

- **`every code the plan resolver can refuse with names a reason, and each
  reason is one of the closed set`** — drives the test from
  `WEB_PLAN_HANDLE_ISSUE_CODES` itself, so a code added to the resolver fails
  this until someone chooses a reason for it. This is the mechanical guard
  against the flattening quietly coming back.
- **`the reason is the first the refusal names, and nothing but a code can
  become one`** — priority order, and that positions (`web.handle.unknown:target`),
  shape hints and arbitrary strings are passed over rather than matched.
- **`a detail carrying the resolver's codes is sharpened once, and sharpening it
  again does not move it`** — the idempotence above, and that a reason which was
  never the resolver's is left exactly as the caller wrote it.

### A second defect the tests exposed

The fixture's three supposedly different cases — a handle no packet carried, a
control that left the page, and a page that was navigated away from — **all
produce `web.handle.unknown`**, so all three now read `handle_not_in_packet`.

That is the resolver being honest about what it knew, not a fault in the table.
Running any node recaptures the page first and remembers the new packet in that
page's place (`node-run/run.ts`, `run.shown`), so by the time the handle is
resolved it is simply not among that page's handles. `web.handle.stale` is only
reachable once a page has been *let go* by the bounded store, and
`handle_no_longer_on_page` is not reachable on this path at all.

**This means the three-way distinction the brief wants is still only two-way on
the live path.** Telling "was issued, and a recapture replaced it" apart from
"was never issued" needs
`domain/src/runtime/llm-evidence/plan-resolution/target-packets.ts` to remember
the handles a recapture replaced, and to answer a different code for them. I did
not invent the distinction in my table, because the table can only be as precise
as the code it reads; I recorded it in the test comment where the next reader
will meet it.

## What is still needed outside my file

The reason has to ride **inside the result code** — that is the only field the
artifact keeps. Two domain files, neither mine, and no Core or Lab change at all:

1. `domain/src/runtime/llm-evidence/vocabulary.ts`
   - `webLlmToolRejectionResultCode(code, reason?)` → `web.action.rejected.<code>`
     when there is no reason, `web.action.rejected.<code>.<reason>` when there is.
   - Derive `WEB_LLM_EVIDENCE_RESULT_CODES` as the cross product of
     `WEB_LLM_TOOL_REJECTION_CODES` and `WEB_LLM_TOOL_REJECTION_REASONS` plus the
     bare codes. That is 19 × 28 + 19 = 551 frozen strings; if that is judged too
     broad, restrict the product to the four codes that actually carry reasons
     (`invalid_input`, `no_progress`, `target_unobserved`, `permission_required`).
     Deriving it is what makes both Lab filters (steps 8 and 9 above) accept the
     new codes **without any change in `packages/test-runner`** — which is the
     whole reason the set is derived rather than hand-maintained.
2. `domain/src/runtime/llm-evidence/node-run/run.ts:356` and
   `domain/src/runtime/llm-evidence/harness-options/execute.ts:112` — pass
   `detail?.reason` into that call. One argument each.

One caller must change with it, or it will silently stop matching:

- `domain/src/runtime/llm-evidence/harness-options/exploration-terms.ts:67`
  compares `resultCode === webLlmToolRejectionResultCode("out_of_scope")` and
  `… ("cross_origin")` by **exact equality**. `cross_origin` carries the reason
  `another_origin`, so a reason-bearing code would stop being classified
  `out_of_scope_refused` and an out-of-scope refusal would no longer end the
  exploration. It needs to compare the code part, not the whole string.

Checked and **not** affected: Core's `NOT_RUN_RESULT_CODES`
(`exploration-reduction/evidence-loop-trace.ts:161`) holds Core's own
`llm_evidence_loop.*` codes, not this domain's, so a longer domain code passes
through it untouched; and `classifyOutcome` is supplied by the domain classifier
above, so fixing that one comparison covers it.

Also worth handing to whoever owns `node-run/run.ts`: `firstHandle()` only
matches the `target.N` pattern, so a **malformed** handle comes back with no
`target` at all — the model is told its handle was malformed without being shown
what it wrote. Echoing the offending token back (bounded, and it is the model's
own input) would close that.
