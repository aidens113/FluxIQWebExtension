## What changed and why

1. **The 400 refusal is now `facility.contract`.**
   - `packages/test-contracts/src/evaluation.ts` adds `facility.contract` to `failureCategories`, with a doc comment.
   - `packages/test-runner/src/existing-fluxiq-control.ts`: `automationStudioCall` passes the request through `contractRefusal`. A `RunnerFailure` whose `details.status === 400` is raised again as `facility.contract`. Its message reads `Core refused a value the Lab sent: FluxIQ control request failed: <path> (400): <Core's sentence>`, and the details (path, status, reason) are kept. Any other status keeps `environment.missing`.
   - The facility diagnostic's `reason` is still `unclassified`. Its projection is in `facility-failure/project-facility-failure.ts`, which I do not own (see Open questions).
2. **`flowCreated` is set from the build record.**
   - The evaluation writer is `selectLaneObservation` in `packages/test-runner/src/flow-lane/lane-observation.ts`. It takes an optional `stoppedLane` (the created lane's incomplete record). The lane counts as having created a Flow when `flowId !== null`, `build.outcome === "proposed"` and `review != null`, meaning the proposal was applied.
   - `run-scenario.ts` keeps the record in `recordIncompleteEvidence` (`stoppedLane = incomplete`) and passes it on: `published: flowObservation, stoppedLane,`.
3. **The campaign reports the run's whole spend.**
   - `scripts/lab/live-campaign/row/reported-spend.mjs`: when `liveLlm.runSpend.totalEstimatedCostUsd` is a number, the row's `costUsd` is that figure and `source` is `"run"`.
   - Tokens are still the phases' figures, because `runSpend` holds no token count.
4. **`observedCalls` is filled from the step log.**
   - New file `packages/test-runner/src/live-llm/call-rows.ts` (`stepLogObservedCalls`) makes one row per `steps/*/meta.json` that names a provider: request id, task kind, stage, provider, model, tokens and cost.
   - Prompt version and validation verdict come from Core's per-call line with the same request id. A Core line whose request id is not in the log is appended. A Core row with no request id is not listed again.
   - `perCallRecords` and `unrecordedCalls` are recomputed against the run's whole call count.
   - `live-llm-run.ts` `writeSnapshot` applies this to the snapshot only (`...stepCalls`). The budget checks still read the settled phase.
5. **Playback closes the other tabs.** In `run-scenario.ts` `prepareFlowPage`, when the moment is `"playback"`, the runner closes every page except `page` and `extensionControl` whose URL is on the fixture origin or is `about:blank`. It does this before the start page is prepared.
6. **Playback steps are numbered in time order** (`packages/test-runner/src/lab-runs/write-playback-steps.ts`, `numberInTimeOrder`).
   - Each new playback entry takes the place of the first existing folder whose `meta.startedAt` is later than it. That folder and the ones after it move up: the folder is renamed, highest first, and its `meta.json` `step` is rewritten.
   - Folders whose meta has no `startedAt` keep their number.
   - This runs only after Core has stopped, at the existing call site.
7. **Docs.** `docs/architecture/testing-facility.md` now covers all of the above.

## Open questions or contradictions found

- **The diagnostic reason is still `unclassified`.** The campaign row will read `facility.contract; unclassified`. Adding a closed reason such as `http.refused`, with endpoint and status, needs `facility-failure/project-facility-failure.ts` and the validator in `test-contracts`. I did not own the first, so I did not change it.
- **The new category is not in `failure-taxonomy.md`.** That file, `docs/architecture/failure-taxonomy.md`, lists the categories by example and was not in my brief. It may want a line on `facility.contract`.
- **Not every 400 is the Lab's value at fault.** Every 400 on an Automation Studio call now reads `facility.contract`. That includes Core's `FLOW_BOOTSTRAP_PERMISSION_REQUIRED` refusal on `review-flow-adaptation`. The campaign now catches that case earlier, but if it ever surfaces as a 400 again it will read as a contract failure, not as the product's behaviour.
- **I created two new files outside the named list:** `live-llm/call-rows.ts` and `live-llm/tests/call-rows.test.ts`. `live-llm-run.ts` was at 799 of the 800-line limit, so the step-log reader could not go in it. No other worker owns either file.
- **Prompt versions stay null.** The step-log `meta.json` holds no `promptVersion`, so rows have one only where Core's per-call line for the same request id gives it. In created-Flow builds that line has never had an id, so `promptVersion` stays null there.
