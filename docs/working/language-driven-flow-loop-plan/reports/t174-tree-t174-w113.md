# t174-w113: Lab UI-review records (tabs, page loads, overlay text, moment labels)

## Outcome

Done. All four items are fixed in `packages/test-runner/src/run-scenario/ui-review/`, and each has a test that failed first. The 36 ui-review tests pass. The structure audit has no violation in my paths. Its one remaining FAIL is in `live-llm/`, which another worker owns.

## What changed and why

- **R7: every open tab is recorded.**
  - `choose-scenario-tab.ts` now makes one `chrome.tabs.query({})` call instead of `{active: true}`. That one call gives both `frontTabs` (unchanged) and the new `openTabs: {url, inFront}[]`, in the browser's order.
  - If the browser's tabs cannot be read, it falls back to the context's open pages, with `inFront: "unknown"`.
  - `capture-scenario-tab.ts` screens each entry through `screenLocation` into `UiReviewCapture.openTabs: {location, inFront}[]`.
  - The recorder passes the tabs through, and its log line ends with "N tab(s) open". The sidecar summary has `openTabs` (a count) for each moment.
- **D13: a navigation that ends a window in a failed read is now counted.**
  - In `read-overlay-sample.ts`, the read is split into `readOnce` plus a catch. A failure shaped like a navigation sets `navigationSuspected: true` and re-reads the tab's document (`performance.timeOrigin`, `location.href`). The failed sample then carries `documentOrigin`/`pageUrl` for the document the tab holds after the failure.
  - "Shaped like a navigation" means the host went away between two reads, the execution context was destroyed, the context could not be found, or the inspected target navigated.
  - If the re-read also fails, the sample carries `documentError` with the reason. Returning nothing there would break the audit's failure-as-empty rule.
  - In `count-overlay-changes.ts`, the origin is now read from error samples too, so `pageLoads` counts the change. A failed read still makes no toggle.
  - There is a new count, `probablePageLoads` (0 or 1, never added into `pageLoads`). It is 1 when a navigation-shaped failure is not later settled by a sample naming either a new document or the same one.
  - Both counts are in the log line and the summary.
- **D14: the overlay keeps the paths it shows.**
  - There is a new `screen-overlay-text.ts` (`screenOverlayText`), used for the overlay's text parts and attributes.
  - A URL is kept as `screenLocation` keeps one: origin and path. A bare path is kept whole. Query and fragment are dropped from both.
  - Secrets, token patterns (`redactText`) and six-digit codes are screened everywhere. Any other run of 32+ opaque characters becomes `[long]`.
  - The URL match stops at curly quotes. Before this fix, `screenUrl` also swallowed the closing `”`; the pre-fix output below shows it.
  - Error strings still go through `screenText`.
- **D20: moments are labelled by what had run.**
  - In `schedule.ts`, the moment taken on entering the `flow-run` phase is labelled `before-flow-run`. Periodic moments taken while the run is still in progress are labelled `flow-run`.
  - The reason: the spine reports that phase while it is still preparing the run, before the settings call (`run-scenario.ts:318`).
  - `UiReviewLabel` gains `before-flow-run`.
- **Barrel:** it now exports `chooseScenarioTab`, `captureScenarioTab` and `OpenTab` for the tests.
- **Docs:** I updated only the section "The UI review's overlay counts" in `docs/architecture/testing-facility.md`.

## Open questions or contradictions found

- D20 is fixed only within my ownership. The entry moment is honestly labelled `before-flow-run`. A periodic `flow-run` moment still means "the run phase was still current a full period later", not "a step was confirmed to play".
  - A definitive fix moves `uiReview.phase("flow-run")` after the settings call, or adds a recorder hook when playback starts. Both are in `run-scenario.ts:318`, which I may not edit.
- `screenOverlayText` keeps paths whole, the same as `screenLocation`. So a path segment that is a secret token but matches no redactor pattern and is not a run secret would be kept. That is the same policy `screenLocation` already applies to page locations.
