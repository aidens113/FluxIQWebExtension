## Open questions or contradictions found

- **"read once at load" vs the cost ceiling.** The brief describes the cost ceiling as "read once at load". In fact, `model/run-cost-ceiling/` is read when asked (from `model/flows.ts`), and only `runtime/llm/flow-execution-limits/run-cost-ceiling.ts` holds a constant resolved at load. I followed the brief: one constant resolved at load.
- **Where the resolver lives.** It is in `runtime/llm/deepseek/models.ts`, not under `model/`:
  - `model/` must not import the runtime;
  - the model list is in `models.ts`;
  - a new Flow's default settings (`model/flows.ts`) carry no model at all. The "new-Flow default" is in practice the session-key resolver's fallback, which reads `AUTOMATION_STUDIO_DEEPSEEK_DEFAULT_MODEL`.
  - I did not add `llmModel` to new Flows' saved settings, because that would freeze the knob's value into each stored Flow.
- **The chat window's own model.** The knob also changes the model the chat window's own reading of a message uses (`panel-command.ts`, bound without a model in `_shared/runtime.ts`), not only the build. In a v4-pro comparison run the chat's interpreter call is on v4-pro too. If the supervisor wants only the build to change, pin the panel command to `AUTOMATION_STUDIO_DEEPSEEK_BUILT_IN_DEFAULT_MODEL` in `_shared/runtime.ts`.
- **The campaign always passes `--llm-model`.** `scripts/lab/live-campaign/lab-run/command.mjs` passes `--llm-model` on every run (default `deepseek-flash`). Every campaign run therefore now gives Core `FLUXIQ_LLM_DEFAULT_MODEL=deepseek-flash` explicitly, which matches Core's unset default. `pnpm lab:campaign <task> --llm-model deepseek-v4-pro` is the comparison.
- **Ceiling vs v4-pro rates.** v4-pro is about 4.4x the per-token price, so the $0.10 per-build ceiling buys far fewer calls. A fair comparison likely needs `--llm-cost-ceiling-usd`. The docs say so.
