## Step 0: what I found

- The read account (`read-condition.ts`, `AutomationStudioResultReadCondition`) has only the rendered `condition`
  text, for example `club equals ["A Club", "B Club"]`. Beside `leftOutOnlyByThis` it has `number`, `leftOutCells`
  and `testedLabel`, but no structured `field` or `equals`.
- The structured condition already reaches the summary in a second place, `summary.flowShape[].parameters`. It holds
  the step's authored parameters, screened so that only secrets and locators are withheld
  (`recovery/repair-context/parameter-screen.ts`). It is joined to the account by `nodeId` and `definitionId`.
  `read-account/accounts.ts` builds the account from those same authored parameters, and
  `read-account/read-parameters.ts` already finds the read's own object inside them. `result-summary.ts` no longer
  has a byte budget, so the parameters are present whenever denied keys are given.
- So I added no field to the account. Adding one would have needed an edit to `read-condition.ts`, which I do not
  own. It would also have put Core bookkeeping on the model's copy unless it was stripped the way `testedLabel` is.
  Instead, Core reads `where[number - 1]` from the authored step. It never parses Core's own wording back.
- Gap: a read whose node is not in `flowShape` (a called part's read) gets nothing from this. F1 then does not apply,
  and the defect is located as it is today.
- I first put the helper in `read-account/` as the narrowest owner. That took the directory to 26 files, and the
  structure audit failed it (25-file limit). I moved the helper to `located-defects/condition-equals.ts`, next to its
  only reader. `read-account/` ended up unchanged: I restored `index.ts`, including its CRLF line endings.

## What changed and why

- `located-defects/condition-equals.ts` (new): `automationStudioResultReadConditionEquals(flowShape, read, number)`.
  It returns `{ column, values }` only when the condition has a single relation, `equals`, against a string, a number
  or a list of them, and is not negated. If any value was withheld, it returns undefined. The column comes from
  `automationStudioResultReadConditionColumn`.
- `located-defects/tested-value-only.ts` (new): `automationStudioResultAskedTestedValueOnly`. It returns Core's
  finding only when all of these hold:
  - the request has wording (`record.says`), and `says(value)` is false;
  - every place a read left the row out is one condition alone, and no `leftOutTogether` set names it;
  - each such condition is an `equals` test of the defect's column (matched the way `located-defects.ts` compares
    columns);
  - the quoted value is not one of the values the condition keeps;
  - the row's own cell in that column holds the quoted value (`leftOutCells`, or the value said after the label).

  The finding reads: `Core's record of "<row>" holds "<value>" in "<column>", the value condition N (<wording>)
  tested and left out as written; the request does not say "<value>", so whether it asks for that row is not
  something Core can find in the row's cells.` The condition is named the way every line names one
  (`automationStudioResultConditionName`).
- `located-defects/located-defects.ts`: `notFound` now runs the new check only when `askedCellNotFound` would locate
  the defect: `askedCellNotFound(...) ?? automationStudioResultAskedTestedValueOnly(...)`. Where the request names the
  value, the defect is located as before.
- `located-defects/tested-cell.ts` (new): I moved `testedCell` out of `row-cells.ts` so both readers can use it.
  `row-cells.ts` now imports it, and its behaviour is unchanged.
- `located-defects/index.ts`: a t785 paragraph in the header, and the three new modules added to the barrel.
- Tests:
  - `located-defects/tests/club-posts-fixture.ts` (new): the generic club example, with no realistic scenario's words.
  - `located-defects/tests/tested-value-only.test.ts` (new): the two cases the brief specifies. Against "every post in
    a club I belong to" the defect is not located, and the finding is that exact sentence naming condition 1. Against
    "every post in A Club, B Club or C Club" it is located.
  - `agreement/tests/membership-reask.test.ts` (new): runs through `verifyAutomationStudioRunResult` with a mock
    provider. Both calls give the double no. Each no is re-asked once with `recheckWords`, and each recheck carries
    the condition-1 finding. The two re-asked yeses give `answers`, with no `unsupportedNo`, and the run is not

### Defect found by the first headed run, and the fix

- **First run: failed, and it reproduced the original bug.** The double no stood (`refuted`,
  `core.result.does_not_answer_request`, 2 calls), and a repair loop followed.
- **Cause.** A real summary's `flowShape[].parameters` go through the parameter screen
  (`recovery/repair-context/parameter-screen.ts`). The screen writes every list as `{ count, items }`, so the
  authored `where` and the `equals` list both arrive in that shape. My helper read only plain arrays, so it found no
  condition at all. My unit fixture had used plain arrays, so the unit tests could not catch this.
- **Fix in `located-defects/condition-equals.ts`** (my own file):
  - A list is read as its items, plain or as `{ count, items }`.
  - It is read only where `items.length === count`. A withheld item makes it unusable, because a lost condition
    would shift every number after it.
  - The header explains this, citing the headed run.
- **Fixture.** `located-defects/tests/club-posts-fixture.ts` now carries the screened shape a live summary carries:
  `extractList.where: { count, items }` and `equals: { count, items }`.
- **Second run: passed.** Verdicts were `does_not_answer, does_not_answer, answers, answers` (4 calls), with code
  `core.result.answers_request`. The recheck carried Core's finding: `Core's record of "Kim Tran — Urban Growers
  Network" holds "Urban Growers Network" in "group", the value condition 1 (group equals ["Riverside Allotment
  Society", "Harbourside Runners", "Old Town Bakers' Circle"]) tested and left out as written; the request does not
  say "Urban Growers Network", so whether it asks for that row is not something Core can find in the row's cells.`
