## What changed and why

### E3 — the record carries what Core sends, by the shape of the value

`build-proposal.ts` had the same three-field whitelist written twice — at
`:314-319` for a proposed build and again at `:329` for a refused one — so
widening the record meant widening it in two places and forgetting one. There is
now a single `buildSteps()` that both paths call, and it names no field.

A row is kept when it names a tool in the vocabulary. **Every other member Core
wrote on it is carried through, bounded by the shape of its value rather than by
a list of names**, which is what stops the next field Core adds from being
dropped here again:

- numbers and flags travel as they are;
- a string travels only if it matches `PUBLISHABLE_TEXT`
  (`/^[A-Za-z0-9_.:+-]{1,128}$/`) — Core's own rule for a code in
  `flow-bootstrap-commands/evidence-trace.ts`, widened only by `+` so a
  timestamp's UTC offset survives. No whitespace, so no sentence;
- a list keeps the members of it that pass, as `exploration-record.ts` already
  does with a list of codes; a record one level deep — Core's per-call `usage` —
  keeps the scalar members of it. Nothing nests deeper, so a structure large
  enough to hold a page is not a member of a decision.

A selector (`[data-testid="card"]`), an address
(`http://127.0.0.1:53017/scenarios/…`), a reply and a control's label are all
rejected by that shape, and a unit test asserts each of them is absent from the
serialized record. `CreatedFlowBuildStep` gained an index signature plus named,
documented entries for the six members Core keeps today (`iteration`, `callId`,
`evidenceBytes`, `reason`, `usage`, beside `effectApplied` and `resultCode`), so
a reader still sees what a row holds without the type being the filter.

**Redaction was not weakened, and here is the exact boundary.** What may now
travel that could not before is any whitespace-free token of at most 128
characters sitting in a field Core chose to publish on a decision row. That is
the identical rule Core applies to `resultCode` today, on the same audit detail,
and Core is the upstream authority on what may ride there. The residual risk is
a bare one-word value read off a page (`Submit`) if Core ever published one per
row; a label with a space, a selector, a URL, a prompt or a reply cannot pass.

### E5 — the per-call ledger for a build is read from the rows

`build-usage.ts:35-37` hard-coded `observedCalls: []` and
`perCallRecords: "not recorded"` for every build ever measured, so **no per-call
cap was ever checked on the one paid step of a created-Flow run**, and no bundle
said what a single call of a build cost. `buildProviderCalls()` now itemizes the
calls from the decision rows that record one (a `callId`, a `usage`, or both).

Three decisions worth knowing about:

- **Grouped by iteration, not by row.** Core counts a provider call per loop
  iteration, and an `amend_draft` decision that re-runs a step writes two rows
  under the one iteration that paid for both. Figures are filled in from the
  first row that reports them and never added together — summing them is the
  arithmetic that made every per-call figure of `run-mudw1ktb-0557816b` 27% too
  low. Iteration 0 is the deterministic observation before the first decision
  and is not a paid call, so it is left out.
- **`incomplete` is never reported for a build, deliberately.** For a run it
  means a call escaped every per-call cap, and `budget.ts:72-77` fails the run
  on it. A build's counted calls include the ones Core makes outside the loop —
  the instruction-authority derivation — which write no decision row and can
  never be itemized from one. Judging a build's rows as a run's lines would have
  failed **every correctly accounted build** as a `performance.budget` breach. A
  ledger short of the count is reported as the fallback it is: the calls it did
  itemize are published and each is still held to every per-call cap, and
  `unrecordedCalls` says how many were not.
- **`totalTokens` is derived** from input plus output when a row reports the two
  but not the sum, because Core keeps that identity and an unreported total
  would otherwise go unchecked against the per-request ceiling. Provider and
  model come from the build's own accounting — one grant, one provider, one
  model, and `live-llm-run.ts:339-341` already fails the run if Core reports
  another. Task kind, stage, prompt version and validation verdict are `null`
  rather than invented: Core names none of them per row.

### E6 — 21 of 22 calls stop being hidden

`vocabulary()` filtered the whole `core.` prefix. The tool the model explores a
page with is `core.run_node` (`AUTOMATION_STUDIO_LLM_RUN_NODE_TOOL_ID`), which
lives in the same namespace as Core's decision names, so the tool list of a
build that ran nodes came out empty or nearly so. It now filters
`AUTOMATION_STUDIO_FLOW_BOOTSTRAP_DECISION_STEP_IDS`, imported from
`fluxiq/automation-studio` — Core's own closed set, already exported through the
public barrel. A decision name Core adds is excluded here with no change; a tool
it adds is not dropped.

## What changed and why

### The rule is shared, not copied a third time

The defect being fixed was one rule written twice. Writing it out a third time
in a second file would have reproduced that defect at a larger scale — the next
person to widen it would have had two files to find instead of one. So the rule
moved to a new file both readers import:

`packages/test-runner/src/existing-fluxiq-control/publishable-step-value.ts`
holds `publishableStepValue()` (one member, judged by its value's shape),
`publishableStepFields()` (a row's members beside its `toolId`), the
`PublishableStepValue` type and the four bounds. `adaptation-evidence-loop.ts`
(a proposed build) and `flow-lane/creation/build-proposal.ts` (a refused one)
both call it, so a proposed build and a refused one are built by one rule rather
than by two copies that can drift. `build-proposal.ts` lost its local copy
entirely; `CreatedFlowBuildStepValue` is now an alias of `PublishableStepValue`,
so no downstream type name changed.

The direction is the existing one — `flow-lane` already imports this barrel
(`creation/tests/parked-proposal.ts`), and the directory imports nothing from
`flow-lane`, so there is no cycle.

### The policy the doc comment states still holds

The comment said "Nothing the tool returned and nothing the model wrote is
admitted", and the code enforced it by keeping three named fields. That policy
is unchanged and is now enforced by the shape of each value: identifiers, closed
codes, counts, byte sizes, flags and timestamps pass; prompts, replies, free
text, selectors, addresses and labels cannot. The comment has been rewritten to
say that, with the run that paid for the lesson (`run-muf8dstp-0135804a`) named,
so the next reader sees the rule the code actually follows.

`ExistingAdaptationEvidenceLoopStep` is now exported, with the six members Core
writes today named and documented beside an index signature — the same shape as
`CreatedFlowBuildStep`, deliberately, so the two records read alike.

### Two behavioural changes worth stating plainly

- **`effectApplied` is no longer coerced.** It was `Boolean(step.effectApplied)`,
  which turns the string `"false"` into `true`. It now travels as what Core sent
  it. Core writes a boolean; a coercion that can invert a value is worse than
  passing it through.
- **A malformed member no longer refuses the whole record.** `resultCode` went
  through `text()`, which throws on a non-string or an empty one, so a single
  odd member failed the entire reading. A member that fails the shape test is
  now left behind and the rest of the row is kept. This is deliberate and it is
  the same failure mode I flagged in Core's `hasExactFields`: refusing a whole
  record because one member was unexpected is how a widening turns into a total
  loss of the diagnostic. `toolId` is still validated and still refuses — the
  row's identity is not optional.

### A cast in my earlier test became a compile-time check

`build-proposal.test.ts` had a `publishedSteps()` helper whose only job was to
cast widened rows past the narrow type this file used to declare. The type now
carries them, so the helper is deleted and the literal is checked against the
real contract. That is what proves the two halves meet: the rows the fake Core
feeds are, by type, the rows `adaptationEvidenceLoop` produces.
