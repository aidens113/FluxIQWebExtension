## What changed and why

Nothing changed except this report. Findings follow.

### 1. Call path: how a build test resets, and how it follows a new tab

Reset (Core, browser-agnostic):

- `!FluxIQ/packages/fluxiq/src/programs/automation-studio/runtime/llm/node-tools/replay-draft.ts:163-171`
  `replayAutomationStudioFlowDraft` sends `dryrun.<n>.reset` through the ordinary executor, using the first step's tool id.
  The value is `automationStudioNodeReplayResetCall(from)` = `{ replay: "reset", from }` (`node-tools/replay.ts:128-129`).
  Core reads only `resultCode` and `effectApplied` from the answer. It knows nothing of tabs, and `dry-run.ts:80-81` says
  the reset is "a navigation" by contract.
- Downstream: `domain/src/runtime/llm-evidence/node-run/replay.ts:216-217` calls `replayWebOutputNode`, then `resetPage`
  (`:229-251`). That sends one `web.browser.navigate` (`RESET_ACTION`, `:91`) with `parameters: { url: from.location }` (`:242`).
  The step's other tabs are never mentioned.
- Extension: `apps/extension/src/runtime/action-runner.ts:100-106` resolves the tab with `tabRequestFor` (`:180-205`).
  A navigation that names no tab drives `navigationTargetTab(request.activeTabId, …)` (`navigation-target.ts:37-48`), which is
  the page in front. The command router re-reads Chrome's active tab before each action (`command-router.ts:35-37`).

Tab-follow (extension only):

- `apps/extension/src/runtime/click-landing.ts:186-218`, `sendClickCheckingLanding`: `watchOpenedTab(tabId)` (`opened-tab.ts:31-60`,
  `webNavigation.onCreatedNavigationTarget`) catches the tab that a `target=_blank` click opened. `driveOpenedTab` (`:247-282`) then
  calls `setAutomationTab(openedTabId)` and drives that tab from then on. Nothing records that FluxIQ opened it, and the only
  code that closes such a tab is `closeOpenedTab` (`:287-297`), which runs only on a 429/503 landing.

How the tabs pile up: exploration's click opens item tab T1, which is now in front. Test 1's reset navigates the page in front (T1)
back to the results URL, and the replayed click opens T2. Test 2's reset navigates T2 back and its click opens T3, and so on.
Each test leaves one more tab behind, because the reset reuses the newest tab and never closes the older ones. That fits the
live run: four item tabs by test 2, and five scenario tabs at the end.

### 2. Existing close contract, and which side owns the fix

- A close already exists: `web.browser.tab` with `{ operation: "close", tabId? }` (`domain/src/actions/types.ts:283-286`,
  `apps/extension/src/runtime/browser-tab.ts:223-250`). It closes one named tab or the current automation tab. It is a recorded,
  authorable Flow act: `background/connection/runtime-status.ts:152` maps it to the `tabClosed` input. It cannot say "the tabs
  FluxIQ opened", and the domain never learns the ids of tabs opened by a click. Reusing it would mean the domain sends tab ids
  it does not have, or an authorable act grows a replay-only scope. I do not recommend either.
- Core should not own this, and it needs no change. Its reset is already an opaque `{replay:"reset", from}` that the host
  carries out. "Put the target back the way the first step found it" is the host's job, and on the web that includes the
  tabs. No Core file is touched, so the change does not cross the repository boundary.
- Ownership splits two ways. The **extension** knows which tabs it opened, so it should keep that record and do the closing.
  The **domain** knows that a navigate is a replay reset and not a Flow's own navigate, so it should ask for the close. The
  request should be one flag on the reset's navigate, read the same way `newTab` is (`command-options.ts:64-66`). Gateway
  mapping already copies every parameter into `options` (`domain/src/client/gateway-mapping.ts:198`). Navigate's
  `parameterSchema` has no `additionalProperties` (`domain/src/actions/schemas.ts:217-224`), so the flag needs no gateway or
  schema change. It must stay out of the authorable schema, because a Flow must not be able to author it.

### 3. Smallest correct fix: never close the person's tabs

Domain side (one constant, one line):

- Export a shared key from the domain client barrel, for example
  `WEB_AUTOMATION_CLOSE_OPENED_TABS_PARAMETER = "closeOpenedTabs"`. Put it in a new single-export file under
  `domain/src/client/` and add it to that barrel, so both sides use one name.
- In `replay.ts:242`, `resetPage` sends `parameters: { url: location, [KEY]: true }`. This affects only the reset, never a Flow
  step's navigate or ordinary playback.

Extension side:

- New module `apps/extension/src/runtime/fluxiq-opened-tabs.ts` exports one object, `fluxiqOpenedTabs`, with three methods:
  - `note(tabId, sourceTabId)` records a tab together with the tab it was opened from.
  - `forget(tabId)` drops it from the record.
  - `closeAll(): Promise<{ closed: number[]; returnTo?: number }>` removes every tab in the record. It catches and ignores a tab
    that is already gone, and forgets each one. `returnTo` is the source tab of the oldest tab it closed, if that source is still
    open and not itself closed.
  - The record holds only tabs FluxIQ opened, so a person's own tab, including the tab the first click was pressed in, can
    never be in it.
- Record a tab:
  - in `click-landing.ts` `driveOpenedTab`, with `note(openedTabId, sourceTabId)`;
  - in `closeOpenedTab`, with `forget(openedTabId)`;
  - and optionally in `browser-tab.ts` `openTab`, plus the `forceNew` create in `automation-tab.ts` `resolveAutomationTab`, so a
    Flow step that opens a tab is covered too.
  - Do not record the plain fallback automation tab that is created when the panel is in front. It is the reset's own
    target, and closing it would only make the reset create it again.
- Read the flag in `command-options.ts` with a new `closesOpenedTabs(action)`, which reads `options[KEY]` as a boolean the same
  way `opensNewTab` does.
- In `action-runner.ts`, before `resolveAutomationTab` (`:106`), when `isNavigation && closesOpenedTabs(action)`:
  1. Call `closeAll()`.
  2. If `request.activeTabId` was among the closed tabs, run on a copy of the request whose `activeTabId` is `returnTo`. If
     there is no `returnTo`, use `latestOpenAutomationTab()`.
  3. Bring that tab to the front with `chrome.tabs.update(returnTo, { active: true })`, so Core's next snapshot reads the
     page that was reset.
  4. Then resolve the tab and navigate as today. The stale `activeTabId` matters here: the router read it while the opened
     tab was in front.

## Not verified

## Open questions or contradictions found

- A rerun's put-back (`step-place.ts`, run-flow-part) sends the same reset call, so it would also close FluxIQ-opened tabs.
  If its `from` is a page inside the item tab, it would load that page in the source tab instead. I think this is correct,
  because the page is reached by navigation either way, but the supervisor should confirm.
- If the person starts using a tab that FluxIQ's click opened, a later build test would close it. The record is cleared on
  each reset, so the exposure lasts only until the next test of the same build.
