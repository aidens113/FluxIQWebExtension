## What changed and why

**D12. A retry is not a repair.** File: `apps/extension/src/background/activity/pacer.ts`, plus the comment in `headline.ts`.
- Core reports both a retry and a repair in its `repairing` phase. A retry is the recovery ladder: the "Recovering from a failed step" row, then a choice such as "Trying the step again" (Core `executor/graph-run.ts:576,602`, `activity/wording/recovery-choice.ts`). A repair is Core working out a fix: "Working out what went wrong", "Deciding how to repair the step", and so on.
- A new private `RunRetry` in the pacer tells the two apart. The headline is `repairing` only when `UnitSituation.repairing` is set and RunRetry also says repair.
- For a build, every `repairing` event is still a repair, so builds behave as before.
- While a run retries, the detail line is `<why>, trying again`. The why comes from Core's `activityActionOf(event).why` in `fluxiq/ui`, the same reason the chat card shows, for example "The page was busy, trying again". When no code explains the failure, it reads "That step didn't work, trying again".
- The ladder's own thought, "Trying the step again", keeps that line instead of Core's generic sentence.
- RunRetry resets when the run reports its next step.

**D6. A finished step never shows "— done".** File: `pacer.ts`, new `statusSentence`.
- When a step finishes well (a `tool` row, `succeeded`, wording outcome "done"), the status line keeps only the action words.
- So the status never says "<previous step> — done" while the next step is running, and a finished step makes no visible change.
- Failed and tested outcomes still show ("— that didn't work…", "checked, not pressed").

**D7. The panel and the overlay disagreed.**
- Cause: both read the same paced `display` (`activity-relay.ts`: `state().display` for the panels and `contentMessage().display` for the page). But the overlay also ran its own `StatusDwell` (1.6 s) on top of the pacer's 1.2 s pace, and the panel's status row did not.
- The overlay therefore lagged the panel by up to about a second. That matches moment 4: the panel showed "Deciding" at about 190 ms while the overlay showed "Clicking “Get coupons”" until 1005 ms.
- Fix 1: I removed the overlay's dwell. `content/activity-overlay/overlay.ts` now draws each display as it arrives. I deleted `status-dwell.ts` and `tests/status-dwell.test.ts`, and took the dwell out of the barrel `index.ts`.
- Fix 2: I moved the dwell's guarantee into the pacer. `ACTIVITY_DETAIL_INTERVAL_MS` goes from 1200 to 1600, so any three seconds of paced changes show at most two.
- Fix 3: a step that starts (a `tool` row, `started`) while the shown status is a decision still being made ("Deciding the next step") now shows at once. The status can no longer say "Deciding" beside that step's working card.

**D10. The message moves into the stream at once.**
- Send files: `apps/extension/src/panel/chat/conversation/controller.ts` and `conversation/composer.ts`.
- Composer: the box empties on submit. If the send fails, the words come back, placed ahead of anything typed since (`words\nnew`), and are saved as the draft. An old owner's failed send never restores into a new owner's box.
- Controller: while a message is on its way, `state().turns` includes it as a provisional person turn (`sending:<n>`). It stays until Core's own person turn with the same words, absent when the message was sent, is read. So the message shows once and is never missing. It is removed when the send fails or the target changes. `mode` counts it, so the welcome screen does not flash.
- `live-line-model.ts` needed no change: "Sending your message" still shows below the bubble.

**D3 and D5, extension strings only.** File: `apps/extension/src/shared/activity/wording.ts`.
- D3: `OUTCOME_PLAN_OK` went from "the plan checks out, it still has to run cleanly" to "looks right, testing it next".
- D5: the type fallback now names the field, as clicks already did. A label gives `Typing into “Quantity”`, a typing-verb label is kept as written ("Type the product name"), and with no label it is still "Typing into the page".

## Open questions or contradictions found

- **Docs out of date (not mine to edit):**
  - `docs/architecture/extension-client.md:465` still describes `STATUS_DWELL_MS` (1.6 s, `status-dwell.ts`).
  - `shared/activity/activity-display.ts:16` still says "changed at most once per 1,200 ms".
  - Both should say the single pacer interval is 1.6 s, the overlay draws as it arrives, and a step that starts after a decision shows at once.
- **Pace versus "as soon as" (D6/D7).** The fixes stop "— done" and "Deciding the next step" from showing beside a working card. In a fast test run, though, a step that starts within 1.6 s of the last paced change still waits for the interval, so the status can name the previous step, without "— done", for up to 1.6 s. Showing every start at once would bring back the flicker the Lab flags (three or more changes in 3 s).
- **Small flicker risk.** The at-once paths (stages, settles, headline changes, a step after a decision) can now reach the page without the old dwell. So three changes in three seconds is possible in rare sequences, for example a fast model answer right after a paced change.
- **Recovery-ladder titles are copied from Core.** `RETRY_CHOICES` and `LADDER_ENDS` in `pacer.ts` copy Core's `recovery-choice.ts` titles. If Core renames them, a retry falls back to being headed "Fixing your Flow". A machine-readable mark on the ladder's rows in Core (for example a `ref` or `kind`) would remove this coupling.
