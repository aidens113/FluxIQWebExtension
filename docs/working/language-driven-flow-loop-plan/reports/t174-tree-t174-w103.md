## What changed and why

### Core (`C:/Users/osrs_/FluxStuff/fxwork/t174/!FluxIQ`)

Paths below are under `packages/fluxiq/src/programs/automation-studio/runtime/` unless they start with `docs/`.

- **`flow-draft/reversal.ts` (new): `automationStudioFlowDraftDropReversals(steps)`.**
  - It walks the draft in position order. For each kept, proposable step L that carries `toggle`, has no `cancels` and has no `routing`, it finds P: the latest proposable step before L with the same key. It passes over any step Core already took out (one with `cancels` that is not kept).
  - **Rule (a):** P is kept, has no `cancels` or `routing`, and has the opposite `to`. Both steps become `dropped`, each gets `cancels` set to the other's id, and both lose their `acts`.
  - **Rule (b):** P is not kept and has the opposite `to`. Only L is dropped, with `cancels` = P's id and its acts cleared.
  - A same-direction pair is left alone.
  - P being kept and already carrying `cancels` (the model put it back) is also left alone, so the model's decision stands.
  - It returns the steps it took out.
- **`flow-draft/step.ts`:** added `AutomationStudioFlowDraftStepToggle` (a type) and the step fields `toggle?` and `cancels?`, with docs.
- **`flow-draft/index.ts`:** barrel export and header line.
- **`flow-draft/amendment.ts`:** calls DropReversals after an amendment that keeps a step. It runs after the openers, the routing clear, the act claim and the move, so pairing sees final positions and an act claimed onto a step that is then dropped is cleared.
  - The design placed this call right after `KeepOpeners`. I moved it after the act claim, because otherwise `ClaimAct` would put an act back onto a just-dropped half.
- **`flow-draft/entry.ts`:** a step with `cancels` that is not kept shows an `out` line, built by `takenOutLine`. It is worded by position, and the "already chosen / not chosen" word is the later half's `to`. Example, for run-1 step 2:

  > taken out by Core: step 3 pressed the same control back, so the two together changed nothing. The control was already chosen before step 2, the state the Flow needs: an act about it belongs on the step after which the page first showed it chosen, and pressing it again would undo that state. Add both back only if a step between them needs the control the other way.

  - The later half reads: "it pressed back the control step N pressed, ...".
  - Rule (b) reads: "... and step N is not in the Flow, so in the Flow it would flip the control the wrong way. <same state sentence> Add it back only if the Flow needs the control the other way."
  - `AUTHORED_INSTRUCTION` and the system prompts are unchanged.
- **`llm/evidence-loop-decision.ts`:** `"toggle"` added to `readCallRecord`'s exact key list. The new `toggleOf` keeps the value only when it is a record with exactly `key` and `to`, `key` is a closed code and `to` is `on` or `off`, and the statement's `effect` is `mutate`. Anything else is withheld, never refused.
- **`llm/evidence-loop/tool-execution.ts`:** the type for `toggle?`, with docs.
- **`llm/evidence-loop/call-record.ts`:** copies `toggle` onto the record, so it is spread onto the appended step.
- **`llm/evidence-loop.ts`:** calls DropReversals after `KeepOpeners` in `draftRecord`, and after `automationStudioLlmEvidenceRerunReplaced` (the design's optional one-line rerun join). Both calls are authoring-only.
