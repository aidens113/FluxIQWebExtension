## What changed and why

### E1 — `flow-lane.json` is written for a failed build

`packages/test-runner/src/flow-lane/creation/lane.ts`

`runCreatedFlowLane` published its snapshot from one place, `recordEvidence`,
which is reached only after the Flow has been built, applied, read and run.
Every failure before that point wrote no `snapshots/flow-lane.json` at all.

- `runCreatedFlowLane` is now a thin wrapper. The body moved unchanged into
  `buildRunAndJudge(input, progress)`; the wrapper catches, writes the partial
  snapshot, and rethrows the original error untouched. No failure is swallowed
  and no verdict changes.
- A `progress` record is filled in as the lane advances — `flowId`, `build`,
  `review`, `shape`, `authoredNodes`, `ownPage`, `run`, and a `stage` naming
  where it is. `progress.build` is set **before** `settleBuild` and before both
  refusals, so a build that proposed nothing, a build that asked for a
  permission, and a settlement that breached its cap all keep the build record.
- New exported types `CreatedFlowLaneStage` and `CreatedFlowLaneIncomplete`, and
  a new optional input hook `recordIncompleteEvidence`. Both flow to
  `run-scenario.ts` through the existing `export *` barrels; no barrel was
  edited.
- The partial document uses the complete snapshot's own field names
  (`flowShape`, `authoredNodes`, `ownPage`, `runtimeRunId`, `status`,
  `resultVerification`, `route`, `actions`, …) plus `complete: false`,
  `stoppedAt` and `failure`. Every field is a subset of what
  `createdFlowLaneSnapshot` already publishes, so **no new disclosure**: the
  authored nodes are the same screened ones, the instruction is still counted
  and hashed by `describeCreatedFlowRequest` rather than quoted, and
  `failure.message` is the same string the bundle already publishes as the run's
  failure.

**Design decision the supervisor should know about.** The write is gated on the
lane having created its own Flow (`progress.flowId !== undefined`). Two refusals
happen before that — a workflow that is not the task's, and a blank Flow Core
did not leave blank — and for those the failure message already says everything;
an artifact of nothing but nulls would say nothing by being present, which is
the rule `snapshots/extraction-mismatches.json` already states for itself. This
also keeps the existing assertion `assert.deepEqual(mismatched.calls, [])`
honest. Everything from the build onward writes.

`run-scenario.ts` passes the hook as one line:
`recordIncompleteEvidence: incomplete => bundle.writeStructured("snapshots/flow-lane.json", incomplete)`.
A failure of that write is caught with an explicit `best-effort:` marker and the
lane's own failure is rethrown, so a failed artifact write can never replace the
finding.

### E7 — the run-wide capture controller has a screenshot adapter

`packages/test-runner/src/run-scenario.ts`

The adapter already existed at the old line 321, wired only into `stepCapture`.
It is now defined once, above both controllers, and passed to both. The run-wide
`capture` — which publishes every `runtime.dispatch`, every `runtime.settle` and
the `error` event — no longer resolves `capture-unavailable` for lack of one.

- The adapter photographs `stepRunner?.activePage() ?? scenarioPage`: exactly the
  rule the failure screenshot in the `catch` block already used.
- The `sensitive-input` exclusion is preserved verbatim.
- Before the scenario tab exists the adapter returns `undefined`, so early
  events still say `capture-unavailable` — truthfully, because there is nothing
  to photograph. Closed pages are guarded the same way.
- The evidence policy is untouched and redaction is untouched: the adapter
  claims the same `redactionVerified: true` the step adapter always claimed.

One behavioural nuance worth recording: the old step adapter fell back to `page`
(the scenario tab as first opened), the shared one falls back to `scenarioPage`,
which `findScenarioPageWithExpectedState` may re-point at another tab holding
the expected state. They are the same object until that happens, and the new
behaviour matches what the failure screenshot has always done.

### E8 — `error.details` is published for `runtime.behavior`

`packages/test-runner/src/run-scenario.ts`, the failure event in the `catch`.

The condition changed from `error.category === "recording.contract"` to that
**or** `runtime.behavior`, which is the class the created-Flow lane actually
raises: a build that proposed nothing, a build that asked for permission, a Flow
with no action node, a Flow with no extract node, a record count that did not
match.

**This one needed a judgement call, and I did not implement it literally.**
The brief's premise — "these are identifiers, codes and existing structures, not
prompts or page content" — holds for every `runtime.behavior` payload I checked
except one. `assertExtraction`
(`run-expectations/extraction/judgement.ts:196`) throws with
`details: { stepId, index, expected: entry.records[index], actual: records[index] }`,
and `actual` is a record read from the live page. Publishing that unconditionally
would push observed page values into `evidence-events.json` and the HTML report,
bypassing the disclosure rule `snapshots/extraction-mismatches.json` was built
around — whose header says in as many words that `RunnerFailure.details` reaches
no artifact today, and whose own rule withholds observed values when the
scenario declares a replay secret, because such a page has a secret on it by
construction.

So the publication carries that same gate and no new one:
`error.category === "runtime.behavior" && !scenario.secrets?.length`. For the
fixture scenarios this loop runs on, which declare no replay secret, the details
are published in full. For a secret-declaring scenario nothing new is published
at all. `recording.contract` is unchanged in both directions. Redaction is not
weakened anywhere; if the supervisor wants the details for secret-declaring
scenarios too, that is a deliberate widening and should be its own decision.
