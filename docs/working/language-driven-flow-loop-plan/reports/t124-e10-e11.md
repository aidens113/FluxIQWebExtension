## E11 — the new bound, and what it is derived from

### The bound

`TERMINAL_DETAIL_WAIT_MS = 90_000` is gone as a whole-run deadline. It is now
`TERMINAL_DETAIL_BASE_WAIT_MS`, the fixed part, and the bound is a function of
the Flow:

```
terminalDetailWaitMs(n) = min( 600_000 , 90_000 + (n - 1) × 91_250 )
```

`n` is the Flow's action-node count. In practice:

| Flow | Old bound | New bound |
| --- | --- | --- |
| 1 node | 90 s | 90 s (unchanged) |
| 2 nodes | 90 s | 181 s |
| 6 nodes | 90 s | 546 s (9.1 min) |
| 7 nodes and up | 90 s | 600 s (10 min, the cap) |

### Where each term comes from

Nothing here is a guess or a fresh measurement. Every term is a constant Core
publishes, applied by Core's own rule, so a Core that changes a ceiling moves
this bound with it.

- **90 s base** — unchanged, and kept for exactly the case it was measured on.
  It is the load-proven window from the two-bench campaigns, where the slowest
  observed single-node run completed its runner cleanup 46.5 s after Flow-lane
  dispatch. It is now the cost of a run *beyond its nodes*, which is why a
  one-node Flow still gets precisely what it got before.
- **91,250 ms per node after the first** — Core's own worst case for one node:
  - `AUTOMATION_STUDIO_READINESS_CAP_MS` = 30,000 ms, the ceiling on waiting for
    a node's recorded state. Core awaits readiness **per attempt**, not per node:
    the wait is named `<node>.attempt.<n>` inside the attempt loop
    (Core `runtime/executor/graph-run.ts:332`).
  - `AUTOMATION_STUDIO_DEFAULT_NODE_RETRY_POLICY` = 3 attempts, with backoffs
    `[250, 1000, 2000]` ms read by attempt number. Retries are on by default.
  - So: 3 × 30,000 ms of readiness ceiling, plus the backoff before attempt 2
    (250 ms) and attempt 3 (1,000 ms), summed with Core's own
    `automationStudioRetryBackoffMs` rather than by indexing the array here.
    3 × 30,000 + 1,250 = **91,250 ms**.
- **600,000 ms cap** — `AUTOMATION_STUDIO_LLM_EXECUTION_GRANT_MAX_RUN_MS`, Core's
  lease on a claimed grant. It is the only whole-run deadline Core publishes and
  is already this package's bound for a granted run (`GRANTED_RUN_WAIT_MS`).

The cap binds from seven nodes up, and that is deliberate. The per-node figure is
the worst case Core *permits*, not what a node costs — a node that resolves its
target and runs takes seconds. Uncapped, a twenty-node Flow would earn 30.4
minutes, and a nineteen-row campaign of stuck runs would spend 9.6 hours, which
is the exact arithmetic `RECOVERY_RECORD_WAIT_MS` was cut down for on 2026-09-23.
Ten minutes is the longest any run in this facility is allowed to be in flight,
so a deterministic run still unfinished after it is not a run that was merely
taking long.

### Where the bound is applied

`executeRecordedFlowRun`'s read-back path, in `persisted-flow-run.ts`. The
previous code gave the longer window only to a *granted* run:

```ts
const timedOut = granted && error instanceof RunnerFailure && error.details?.bounded === "timeout";
const wait = { ...(timedOut ? { timeoutMs: GRANTED_RUN_WAIT_MS, intervalMs: GRANTED_RUN_POLL_MS } : {}), ... };
```

A deterministic run — which is what a created Flow's replay is — fell through to
the 90-second default. Now:

```ts
const timedOut = error instanceof RunnerFailure && error.details?.bounded === "timeout";
const readBackMs = granted ? GRANTED_RUN_WAIT_MS : terminalDetailWaitMs(input.actionTypes?.size);
```

`input.actionTypes` is the map of the Flow's output-dispatching nodes, read from
`get-flow` across the parent Flow and every subflow graph — the same map
`stopWithoutFailedAttempt` already counts over. Every caller of
`executeRecordedFlowRun` passes it (`run-flow-lane.ts`, `creation/lane.ts`,
`saved-flow-replay/replay-saved-flow.ts`, and `repair/replay-repair.ts`
conditionally), so the bound is the Flow's own shape rather than a guess at it. A
caller that names none gets the one-node bound, which is exactly what every
caller got before.

Two deliberate non-changes:

- **A caller's own abort keeps the short window.** `bounded === "abort"` is
  somebody stopping the run, not the run taking long, and it still falls to the
  base default.
- **The granted path is untouched.** It already had Core's lease, which equals
  the new cap.

One further change: the read-back poll for a run that outlasted its request is
now 1 s for deterministic runs too, not 250 ms (the constant is renamed
`GRANTED_RUN_POLL_MS` → `READ_BACK_POLL_MS`, same value). At 250 ms over a
ten-minute wait, the lane would serialize 2,400 whole run details out of the
very Core that is still executing the run it is asking about.

### Why this mattered before a live multi-node run

The failure mode is not "the wait was short". It is that the wait's expiry
**rethrows the request's own timeout** as the run's result. A six-node Flow that
was executing perfectly well at second 91 would have been recorded by the Lab as
a product failure with an HTTP timeout attached — a verdict about a run nobody
observed fail. The deterministic replay path reaches this code on essentially
every multi-node run, because the control client's request bound is 30 s
(`http-control/index.ts`, `boundedTimeout`) and any Flow of several nodes
outlasts it, so the read-back *is* the deadline that governs a multi-node replay.
