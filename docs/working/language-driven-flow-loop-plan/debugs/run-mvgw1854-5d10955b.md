## Pattern across rounds 2 to 4, and one structural change

The same shape recurs: a refusal or failure carries a closed code and a generic instruction, the model varies the
call, every variation is refused for a reason it is not told, it resends one, and the guard ends the brief. Round 3
had it with `target_not_actionable` hiding the real `RATE_LIMITED` (fixed by t741). Round 4 has it with
`undo_unproved` hiding a subject mismatch.

**Proposed structural change (Core, general): every gate refusal names the condition that failed, as a closed
reason, and says whether any call on the current page can meet it. When the gate knows none can, the item stops
being listed as something to do here.** For the reset ledger this means:

1. `automationStudioSiteResetUndoAdmission` returns a closed `failed` reason on each refusal (`subject_differs`,
   `consequence_not_inverse`, `no_destination_baseline`, `subject_in_baseline`, `subject_not_present_now`,
   `already_undone`, ...). The words name it generically: "this control is about a different item than the one
   the act pressed".
2. When the ledger can show that no subject still present in any read destination matches the act's subject,
   `actsToUndo` marks the act `notSettleableHere` with that reason, and it stops being re-listed as something to
   undo. The brief is then offered its honest exits: end the brief naming the act, or ask the supervisor, which can
   end with the act named as left on the site. Neither exit admits a trial on leftovers, so no safety rule is
   weakened.

This breaks the loop generally because the model's next call no longer depends on guessing a hidden reason. Either
the reason is fixable and named, or the item leaves the to-do list. The same shape applies to any gate whose
refusal re-lists its subject (`candidate.create_baseline_required`, `trial_reset_required`). The repeat guard stays
as it is, as the backstop. Nothing in it names a site, task, saving or job boards.

## Cause

**A product defect, decisive. Not task, oracle, fixture or environment.** The task is achievable: the oracle's
saved set is the two pre-existing jobs plus Quillmark's three remote UK jobs (`breadth/save-quillmark-remote/
expected.ts`). The failing first save is a documented fixture trait (`manifest.ts`). The Lab log shows no fault, and
the run cost $0.059 of $0.25.

1. **Decisive (domain plus Core seam): a loop pass's lasting act is recorded on the template row, not on the row it
   acted on.** `domain/src/runtime/state-diff/places/diff.ts` `spotOf` uses only the recorded selector. Core's
   `runtime/executor/host-state.ts` `enrichAttemptWithHostState` gives `inspectStateDiff` no attempt inputs, so the
   domain cannot apply the pass's row. Effects: a correct undo is refused (0153), a wrong-row undo is admitted by a
   shared title (0149), and a reset after any looped trial is impossible on a site with no start hook.
2. **Decisive for the ending (Core words): `candidate.undo_unproved` names no failed condition and keeps the act
   listed as undoable** (`site-reset/undo-admission.ts` `unproved`, `site-reset/words.ts` `unprovedUndo`). See the
   structural change above.
3. **Secondary, for distance to a pass (not traced): a press the page answers with its own failure message counts
   as succeeded and as a landed act.** Trial step 7 "succeeded". The fixture's failure toast and the `heartBusy`
   class likely made the diff non-empty, so `landed-acts.ts` `noEffectSeen` kept act-10. The trial feedback says
   nothing of it. The judge put the missing job down to the company condition, which is wrong for that job.
   Revision 2 (`equals "Quillmark"`) would still have missed it. The "every node retries automatically" rule
   suggests a press answered by the page's own error should be retried, but where that read belongs was not traced.

Model behaviour on top, not the cause: brief-1's navigation loop (0043 to 0059) while it searched for a control
whose purpose is written nowhere, and the early `scope_refused` submit (0070).

## Proposed fix (least general) and its test seams

**Decisive, cross-repository (Core edit needed).**

- Core `runtime/executor/host-state.ts` `enrichAttemptWithHostState`: pass the attempt's `inputs` (at least
  `item`) to `inspectStateDiff`, and add the field to the host-runtime contract type.
- Domain `runtime/host-runtime.ts` `inspectStateDiff` and `state-diff/places/diff.ts` `spotOf`: when an `item`
  arrived, scope the node's parameters with `webAutomationScopedToRow`. Resolve the spot's handle to the control at
  the recorded place inside the record holding the row's values (the rule `content/action-runtime/pass-row/` uses at
  dispatch), never the template's. Where no such record is on the page before, give no spot rather than the
  template's.
- Tests:
  - Domain `state-diff/places/tests/`: a generic two-row list (a library catalogue's per-book "reserve" icon). The
    node's selector addresses row 1's control, the inputs carry row 2's values, and the spot's `item` and `subject`
    are row 2's. Without an item, it reads as today.
  - Core `executor/tests/`: the diff call receives the attempt's inputs.
  - Core `site-reset/tests/ledger-subject.test.ts`: three looped creates on distinct rows, each undone on its own
    row, are admitted. An undo on a row sharing only a title with another act's row is refused.

**Decisive for the loop, Core.** In `site-reset/undo-admission.ts`, carry a closed `failed` reason on every
`unproved()` refusal, and in `site-reset/words.ts` name it generically. In the ledger's `inPlace`/`named`, mark an
act `notSettleableHere` when no subject still present in a read destination matches its spot. Test in
`site-reset/tests/settlement-shapes.test.ts`: a subject-mismatched undo answers `subject_differs`, and an act with
no matching subject anywhere is listed as not settleable with that reason.

**Small, Core.** Name a looped trial act's pass ("trial step 10, pass 2 of 4") in `ledger.ts` `trialRan`'s `did`,
so the model can tell the acts apart when the control has no words.

**Secondary (needs its own trace).** A press answered by the page's own failure message should be read as failed
and retried, not counted as landed.

Not proposed: any change to the fixture's failing first save, the hearts' markup, the task, the oracle, or any
guidance that names saving, hearts or job boards.
