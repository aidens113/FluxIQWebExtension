## Cause

**Model behaviour the product should have prevented generically**, with two product defects that made the dead end
costlier and less legible.

1. **Decisive (Core): a reversible lasting act with no possible witness is admitted before any original is
   recorded.** The builder ignored the observe-first rule, and Core enforces that rule only for identified
   `create_new`. A `modify_existing` or `delete` press whose control sits in no recorded list, has no stated state,
   and names no issued `resetDestination` is, at admission time, already known to be unsettleable once it lands
   and seals the baselines. Owner: `site-reset/create-baselines.ts` `AutomationStudioSiteResetCreateBaselines.check`
   (and its caller in `ledger.ts` that runs it before a press).
2. **Secondary (Core): the settle words instruct something impossible after the seal.** With no ref issued and the
   baselines sealed, `settlement-words.ts` `clause` still says "read the list where it would show completely and
   name that list's ref as resetDestination". No ref can be issued any more, so the model invented
   `destination-1` (0104, 0106, 0142, 0146).
3. **Secondary (Core): an invented ref is silently ignored.** `ledger.ts` `explored` resolves
   `call.resetDestination` with `createBaselines.named`, which returns `undefined` for an unissued ref, and the call
   runs as if nothing was named. The tool's description says "Never invent a ref", but nothing refuses it, so the
   model got no signal (0105, 0107 ran; 0143 was refused for its undo press, not for its ref).

Not the cause: task wording, oracle, fixture or environment. The task is achievable (audit, `tasks-job-board.md`
row b), the Lab log shows no fault, and the cost was well under the ceiling. Every Core refusal in the run was
correct on its own terms. The undo presses at 0135, 0143 and 0149 aimed at a job saved before the build and were
rightly refused.

## Proposed fix (least general) and its test seams

**Decisive, Core only.** Extend the baseline precondition from identified `create_new` to every reversible lasting
press that has no witness, while the baselines are unsealed:

- In `create-baselines.ts` `check`: refuse unrun (same closed code `candidate.create_baseline_required`, or a sibling
  such as `candidate.reset_witness_required`) a press whose consequences are all in `REVERSIBLE` when none of these
  holds: its control's scope is a recorded original (it sits in a complete list), its control has a stated state
  (toggle witness; the ledger's tracker knows the place), or it names an issued ref under `resetDestination`. A
  refusal changes nothing and seals nothing. Its instruction is the existing one: observe the list where the
  effect would show, then retry with the ref that observation issues.
- Keep the existing `create_new` behaviour unchanged. Apply it only before the seal. After the seal, the refusal
  would block every later act and fix nothing.
- Tests in `site-reset/tests/` (generic example, such as adding a book to a reading list): an unsealed ledger
  refuses a `modify_existing` press with no witness and records no act; the same press with an issued destination
  ref is admitted; a press on a control in a recorded complete list is admitted; a press on a stated toggle is
  admitted; a refusal does not seal (a later observation still becomes an original).

**Secondary, Core:**

- `settlement-words.ts` `clause` for the no-witness reason: when baselines are sealed and no ref was issued, say
  that this act cannot be settled in this build, because nothing was read complete before the first lasting act,
  so no trial can run. Do not instruct naming a ref. Test in `settlement-shapes.test.ts` next to the existing "(no
  list was read complete before the build acted)" case.
- `ledger.ts` `explored` (or the undoes tool's admission): refuse a call whose `resetDestination` is not an issued
  ref, with a closed code and words saying refs come only from a `resetDestinations` receipt. Test: an invented
  ref is refused unrun; an issued one is admitted.

**Secondary, downstream UI:** the `left-told.ts` counting fix above.

**Open, for the supervisor:**

- **Subject distinctness.** `subjectsOf` requires distinct row subjects, and a row's subject is its title text
  alone. Many real lists repeat titles across rows that are different items, as here. Making such a list vouch
  (for example, telling rows apart by their primary link) would add a witness, but take care. For a press whose
  effect lands in another list, and whose own row shows no stated change, an unchanged source list would settle
  the act as "left as it is" even after a successful save. Do not take this up as the fix for this run.
- **The design bet.** The decisive fix turns a guaranteed late dead end into an early, recoverable refusal. If a
  site has no complete list anywhere that shows an act's effect, the build would be refused at the first press
  instead of at the first trial. The outcome is the same, and it comes sooner and cheaper.

Not proposed: reopening a trial on unproved leftovers, letting `cannotUndo` settle a reversible act, or any change
to the task, fixture, oracle or model guidance that names this site's behaviour.
