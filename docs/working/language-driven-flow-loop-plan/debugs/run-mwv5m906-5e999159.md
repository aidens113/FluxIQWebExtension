## Which read is the result, and how another becomes it

The result is the output group of the draft's read steps (`result/output-step.ts`): the last read step not marked intermediate, after any steps appending to its named output. Step 6 was the only draft read step, so it was the result from step 12 on. A read of the cart becomes the result as a draft step: a read call made with `add: true` (it is then the last read step), or `amend_draft` with `change: "take"` and the call id of a read already run outside the draft. Both are tools the model had and used in this run (`add` at 0011, `take` attempted at 0141 on another read). Where result processing is set (it was, over the listing's columns), it must be set again over the new step's columns, or the readiness check refuses the completion with a binding message.

## Fix, t1032

Core (`answer-first/result/`, `result-feed/`, `completion/`):

- `result-feed/list-pager.ts` (new), `result/types.ts`, `result/ledger.ts`, `result/header.ts`: a call's answer may carry `listPaging: [{ listKey, pages }]`; the ledger keeps the latest declaration per list (`pagers`), and the header says "the list shows no pager, so it holds one page" for a step whose list is declared pagerless and has no verdict, instead of "paging after X not yet checked". A list declared to page, or not declared, is unchanged.
- `result-feed/feed.ts` (`passed`): a pass whose answer names no list reads the step's own list (the ledger step's `listKey`), so a replay of the step on the page it read is that page again.
- `runtime/result-verification/asked-words/held-column.ts` (new, the one matcher of a named column, used by `answer.ts`, the header, the completion words and the judge), `result/header.ts`, `result/port.ts`, `result-feed/feed.ts`: where the request names columns (reader sure) that the rows do not hold, the header says "columns asked: ..., but the rows hold ... (no ...)", from the answer's columns after processing where the feed has them (the feed's port passes them, so the refusal's `resultHolds.result` says it too).
- `completion/result-columns.ts` (new), `completion/check.ts`, `completion/refused-words.ts`: every judge or caller-check no/unsure, and a refusal of the same evidence again, says which named columns the rows the check read lack, that they are not the table asked for, that the result is the draft's last read step, and the two ways a read of the asked table becomes it (`add: true`, or `take`), plus that processing must be set again over the new step. The words refuse nothing themselves.

Core (`runtime/result-verification/`), the lead's follow-up:

- `cited-yes/records-yes.ts`, `verdict/types.ts`, `verdict/result-verdict.ts`, `flow-less/judge.ts`: where the result's own contract names the table asked for (`resultEvidence.answerContract`, reader sure), a yes is refuted (unsure, asked again once with Core's sentences) when it says no records are asked, or when the rows held have nothing for a named column (no column of that name and none sharing a word with it: the contract reader reads "with columns title only" as `title only`, and an exact rule would make that a refusal nothing could answer). **The 0094 yes is refused** with "... so it asks for records, and the yes says it does not ... have no title or copies column, so they are not the table it asks for"; the completion then adds how the asked table becomes the result. The asked table's own rows, yes with `asked: true`, pass in one call.
- `flow-less/held-yes.ts` (new), `flow-less/judge.ts`: a yes Core holds says "The check said yes, but Core held it unconfirmed: <Core's reason>", and for unread evidence names each call and code, never only "could not tell".
- `judge-evidence/core-call.ts` (new), `judge-evidence/project.ts`: Core's own calls are never handed to the host projector: its `core.*` tools (all but the four that run the host's nodes) and its control-flow and timing nodes (t1029 found waits, merges and For Each passes named gaps the same way). Each is an observation with no host facts and no gap, at the single gateway every projection goes through. t1029's downstream bookkeeping branch is then redundant; its toggle fix (`action.ts`) is the web's own evidence and stays.

Downstream (`domain/src/runtime/llm-evidence/`):

- `judge-evidence/structure.ts` (new), `judge-evidence/project.ts`: a structure packet is an observation with its item count, column keys, pagination and list name (no samples, labels or notes); no gap.
- The interim downstream guard that declined calls the web did not answer (`judge-evidence/domain-call.ts`) was removed once Core stopped sending its own calls: its only job was Core's calls, and for any other unknown call a gap is the right answer.
- `structure/list-paging.ts` (new), `structure/packet.ts`: every packet carries `listPaging`, per handle's binding the `listKey` a read of that list stamps (`output-nodes/extract-list/answered.ts`) and whether the binding kept a pager.
