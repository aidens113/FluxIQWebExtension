So the draft showed the step as `changed: no`, `disposition: did_not_work`, `inResult: false`, and the model reran it pinned to the Next it could see on page 2. Twice it tried to remove the pin, and both attempts were refused `changes_nothing`, because the repeat guard held the original call as failed. The pin stayed in the Flow.

**2. A next page was reported as no next page.** This site draws Next as a plain div, and its handler is broken on purpose: the fixture's only ways forward are the page numbers and "Go to page". Pinned on page 2, where Next is the only div in the pager, the path is `... > div`. Played back from page 1, that path names the disabled Previous. The fallback then looked for a control labelled Next, which a plain div is not, or a number after one marked `aria-current`, which this pager does not use. So the step answered `control_absent` while the pager showed two more pages, and the read kept 3 rows from page 1. `nextControlOnPage` decided the current page by its own narrower rule, though `pager-reading/current-page.ts` exists so that readers do not disagree on it.

Any Flow filtering by a read of its own, on a request naming that first column, can fail this way. This check has been in place since `892cfdf5a` (2026-10-29).
