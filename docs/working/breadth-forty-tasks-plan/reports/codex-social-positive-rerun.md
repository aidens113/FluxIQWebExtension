## Final bounded design proposal: explicit transient intermediate output

Status: Design only; supersedes speculative owner lists above. No product/test edit, build, browser or paid retry performed. This is a proposed contract requiring supervisor approval, not a claim that the existing API already implements it.

### Choice and semantics

Choose optional `recordOutput.purpose: "answer" | "intermediate"`. Omitted remains answer. Explicit answer is identical to today's behavior. Unknown values, null purpose, malformed objects and malformed schema are refused by the existing strict output parser, rather than guessed or silently reclassified. Do not infer purpose from names, column count, an explicit output elsewhere, row-loop consumption, source dataset IDs or oracle success.

For explicit intermediate output, Core still parses the full recordOutput and validates/allowlists its rows, drops excluded fields, enforces schema/encryption limits, preserves validated `outputs.records` and the native result's row path so the real repeat/row-binding compiler works as today. It emits NO durable record batch. The rows are transient computation/control state, not an additional answer table. All action execution, read accounts, condition witnesses, row binding, retry policy, site permissions and final-state checks remain active. This is not a blanket removal of helper evidence from the verifier.

This is smaller and safer than persisting an invisible intermediate dataset with a role column: no SQLite migration, new dataset-summary protocol field, catalog rewrite, role merge rules or verifier exemption. It also avoids `recordOutput:false`: the current contract deliberately refuses false, and dropping the whole declaration would lose schema validation and the validated `outputs.records` alias the compiler may bind. A purpose marker keeps the complete existing schema contract.

Apply the same explicit transient semantics consistently to the two existing Core capture seams (policy-output dispatch capture and records.write capture), retaining their validated output/effect rows but no store batch. A write node with explicit intermediate purpose now means producing that validated row set for further computation, not durably saving an answer; generic parameter documentation must say so. Defaults remain durable answer writes. Never return early before validation or sensitive-field handling.

### Why compiler inference is rejected

Current authoring fills omitted/null extraction outputs and current answerability treats both raw-row-producing and explicit-storing nodes as capabilities. An explicitly named final recordOutput elsewhere does not prove another auto-derived dataset is unwanted: several answer tables and reads that both feed a loop and intentionally answer are legitimate. Once canonical parameters are assembled, declaration provenance is not retained. Inferring intermediate from an ID pattern or omitted label would be a hidden heuristic. Even tracking derived-vs-explicit provenance is insufficient to decide intent without a new ownership rule. An explicit opt-in purpose makes intent reviewable and survives ordinary Flow serialization.

The failed candidate has no marker. Its existing retained27rows therefore remain answer rows under the current contract; this design does not retroactively pass it or alter existing artifacts.

### Persistence, reopen and compatibility

Purpose is ordinary recordOutput JSON inside the saved Flow's existing node parameterValues. Current generic Flow compilation/document persistence already retains canonical JSON; strict output normalization/parser must preserve the recognized new property. Reopening and running the same Flow uses that marker again. There is no new storage metadata to reconstruct and no dependency on the authoring session.

With no batch emitted, current run processing/listRunDatasets/reopened service summaries never receive an intermediate dataset. Both actual service processing and build-test reconstruction must agree: `build-test/stores.ts` currently reconstructs every recordOutput from tool answers, so it must skip ONLY a successfully parsed explicit intermediate output as an answer store, while leaving the corresponding read/coverage/action evidence in the summary. Invalid or uncertain declaration cannot confer exemption.

Old Flows and old persisted runs have no purpose and stay answer by default. Existing failed-run helper datasets remain real stored answers; no migration or deletion changes their meaning. Explicit intermediate and answer outputs sharing a datasetId cannot erase or relabel each other's durable rows: intermediate produces no writes, while answer append/replace operates exactly as today. In particular an intermediate replace declaration must not clear a real answer dataset.

An older Core rejects the new property under strict record-output parsing. Coordinate paired release/build currency rather than allowing an old runtime to ignore it and accidentally save intermediate rows. Current public contract shape grows by one optional field; old serialized objects and stored schema/dataset formats are unchanged.
