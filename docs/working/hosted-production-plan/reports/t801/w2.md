## Gaps found
1. **BLOCKING: Core's server never starts the provisioning listener.**
   - `startProvisioningListenerFromEnv` has no caller outside tests (`grep` over Core `apps/web/src` and `packages`). `apps/web/src/instrumentation.ts` only calls `initializeFluxIQWebRuntime()`.
   - So `FLUXIQ_PROVISIONING_LISTEN` and `FLUXIQ_PROVISIONING_TOKEN_FILE` do nothing in a served panel, and createAccount/getAccount cannot be reached.
   - Core needs a one-line start in `register()` (get services from `getPlatformServices`). This is Core work and was not edited. `up.mjs` fails with this explanation after 120 s.
   - A fix was not attempted from this repo: the listener needs Core's in-process services.
2. `FLUXIQ_PROFILE` is read by no code (`grep` in `packages/fluxiq/src` and `apps/web/src`). It is harmless to set, but nothing changes with it.
3. Core has no `FLUXIQ_EMAIL_SENDER=file:<dir>` (known). The outbox is `<FLUXIQ_ROOT>/.fluxiq/platform/outbox`, where `<fluxiq>` is assumed to be `<root>/.fluxiq`. This is unconfirmed at runtime; `up.mjs` scans for the real directory.
4. `workspace:"new"` under the web composition's single tenancy: by source it is accepted. `resolve-account-workspace.ts` line 18 maps `"new"` or the one workspace id to the one existing workspace. Not proven live. Under single tenancy, "new personal workspace" is not created, so every account shares `workspace-main`.
5. Building through `prepareWebBuild` may regenerate the gateway artifact in place in Core (`ensureGatewayArtifact`) and saves a stat cache. Both are Core's own tooling and are a no-op when current; flagged because W2 was told not to write into Core.
6. The package directory `packages/website-stand-in` had only `public/` when I checked. `server/` and `package.json` did not exist yet, so the site part could not be tested.
