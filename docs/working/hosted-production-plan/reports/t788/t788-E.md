### `platform/iam/predefined/` (new)

The directory holds 13 files, a barrel and `tests/`. Each file exports one thing.

**Building blocks**

- `define-predefined-policy.ts`: `defineIamPredefinedPolicy(name, version, statements)`.
  - It looks up the kind from the contract's `IAM_PREDEFINED_POLICIES`, and throws for a name the contract does not list.
  - It runs `parseIamPolicyDocument(doc, kind)` **at load** and throws on any refusal.
  - It sets `Id` to `<name>.<version>` and deep-freezes the parsed result.
- `predefined-policy-definition.ts`: the type `IamPredefinedPolicyDefinition = IamPolicy & { version }`. Every policy is at `v1`.
- `workspace-patterns.ts`: `IAM_WORKSPACE_PATTERNS`.
  - `content` is `frn:fluxiq:*:${fluxiq:WorkspaceId}:*`.
  - `workspace` is `frn:fluxiq:platform::workspace/${fluxiq:WorkspaceId}`.
  - Grants that cover the whole workspace list both, because the content pattern does not match the workspace FRN.
- `action-list-statements.ts`: `iamActionListStatements`. It makes one statement per service and splits any list longer than 100.
- `predefined-policies.ts`: `IAM_PREDEFINED_POLICY_DEFINITIONS`, all seven, in contract order.
- `resolve-predefined-policy.ts`: `resolveIamPredefinedPolicy(name): IamPolicy | null`. It does an exact, case-sensitive lookup in a Map, and has the same shape as the store's `resolveManagedPolicy`.

**The seven policies** (each choice is also documented in a comment in its file)

| Policy (file, export) | Statements |
| --- | --- |
| `FluxIQOwnerFullAccess` (`owner-full-access.ts`, `IAM_OWNER_FULL_ACCESS`) | `Allow *` on [content, workspace FRN]. There is no condition, so it takes the full-access fast path, and that path covers the workspace FRN too. It reaches nothing outside the workspace. |
| `FluxIQAdministratorAccess` (`administrator-access.ts`) | `Allow studio:* secrets:* gateway:* iam:* ops:*` on [content, workspace FRN]. There is no `platform:*`. It uses service wildcards because today's admin reaches every endpoint. It is not full-access, so list endpoints filter an admin's results per item. |
| `FluxIQReadOnlyAccess` (`read-only-access.ts`) | Built at load from the generated `IAM_READ_ONLY_ACTIONS`, with one `Allow` statement per service (`ReadOnlyIam`, `ReadOnlyOps`, `ReadOnlySecrets`, `ReadOnlyStudio`) on [content, workspace FRN]. It grants exactly the 98 actions. |
| `FluxIQUserAccess` (`user-access.ts`) | **`OwnData`**: `studio:*`, `secrets:*` and `gateway:*` on those services' FRNs in the workspace, with `StringEquals fluxiq:ResourceOwner = ${fluxiq:PrincipalId}`.<br>**`WorkspaceCreateList`**: `Create*` and `List*` of the same three services, on the workspace FRN only.<br>**`SelfService`**: `iam:SetPassword`, `SetPin`, `BeginTotp`, `ConfirmTotp`, `DisableTotp`, `CreateSession`, `RevokeSession`, `UnlockVault` and `LockVault`, on `frn:fluxiq:iam:${ws}:user/${fluxiq:PrincipalId}`. It does not include `CreateUser`, `UpdateUser` or `iam:Snapshot`. |
| `FluxIQBrowserSession` (`connected-session.ts`, `IAM_CONNECTED_SESSION`, so no identifier contains "browser") | **`SessionScope`**: `Allow gateway:* studio:*` on [content, workspace FRN].<br>**`SessionNeverIdentityOrReveal`**: `Deny iam:* secrets:RevealKey` on `*`.<br>**`SessionNeverDestructive{Ops,Studio}`**: `Deny` every action in `IAM_DESTRUCTIVE_ACTIONS` (all 16) on `*`. |
| `FluxIQProvisioner` (`provisioner.ts`) | **`ProvisionAccounts`**: `Allow platform:*Account*` on `frn:fluxiq:platform::account/*`.<br>**`DenyWorkspaceContent`**: `Deny *` on `frn:fluxiq:*:?*:*` (any FRN that has a workspace segment) and on `frn:fluxiq:platform::workspace/*`. A test shows that `?*` does not match platform-level FRNs such as `iam::policy/...` and `ops::program/...`. |
| `FluxIQServiceGuardrail` (`service-guardrail.ts`) | `Deny ops:*` and `Deny platform:*` on `*`. `ops:*` covers framework migrate (`ops:RunMigration`, Database Manager) and `ops:RegisterNode`. |

Things the guardrail does not deny yet, because no action exists for them:

- **Custom-node registration.** No endpoint registers a custom node; Studio only has `list-native-node-definitions`.

`studio:MigrateFlows` and `studio:MigrateLegacyFlowRepresentation` migrate the user's own Flows, so they stay allowed.

### `platform/iam/parity/` (new)

- `compare-role-parity.ts`: `compareIamRoleParity({registrations, roles, workspaceId?, profiles?, currentTimeMs?})`. It is pure. For each registration and role it compares two answers:
  - today's `permissions.includes(permission)`;
  - `compileIamPolicySet` with the role's policies as identity policies (no guardrail, session or boundary), then `evaluateIamRequest`.
- How it evaluates each pair:
  - The action is `iamActionName(iamProgramService(programId), endpoint)`.
  - The resource is `iamProgramFrn(ws, programId)` for `ops`, and `iamWorkspaceFrn(ws)` for everything else.
  - The origin is `panel`, and each pair runs under the profiles `local` and `self-hosted`.
- `parity-role.ts` holds the type `IamParityRole`.
- `parity-report.ts` holds the type `IamParityReport`: the counts per role and every mismatch, with its action, resource, profile and matched statement.
- Tests:
  - `tests/role-parity.test.ts` holds 3 synthetic unit tests. One proves that a mismatch is detected and reported.
  - `tests/live-role-parity.test.ts` runs over `createGlobalProgramRuntime().api.endpoints()`.

## Open questions or contradictions found

1. **`FluxIQUserAccess` grants almost nothing today.**
   - Today every non-`ops` action evaluates against the workspace FRN, because catalog `resourceTypes` is `["*"]`. The workspace FRN has no owner, so `OwnData` never matches.
   - A UserAccess-only principal is therefore limited to `Create*` and `List*` on the workspace FRN. It cannot use `studio:Snapshot`, `studio:Projects` or any `Get*` until B3 declares per-resource FRNs with owners.
   - This matters for a getfluxiq.com account created with `FluxIQUserAccess` before B3 lands.
   - I did not widen the policy: granting reads on the workspace FRN would expose an organisation workspace to every member.
2. **The ReadOnly version can go stale.** `FluxIQReadOnlyAccess` and `FluxIQBrowserSession` are built from the generated lists. Regenerating the catalog changes their documents while the version stays at `v1`, and no check enforces a bump. A test that pins a digest of each document against its version would close this.
3. **`studio:ExecuteClientAction` is denied to the browser session.** It is classified destructive and appears in the generated list, so the browser session denies it, as the brief requires. Confirm that a browser credential never needs to call it.
4. **Self-service actions that do not exist yet.** The plan's "deletion request" has no action yet. Browser management is covered by `OwnData` on `gateway` rather than by `iam`.
5. **`platform:*Account*` is speculative.** No `platform` action is registered, so this pattern is a guess at future provisioning names (createAccount, setPolicies, addMember). If addMember is named something like `platform:AddMember`, the pattern misses it.
6. **No full-access fast path for admin.** `FluxIQAdministratorAccess` uses service wildcards rather than `*`, so admin list endpoints filter per item, which costs some list performance. The plan reserves the fast path for the owner; confirm that is acceptable for self-hosted admins.
