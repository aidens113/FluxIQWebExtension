### API (`import { IamStore } from ".../platform/iam/store/index.ts"`)
- `new IamStore({ workspaceId: string | null, repository: IamRecordRepository, resolveManagedPolicy(name): IamPolicy | null, auditSink?, now? })`.
- `IamRecordRepository` (list/get/put/delete over `IamRecordEnvelope`) is structural, so database-manager's `Repository` is assignable. Core's `JsonObject` is the only import from outside the directory (type-only); no `programs/` import.
- Every mutation takes an `IamChangeContext { actor (FRN), origin, requestId, ipPrefix?, matched? }` (last argument).
- Policies: `createPolicy(name, kind: identity|boundary|guardrail, doc)`, `getPolicy`, `listPolicies`, `createPolicyVersion(name, doc, makeDefault)`, `setDefaultPolicyVersion`, `deletePolicyVersion`, `deletePolicy`.
- Attachments: `attachPolicy(principalFrn, name)`, `detachPolicy`, `listAttachedPolicies`; inline: `putInlinePolicy`, `deleteInlinePolicy`, `listInlinePolicies`; `setPermissionBoundary(frn, name | null)` (user or role only), `getPermissionBoundary`; `attachGuardrail`, `detachGuardrail`, `listGuardrails`.
- Groups: `createGroup/getGroup/listGroups/deleteGroup/addUserToGroup/removeUserFromGroup`. Roles: `createRole(name, trustDoc, ctx, { boundary? })/getRole/listRoles/updateAssumeRolePolicy/deleteRole`. Service identities: `create/get/list/deleteServiceIdentity`. `principalFrn(type, id)` builds FRNs.
- `resolvePolicySet(principal, { assumedRole?, sessionPolicies? })` -> `IamPolicySet`.
- Errors: `IamStoreError` with a closed `IamStoreErrorCode` union (22 codes, e.g. `invalid_name`, `invalid_document`, `reserved_policy_name`, `policy_attached`, `attachment_limit`, `unresolvable_policy`, `policy_kind_mismatch`, `workspace_mismatch`).

### Record kinds and ids
Envelope `kind` is `iam.<kind>`, `scope.domainId` is the workspace id (null at platform level), id is `<kind>/<key>`:
`policy/<name>`, `group/<name>`, `role/<name>`, `service-identity/<name>`, `attachments/<principal FRN>`, `inline/<principal FRN>/<name>`, `boundary/<principal FRN>`, and the single `guardrails`.

## Decisions
- Attachments are uniform: one `attachments/<FRN>` record per principal of any type, instead of embedding attached policies in the group, role and service-identity records. A group, role or service identity record holds only its own data (members, trust policy). Deleting one removes its attachments, inline policies and boundary.
- Audit `matched`: the store does not authorize, so it cites `{ policy: "store", sid: null }`, unless the caller passes the deciding statement as `context.matched`. `"implicit"` would be wrong. `time` is `floor(now/1000)`. Records are emitted only after a successful write, never for a refusal.
- Action names are by convention `iam:<Verb><PrincipalLabel>...`: `CreatePolicy`, `CreatePolicyVersion`, `SetDefaultPolicyVersion`, `DeletePolicyVersion`, `DeletePolicy`, `Attach/Detach{User,Group,Role,ServiceIdentity}Policy`, `Put/Delete{...}Policy` (inline), `Put/Delete{User,Role}PermissionsBoundary`, `Attach/DetachWorkspaceGuardrail`, `Create/DeleteGroup`, `AddUserToGroup`, `RemoveUserFromGroup`, `Create/DeleteRole`, `UpdateAssumeRolePolicy`, `Create/DeleteServiceIdentity`. I did not check them against the catalog (being written in parallel); B3 should reconcile.
- Resource FRNs in audit: `frn:fluxiq:iam:<ws>:policy/<name>` for policies (workspace segment empty at platform level), principal FRNs for principals.
- Added limits not in the brief: 5 versions per customer policy (`version_limit`), 20 guardrails. Group deletion is allowed with members.
- Policy kind must match the use: attached = identity, boundary = boundary, guardrail = guardrail. Checked on write (predefined kinds from `IAM_PREDEFINED_POLICIES`) and again on resolve against what the injected resolver returns.
- Inline policies appear in the set named `inline:<type>/<id>/<name>`. Managed names are de-duplicated across principal, groups and role.
- Boundary in the set is the assumed role's if a role is assumed (null if the role has none, the user's is not used), otherwise the principal's.
- Writes are read-modify-write with no locking; single writer per workspace is the caller's job (noted in the class doc).
