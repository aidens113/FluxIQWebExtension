## Existing authority worth reusing

Paths below are relative to Core `packages/fluxiq/src/programs/automation-studio/` unless stated otherwise.

Durable instructions already live in Core; no extension-local store is needed.
- `runtime/service.ts:3275` saves the instruction JSON, summary/index and SQL projection. `runtime/service/flows/store.ts:454` writes the SQL instruction resource/content digest; full JSON remains necessary because SQL body fields are null and source/attachment metadata is not projected. - `api/handlers/instructions.ts:57` implements `save-flow-instruction`. Request shape is `api/contracts/instruction.ts`.
- `runtime/service/flow-bootstrap-commands/save-goal.ts` stores an active required Flow-scoped generation instruction with metadata.source `evidence_guided_generation`. `service.ts:3286` exposes `saveFlowGenerationInstruction`, but its target assertion is CREATE/blank-only. Existing saved Flow migration cannot use this command unchanged; extend the owning instruction writer or add an explicit existing-Flow task writer using the same inventory.
- `runtime/service/flow-bootstrap-commands/instruction-inventory.ts` already enumerates all active scoped instruction IDs, paginates, and optionally checks completeness/duplicate/changed/missing records. `runtime/llm/harness/instruction.ts:86` resolves active applicable instructions and detects required-instruction conflicts. It accepts global/project/router/subflow/node instructions; any applicable instruction is not necessarily the automation's explicit task.
- `runtime/service/flow-bootstrap-commands/generation-context.ts:31` ALREADY refuses empty resolved instructions or error diagnostics for every generation mode, before provider resolution in `service.ts:1481`. Candidate mode additionally captures validated immutable original instruction inventory using `runtime/service/candidate-drafts/source.ts`; originalSources/originalInstructionsDigest are reused by candidate fingerprints and trial/promotion logic. Do not replace this existing ownership/pinning mechanism with trace-derived task text.
- `service.ts:1766` bootstrap proposal creation checks nonempty active in-scope source IDs, including global/project records. `runtime/service/flow-bootstrap-commands/applied-parent.ts` records bootstrapSourceInstructionIds and instructed consequences on the parent. This establishes build provenance but is not a mandatory persisted-run task gate.

## Explicit person text versus model/context prose

`runtime/conversations/person-words.ts` deliberately reads complete person turns and excludes assistant turns. `runtime/conversations/commands/argument.ts` returns `{text,from:person|argument,saysWhatToDo}`; create-here/describe/explore/improve use this helper. When no person turn is found, it falls back to command arguments. The saved instruction loses that `from` distinction: generation save writes the same metadata.source, and general instruction API preserves metadata rather than stamping trusted provenance. `improve.ts` saves the instruction through the general endpoint.

The durable model has no typed explicit-origin/authoritative-task selector. `sourceActorId` alone cannot prove whose text it is and is not stamped by the inspected save endpoints. LLM instruction_suggestion is a supported response kind; its existence must never satisfy a task gate automatically. Domain/Core stage system instructions are also separate from automation task authority.

Reuse inventory with a narrowly typed, server-written authority designation for new explicit Flow task writes, plus persisted actor/person-turn provenance where available. Keep valid legacy Flow-owned instruction records compatible unless they are known generated/inferred evidence. A command argument supplied by a model without source person text must not self-certify as the person's instruction. Direct operator/API task text should be an explicit authoring operation. Do not infer authority from tags alone, generated titles, metadata.source, recording descriptions, notes or Flow trace labels. Existing legitimate nonempty user-written FlowInstruction bodies must remain compatible even when they lack a newly added marker. Reject known model suggestions and inferred recording metadata; do not classify every legacy body as untrusted. Provenance is ambiguous where old endpoints discarded it, which is a documented limitation rather than grounds for a blanket migration block. An explicit adoption/edit path repairs known ambiguous/inferred sources without inventing authorship.

## Recordings are currently executable sources

- `service.ts:2100 reviewRecordingFlowProposal` approves directly into a newly created/existing Flow's primary graph, including `policyOverride`, or executable private/public reusable node definitions. It has no instruction check. Merely adding a nonempty instruction check would still preserve standalone trace compilation and does not establish instruction-led authoring.
- `runtime/service/proposals/approval.ts` approves mined policy proposals into a Flow/primary graph, with recording-derived source metadata and proposal.summary as Flow description. This is a second independent standalone recording path.
- `runtime/service/proposals/generation.ts generateRecordingProposal` accepts `instructions`/constraints/title, but stores them only in proposal.metadata and maps/mines the trace directly; requested llm_assisted is recorded as not_invoked. Those strings are not durable FlowInstruction authority.
- `runtime/service/recordings/proposal-generation.ts` deterministically maps executable recording actions. Retain recordings/proposals as inspectable evidence, but redirect/remove public executable approval destinations and mining activation. A described demonstration can be attached to an instruction-led draft/build; direct reusable executable node approval must not remain a shortcut around authority.

Recording model `model/recordings.ts` has metadata and notes, but no typed description. `model/recording-framework.ts CreateRecordingSessionInput` accepts metadata; `service.ts:889 updateRecording` owns mutation under the recording lock and accepts only name/archived. `api/contracts/recording.ts UpdateRecordingRequest` mirrors that. Add an owned description contract through these existing services, preserving legacy recordings and allowing explicit description edits without touching raw timeline/state. Generated name or task-scoped note is not automatically an explicit description. New recording start requires provided description; old undescribed records remain readable but cannot be attached as supporting evidence until described.

`FlowInstruction.linkedRecordingIds` is an existing attachment seam. No build-time linked-recording/description loader was found in generation-context; build context currently receives resolved instruction text and catalog/size. `runtime/recovery/context.ts recordingContextSection` carries only IDs from adaptation sourceRecordingIds. Add described, ownership-checked supporting evidence beside authoritative instruction context, clearly subordinate; never copy it into instruction body. Domain-specific trace projection remains host-owned.

## Minimal implementation partitions and migration

1. **Instruction authority/contracts writer**: model instruction optional authority/provenance fields and validation; API contracts/handlers instructions; existing save-goal/inventory plus a focused service instruction-readiness module. General save must enforce owner/validity and protect server-only origin fields. Summary readiness must not rely on title-only summaries or first page.
2. **Persisted execution/activation**: service.ts run/start/publish/bootstrap apply wiring, run-refusal closed codes/response, run-control authorization/checkpoint and repair-rerun ports. This worker owns the large service file exclusively or integration is serial; do not partition workers into concurrent topic edits of it.
3. **Recording description/supporting-evidence**: model recording creation, update/API contracts, service recording mutations, attachment validation and focused described evidence context loader. service.ts overlaps partition 2, so serialize facade wiring. Preserve old raw state/proposals.
4. **Recording-only exit removal**: service recording proposal review, policy approval/generation public routes; return actionable redirect to instruction-led draft/attachment instead of creating executable graphs. Rejecting a proposal and inspecting legacy evidence remain valid.
5. **UI/domain/Lab**: owned by separate workers; use production contracts, explicit task text and explicit description. No scenario-shaped model instructions or hidden recorded-only test bypass.

For old automation without explicit instructions: refuse before its next actual run; preserve editing/export/history. Attach or explicitly adopt a written task through the existing Flow inventory. Existing legitimate active nonempty Flow-owned user instructions do not require rewriting merely because a new optional origin field is absent. Distinguish task attachment from proving an old graph implements it: recording-derived graphs have no original instruction build binding. Do not fabricate one from recording labels. A safe instruction-led reauthor/extend from the preserved graph and described evidence uses existing candidate source pinning; deterministic explicit graph review/adoption can avoid mandatory new model calls, if the supervisor defines that user-authorized contract. Changed instructions invalidate old bound build/permission claims rather than silently trusting them. This is an explicit migration design decision, not something current records can prove automatically.
