## What changed and why

### 1. Recovery gets the page channel; `web.recovery.inspect` is withdrawn

**Why recovery had no channel (the cause).** The loop could already carry one: `runtime-exploration.ts` passes
`input.loop.pageChannel` to the evidence loop. Two places dropped it before it got there, both in
`runtime/adaptation/recovery/annotation/exploration.ts`:

- `explorationRegistryBinding` rebuilt the binding field by field and left out `pageChannel`, so the recovery's
  registry never declared one (and never offered `core.full_page`);
- the `loop` object handed to the runner carried only `tools` and `executeTool`, not the registry loop's `pageChannel`.

Both now carry it (Core, `exploration.ts`). The recovery's decisions are then projected exactly as a build's are
(whole once per page key, then changes, `core.full_page` offered from the first decision).

**A latent defect found on the way (Core `view-channel/binding.ts`, an addition).** The web domain's
`pageChannel.fullPage` hook returns the published page (`{schemaVersion, location, ..., pageView}`), while Core's
binding read only a bare view (`{key, lines}`). Every `core.full_page` call in production would have answered
`core.full_page.unavailable`. Nothing exercised it before: the t1036 scripted runs never called it, and the domain
tests call the hook directly, not through Core. Core now reads either a bare view or a result holding one under the
declared member; nothing else of the result is shown. New test in `view-channel/tests/binding.test.ts`.

**The opening look without a look command.** A recovery needs the page before its first decision, and the evidence
loop takes that only from a tool with `initialObservation` (W3 owns `evidence-loop.ts`, so the mechanism is
unchanged). It now rides the domain's navigate option exactly as a build's rides `core.run_node` (whose capture node is
outside the `node` enum): `web.recovery.navigate_in_scope` declares `perCallEffect: true` and
`initialObservation: { input: {} }`; its schema still requires `url`, so the model can never send the opening's
input. A navigate with no address captures the page where it stands and moves nothing (`web.inspect.succeeded`,
`effectApplied: false`). The person-needed fresh look after Continue uses the same call (Core picks the
`initialObservation` tool). `perCallEffect` is required by Core for a mutating option to carry an opening, and stops
the "look needs an attempt" withholding that an observe-only carrier (wait, describe, `core.full_page`) would have
suffered (`repeat-policy.ts` `automationStudioLlmEvidenceLookNeedsAttempt`); I rejected those carriers for that reason.

**Stable handles in recovery.** Recovery captures used to number their own elements per capture, so a full page
(stable, authoring numbering) and the recovery's pages would print different handles for one element, and every press
would renumber the page (the channel would send near-whole diffs). Every recovery capture (opening, press, entry,
wait, navigate, refusal pages, detection's `restamp`) is now numbered by the runtime's `stableHandles.restamp`
(`WebRecoveryHarnessContext.restamp`, required; wired in `tools.ts`). Restamping is by address, so numbering an
already numbered capture is a no-op.

`web.recovery.inspect` is removed from the ids, options, implementations and barrel (`harness-options/vocabulary.ts`,
`options.ts`, `execute.ts`, `index.ts`). Recorded runs and test-runner fixtures still name it as a string; nothing
registers it.
