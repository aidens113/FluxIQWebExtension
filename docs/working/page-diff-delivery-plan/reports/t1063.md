## Step 2, project build (`project-build/run.ts`): reachable, but a stall cannot end it

- **Every stall goes through one function.** All three routes call `automationStudioLlmEvidenceLoopRaise` (`runtime/llm/decision-handlers/loop-signal.ts`). That function answers `"continue"` when the loop has no `loopSignal`:
  - the top of the ladder: `ladder-top.ts:30`, called from `refused-repeat.ts:139,154` and `refusal-run.ts:74`;
  - a refused completion repeated: `evidence-loop/refused-again.ts`, then `evidence-loop.ts:304`;
  - the model's `ask_person`: `model-decision.ts` `asked()`. It is also not offered, because `personReachable` falls back to `loopSignal !== undefined`.
- **The supervisor loop is never given a `loopSignal`:**
  - `run.ts:307` passes `loop: { ...loop, unusableDecisions, decide }`, where `loop` is `draft.loop` without purse, signal and budget;
  - `draft.loop` comes from `service.ts:1577` (`{ ...bootstrapLoopLimits.loop, rerunAuthority, ... }`), which has no `loopSignal`. `automationStudioFlowBootstrapEvidenceLoopLimits` returns only `{ minToolCalls, budget }`;
  - `runtime/project-agents/supervisor/supervisor-loop.ts:266` `loopInput` adds none either.
- **So the supervisor's `stalled` callback at `run.ts:283-286` (`flowBootstrapEvidenceUnusableDecisionFailure`) cannot be reached.** A supervisor that keeps repeating itself is steered, the loop decision included. It ends on its result, the purse, the project build's clock (`AUTOMATION_STUDIO_PROJECT_BUILD_MAX_DURATION_MS`) or Stop.
- **Brief builders do have a `loopSignal`** (`brief-ports.ts:316`). Their stall throws out of the builder, and `runtime/project-agents/dispatch/ending.ts:227` (`thrown`) turns it into a brief return. The supervisor can re-dispatch or repair, so a brief's stall is not the build's failure.
- **What I changed: nothing.** The branch at `run.ts:283-286` is dead code. Whether to remove it is the lead's call.

## Step 2, candidate build (`candidate-generation.ts`): reachable, and a stall ends the build. Blocked.

**What happens today.**
- `candidate-generation.ts:158` gives the loop `automationStudioFlowBootstrapLoopSignal()` (`"end"`).
- At the top of the ladder, the loop first asks `recoverStall`. That is the trial gate's retest of the latest revision (`candidate/stall-retest.ts`, set at `authoring-loop.ts:154`).
- If no retest is left, `unusableDecisions.stalled` throws `evidence_repeat_without_progress` or `evidence_unusable_decision`, and the build ends.
- The comment at line 157 says "the build tests what it has and repairs it". That is true only for the bootstrap path. A candidate build has no round loop.

**Why I could not reuse `runAutomationStudioFlowBootstrapBuildPhases` from my owned file:**
1. **A new round would lose everything the build has done.** The submission controller (revision counter, latest accepted candidate, refusal memory), the trial gate (trial counts per revision, standing verdicts, refutations) and the site-reset start check are created inside one call of `runAutomationStudioFlowCandidateAuthoringLoop` (`authoring-loop.ts:106,109,124`). They are not exported or injectable. A second call per phases round would:
   - start again at revision 1 under the same `candidateId`, whose trial records are kept at service level (`service.ts:1573`, `trials.records()`);
   - lose the accepted candidate and the trial history.

   The authoring loop also forces `draft: false` and omits `draft` from its input type, so a phases `repair.resume` has nowhere to go.
2. **The phases code cannot test or judge a candidate's Flow.**
   - It works on `AutomationStudioFlowDraftStep[]`. A discovery-only candidate round has no draft steps; its Flow is `candidate.buildPlan`, and Core has no buildPlan-to-draft-steps converter.
   - So every candidate stall would take the `!judgement.stepsInFlow` branch (`phases.ts:556`). That branch announces "Nothing is in the Flow yet", which is false for a build with accepted revisions, and opens an exploring round with no test and no judge.
   - The candidate's test and judge is its trial port. The phases input has no way to plug that in.

**What is needed to finish step 2 for candidates (the lead decides):**
- **Option A: a real repair round.**
  - Own `runtime/flow-authoring/bootstrap/candidate/authoring-loop.ts` and allow a new sibling module there. Split it into a per-build session that keeps the controller, gate, start check and `acceptedIn`, plus a per-round run. Each new round shows the latest accepted script and the standing trial as evidence.
  - Add a seam in `unfinished-build/phases.ts` for a round whose Flow is not draft steps. The phases' test and judge would be the caller's (the trial port), and "Flow so far" would be the latest accepted revision.
  - This is a design change across three modules.
- **Option B: one line in my owned file.** Drop `...automationStudioFlowBootstrapLoopSignal()` from the candidate loop and keep `personReachable: false`. This matches what the project supervisor already does:
  - the top of the ladder still runs `recoverStall`, the gate's retest (test plus two judges), and the round goes on with its answer;
  - otherwise the model's loop decision steers it;
  - the build ends only on its result, the purse, the clock or Stop;
  - the cost is no fresh context window: the same build keeps going rather than starting a new round.
- **Option B was probed, then reverted.** With the line replaced by `personReachable: false`, I ran `npx vitest run` on `candidate-unusable-reply.test.ts` and `candidate-failure-kept.test.ts`: 3 failed, 4 passed (7).
  - All three failures are tests that pin the stall ending. Each now ends `flow_bootstrap.evidence_iteration_limit`, the budget ending: the purse ran out.
  - In the unusable-reply case, the accounting stayed `closeTo` the spent figure inside the $0.03 purse.
  - Those three tests would be re-pinned to the purse ending, as t1056 round 4 did for the bootstrap.
  - The file was restored from a copy afterwards, and `git status --short` in Core is clean.
