## Findings (cause)
Step 7 really did hold the change: the draft shown at 0023 lists step 7 as "repeats through step 8 while it succeeds", inResult true, and `result` already set. The model resent `repeat 7 while 8` and `result 7` anyway (0023, 0029, 0034), each refused `already_so`. Three causes:
1. The `already_so` refusal said only "Step 7 already says that". It named neither what was so nor how the step stands, so the model read it as "not yet applied".
2. Two amendments of one decision refused alike (0024: repeat and result on step 7) were marked `repeated: true`, the second falsely, since the model had not been told before. Draft refusals `repeated` also feed `repeatedOnly`, so a false flag distorted the ladder.
3. Detection gap: `amendmentRepeats` in the loop detector refused unrun only an edit that had once changed the draft (`amendmentsLed`). An edit that changed nothing was counted and steered at its second time (0030 steer, 0033 loop decision: change_approach), whose note said "the next one like it will be refused before it runs", but the third (0034) ran and was refused again. The steer's promise was false for no-op edits.

## What changed
- `runtime/llm/draft-amendment-feedback/stands-as.ts` (new) and `fallback.ts`: `already_so` now says the draft already holds exactly what the amendment says, that sending it again changes nothing, and shows the step as it stands in the draft's numbers ("it is in the Flow, it repeats through step 8 while it succeeds, it holds the result"). `step.ts`: feedback step type gets `result`.

Outside the named owned dirs, but it is the repeat detection for amendments.
- Tests: `draft-amendment-feedback/tests/already-so.test.ts` (new, run's step 7 shape), `repeat-guard/loop-detection/tests/no-op-amendment.test.ts` (new, run's 0023/0029/0034 key), `evidence-loop/tests/stalled-amendments-replay.test.ts` (memory describe added; third identical no-op decision now asserted refused unrun, second decision's repeated flags updated), `decision-handlers/tests/refusal-way-out.test.ts` (wording assertion updated).

## Addendum: lead's failed check and its fix
The lead's run of `src/runtime/llm/tests/draft-amendment-feedback.test.ts:523` ("stalls a round its caller ends on the signal as amendments refused, not as a refused call") got `llm_evidence_loop.repeat_refused` where it expected `llm_evidence_loop.draft_amendments_refused`.

Decision: the test is right, the new code was less accurate. A no-op edit refused unrun is still an amendment repeated, and `refusedUnrun` (`runtime/llm/decision-handlers/amendment.ts`) called `automationStudioLlmEvidenceRepeatStop(context, inARow)` without the amendments code, whereas the ran path passes `AUTOMATION_STUDIO_LLM_EVIDENCE_AMENDMENTS_REFUSED_CODE`. Before my detector change a no-op edit always ran and took that path; the unrun path was reached only by edits that had led somewhere. The fix passes the amendments code on the unrun path too, so the stall is said as amendments refused while still counting on the same refused-repeat ladder (`context.repeats.refusedAgain`, `automationStudioLlmEvidenceRepeatStop`). The test is unchanged and still protects: a round stalled by repeated amendments reports `draft_amendments_refused`, never a refused call.
