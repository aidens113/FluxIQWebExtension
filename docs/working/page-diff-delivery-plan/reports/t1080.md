# t1080: the page window is append-only (Core fluxiq 0.54.34)

## Outcome

Done in Core, with one follow-up downstream outside my ownership (see Open questions 1).

- Earlier prompt records are now never rewritten. Each result's page member becomes a short note, fixed when the
  record is first projected and based only on earlier records.
- The page deliveries now sit in one trailing entry, `core.page_window`. It keeps the same 20,000-character budget,
  "whole once, then changes", D7 re-basing, parts and `core.full_page`.
- Re-projecting the 28 attempt-1 requests of run-mwytbimp-e0c33977 through the new code:
  - the shared prefix falls back behind the previous request's settled history 0 times (before: 10);
  - estimated cache writes fall from 429,680 to 63,868 tokens;
  - estimated input-side cost falls about 29%.

## What changed and why

Core tree `C:/Users/osrs_/FluxStuff/fxwork/t1080/!FluxIQ`, `packages/fluxiq/src/runtime/`.

**`llm/view-channel/projection.ts` (rewritten).** The function now returns `{ history, window? }`.

- The state machine is the same as before: key states, holders, the budget loop, parts, recall.
- Output used to be rewritten into earlier records. Now:
  - **The note on each result is fixed when the record is projected:**
    - `{ key, shown: "whole", in: "core.page_window" }`;
    - `{ key, shown: "changes", since, in }`;
    - `{ key, since, unchanged: true }`;
    - a part answer `{ key, from, shown: "part 2 of 3", in }`, or `{ key, missing }`;
    - a recall `{ key, recalled: true, shown: "whole", in }`.
  - **The trailing entry:** `{ read?: legend, pages: [{ key, recalled?, current?, shown: [{ call, whole | since+changes | part/from/rest }] }], letGo?: [{ key, at }] }`.
    - Pages are in last-delivered order, so the current page comes last.
    - When a page is replaced or let go, its deliveries leave the trailing entry. Nothing earlier is touched.
    - `letGo` names the pages dropped for the budget until they are held again.
- The `replacedBy` and `droppedAt` rewrites are gone.

**Other Core files:**

- `llm/view-channel/window-tool-id.ts` (new): `AUTOMATION_STUDIO_LLM_PAGE_WINDOW_TOOL_ID = "core.page_window"`. The barrel `index.ts` exports it.
- `llm/context-window.ts`: puts the page window after the history and passing notes, before `core.current_view` and `core.current_flow`. The header and doc comments are updated.
- `llm/evidence-moves/evidence-that-moves.ts`: adds `core.page_window` to the entries rewritten each decision. This makes the Anthropic adapter put its cache mark before the window, never on it.
- `llm/view-channel/description.ts`: the `core.full_page` tool text now explains the notes, the window, `current`, `letGo`, and that read rows stay in view. It is 1,426 of 2,000 characters, generic words only.
- `llm/decision-context/shown.ts`: the header's order and cache comment is updated. No code change.

**Tests:**

- `view-channel/tests/projection.test.ts`: rewritten for the new shape. Two new tests check earlier records stay byte-unchanged:
  - one key going between two pages too large to hold together, with other keys between, over 24 appends;
  - every kind of delivery: whole, changes, unchanged, parts, recall, full page.
- `llm/tests/context-window.test.ts`: the page-channel block is updated. A new test covers pages 1 and 2 of one list under one key, with a budget that holds one page:
  - the window holds only the newest page;
  - `core.current_view` keeps both reads' rows;
  - no window entry changes as records are appended.
- `evidence-moves/tests/evidence-that-moves.test.ts`: holds `core.page_window` to its owner.
- `adaptation/recovery/annotation/tests/exploration.test.ts`: four assertions now read deliveries from `core.page_window`.
  - This file is outside the brief's paths, but my wire change broke it. Only the test is changed.

### 2. Caching the window when it has not changed: measured, not kept

The replay gained two variants:

- **markSame:** the window moves to just after the settled history, before Core's passing notes. When it is byte-identical to the previous request's, a mark goes after it. The 19-back lookback mark gives way, so a request still carries 4 marks with the system prompt's.
- **markAlways:** the same, with the mark after the window on every request.

| run | variant | read | write | uncached | input-side estimate |
| --- | --- | --- | --- | --- | --- |
| mwytbimp (window unchanged in 11 of 28 requests) | t1080 as built | 1,601,534 | 63,868 | 410,200 | ~$1.157 |
| | markSame | 1,616,115 | 123,262 | 336,226 | ~$1.160 |
| | markAlways | 1,621,197 | 221,279 | 233,130 | ~$1.196 |
| mwynbry2 (unchanged in 4 of 14) | t1080 as built | 514,830 | 41,021 | 128,308 | ~$0.411 |
| | markSame | 523,744 | 64,706 | 95,707 | ~$0.408 |
| | markAlways | 523,744 | 123,636 | 36,778 | ~$0.434 |

- markSame changes cost by +0.3% and −0.7%, which is noise.
- Why: a window that is identical to the previous request's is still preceded by the new result in almost every request. It is written to the cache (at 1.25×) and read back only when the next request appends no result.
- So I left the adapter and the window order unchanged. This is recorded in the Core doc.
