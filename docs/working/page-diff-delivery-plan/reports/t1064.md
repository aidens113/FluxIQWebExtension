# t1064 report: the Lab carries no call count

## Outcome
Done, with two pre-existing unrelated test failures and one deviation in the Lab run (below).

## What changed and why
No count of calls ends or invalidates a Lab run any more (AGENTS.md "No arbitrary limit ends or resets a run"; Core t1056).

- `packages/test-contracts/src/llm.ts`: removed `LLM_LAB_MAX_CALLS_PER_RUN`, `maxCallsPerRun` from `LlmTokenBudget`, `DEFAULT_LLM_LAB_BUDGET`, the dry budget and `LlmRunEvaluation`.
- `packages/test-contracts/src/llm-validation.ts`: removed every `maxCallsPerRun` rule. The key stays in the allowed-keys lists so older records on disk are accepted and ignored, never required. A run token budget is now only "a whole number of at least one request"; the `perRequest * calls` upper bound is gone.
- `packages/test-runner/src/live-llm/live-llm-plan.ts`: removed `CORE_MAX_CALLS`, `declaredCalls`, `maxCalls`. `maxTotalTokensPerRun` is now optional (present only when `--llm-max-run-tokens` was typed).
- `--llm-max-calls` is refused with "no count of calls exists, and the purse (--llm-max-cost-usd) bounds a run" in `commands.ts` (lab CLI) and `demo-llm-profile.ts`. It stays in the known-options list so the refusal is the message the operator sees.
- `live-llm/budget.ts`: dropped the call-count breaches and the run-wide input/output derivations (`declared * calls`); the run token budget is checked only when typed. Per-call caps and the dollar ceiling stay.
- `live-llm/flow-settings.ts`: Core's Flow settings schema still REQUIRES `llmExecutionSettings.maxCalls` (1 to 250; nothing reads it). The Lab now saves an inert constant `FLOW_SETTINGS_INERT_CALLS_FIELD = 250` there with a comment, and no longer reads it back as a mismatch.
- `live-llm/live-llm-run.ts`, `provider-failure/provider-failure-record.ts`: dropped `maxCalls`, `maxCallsPerRun`, `authorizedBuildCallLimit` from records and bounds.
- Removed the Lab's pass-through of a call count into Core: deleted `live-llm/call-limit-env.ts`, `live-llm/answer-first-call-limit.ts` (and its test) and the `buildCallLimit` option from `environment.ts`, `coordinator.ts`, `run-scenario.ts`, `attempt-lane/live/attempt/session.ts` and `run-attempt-command.ts`. The Core child's environment still drops an inherited `FLUXIQ_LLM_BUILD_CALL_LIMIT` and scope.
- `existing-fluxiq-control/adaptation-evidence-loop.ts`: removed the upper bounds; kept shape checks (whole safe integer, at least 1 for the loop count, total not below the loop's count and equal to loop plus additional).
- `demo-llm-adaptation-control.ts` (`adaptationCallCountWithinCeiling`), `demo-llm-adaptation.ts`, `demo-llm-creation.ts`, `demo-llm-live.ts`, `demo-llm-profile.ts`: removed `maxCallsPerRun` and the ceiling on an adaptation's call count (function name kept to limit churn).
- `scripts/lab/live-campaign/lab-run/command.mjs`: the campaign no longer passes `--llm-max-calls 26/48`; its tests updated.
- `docs/architecture/testing-facility.md`: rewrote the call-cap passages and the "resolved build-call allowance" section.
- Tests updated across test-contracts, test-runner (live-llm-plan, budget, live-llm-run, commands, cli-llm, demo-llm-*, existing-fluxiq-control, evidence-loop, environment, provider-failure) and scripts/lab.
