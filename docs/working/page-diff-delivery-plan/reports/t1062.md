## Cause

1. **Where the keys join a step.** When a handle names an element in a child frame, domain plan resolution writes
   `browserFrameId` and `browserFrameUrlPath` onto the resolved parameters
   (`domain/src/runtime/llm-evidence/plan-resolution/resolve-plan-node.ts:677-680`). The draft step's `ranWith`
   carries them, and the Flow is written from `ranWith`. Two other writers put the same keys on nodes: the recorder
   (`output-nodes/payloads.ts`, `withRecordedFrame`) and list detection (`structure/detect.ts`). The gateway lifts
   both keys onto the command (`client/gateway-action-parameters.ts`).
2. **Where Core refuses them.** Core's `validateParameters` (`runtime/flow-authoring/bootstrap/plan/validation.ts:216`)
   refuses any key the node definition does not declare. It runs on the resolved plan, in
   `runtime/llm/harness-options/bootstrap-completion.ts` `checkPlan`. No web output node definition
   (`domain/src/output-nodes/definitions.ts`) declared either key. So every node that ran in a frame was refused as
   `bootstrap.unknown_parameter`.
3. **Core is right.** This was not W3's fault either. A model-written plan with a handle in a frame resolves to the
   same keys and was refused the same way, so no Flow with a step in a child frame could ever be saved.

Reproduced before the fix: the new `output-nodes/tests/frame-parameters.test.ts` failed 3 of 3. It hit
`bootstrap.unknown_parameter` at `...parameters.browserFrameId` and `...parameters.browserFrameUrlPath`, the
same issues the run logged at step 0037.

## Where frame targeting belongs, and why

The frame stays a node parameter, and the domain owns it:

- Frame targeting is a web concept. Three domain writers and the gateway lift already treat the two keys as node
  parameters.
- Core's Flow node has no host-scope slot. Moving the frame into the target object would change the recorded
  format, the gateway lift, the extension command and dozens of tests, for no gain.

So the web's node definitions now declare what the web writes, and Core's check stays strict. Nothing in Core was
loosened.

## How a frame is found again on a later attempt

- **`browserFrameId` is run-scoped.** The browser gives a frame a new id each time its document loads, and a later
  attempt reloads the start page.
- **`browserFrameUrlPath` is the address.** It is the pathname of the frame's document. The extension already sent
  a command to the one child frame at that path, and used the id only to break a tie between frames at one path
  (`apps/extension/src/runtime/frame-address.ts` `chooseFrame`; existing test "the one child frame at the path is
  chosen over a stale id").
- **The domain disagreed with that rule until now.** Its own reads of the frame compared the frame a read reached
  with the saved id. Those reads are the before-action scoped capture, the frozen command scope and the looked-up
  re-acquire. Each refused the right frame as another document, so a replayed frame step's stale target could never
  be found again (`place_unproved`).
- **Now one rule holds everywhere.** When a read names a path, the path proves the frame and any id agrees. A frame
  named by id alone must keep that id.

The saved element is found again by its fingerprint inside that frame, as before.

   - The flowRun says "skipped: This was already done earlier in the task". Core's run-act gate (t994,

   - From the route states the run recorded (before: "… Chat | [Where are you?] Next"; after: "… Chat | [Get 10% off

   - **Fixed (frame-related, domain):** `own-layers/opened-by.ts` now says only a layer captured in the pressed

**What the probe showed.** The probe was a temporary log in the domain host of every `signRouteEffect`, `routeEffectSeen` and `observeRouteState` call. It is now removed.
- Attempt 1 recorded the effect of Next. That effect added one control name, "Back".
- In attempt 2, Core's run gate never asked the domain whether that effect was on the page. Its check (`effectNotOnPage`) stopped first, because Next's node in the assembled Flow had no `routeSignatures.effect`.

**Why the node had no effect.**
- Attempt 2 builds its Flow from the steps the task memory kept (`best.steps`, read in `attempt/opening.ts`).
- It looks up each step's signatures with its own routing's `signaturesOf` (`flow-run/assemble.ts`).
- Each attempt has its own routing. A routing knows only the page digests its own calls reported.
- The kept steps carried only attempt 1's digests. So no step kept from an earlier attempt ever had an effect.
- Without an effect, t994's page check can never release a held press on a replay. That gate path had only been tested with nodes given an effect by hand (`run-acts/tests/carried-press.test.ts`).

**A second gap, in the domain.** Even with the effect, `routeEffectSeen` would have answered `unknown`, not `not_seen`. `not_seen` required at least 3 added control names, all missing from the page. A stepper's Next adds "Back" or nothing.
