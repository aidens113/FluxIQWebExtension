## Outcome

Done in Core. The recovery exploration no longer ends on `maxActions` 24, `maxProviderCalls` 24, `maxRepeatsPerAction` 2
or `maxRefusedActions` 2. Its evidence loop now takes loop detection's signal (`loopSignal`), the same mechanism the
answer-first rounds use. So no count inside the loop ends it either: not its turns, calls, looks, refused repeats or
unusable replies. A repeat goes up the loop-detection ladder to the model's own `core.loop_decision`. A refusal reaches
the model as the action's result and is recorded by kind. What ends an exploration now:

- its answer;
- the purse, on the run budget's own codes (money, tokens, or a declared call count);
- its clock;
- a person's request or check;
- the model's own `ask_person` loop decision. Nobody is asked in the middle of a Flow, so the exploration ends there
  with what it gathered.

The guard against repeating a lasting act still holds. Loop detection refuses a stated lasting act on one target from
its third landing, which is the same bound the old repeat window gave.

One downstream follow-up is needed before the domain check passes against this Core (Open question 1).

## What changed and why

Core, `packages/fluxiq/src/runtime/adaptation/recovery/`:

- `exploration-budget.ts`:
  - The budget is now `maxDurationMs`, `allowDestructive: false` and `scopePolicy`. The four counts are gone from the
    type, the defaults, the ceilings and the resolver. A caller that still passes one is ignored.
  - The ledger still records every action and every provider call. It also records how often each identical action was
    attempted (`repeatedActions`) and the refusals by kind (`refusals`). The only thing that stops it is a clock.
  - `recordAction` takes `refused?: AutomationStudioExplorationRefusal`.
- `exploration-outcome.ts`:
  - Stop reasons are now only `wall_clock_expired`, `recovery_deadline_expired` and `operator_approval_required`.
  - Deleted because nothing produces them any more: `action_limit`, `provider_call_limit`, `repeat_window`,
    `refusal_limit`, the outcome `unsafe_action_blocked`, and the two refusal kinds as stop reasons.
  - New `AUTOMATION_STUDIO_EXPLORATION_REFUSALS` / `AutomationStudioExplorationRefusal` (`destructive_action_refused`,
    `out_of_scope_refused`). These record what a refusal was; they never end anything.
- `loop-signal.ts` (new, exported from the barrel): `automationStudioExplorationLoopSignal()`.
  - It answers `change_approach` with `continue`: the repeat stays refused and the model has been told.
  - It answers `ask_person` with `end`.
  - The answer-first rounds answer `end` to both, because they can start a fresh round; an exploration cannot.
- `runtime-exploration.ts`:
  - Passes `loopSignal` and no longer passes `maxIterations` or `maxToolCalls` (the loop ignores both under a signal).
  - `decide` and `executeTool` are refused only by the clock.
  - A permission request still ends the exploration as before. A person's no, and any domain refusal, is recorded and
    the exploration goes on.
  - The classifier type now returns `AutomationStudioExplorationRefusal`. Any other truthy answer is recorded as
    `destructive_action_refused`.
  - The result and its trace detail gain `repeatedActions`, plus `refusals` when any refusal was classified.
  - An `ask_person` ending is named `no_progress` / `llm_evidence_loop.loop_ask_person`, with Core's own sentence.
  - The trace status table loses `unsafe_action_blocked`.
- `annotation/patch-reserve.ts`:
  - The patch reserve now holds one reservation per call that comes after the exploration. The ledger counts each
    pending reservation as one call, so a declared call count leaves the patch and re-plan their calls through the purse
    itself (`llm_budget.run_call_limit`).
  - Before, a declared count lowered the exploration's own call ceiling (`provider_call_limit`). That required a single
    hold for two calls, which the call count saw as one call.
  - `declaredCallsPerRun` and `explorationBudget` are removed.
  - If any part of the hold cannot be afforded, none of it is taken.
- `annotation/annotate.ts`: no longer passes `declaredCallsPerRun` or the lowered budget.
- `annotation/exploration.ts`: comments only.
- Spending: unchanged. Decisions still go through the harness on the run's purse, and a purse refusal is renamed to
  `budget_exhausted` with the purse's code as `endedBy`.
- Model-facing words: none added. `core.loop_decision` is now offered to recovery decisions. Its text belongs to Core's
  `runtime/llm/loop-decision` (not touched here).

Core docs: `docs/architecture/automation-studio.md` (recovery guards 4 and 6, the backstop paragraph, the exploration
signal line) and `docs/architecture/package-boundaries.md` (a compatibility note for the removed fields, codes and outcome,
the classifier type, the new result fields and the patch-reserve signature).

## Open questions or contradictions found

1. **Downstream must follow; this needs a brief that owns these paths.** The fixes are small:
   - `domain/src/runtime/llm-evidence/harness-options/exploration-terms.ts` types its classifier's return as
     `AutomationStudioExplorationStopReason`. `out_of_scope_refused` is no longer a member, so the domain check fails.
     The fix is one line: annotate it with `AutomationStudioExplorationRefusal` from `fluxiq/automation`.
   - Its comment says refusals are bounded by "the budget's repeat limit", "Core's no-progress guard" and "charged
     against the action budget … ends in `budget_exhausted`". None of that is true any more.
   - `harness-options/tests/options.test.ts` ("ends a run that asked to leave its scope in unsafe_action_blocked") passes
     `maxRefusedActions: 1` and expects `unsafe_action_blocked` / `out_of_scope_refused`. It should now expect the run to
     go on, with `refusals: { out_of_scope_refused: 1 }`.
2. **Two bounds remain that are not the recovery ledger's, and I did not touch either.**
   - **Run call backstop.** The run budget still has a 250-call backstop when no call count is declared
     (`AUTOMATION_STUDIO_LLM_RUN_CALL_BACKSTOP`, `runtime/llm/flow-execution-limits/`, must-not-touch;
     `annotation/run-budget.ts` falls back to it). In my first purse test, calls were so cheap that the backstop ended
     the exploration (`llm_budget.run_call_limit` at about 248) before money did. Under the user's rule it is a count.
     Removing it is an llm-layer change.
   - **Clock.** The exploration's 600 s wall clock / recovery deadline still ends it. It is a clock, not a count, and the
     brief did not ask for it to change.
3. A provider failure that reports no usage (for example `llm.provider_output_invalid`) appears to charge little or
   nothing. So a model whose every reply is unusable is bounded only by a declared call count, the 250 backstop or the
   clock, never by money. That is why the all-unusable test now declares 40 calls. I have not traced how the harness
   charges such a call.
4. In a domain whose tools report no page state, an identical refused call is answered from memory forever and never
   escalates to a loop decision (shown by the 28-press test). Only the purse ends such a run. The web domain does report
   state, so this applies only to stateless domains.
