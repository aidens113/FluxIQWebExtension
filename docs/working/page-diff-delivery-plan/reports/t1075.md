## What changed and why

### A. Core's run parameters are one list, and none of them is identity

- **New** `runtime/flow-authoring/bootstrap/run-parameters/` (`step-run-parameters.ts`, `index.ts`): the
  `AUTOMATION_STUDIO_STEP_RUN_PARAMETERS` list, re-exported from the bootstrap barrel. It holds `requiresChosen`,
  `ensureState`, `expectedState`, `routeSignatures`, `timeoutMs`, `paceMs`, `retry` and `recordOutput`.
- `runtime/answer-first/act-record/identity/target-keys.ts` builds its not-identity test from that list. A separate
  pattern covers only what a model or a domain adds (`consequences`, `wait.*`, `timeout.*` and so on).
  `ensureState` and `routeSignatures` moved off that pattern and onto the list.
- The writers take their names from the list:
  - `instructed-acts/chosen-precondition.ts`: `AUTOMATION_STUDIO_REQUIRES_CHOSEN_PARAMETER` is now the list's
    `requiresChosen`;
  - `script-statements/step-done-when.ts`: `expectedState`.
- Test `act-record/identity/tests/run-parameters.test.ts`, which:
  - checks, for every name on the list, that a node's keys with that parameter equal the keys without it;
  - checks that the list holds the names the assembly writes;
  - checks that run-mwynbry2's saved s11 (with `requiresChosen`) keys as `d443…` with place key `1702…`. Those are
    the landed act's two keys, read from the run's `global.sqlite` row.

### B. A by-hand act is named by the step its call became

- **New** `act-record/call-acts.ts` (`AutomationStudioAttemptActCalls`) is the record's collaborator, reached as
  `record.calls`:
  - It remembers, in memory, which act each call of the attempt made, keyed by the loop's call id.
  - A call id that two acts answered to (a fresh round reusing it) names neither act.
  - `stepsOf(stamps)` gives an act `steps: ["step:<plan key>"]`. It does so only where the act answers to one of the
    forms the step says its call was sent or ran with. Without that check, a step an earlier attempt kept would stamp
    this attempt's act whenever the model reused the same call id. The draft really does keep earlier call ids:
    attempt 2's draft still held d10 with `callId: "c9"`.
  - `actOf(callId)` returns the act a call made.
- `act-record/contracts.ts`: `AutomationStudioAttemptActCall` gains `callId?`.
  `gate/read-call.ts` copies the call id onto the read act.
- `act-record/record.ts`:
  - begun, settled and rolled-back calls are noted in `calls`;
  - a step-name match in `carriedMatches` must pass `sameStepAct`. For an act a call made (it has keys), the step's
    action must be one the act answers to, and where both name a control in words, the words must agree. A plan key
    is a position in its Flow, so a later revision's s11 that presses something else is not held by it. Acts merged
    from a trial or run ledger (no keys) keep matching by name alone, as before.
- `act-record/seed.ts`: the seed's union also merges `steps`.
- **New** `answer-first/run-acts/step-stamps.ts` (`automationStudioAnswerFirstRunActStepStamps`): for each plan node
  that is a draft step's own node (same action, so not a merge its statement made), outside every repeat span, it
  returns the call id, `step:<node.key>` and the forms read as the act gate reads a call.
- `answer-first/attempt/draft-save.ts`: after the draft is saved, it calls
  `run.record.calls.stepsOf(automationStudioAnswerFirstRunActStepStamps(...))`. It runs only once the Flow is saved,
  because a name for an unsaved Flow could name a step of another. The ending flushes the record after this.

### D. A carried act's judge is shown what the act landed with

- **New** `answer-first/witnesses/act-evidence.ts`: for each of an attempt's own acts, the trail entries after the
  previous act's landing, up to and including its own. The landing entry is found by `judgeAct.actId`, or else by
  `record.calls.actOf(callId)`. Copies drop `callId`, `judgeSource`, `judgeSources` and `judgeAct`, so another
  attempt's judge never reads them as its own result's sources, and repeated values never point at a reused call id.
- **New** `witnesses/carried-evidence.ts`: an in-memory per-service holder, like `before-readings.ts`, holding at most
  32 attempts. An attempt hands on what it was handed plus its own acts' evidence, read when the next attempt opens.
  So attempt 3 finds attempt 1's evidence through attempt 2.
- **New** `witnesses/carried-trail.ts`: Core entries `core.carried_acts_evidence` and `core.carried_acts_evidence_end`,
  with the carried acts' entries between them. The words are generic and name no site.
- `attempt/run-attempt.ts`:
  - it reads the evidence for the attempt its seed came from;
  - it holds its own evidence for later attempts;
  - the completion check's `trail` is now `[...carriedTrail(), ...trail]`, for the summary only. `run.trail`, the
    journal, the checkpoint and the digest are unchanged.

  the saved s11 node and the recorded keys.

## Open questions or contradictions found

- **Plan keys are positions.** `s11` names the 11th assembled node. A later Flow revision may put another press there.
  `sameStepAct` requires the same action and, where both name one, the same control words. A revision whose s11 is
  another "+ Add" (same words) on another item would still be held: too little done, which a judge sees, rather than
  done twice. Naming acts by the draft step's stable id (`step.id`, as `step-of-node.ts` does) would remove this, but
  the run gate would need each node's draft step id from `flow-run/flow-run.ts`, which this brief did not give me.
- **Identity readers now share one list (done in the lead's follow-ups).** See "Follow-up" below. That includes
