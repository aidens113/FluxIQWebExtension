## What changed and why

Every path below is under Core `packages/fluxiq/src/framework/automation-service/service/answer-first/`.

### The first round, still in place

- **`result/output-group.ts`.** The answer's steps are:
  - the output step;
  - its run of appends;
  - the other result reads of the output step's list, matched by `listKey`, which both steps must state.

  Intermediate reads, reads of other lists and reads with no stated list stay out. So does a read whose output was
  started over.
- **`result/statement-words.ts`** (`joined`), `header.ts` and `change-line.ts` word the join as "each a result read of
  the same list".
- **`result/coverage.ts`** and `header.ts` state the list's coverage once, from every same-list step's pages.

### Review point 1: only the list's latest state joins

In `result/output-group.ts`, a same-list read joins only when every page it holds was read at the address of the output
step's most recently read page. The address is the page's `where`. It is the view with only the page-turning words taken
out (`rows/address-split.ts`), so:

- page 1 and page 2 of one search share it;
- another filter, sort or search gives a different address.

This is the same address t1074 (`page-set.ts`) and t1085 (`returned-pages.ts`) compare. The fallback cases, all described
in the code:

- If the output step's latest page has no recorded address, the answer is the output step's alone (plus its appends), as
  before t1091.
- A read holding any page with no address stays out.
- A read with no page joins nothing.

### Review point 2: overlap dedupes on shared fields

- **`result-feed/shared-fields.ts`** (new, exported from the barrel) names the stored field ids that every contributing
  page's schema holds. It returns them only when the pages come from more than one field set, every page has a schema,
  and at least one field is shared.
- **`result-feed/feed.ts`** computes that identity over the answer's pages. It is skipped when the merged schema declares
  a primary key, because that is the identity the reads already agree on. The identity goes to the data stage and to the
  legacy path.
- **`result-feed/stage.ts`** has a new `identity` input. When the bound processing declares no `dedupe`, this evaluation
  runs the data layer's own `processAutomationStudioRecordRows` with `dedupe: { by }`:
  - `by` is the bound asked columns (`process.columns`, which defaults to the sure request columns) when every one of
    them is a shared field;
  - otherwise `by` is the shared fields.

  Only that evaluation uses the key. The bound, stored and judge-shown declaration stays the model's, so nothing extra is
  saved into the Flow.
- **The legacy path** (`processed` in feed.ts) applies the same key:
  - with a declaration, it injects the same dedupe;
  - without one, it dedupes by `automationStudioRecordRowIdentity` over the key (the data layer's row identity) instead
    of the whole row.

## Not verified

- **The live join.** The kestrel harness never formed two result reads of one list, so the new join and the shared-field
  dedupe ran only in unit tests, not in a browser run. Bigbox's answer is a cart read, and its unsorted-then-sorted shape
  did not come up as two result-read steps either.
- **Kestrel join with unsaid places.** In t1082's run, both step 6's pass and step 12's pass read their page as
  "unplaced", with no pager place. Their `where` is the same, because the page word is stripped. t1074's supersede rule
  (`result/page-set.ts`, unchanged) treats a later page of the same list at the same address as a re-read when either
  place is unsaid. So when step 12 re-reads page 1, step 6's page 2 can still leave the ledger before the join sees it.

  Nothing in today's page records tells page 2 from page 1 in that case:
  - spots count list moves, and a re-navigation does not reset them;
  - the page word of the address is stripped and not kept.

  My unit test uses pager places (`page=1` and `page=2`), which do tell them apart. The harness answered 10 rows, so no
  9-row trace was needed, but it confirms the condition: the paging loop's pass read of page 2 came back "unplaced read
  1". Two records lack the page words:
  - the pass read's own answer, which carries no pager `place`;
  - the page's `where`, which `rows/read-evidence.ts` keeps as `list.view` from the address split and so drops the
    address's page words.

  A real fix needs one of those recorded on the page. Both live in `rows/` or the domain, which I do not own.
- **Judge evidence** still gives coverage per step, and `collectionReplaced` checks completeness per step. The save check
  covers only the output step.
- **Overlaps that change between reads.** The shared-field key can still miss an overlapping listing whose shared fields
  differ between the two reads, such as a bid count or time left that changed in between. The asked columns are the key
  only when all of them are shared.

## Open questions or contradictions found

1. **Unsaid places.** When the pager gives no place, two steps' reads of page 1 and page 2 of one search share an address,
   and t1074's supersede rule takes the later one as a re-read of the earlier. That would defeat the join. A pass read's
   missing pager place and the page words dropped from `where` are the records to fix (`rows/read-evidence.ts` or the
   domain), not the ledger. It did not occur in these runs.
2. **Other lists, unchanged from the first round.** Compose's `isResult` (in `attempt/round.ts`, which I do not own) still
   keeps a non-intermediate read of another list as a result read, and the ledger calls it a working read.
