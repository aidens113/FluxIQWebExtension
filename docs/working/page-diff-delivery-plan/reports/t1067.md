# t1067: the judge sees every read, the standalone judge sees the pages, and the add act names its item

Core worktree `fxwork/t1067/!FluxIQ` (branch `task/t1067-judge-sees-every-read`, fluxiq 0.54.31). Downstream worktree
`fxwork/t1067/!FluxIQWebExtension`. Nothing committed. No git command that changes anything was run, and no paid or live run.

## Outcome

Done, with one uncertainty and one limit, both under "Not verified".

1. **Working reads (Core, result feed).** Every read that ran and then left the draft now goes to the judge in
   `resultEvidence.working`, one page at a time with its rows (the same shape t1048 uses). That holds whether the draft dropped
   the step or an amendment dropped an old version.
2. **Page views (Core, judge evidence plus unreadable asks).** A judge asked on its own request after an unreadable reply
   now gets `pageViews`. That holds the end view, plus the before view where a lasting act ran, as the page text the decider
   read. All views together stay within the page budget (20,000 characters). The continuing judge's first ask and the
   deciding digest do not change.
3. **The add act (downstream domain).** A press on a card in a grid whose cards are keyed one by one now names the card. A
   card is keyed when it carries `data-item-id` or a similar per-card attribute, even if the page draws no list around it.
   The names come through `actedOn` and `actedOnItem`, as `item i/n (words)`. On the recorded grid, the add names
   "ValueRidge Essentials Paper Towels, 1 Roll, $1.28".

## What changed and why

### 1. Working reads: `answer-first/result-feed/`

- **Cause.** The ledger (`../result/`) holds only the draft's read steps. When a step leaves, `dropped.ts` removes its pages.
  The feed's `working` list (feed.ts:272, t1048) was built only from steps still in the ledger. So c15 and c50 vanished from
  every judge once compose rule 2 dropped them (0083, 0101).
- **New file `left-reads.ts`.** It compares the ledger before and after each change. It keeps any page that left every
  step, under the step and version it was read under. Two kinds of page are not kept:
  - a page read again at its place under the same step and version (the newer read stands for it);
  - a page carried in from an earlier attempt.
  A kept page is released again if a step takes it back.
- **`feed.ts`.**
  - The feed's port now wraps `record`, so every change to the ledger goes through the left-reads check. That includes the
    `port` the feed exposes.
  - `working` now lists the current working steps first, then the left reads in the order they ran. A left read has no
    `position`, because its step is no longer in the draft.
  - Nothing is capped. Existing `read-evidence.ts` validation and `from-batches.ts` already accept page-shaped working
    entries.
- **`index.ts`.** The barrel now exports `left-reads.ts`.

### 2. Page views for the standalone judge

- **Cause.**
  - The judge's projection (`judge-evidence/summary.ts`) shows views only as the domain's semantic state; the page itself
    is deliberately left out (`captureOmitted`).
  - A continuing judge reads the page in the decider's conversation. The standalone request has no such conversation, so it
    had no page at all.
- **Why the pages are not simply added to the projection.**
  - The deciding digest (t1036) hashes exactly what the judge is shown. A page that is read afresh differs by a scroll line,
    so the digest would change, and the same verdict would be judged again.
  - A continuing judge would also pay for the page twice.
- **New file `judge-evidence/page-views.ts`.** It holds one class, `AutomationStudioJudgePageViews`:
  - `read` finds each view's page by shape alone. It uses `automationStudioLlmPageViewOf` (a page key plus keyed lines) and
    never reads line text.
  - The order is: end view, then the before view (only where a lasting act ran), then the after witness (only where it
    differs from the end view).
  - The views share one page budget, `AUTOMATION_STUDIO_LLM_PAGE_BUDGET_CHARS`. Lines stay whole. A view that does not fit
    reports how many lines it left out (`linesNotShown`), so nothing is cut silently.
  - Everything goes through `automationStudioResultEvidenceScreen`.
  - `keep` and `of` store the views in a WeakMap next to the judge's summary object, never inside it. They are also keyed by
    the summary's `trail` object, which survives the citation re-ask's shallow copy.
- **`judge-evidence/summary.ts`.** Where views are required (`stateRequired`), it reads the page views from the raw
  `endView` and `witnesses` and keeps them beside the copy it returns. The before view is included only where a lasting act
  ran.
- **`unreadable-asks/note.ts`.** Every ask after an unreadable reply is a standalone request (`asks.ts`). Each one now
  inserts the kept `pageViews` just before `unreadableReply`, after everything the first ask sent, so any cached prefix still
  holds.
- **`judge-evidence/index.ts`.** The barrel now exports the class.

### 3. The add act names its card: downstream `domain/src/runtime/llm-evidence/node-run/press-effect/`

- **Cause.**
  - bigbox's grid tiles are `<div class=tile data-item-id=...>`. Its extraction rows carry `"data-item-id": "418830166"`.
  - The capture (`apps/extension/src/content/identity/record.ts`) treats `data-item-id` as a per-instance record key.
    Records found by key carry no text ("a keyed record carries no text").
  - `listPosition` is set only for `li` and similar list items.
  - So `element.item`, `element.cell` and `within` are all absent. As a result `webLlmItemRow` and `webNodeActedOnCard`
    returned nothing, and 0020 had no `actedOn`, no `actedOnItem` and no `actedOnCard`.
  - The binding still keeps a record address (`key<US>data-item-id<US>id`) for every element in the card, its text lines
    included (`describe-element.ts` sets `context` on every described element).
- **New file `keyed-item.ts`.**
  - It names the card when the element sits in a keyed record that is one of two or more records keyed by the same
    attribute. Its place is that record's position among them in page order.
  - Its words are the page-view lines of that record's elements, read the way `structure/item-row.ts` reads an item: text,
    image words and links, but never another control's words.
  - A single keyed record is not treated as an item.
- **`acted-on.ts`.** `webNodeActedOn` and `webNodeActedOnItem` fall back to the keyed item. The sentence keeps the first two
  lines, cut to 80 characters, as for an item. The whole words, up to 2,000 characters, go to the record.
- **`acted-on-card.ts`.** It now returns nothing for a keyed item, so a press reads either as an item or as a card in no
  list, never both.
- No Core change was needed for this part. Core's `read-answer.ts` already takes `actedOnItem` (or `actedOn`) for row ties
  and the act's line. `item-words.ts` reads `item i/n (...)`. The downstream projector (`judge-evidence/action.ts`) already
  passes `actedOn` and `actedOnItem` through to the judge's trail.

## Not verified

- **No live or browser run.** The keyed-record explanation comes from source plus the recording. The tile markup is in
  `scenario-lab/.../listing/tile.ts:35`, the record rule in `record.ts`, and the recorded rows carry `data-item-id`. I did
  not capture a real bigbox grid to confirm that every text element in a tile carries the keyed `context.record`.
  `describe-element.ts:138` sets it on every described element, but a real capture is the proof.
- **The page views do not reach every judge.**
  - They reach only asks after an unreadable reply: the continuing judge's standalone fallback, and any re-ask of a judge
    that was never continuing.
  - The **first** ask of a judge that never continues the decider (for example the Flow judge in `verify.ts`, or a provider
    with no continuation) still has no page. Covering it means changing `flow-less/judge.ts` or `verify.ts`, which are
    outside my paths.
- **Whether the views always survive.** They ride a WeakMap keyed by the summary and its `trail`. A re-ask copy that also
  replaces `trail` would lose them. No such path exists today: the citation notice is a shallow spread, and window fitting
  is off for version-1 evidence.
- Full `pnpm test`, `pnpm check` and `pnpm build` sweeps were not run, per the twice-a-day rule.

## Open questions or contradictions found

1. **Owned path.** The brief names `answer-first/completion/unreadable-asks/**`, and no such directory exists. The code it
   cites (`asks.ts:73-76`) is `runtime/result-verification/unreadable-asks/`, which the audit also names. I treated that as
   the owned path and edited only `note.ts` there.
2. **Domain ownership.** The add-act fix is in the downstream domain (`press-effect/acted-on.ts`, `acted-on-card.ts`, new
   `keyed-item.ts`), under "the act record's acted-on fields, wherever they are built". I left the capture
   (`apps/extension/.../identity/record.ts`, `context.ts`) and the page view alone. Grid cards still print no `- i/n`
   marker, so the decider's page view does not show them as items. That would be a broader capture change, and is worth
   deciding separately.
3. **Row ties for keyed cards.** A keyed card's add now ties to read rows by its words, as any list item's press already
   does (t504). Through those words it can also tie to a cart row with the same item name. `acted-on-card.ts`'s header warns
   about this for tiles in no list. I judged a keyed card of several to be a list item; the lead may want to confirm that.
