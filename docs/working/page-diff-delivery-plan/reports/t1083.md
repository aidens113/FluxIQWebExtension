## What changed and why

### F1, Core (`packages/fluxiq/src/`)

- **New port** `runtime/automation-host/contracts/route-reach.ts` (barrel `contracts/index.ts`) and the optional
  boundary method `reachRouteEffect` in `runtime/automation-host/boundary.ts`. Core hands the host the passed-over
  step and its recorded effect (opaque); the host answers one closed word: `stays`, `already_there`, `pressed`,
  `went`, `unreached`. Core reads no link, address or page words.
- **New** `engine/automation/state-routing/route-owed.ts`: `automationStudioNotArisenRouteOwed` asks the host when
  the step recorded an effect. No effect or no method reads `stays` (passed over exactly as before). A throw or a
  word outside the set reads `unreached`. `automationStudioUnreachedRouteSaid` prefixes the `none` record's reason.
- `state-routing/decision.ts`: the not-arisen branch now passes the step over only when the owed route is `stays`
  or reached, and carries `reached` on the `declared` decision. `unreached` falls through to the rest of the
  decision (now `routeByPage`, the old body unchanged) and the ladder, so a run is never sent on from a page it is
  not on. No new counts, caps or waits.
- `state-routing/routed-attempt.ts`: the passed-over attempt records `skipped.reached` ("the record says how").
  `engine/automation/contracts.ts` (the `target_absent` skip type), `flows/authoring/model/flow-adaptation.ts`
  (the run-detail record type) and `framework/automation-service/service/summaries/skipped.ts` (the run-detail
  projection, closed words only) carry it.
- `state-routing/not-arisen.ts`: a step passed over whose route was reached is no longer proof for the next step
  (`didNotAct`). The page it brings about has come, so a chain of not-arisen skips ends there. Header updated.
- `state-routing/announcement.ts`: the chat line says how the page got where the step leads.
- `state-routing/index.ts`: barrel exports.
- Docs: `docs/architecture/automation-studio.md`, "Passing it over keeps where it went", under "A step whose page
  never arose".

### F1 and K1, downstream (`domain/src/`)

- `runtime/route-state/effect/sign.ts`: one effect shape for both. A step that moved (`path` present) now also
  signs `from`, the start's path-shape hash (K1), and `destination`, the path of the address it went to, without
  query or fragment (or origin + path when it crossed origins), at save time beside `routeSignatures` in the
  effect, never in identity. `destination` is left out when it would push the effect past Core's 2,048-character
  bound, because Core would otherwise drop the whole effect. `web-effect.v1` stays: holds/seen read fields by name.
- `runtime/route-state/effect/seen.ts` (K1): in the "none of `added` shown" rule, a step that moved, met on neither
  `from` nor `path` and showing none of `removed`, has left without arriving: `unknown`, not `not_seen`. An effect
  without `from` falls back to "none of `removed` shown". The t1062 `standsWhereFound` rule and the no-`path`
  (Add to cart) case are untouched.
- **New** `runtime/route-reach/` (barrel `index.ts`):
  - `owed-route.ts` reads the route from the effect. With `destination`, an address holds when it has the same
    origin + path. Without it (effects saved before t1083, like this run's d10), it holds when it has the same
    path-shape hash.
  - `route-link.ts` picks the link to press: visible, top frame, not covered. Banner or navigation first, then the
    page body, and a dialog or covering panel last, then document order. For a shape-only effect it presses
    nothing when links of that shape go to different paths.
  - `reach-route.ts` (`webAutomationReachRouteEffect`), in the brief's order: `stays`, `already_there`, then press
    and check, then navigate to the destination and check, else `unreached`. Each command uses the bound it
    already has on this host: 5 s for a read or press, 15 s for a navigate, as `return-to-source-place.ts` uses.
- `runtime/host-runtime.ts` binds `reachRouteEffect`.
