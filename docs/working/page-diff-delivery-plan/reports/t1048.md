## What changed and why

Core tree `C:/Users/osrs_/FluxStuff/fxwork/t1048/!FluxIQ`, branch `task/t1048-read-rows`. Paths are under `packages/fluxiq/src/`.

### 1. Judge: a working read goes with its rows

- `framework/automation-service/service/answer-first/result-feed/feed.ts` (`baseEvidence`, `working`). A draft read step that is
  not the answer now goes to the judge page by page. Each page is built by the same `page(...)` form that the answer's pages use:
  source, step, version, position, conditions, fields, listKey, where, place, kept, rows, invalidCount and leftOut. Before, it went
  as `{step, position, listKey, kept}`. A working step that has read no page yet still goes by its count (`kept: 0`), so it does not
  vanish from the evidence.
- `runtime/result-verification/result-evidence/types.ts`: `working` is now
  `(AutomationStudioResultEvidencePage | AutomationStudioResultEvidenceWorkingCount)[]`. The new exported type
  `AutomationStudioResultEvidenceWorkingCount` lets a bundle stored before t1048, or a step with no page yet, still read. It is
  re-exported from `result-evidence/index.ts`.
- `answer-first/result-feed/read-evidence.ts`: a stored bundle's working entry validates either as a page (`kept` must equal
  `rows.length`) or as a count. `leftOut.found` nulls are decoded for working pages, as they are for pages and looks.
- `runtime/result-verification/result-evidence/from-batches.ts`: a working entry that carries `rows` is held to the page checks
  that pages and looks already get.
- `runtime/result-verification/flow-less/window-fitting.ts`. The brief names this file as `answer-first/flow-less/window-fitting.ts`,
  but it lives under `runtime/result-verification/flow-less/`; I edited that file. `resultEvidence.working` is now a fitting step
  between `resultEvidence.looks` and `resultEvidence.pages`. When the judge's window forces it out, it is replaced in place by a
  `core.summarised` account, and `summarised` names it. The existing note tells the judge in plain words that the item was
  summarised, and that a part settled only by a summarised item must be answered unknown. Nothing is dropped silently. I added no
  count or cap. A count-only working entry is never summarised, because its account would not be shorter.

### 2. Decider: each read keeps its own held group

- `runtime/llm/decision-context/current-view.ts`. A held view whose answer names its list, through `listKey` (Core's documented
  read contract, `engine/automation/records/read/`), is held under `holder:<holder>:<digest>`. The digest is the first 12 hex
  characters of a sha256 over `[listKey, place, address]`.
  - `place` comes from `automationStudioRecordReadPlace`.
  - `address` is the read holder's `url`, else a `location` on the holder or on the answer.
  - The group is never keyed by an element handle (`tN`) or a call id.
  - Each read stays in `core.current_view` until the same page of the same list is read again. That re-read replaces only its own
    rows, and the group keeps its place in the tail.
  - A held view whose answer names no list keeps the single `holder:<holder>` group, as before. The existing tests for that path
    stay as they were.
- **Where I went beyond the brief's wording, and why.** The brief says to key the group by "the read's stored list identity or
  handle". In run-mwvgjb8c-5a1f2ae3, page 1 (`read_results`, step 0022) and page 2 (`read_results_p2`, step 0026) carry the same
  `listKey` (`list.030ae6af307e2d1035ef1f5d969b`) and the same handle (`extraction.1`). Keyed by list alone, page 2 would still
  evict page 1, and the t1044 defect would remain. They differ by `place` (`page=1` against none) and by address (`&page=2`), so
  both go into the key.
- References (`core.view_reference.group`) name the per-read group. The digest is deterministic, so a reference reads the same on
  every request and the cache prefix holds. `evidence-loop-decision.ts`'s instruction ("the latest whole value for each
  independent group") stays true; that file is off limits, and I did not edit it.

## Open questions or contradictions found

1. **The brief's key alone would not have fixed the run.** In run-mwvgjb8c, page 1 and page 2 share their `listKey` and their
   handle (`extraction.1`), so a group keyed only by list identity or handle still evicts page 1. I keyed by list, place and
   address. A re-read of the same page of the same list still replaces only its own rows, as the brief asks.
2. **The brief's path for window fitting is wrong.** The brief names `answer-first/flow-less/window-fitting.ts`; the file is
   `runtime/result-verification/flow-less/window-fitting.ts`. I edited that file and its tests beside it.
3. **A filtered re-read keeps the old rows in view.** A list read before a filter change, then re-read after it (the address
   query differs), stays in view beside the new read, labelled by its call. This follows "every read that ran stays in view until
   the same list's read is replaced". Whether a filter change should count as replacing the read is a product call I did not make.
4. **The judge's instruction text was not changed.** `question.ts` still says "Working reads and looks are evidence outside the
   result", and that is still true. The file was not in my paths. Its trail note, "Data rows ... are supplied separately in full",
   is now true for working reads.
