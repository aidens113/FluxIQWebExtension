## Root cause (traced from the panel step log, 0008-0011)

1. **The 400.** `core_set_result_processing` (tool 8) was sent `strict: true` while `input.process` was
   `{"type": ["object", "null"]}` with no `additionalProperties`. `grammar.ts` counted a schema as an object only for
   `type === "object"` or `properties`, so it called the nullable open object representable.
2. **The waits.** `framework/automation-service/service/answer-first/attempt/decide.ts` (`waitedOut`) handed the
   keep-going table every `llm.provider_http_error` with a forged status of 503. That happened whatever the provider
   answered. `automationStudioLlmProviderUnanswered` counts `llm.provider_http_error` as "unanswered" whatever its
   status. So a 400 was classed `silent` and waited 5, 10, 20 and 40 s, each time inside the same decision. The step
   timestamps match this: 06:32:44.8, 50.0, 33:00.2, 33:20.5, all iteration 1.

## What changed and why

**Fix 1: a nullable object is an object** (`runtime/models/providers/anthropic/grammar.ts`)
- New private `isObjectSchema`: `type === "object"`, a `type` array that holds `"object"`, or `properties`. An open
  one, with no `additionalProperties: false`, makes the schema unrepresentable, so its tool goes non-strict.
- I checked the other `type === "object"` tests in the wire:
  - `grammar.ts:38`, the root check: a tool's input root must be a plain object, so I left it.
  - `isOpenOptionalObject`, the drop of a bare `{type:"object"}` for output formats: left. Because of the change above,
    a bare nullable open object now makes the schema unrepresentable (JSON-text transport) instead of being dropped.
    That is the conservative choice.
  - `strict-answer-schema.ts:33`: not sent today. Its own header says so.
  - `schema-misses.ts:157`: the validator, not the wire. It already handles type arrays.
- Fixture `runtime/models/providers/anthropic/tests/fixtures/panel-2026-11-28-0008-tools.json`: the 0008 request's 12
  tools exactly as sent. These are tool schemas only, with no page data and no key.

**Fix 2: a refusal that names a strict tool demotes it**
- New file `runtime/models/providers/anthropic/strict-fit/named-refusal.ts`. On a 400 whose message starts
  `tools.N`, it names the tool at place N in the `tools` actually sent, but only when that tool went strict.
- `strict-fit/demote.ts`: `automationStudioAnthropicDemoteStrictTool(offered, sent, named?)`.
  - When a tool is named, that tool is demoted first, whatever its size.
  - A named tool that was not sent strict demotes nothing, so the refusal stands.
  - The offer's held set narrows exactly as in t1093, per tool-set digest.
- `strict-fit/index.ts`: exports the new function.
- `runtime/llm/anthropic/provider.ts` (`strictToolDemoted`): a named-tool refusal or a grammar refusal demotes one
  tool and the request is sent again. Each pass removes one strict tool, so it ends by itself.

**Fix 3: a refused request is not silence**
- New file `runtime/answer-first/keep-going/refused-request.ts`. It recognises a refusal from either of two errors:
  - an `AutomationStudioLlmProviderError` with code `llm.provider_http_error` and a 4xx status other than 408 or 429;
  - a build failure `flow_bootstrap.provider_http_error` whose `accounting.providerRefusal.status` or
    `providerStatus` is such a 4xx.
  It returns t1093's words through `automationStudioLlmProviderRefusalWords`. The header records the decision:
  retrying an identical refused request cannot reach the result, so ending on it is no new way for a task to fail.
- `keep-going/thrown-kind.ts`: a new kind, `refused`, checked before `silent`.
- `keep-going/next-step.ts`: a new step, `{ kind: "refused"; why }`.
- `keep-going/next.ts`: order is Stop, achieved, purse or empty balance, refused, silent, fresh round. Silence
  (timeouts, network, 5xx, 429) keeps its backoff and its wording.
- `keep-going/index.ts`: exports the new module.
- **Outside the owned paths: two small edits in the feeders of `backoff.ts`.** The brief says "whatever feeds
  `backoff.ts`"; these files are not in its Owned list, so the lead should review them.
  - `framework/automation-service/service/answer-first/attempt/decide.ts` (`waitedOut`): it now hands the table the
    status the harness recorded (`metadata.providerStatus`) and the provider's refusal. It assumes 503 only when no
    status was recorded. A 400 is therefore no longer waited on. It is thrown as the harness failure, which already
    carries `providerRefusal`.
  - `framework/automation-service/service/answer-first/attempt/rounds.ts`: on `refused`, the rounds throw the round's
    error, after the existing `automationStudioAnswerFirstKeep(run)`. There is no new wait, no new round and no
    second message. The build's ending then says it once, in t1093's words: "Build failed: the model provider refused
    the request: <message>". The integration test below observed this.

## Open questions or contradictions found

1. **How an attempt ends on a refusal is the lead's call.** The attempt status contract has no failure state; it has
   working, achieved, budget_out, stopped_by_person and waiting_for_person. So I end the rounds by throwing the
   refusal, the same way any other Core failure leaves an attempt, and the build's ending says it once in t1093's
   words. The other ways I weighed all say something untrue:
   - `budget_out`: the budget is not gone;
   - `waiting_for_check`: its words are "a person to clear a check on the page";
   - `setup_needed`: that drops a row for an attempt that did act on the site.
   A new status would touch the attempt contract and the UI, which is t1099's area.
2. **Ownership.** `decide.ts` and `rounds.ts` are outside the Owned list, though the brief's "whatever feeds
   `backoff.ts`" points at them. `decide.ts` is where the 503 was forged; without these edits fix 3 cannot work.
3. `runtime/models/failures/unanswered.ts` (not owned) still lists `llm.provider_http_error` as "unanswered" for every
   status. Its comment says only a 5xx reaches the loop. That holds on the evidence loop's own path, because a 4xx is
   not a spent call and is thrown. It did not hold in answer-first's `decide.ts`, which is now fixed. A status-aware
   reading there would close the gap for any future caller.
4. `strict-answer-schema.ts` (not sent today) still treats only `type: "object"` as an open object. If it is ever sent
   strict, it needs the same nullable-object rule.
