## What changed and why

**Cause (confirmed).** On the user's run every readiness wait hit the 20 s deadline. The mechanism has three parts:
- `waitForTabReady` injects `pageSettledInPage`. That function waited for the page world's count of outstanding work to drain, with no bound of its own, so the worker's 20 s timer ended every wait.
- The count held every `fetch`/XHR until it answered, and every timer whose callback was a fresh closure. A real site never drains: analytics beacons chained by fresh closures, long polls, widgets.
- The content script's address-settle wait used the same function, with the same result.

Before the change, the new spec reproduced it on local-classifieds with background traffic: after load, idle, after reload, the listing and the sort each answered `false` at the spec's 21 s cap (log below).

**The rule (`apps/extension/src/page-world/page-work/tracker.ts`).** A page is settled when its document has not changed for `PAGE_QUIET_WINDOW_MS` (100 ms) and no work is out that can still be drawing it:
- A timer within the horizon, or a frame, that begins new work holds the page until it has run. The horizon bounds it.
- A request, and a timer or frame that continues a chain, holds the page until it is done or until the document has gone `PAGE_WORK_HORIZON_MS` (1 s) unchanged since the request or chain began. A chain is the same source again within a horizon of the last piece ending, or while a piece is still out.
- Every change starts the horizon again. So a list fetched and then drawn holds until the drawing stops, and so does a chain that draws as it goes.
- Work that changes nothing stops holding after one horizon, and never holds again. A later change made for other work does not wake an old long poll, so it adds nothing to the steps after it. The first version let such changes wake old work, and the sort case showed it. That is fixed, with a test.
- Sources:
  - a timer's or frame's source is its callback's text (`callback-source.ts`), so loops of fresh closures are one chain; `[native code]` callbacks are always new work;
  - a fetch's source is its address without query or fragment;
  - an XHR has no source, so each XHR is its own.
- Recurring work is still not counted, as before.
- `document-changes.ts` is one `MutationObserver` over the document from `document_start`. A page world that cannot observe its document says it is not counting, and the old one-second fallback applies.

**The asker (`apps/extension/src/shared/scheduled-work-settled.ts`).**
- It answers `true` at once when the page world says the page is not busy.
- Otherwise it asks again one task after the count drains, and every 50 ms in between, because work that changes nothing stops holding with time rather than with an event.
- It now takes `{ withinMs, signal }`. Before, an injected question outlived the worker's wait and stayed in the page, observing, on every page that never settled.

**The page world's events (`page-world/page-work/index.ts`).** BUSY is held work, or a document change within the quiet window. PENDING (press readiness) uses the same held-work rule, deferred timers included as before.

**The worker (`runtime/automation-tab.ts`, `runtime/navigation-events/page-work.ts`).**
- `TAB_READY_DEADLINE_MS = 20_000` is kept. The code says it is only the bound for a page that never stops changing, and that lowering it was never the fix.
- The injected question gets what is left of the wait.
- `ADDRESS_SETTLE_DEADLINE_MS` is documented the same way (`content/action-runtime/page-work/address-settle.ts`).
- `page-quiet.ts` passes `{ signal }`.

**The fixture (local-classifieds, on every page, no mode).** `client/background-script.ts`, wired into `pages/document.ts` and `route.ts`:
- **Beacon.** `GET collect?ev=...&n=...`, answered `204`. One page view, then a heartbeat every 0.6-0.9 s (`beaconInterval`), each scheduled by a fresh closure after the previous beacon answered.
- **Long poll.** `GET updates.json?since=..&wait=25`. The Lab's routes are synchronous and cannot hold a request open, and the server is not in this brief's paths. So the server answers at once with `held: false`, and the client falls back to asking every 25 s. The harness spec holds the request itself with Playwright routing, as a real long-poll server would.

**Tests.**

## Second round: only the press's own requests answer for it

**The defect.** The press check counted any request the page began after a press as that press reaching the server (t465). A beacon lands inside most 800 ms press windows, so a press the page ignored was not pressed again. local-classifieds' radius Apply ignores its first press, so the saved Flow's Apply failed (`run-mwznq45m-4adad633`, attempt 3).

**Attribution** (`apps/extension/src/page-world/request-starts.ts`, `page-world/work-cause/`). Each request is recorded with its cause:
- the armed press whose work it ran in, which `press-work/` already follows: click handlers, and the timers, frames, idle callbacks, microtasks and `then` callbacks they chain into;
- the timer or frame lineage it ran in.

`work-cause/work-origins.ts` is one rising clock. Every timer, interval and frame is stamped when scheduled with the origin of the callback scheduling it, or a fresh one (`page-work/timers.ts`). So a beacon loop of fresh closures keeps one origin. A mark takes a number from the same clock. The rule, in order:
1. The request ran in this press's work: it is the press's.
2. It ran in another armed press's work: it is not this press's.
3. It ran in a lineage whose origin is older than the mark: set going before the press, so not the press's.
4. **The exception.** A `GET`/`HEAD` fetch to an address the page's own background asked for before the mark, with the same method, is not the press's, but only while the press's work is wholly followed (click seen, synchronous handlers, all hooks intact). This catches a beacon whose next timer was set by the last beacon's answer, after the mark, where no lineage can say where it came from. Never excused this way: any other method, an XHR, a `sendBeacon`, a socket message. The method is read without running page code: a plain data property, or a genuine `Request`'s own getter. An accessor the page defined makes the method unknown.
5. Anything else, and any request with no record, is the press's. So a press that may have landed is never pressed again.

The same rule answers `REQUEST_PENDING_EVENT`. Where the page world says its hooks hold, the press no longer also reads the resource timeline, which cannot tell one request's cause from another's (`content/action-runtime/ignored-press/page-press-listener.ts`).

**One hole closed in "wholly followed"** (`page-world/press-work/later-listeners.ts`). The radius picker re-wires its new Apply on the first press, and that includes a `keydown` listener. The press-work watch used to make a press unknown the moment its work registered a listener for any event other than click, which switched off rule 4 for exactly this press. A listener can only run when its event fires, so the press now stops being followed at that moment:
- A window capture listener for the type hears the event before the target's own listeners, and marks the press unknown if the registered target is in the event's path.
- Targets the window may not hear still make the press unknown at once, as before: anything that is not a connected node, the window or the document (an XHR, a port, a detached element), and a node in a closed shadow root.
- So do `unload` and `beforeunload`. The window never listens for those itself, because a window `unload` listener keeps the page out of the back-forward cache.
