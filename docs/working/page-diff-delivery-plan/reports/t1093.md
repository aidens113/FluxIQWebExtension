## What changed and why

### 1. The strict set always fits (Core `packages/fluxiq/src/runtime/models/providers/anthropic/`)

- `strict-fit/` (new; barrel `index.ts`):
  - `grammar-refusal.ts` reads a 400 as a grammar refusal when its screened message says so. It matches the live
    wording ("The compiled grammar is too large ... reduce the number of strict tools") and the docs' wording
    ("Schema is too complex for compilation").
  - `tools-digest.ts` takes a sha256 of every offered tool's name, description and input schema, in order.
  - `held-fits.ts` is the process-wide memory: the strict set each refused offer is now sent with. It holds only
    offers that were refused and never drops one. The set only ever narrows.
  - `demote.ts` demotes the strict tool whose schema, as sent, is largest (ties go by name; `complete` goes last). It
    then holds the offer to the rest of what the refused request sent strict.
- **A finding that changed the design.** I first remembered only the tools that had been demoted. That failed on the
  panel fixture. Demoting `project_write_plan` freed counted budget, so `project_amend_plan` (3,514 bytes, the same
  size) turned strict in its place, and the strict count stayed at 8. Holding the accepted *set* fixes this: a tool
  the refused request sent non-strict never turns strict.
- `decision-tools-wire.ts`: when the offer's digest has a held set, only tools in that set may go strict. The counted
  limits still apply. `AutomationStudioAnthropicDecisionTool` gains an optional `variant.kind`, so `complete` is
  recognised by its decision kind.
- `runtime/llm/anthropic/request.ts`: the prepared request now carries `strictOffer`, the offered tools before
  strictness.
- `runtime/llm/anthropic/provider.ts`: `runTask` is a loop. On a grammar refusal of a request with a `strictOffer`, it
  demotes one tool and builds and sends the request again (`strictToolDemoted`).
  - No count ends the loop. It ends because each pass removes one strict tool.
  - With no strict tool left, the refusal stands.
  - A judge that continues a decider sends the decider's accepted tools byte for byte, so it carries no `strictOffer`
    and is never demoted.
  - A non-strict tool's call is still checked against its unchanged schema (`task-answer.ts` is untouched).

### 2. A refused request says why

- `models/providers/anthropic/messages.ts`: on a non-2xx response the screened `{type, message}` is written to the

  thrown message stays `Anthropic refused the request.` (briefly it carried the provider's sentence; the fourth round
  took that back, see below). The record was already on `error.refusal`;
  `normalizedAutomationStudioLlmProviderFailure` passes it on as before.
- `models/failures/refused-words.ts` (new; exported from the barrel), `automationStudioLlmProviderRefusalWords`:
  - a 4xx reads "the model provider refused the request: <its sentence>";
  - a 5xx reads "the model provider answered with a server error";
  - with no sentence, it names the error type.
- `automation-activity/wording/failure-code-words.ts`:
  - `http_error` is no longer "could not be reached";
  - the function takes an optional refusal record and, given one, uses the provider's sentence;
  - `redirect_rejected` has its own words;
  - "could not be reached" stays for `network_error` and `provider_request_failed`.
- `conversations/instructions/interpret.ts` (`automationStudioConversationModelProblem`): an `http_error` is said
  from the refusal record of a real `AutomationStudioLlmProviderError`. A look-alike object is ignored. "Could not be
  reached" is now only for `network`.
