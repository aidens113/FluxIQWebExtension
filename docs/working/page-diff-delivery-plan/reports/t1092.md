# t1092: the carried-row service repair tests failing on dev

## Outcome

Done. All five tests now pass, and the product needed no change. The cause was the tests' own support code, in two
layers:

1. **The page reader went stale (Core t1080).** A shared test helper could no longer find the page in what Core sends.
   This broke all five tests.
2. **A stale ending behind it (Core t1056).** Once the reader was fixed, one test still ran for about 10 minutes. It
   expected the run to end on a count, and Core t1056 removed counts as an ending on purpose.

Only downstream test files changed. Core was not touched.

Note: the brief puts all five tests in `carried-row-service-repair.test.ts`. Only the first is there; the other four
are in the sibling file `domain/src/runtime/tests/carried-service-repair.test.ts`.

## What changed and why

### Cause 1: the page reader (fixes all five)

**What happened.** The scripted model in both fixtures picks a field to type into. To find it, it calls
`currentPageLines` (`domain/src/runtime/tests/current-page.ts`). On each fixture's first repair decision this threw
`the result carries no published page`.

- The throw happened inside the fixture's fake provider.
- Core saw it as a failed provider call and asked again.
- So the scripted `core.run_node` with `write: true` was never sent.
- The replacement step never reached the draft, and every "replacement checked" assertion failed. This includes
  `actual writer must admit the only faulty-step replacement`.

**Why it threw.** Core **t1080** (Core merge `f98cbc6b0`, wip `b561910ff`, 2026-11-27 05:48, "Earlier prompt records
stay unchanged; pages sit in one trailing window") changed how the page is delivered:

- Each result's `pageView` is now only a note: `{ key, shown: "whole", in: "core.page_window" }`.
- The page text itself sits in one trailing `core.page_window` entry.
- The helper still read the page from `pageView.whole` inside each result. When it found nothing, it fell back to
  `core.current_view`, whose `top` group holds only `judgeState` and no page text.

t1080 updated the Lab's copy of this reader (downstream `dc4d09617`, `scripted-model/scripts/evidence.ts`,
`windowPageOf`) but missed this domain copy. The domain copy's own comment says it is "the same reading as the Lab's
scripted model". t1080's own report lists the Lab copy as the only downstream follow-up.

**Fix.** `current-page.ts` now reads `core.page_window` first, the same way `windowPageOf` does:

- It takes the page marked `current` that is not recalled.
- It starts from that page's first whole delivery, skipping any part answer that carries `from`.
- It applies each later `changes` delivery in order.
- The pre-t1080 in-place reading and the `core.current_view` fallback are kept for old requests.

### Cause 2: the stale ending (fixes `refuses a missing declaration`)

**What happened.** With the page fixed, four tests passed. `actual saved repair refuses a missing declaration before
full-test actions` hit its 120 s limit instead. Instrumenting it showed:

- The Flow is correctly refused with `llm_evidence_loop.full_run_required`. No reset and no action runs.
- The scripted model then answers `complete` again on every decision.
- Loop detection steers it each time (`core.loop_check`: `near_repeat`, then "your next decision is a call to
  core.loop_decision"). Rounds end on the ladder's last rung, and new rounds start (`core.resumed`).
- Nothing ends the task. `core.budget` showed `decisionsLeft 3987`, `costLeftUsd 0.246`, `secondsLeft 539`.

That is the current contract, not a defect:

- Core **t1056** (Core merge `a4058bba5`, 2026-11-26, "No count of calls or rounds ends a run") carried out the user's
  rule of 2026-11-24: "THERE SHOULDNT BE ANY ARBITRARY FUCKING CALL LIMIT THAT RANDOMLY JUST RESETS EVERYTHING".
- It sits beside the rule "a task ends only with its final result or its budget gone" (2026-11-03).
- Core `docs/architecture/automation-studio/failure-control.md`, "No count ends a loop" and "Refusal runs go through
  loop detection too", says only the result, the purse (or the budget's tokens or clock), a person's Stop, or a
  signalling caller ends a round.
- Even `core.loop_decision`'s `finish_with_best` is checked, and if refused the loop goes on.
- The test was written when a count of refused decisions ended the repair.

The real blocker was the fixture's billing. Its fake provider billed every call as a flat 21 tokens ($0.0000063), so the
Flow's default $0.25 purse would take thousands of decisions to run out. A probe with a $0.02 purse took 2,000 decisions
and 34 s.

**Fix (fixture only, in `carried-service-repair.test.ts`).**

- A new helper, `billedAsSent`, bills each fake reply for the size of the request sent: about 4 characters per token
  for input, and 7 output tokens.
- It applies to both the judge and the decision replies in that file. The shared `deepseek-decision-reply.ts` is
  untouched.
- The refused repair now ends on the Flow's own $0.25 purse, as a live run would, in about 2.9 s.
- One assertion was added and none were weakened. The test now also requires
  `flow_bootstrap.evidence_budget_exhausted` in the run's metadata. This pins that it ends on its purse and never on
  a count.
- The other five tests in the file are unaffected. All pass with the new billing.

### Suspects ruled out

t1068/t1069 (amendment atomicity), t1078, t1085 and t1083 are all in this Core tree (fluxiq 0.54.36, with t1085 and
t1083 merged). The repair behaviour the tests check passes on it:

- the replacement is admitted;
- the old step is dropped;
- the fresh whole test runs in order and is judged.

None of them is a cause.
