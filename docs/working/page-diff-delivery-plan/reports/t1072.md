## What changed and why

**1. Kept rows carry the values processing used (root cause).** Before this, the judge saw the kept rows in the asked columns only (`recordSets.sampleRows`), plus the processing's counts. The rows keep every column upstream, but the sort key `posted` was in no row the judge was shown.
- `framework/automation-service/service/answer-first/result-feed/kept-key-rows.ts` (new): `automationStudioAnswerFirstKeptKeyRows(retainedRows, process, askedColumns, now)`.
  - Fields come in this order: the asked columns, then the fields of `where`, `anyOf` and `compare`, then the dedupe `by` fields, then the sort fields.
  - A derived column comes after its source, computed with the contract's own `automationStudioRecordDerivedValues`.
  - A row with no value in a field shows `null`.
  - It returns `undefined` when every such field is already an asked column, so nothing is duplicated.
  - Nothing is cut.
- `result-feed/feed.ts`: both the automatic stage path and the legacy `processed()` path build `keptRows` from the processor's `retainedRows` (whole rows, in answer order). `automationStudioAnswerFirstProcessingEvidence` puts them on `evidence().processing`. The header comment says so.
- `runtime/result-verification/result-evidence/types.ts`: optional `keptRows` on `AutomationStudioResultEvidenceProcessing`, with its doc.
- `result-feed/read-evidence.ts`: a stored bundle may carry `keptRows`. It must be one JSON object per kept row, otherwise the bundle is refused.
- `runtime/result-verification/flow-less/window-fitting.ts`: `resultEvidence.processing.keptRows` can be summarised when a request does not fit the judging model's window. It goes after the acts and before the final rows, so it is never silently dropped.
- Screening needs no new code. The whole bundle already goes through `automationStudioResultEvidenceScreen` value by value, keys included.
- The barrel `result-feed/index.ts` exports the new module.

**2. A no that names no contradiction is unknown.**
- `runtime/result-verification/flow-less/named-contradiction.ts` (new): `automationStudioFlowLessNoNamesContradiction(diagnosis)`. A no names a contradiction when either:
  - it says something in `observed`; or
  - it lists a defect that names what is wrong by itself:
    - `kept_not_asked`, `asked_missing`, `act_missing` or `act_wrong` with a row; or
    - a `wrong_value` whose row, column and value the same reply does not also list in `checked` as right.
- A defect of kind `other` names what it is only when `observed` is there to explain it.
- `flow-less/judge.ts` (`reading()`): when the reply's `answersRequest` is `no` and it names nothing, the result is `{ verdict: "unsure", reason: NAMED_NOTHING [+ " What it said: " + the judge's screened words], checkedWhat }` with no `found`. A no that Core made by refusing a yes is unaffected, because the reply's own answer there was yes.
- Calibration against every recorded judge no I could find: 124 nos in `lab-runs/2026-11-15` to `2026-11-26`.
  - Only two name nothing under this rule: run-mwyfoz8o's 0101, and run-mwveg5ls-0266dfe0's 0149. The 0149 summary says the answer "was not confirmed", which is an unknown in all but name.
  - Every no with `observed` stays a no (116 of 124).
- `flow-less/question.ts`, both in generic words:
  - A new sentence on `resultEvidence.processing.keptRows`: check the order and each condition on these values.
  - The answer rule now asks a no to say what is wrong in `observed` and name it in `defects`. It also states that "A no that says nothing in observed and whose defects are only of kind other, or only values it also gives in checked as right, names no contradiction and is read as unknown."
  - `flow-less/tests/__snapshots__/judged-summary.json` was updated. Its only diff was the `question` line, which I checked before running `-u`.

## Open questions or contradictions found

- **F4's evidence claim is partly wrong.** F4 says "only page 1's raw rows carry [posted]; pages 2 and 3 are labels only". In 0101's request, `resultEvidence.pages` holds all three pages whole, every row with `posted`. Only `readPages.keptRows` is labels. So the judge could in principle have matched the kept rows to page rows by link. It did not, because the kept rows were not shown with their keys. The fix stands either way, but the debug note should be corrected.
- **Lost upstream.** The answer-first processing evidence drops the processor's own `hiddenSortKeys` (with `inOrder`), which the Flow judge's account keeps. `keptRows` gives the judge the raw values instead. A lead may want `inOrder` carried too, as Core's own reading of the order. I did not add it, because the brief asked for row values.
- **Wording of the rule.** The question still lists `other` for "an act that was done wrongly". Under the new rule, such a no stands only when it also says what it saw in `observed`. That holds for every recorded case: all 13 nos with only `other` defects had `observed`.
