## Causes, confirmed on the recordings
1. **`anyOf` meant the opposite of what every model wrote.**
   - What the evaluator did: each `anyOf` group was its own filter. A group held when any one of its conditions held, and
     every group had to hold.
   - What the models wrote: all 31 recorded `anyOf` declarations are alternatives, one group per way a row qualifies.
     They come from runs run-mwyn25dg (17), run-mwyg0x66 (13) and run-mwyfoz8o (1). For example, a pound price in one
     group and the site's pound estimate of a foreign price in another, each with a "why" that says "or".
   - **Which rule drops every row in 0049/0053/0055:** the `anyOf`
     `[[price matches ^£(\d{1,2}|1[0-4]\d)\.\d\d$], [text_4 matches ^approx\. £...]]`. Read as "both groups hold", no row
     qualifies, because a listing priced in pounds shows no estimate. Each `where` condition keeps rows.
   - 0014's "missing evidence" is the same misreading. On a foreign row its second group (no estimate and the pound price
     under 150) could not read the price, while the first group (the estimate under 150) decided the row.
   - The tool description said only `anyOf [[conditions]]`.
2. **Held processing was not rebound through a rename.** Binding resolved only exact ids and unique labels
   (`process/binding/bind.ts`). The output read's `fields` (`title: "link_text"`, ...) were never consulted.
3. **Asked columns and generic keys.**
   - The model knew the mapping. 0014's "why" says "link_text (title), text_5 (bids), text_9 (postage)".
   - But processing cannot rename, and the answer's columns were the keys, so completion refused `not_asked_table` (0087).
     The model then re-read the list under the asked names and declared everything again (0089-0106).
   - Same pattern in run-mwyfx9fs (13 calls).
4. **Bigbox (lead's addition).** The first read was a record batch from the saved Flow's run (0044). Its page's spot is
   `[step, batchKey]`. A model's re-run of the same step on the same page has a spot `[step, list, address, moves]` and no
   place, so it never matched. It went in as a second page beside the stale one (0051, 0068; judge 0059).
   - The read by hand made into a second step (0076-0078) read the same list at the same address. Both steps' pages
     stayed in the answer (judge 0080).
   - **Not exact duplicates:** the run's rows hold absolute links and the hand read's hold relative ones. I checked this
     in the copied `project.sqlite`, tables `run_dataset_rows` and `run_dataset_batches`.
   - Whole-row repeats already collapse with no declaration: the feed's `wholeOnce` on the legacy path, and the evaluator's
     default whole-row identity. `process-defaults.ts:30-33` only adds a `dedupe.by` key from a row identity. Exact
     repeats do not depend on it. I did not change it.

## What changed and why
Core contracts (`packages/contracts/src/record-sets/`):
- **`process/any-of.ts`, `readiness/filters.ts`, `process-rows.ts`:** `anyOf` is one filter whose groups are
  alternatives. A row passes when every condition of any one group holds.
  - **Evidence rule:** a group holds when each condition does, and is settled false by one condition known false. A row
    is kept when some group holds, left out when every group is known false, and withheld only when no group decides
    it. A withheld row's missing evidence names only the undecided groups' values.
  - The account has one `any_of` filter. Its words are `any of (a and b; c)`.
  - Updated to match: `types.ts` and the `parse-processing.ts` comments.
- **Why flip the meaning rather than document the old one:** 31 of 31 real declarations were written this way. Under the
  old reading each one was either empty or withheld. The other form, "any condition of each group", stays expressible:
  a list in one condition covers one column, and two groups cover several. Parsing is unchanged.
- **`process/binding/bind.ts`, `stamp.ts`:** optional `aliases` (written name to stored id). An alias is tried after
  the exact id and a unique label, and only onto a stored field. Its bindings go into the declaration stamp.
- **New `asked-columns/` (`map.ts`, `types.ts`, `words.ts`, barrel):** `automationStudioRecordAskedColumns` places each
  asked column on a stored field. It tries three kinds of evidence in order, and places each field once:
  1. by name: the id or label, ignoring case, separators and plural;
  2. by values: the column's own name appears as words in at least half the shown values, more than in any other field.
     Fields with identical values count as one. A tie places nothing;
  3. by the declaration's own `columns` order: used only when its length matches and every placement from steps 1 and 2
     agrees with it.
  - Nothing is guessed. A column nothing places is reported as unplaced.
  - **Design choice:** the request's own words and the rows' values are the only words compared, so nothing mirrors a
    site or task.
  - **Why the page view's lines are not read:** a label the page draws next to a value is already in that value.

Core fluxiq (`answer-first/`):
- **`result-feed/column-names.ts` (new):** the aliases. A renamed read's old key maps to its new column, from the
  output steps' `reads.fields`. An asked name maps to its placed field. It also writes the sentence shown to the model,
  in ids and the request's names only, never a cell value.
- **`result-feed/asked-view.ts` (new):** the answer shows each placed field under the request's name, in the schema, the
  rows and the columns alike.
  - The stored rows that processing reads do not change, so this is a view (AGENTS.md, 2026-11-20).
  - A name that is not a valid id is written with `_`. A name that collides with another field's id or label is left
    as it was.
- **`result-feed/stage.ts`:**
  - `evaluate` takes `renamed` and binds with the aliases. Once the declaration is bound, its own `columns` place the
    rest by order.
  - It returns the answer view, plus the stored rows for the kept-key rows.
  - The `processing_binding_missing` and `processing_empty` messages end with the placement sentence.
  - `amend` takes the same naming, so a model declaring over the request's names, or over old keys, binds.
  - New `naming()`.
- **`result-feed/feed.ts`:** passes `renamedOf(group)` and the naming to the stage. Kept-key rows are built from the
  stored rows and shown under the answer's names. New `columnNames()`.
- **`result-processing/bound.ts`, `amend.ts`:** pass the aliases. When processing is ready, the tool answer carries
  `columns:` with the placement sentence.
- **Lead's addition:**
  - `result-feed/place-of.ts`: a model's read or a pass on the page of a list a saved Flow's run read takes that batch's
    spot. That holds only when exactly one batch of the step read there and the list has not moved since. So it replaces
    the batch's page. Two batches on one page are an in-place paging loop, and keep separate pages.
  - `result/page-set.ts`: a page of a list (`listKey`) at an address (`where`, query included) removes that list's
    page at that address from every other step of the ledger. Where the pager named a place on both pages, the places
    must agree.
  - `result/` is outside the brief's named paths. It is where the ledger places pages, and `page-set.ts` is the one
    function every page goes through, the hand read's `take` included.
- **Model-facing text**, one phrase each:
  - `runtime/llm/node-tools/result/tool.ts` and `runtime/conversations/instructions/prompt.ts` now say `anyOf [[conditions],
    ...] (a row passes when every condition of any one group holds)`;
  - `bootstrap/plan/record-output-contract.ts` (the help) says the same, in 4 fewer bytes than before, so the vocabulary
    byte bound is unchanged.
