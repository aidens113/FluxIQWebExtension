# t1043 report: a press is never credited with what the page changes by itself; Core never projects its own placeholder

## Outcome

Done. I fixed both causes found by t1041's Opus retry.

- **Domain.** A press is now credited only with what it changed. A change on an element that the page changes by itself is left out of the draft statement that Core reads acts from. It is also set aside when the domain decides whether the press changed the page at all (`pageChanged`, the no-effect retry). The model is still shown it, marked `(changes by itself)`.
- **Core.** Core's own before-side note (`notHeld`, `takenAfter`) is now recognised as Core's. The judge is told it in Core's words. Only a reading beside it, which is page state, goes to the host's projector. The summary path and the semantic checkpoint path both use the same function, so both are fixed.

Provider-free tests prove each cause and the run-level effect, and they fail without the fix. I ran the scripted bigbox run three times (`--attempts 4`, headed, Lab slot 4, `t1043-lab`, run watcher on). All three passed 4 of 4 with 0 alerts. The carousel race did not fire in any of the three runs, so the Lab runs show only that nothing regressed. The forced race is proved by the unit tests.

## What changed and why

### Domain (`domain/src/runtime/llm-evidence/node-run/press-effect/`)

- `self-change/markers.ts` (new) reads the page's own markup.
  - **Changes by itself:** an element whose `aria-roledescription` says carousel, slide or slideshow, whose role is `marquee` or `timer`, or that is a `<marquee>`.
  - **Live region:** `aria-live` polite or assertive, or role `status`, `alert` or `log`.
  - A live region does not count by its markup alone. Pages announce a press's own result into one ("Added to cart", a cart total), so it counts only once the run has seen a line in it change with nothing done.
- `self-change/memory.ts` (new) is a per-Flow memory of page-view lines, by stable handle, whose words changed between two captures with nothing between them.
  - It follows the same comparison rule as t496's `plan-resolution/self-changing/names.ts`: no `acting` since the first capture, the same location and `navigation.timeOrigin`, and both captures of the whole page.
  - A line counts only after two such pairs. A change caused by an act that lands after the following look is seen once per act. Content that changes by itself keeps changing.
  - What it has seen is kept on the capture (`webPressSeenChanging`), so a press reads it from its own two looks.
- `self-change/watch.ts` (new) wraps the run's target packets, so every `remember`, `rememberLook` and `acting` also feeds the memory. These are exactly the feed points of t496's memory.
- `self-change/own-changes.ts` (new) lists the elements whose changes are the page's own. It covers everything inside a marked region, plus lines seen changing by themselves. It makes exceptions where the press reached the element:
  - the pressed control is inside the region;
  - the pressed control's `aria-controls` names the region (a carousel's next arrow);
  - the pressed control is the seen line itself, or around or inside it.
- `self-change/index.ts` (new) is the barrel.
- `change/walk.ts` takes an optional `press: { handle }` and marks such changes `byPage`. With no `press`, it behaves as before; the replay path passes none.
- `change/statement.ts` leaves `byPage` lines out of `draft.changed`, which removes cause 1 at `statement.ts:58`.
- `page-changes.ts` still says `byPage` lines, suffixed `(changes by itself)` and listed after the press's own entries.
- `unchanged-page.ts` takes an optional `own` set and leaves those elements and lines out on both sides.
- `no-effect.ts` passes `webPageOwnChanges(before, after, handle)`. A press that changed nothing while a slide turned now reads as no effect and gets its normal retry.
- `index.ts`, `change/index.ts`: exports.
- `tests/self-changing-page.test.ts` (new) has four tests through the real runtime with the race forced:
  1. A press made while the carousel turns states only `went` for the banner. The slide's lines appear as `(changes by itself)` after it.
  2. A press that changed nothing while the carousel turned is `no_effect`.
  3. A press on the carousel's own control is credited with `reads` (a guard).
  4. With no markup, a ticker seen moving twice with nothing done is left out of the second press's statement and marked in its list.

## Not verified

- **The race was not caught live.** The carousel did not turn inside the `Accept all` press in any of the three runs. The fix on the real bigbox page rests on two things:
  - the forced-race unit tests, which use the same markup shape (`<section aria-roledescription="carousel">` holding the slide's `h1` and `p`);
  - the capture listing every rendered element with all its attributes and parent indices (`apps/extension/src/content/rendered-elements.ts`). I read that code; I did not inspect a raw bigbox packet.
- **What the full suites would catch.** I did not run `pnpm check`, `pnpm test`, `pnpm build` or Core's whole vitest run (the twice-daily sweep rule). Other Core groups and downstream packages that read `webPageUnchanged`, `webNodePageChanges` or Core's judge evidence were covered only by the narrow sets above.
- **Recovery-harness presses** (`harness-options/execute.ts`) do not call `acting`. A recovery press between two captures could therefore look like a quiet change to the run-seen memory. t496's memory has the same gap. It needs two such pairs on one line before it matters.
- **No live (paid) run.**
