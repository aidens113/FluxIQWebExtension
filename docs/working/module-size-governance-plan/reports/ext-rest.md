### Import repair to barrels, not to `../subject`

The shared context offered two repairs: "one extra `../` to reach the
subject, **or** import from the directory barrel." The plain `../` repair is
not viable here. Moving a test from `src/` into `src/tests/` converts a
same-directory import (which the audit's `imports` rule explicitly allows,
`targetDir === importerDir`) into a cross-directory import that reaches past
a barrel — which the rule fails. Taking the `../` option produced **7 new
`imports` failures** in my files.

I therefore routed the moved tests through the owning directory's barrel.
Every barrel involved re-exports the subject with `export *`, so no symbol
had to be added anywhere:

| Test | Now imports |
| --- | --- |
| `packages/boundary-audit/src/tests/audit.test.ts` | `../index.js` |
| `packages/real-site-policy/src/tests/policy.test.ts` | `../index.js` |
| `packages/test-matrix/src/tests/selector.test.ts` | `../index.js` |
| `domain/src/runtime/tests/*.test.ts` (3 files) | `../index.ts` |
| `domain/src/tests/domain.test.ts` | `..`, `../client`, `../output-nodes`, `../runtime` |

That took the 7 new failures down to 1. `apps/scenario-lab` was never
flagged because `apps/scenario-lab/src` has no barrel, and the rule only
fires when the target directory has one.

**The depth hazard did not bite, and here is why.** Four of these packages
run `pnpm build && node --test dist/**/*.test.js`. On this machine pnpm
hands the script to `cmd.exe`, which performs no globbing at all, so the
literal `dist/**/*.test.js` reaches Node — and Node 22's `--test` expands it
itself with real globstar semantics. Recursion therefore works, and the
deepest moved file,
`apps/scenario-lab/dist/scenarios/instruction-only-form/tests/scenario.test.js`
(four levels down), is still collected. I confirmed collection by listing
`dist/**/*.test.js` after the build and by matching the test-name sets, not
by trusting the totals. **No `package.json` glob needed correcting for this
reason**, but the globs remain fragile on a POSIX `sh`, where `**` collapses
to `*` and Node never sees the pattern. See *Open questions*.

## Open questions or contradictions found

1. **The brief's verification command does not catch the regression the
   brief's own repair instruction creates.** The brief says to verify with
   `--rule test-placement`, and that rule is clean. But the relocation
   necessarily converts same-directory test imports into barrel-skipping
   ones, which the `imports` rule fails. Verifying only `test-placement`
   would have hidden 7 new failures in my files. I found them only by
   accidentally triggering a full audit run. **The supervisor should check
   `--rule imports` for the `test-runner` worker too** — that package
   currently shows 51 such failures, which a baseline regeneration would
   silently freeze into the ratchet. The `Current State` records 29
   barrel-skipping imports as the frozen figure that "may only shrink";
   regenerating now would raise it to roughly 80.

2. **One failure remains that I could not clear without editing a subject
   module.** `domain/src/tests/domain.test.ts` imports
   `mapWebRecordingObservation` from `../web-panel-host`, and
   `domain/src/index.ts` does not re-export `./web-panel-host` — it is the
   one module in `domain/src` missing from the root barrel. Clearing this
   would mean adding `export * from "./web-panel-host";` to the barrel,
   which changes the package's public surface to accommodate a test; the
   shared context says never to do that. Whether `web-panel-host` *should*
   be in the barrel is a real design question, but it is not mine to answer
   inside a mechanical relocation. Left for the supervisor: either baseline
   the single finding or decide the barrel is incomplete.

3. **`domain`'s test entry point is hard-coded and discovers nothing.**
   `domain/scripts/test-domain.mjs` bundles exactly one file. Any domain
   test added anywhere other than inside `domain.test.ts`'s import graph is
   silently never run — which is exactly what happened to the three runtime
   test files, and they appear to predate this task by some margin. Wiring
   them in is out of scope here (it would change behaviour and could surface
   failures unrelated to this move), but it is worth a follow-up: three test
   files' worth of coverage is currently inert.

4. **I deleted tracked files and restored them.** `domain/.test-build/` is
   tracked per `AGENTS.md`, and I ran `rm -rf domain/.test-build` to get a
   clean count. That removed ~230 tracked `.js` files plus
   `domain.test.external.mjs` — stale artifacts from an older version of
   `test-domain.mjs` that emitted a tree rather than a single `outfile`, so
   re-running does not recreate them. I restored the whole directory with
   `git checkout -- domain/.test-build/` and re-ran the test; the directory
   now shows only the expected `M domain/.test-build/domain.test.mjs`. Worth
   noting that a large tracked build artifact is committed which the current
   build no longer produces, and it will stay stale until someone prunes it.

5. **Two transient failures during validation, both environmental, neither
   reproducible.** `test-contracts` once exited 139 (segfault, no output)
   and once reported 21 tests with 1 failure instead of 26/0; `domain` once
   failed with `ERR_MODULE_NOT_FOUND` for
   `F:\!FluxIQ\packages\fluxiq\dist\index.js`, and a directory listing at
   that moment showed the file absent while a listing seconds later showed
   it present. Both point at a concurrent rebuild of FluxIQ Core and of
   `test-contracts/dist` — the other worker's `test-runner` package depends
   on `test-contracts`. Clean re-runs gave 26/26 and a passing domain smoke
   test, and the counts in the table above are from the final consolidated
   pass. Flagging it because parallel worker dispatch across packages that
   share a build graph can produce failures that look like real regressions.
