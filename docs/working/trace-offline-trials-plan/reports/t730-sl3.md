# t730-sl3: retire six synthetic browser specs

## Outcome

Done. All six specs are deleted. Each one opened a synthetic fixture page in Playwright. Six browser-free `lab-server.test.ts` files (27 tests) now cover every server-side or pure-logic check those specs made that no unit test already covered. All 27 pass.

## What changed and why

- Deleted `apps/scenario-lab/e2e/{member-directory,modal-flows,order-operations,product-catalog,storefront-checkout,support-desk}.spec.ts`. Before deleting, I grepped for imports of the specs or their helpers. Nothing imports them: each spec defined its helpers (`locate`, `assertFacts`, `runScript`, `extract`, `readColumn`, `topmostOver`, `coveredBy`) privately. The only references left are historical docs and one `.structure-baseline.json` entry (see Open questions).
- Added `apps/scenario-lab/src/scenarios/<id>/tests/lab-server.test.ts` for each of the six scenarios. They follow the sibling `admin-console/tests/lab-server.test.ts` pattern:
  - start `startScenarioLab`
  - drive `/api/<id>/<operation>` with the run token, arming variants through the manifest's own `variant.arm`
  - read `/__control/final-state`
  - GET the start page or route subpaths to check what the next request serves (the server-side half of a "reload")
  - where a spec checked a toolbar count that the server's mirror of the client filter computes, call the pure `filterMembers`, `filterOrders` or `filterTickets` directly.
- The existing `tests/scenario.test.ts` files already covered almost all pure state logic: mutations, guards, manifest-to-render agreement and the variant renderings. The new tests add the HTTP path (route name, auth, arm, oracle, GET re-render) and the few filter counts or rendered strings that only the browser specs pinned.

## Generic capabilities a realistic spec should prove instead

These were proven only by synthetic browser specs, and they are not specific to those fixtures:

1. **A click on a control covered by an overlay is refused** (support drawer, consent scrim, chat launcher, sticky header, help launcher). The runner and executor must treat "intercepts pointer events" as a blocked target. Suggested home: crossborder-marketplace `interruption.test.ts` (it already has an interruption popup), or the everything-store or bigbox-retail consent and cookie banners if they have one.
2. **Dismissing a modal dialog or interstitial unblocks the page** (`inert` shell, focus trap, Escape restores focus). Suggested home: crossborder-marketplace interruption path, or auction-marketplace or photo-social login and modal flows.
3. **A native `confirm()` dialog is answered** (accept or dismiss). Suggested home: a realistic "remove" or "delete" action that confirms natively, for example local-classifieds deleting a listing or everything-store removing a cart line. Check whether any realistic site uses `confirm()`. If none does, the capability has no realistic proof.
4. **A target and a form inside a cross-origin or same-origin iframe** (card frame, `frame:<title>/testid:` targets, postMessage to the top document). No realistic scenario that I know of embeds a payment frame. Suggested home: bigbox-retail or everything-store checkout, if a frame is added to the realistic fixture. Otherwise this is an uncovered generic capability.
5. **Pagination extraction over next, link and numbered controls, null for absent fields, lazy `data-src` images.** Suggested home: crossborder-marketplace or job-board `breadth-paths` read-list paths. The realistic browser harnesses already page through results.
6. **A page with more than 2,000 snapshot candidates** (the content-script cap in `apps/extension/src/content/dom-snapshot.ts`). Suggested home: a realistic long listing such as social-network-feed or everything-store search results at full scale.
7. **Hashed or generated class drift with identical structure** (`restyled`, element identity that does not lean on classes). Suggested home: a realistic site under the identifier policies (`set-identifiers` arm), for example company-website or professional-network.
8. **`/api` run-token auth.** It is server-generic and was not in `src/tests/server.test.ts`, which tests only `/__control`. I added it in member-directory LS. Suggested proper home: `apps/scenario-lab/src/tests/server.test.ts` "health and control endpoints require the run token" (not owned by this brief).
