All three shapes are fixed generically, each with tests that failed first:

- **Slot 2 (stale in-place read).** A list read in place after a landed undo is one recorded fact
  (`reset-settlement/observations.ts`), read by `judge.ts` (`evaluate`, `lookFirst`; the private
  `reloaded` copy is gone) and `site-reset/undo-reach.ts`. Such a read is never used to judge reach,
  so it can no longer make an act `no_admissible_undo`. A subject removed by a spent act's landed undo
  is assigned to that act. Refusal consistency: `reset-answers/agreeing.ts` moves any act that a
  refusal's own `canMeet` leaves meetable out of `actsUnsettleable`, so one answer can never say both.
- **Slot 2, shared list (w10).** An act whose own undo landed settles `restored` (never `unchanged`) on a
  load read that is back for its own subjects while other rows still differ, when each differing row is
  another open act's own subject on the same list (`reset-settlement/group-witness.ts`, `act-groups.ts`,
  `judge.ts`). So after two of three undos only the third act stays to undo and is reported left. A row no
  act added, an original row gone or changed, or an unexplained reorder still keeps every act open.
  w11 found that a destination-removal undo's proved row (`subjectUndo.subject`) was ignored. It is now
  counted as the act's own row on that undo's group (`reset-settlement/group-subjects.ts`).
- **Slot 4 (per-pass place).** `site-reset/trial-stamp.ts` (moved out of `ledger.ts`, `stamped`)
  files a pass on another item under the pass's own place and never overwrites `act.spot.place`.
  `reset-settlement/own-control.ts` is the one "is its own control back" check, read by
  `undo-admission.ts` (`already_back`) and `control-tracker.ts`/`judge.ts`. If admission says back
  while the witness stays open, the act closes `gate_unsatisfiable` with `failed: already_back`
  (`own_back`), instead of livelocking. w9 found that keeping the pass's own place broke the existing
  `photo-dialog-act` spec. On dev it had passed by accident: a wrong original was filed under the
  receipt's place. Now `control-witnesses.ts` `passed()` files the pass's own pre-press counts as that
  place's original (only where nothing is filed and the place is readable) before `locate` touches it, so
  the twin step is stamped by the state the build found.
- **Slot 1 (choice confirmed by a reloading press).** The domain reports shown values by place: start
  reads carry `values`, and a step diff that stayed on its page (a same-address reload now counts)
  carries `values.replaced`. Core records a value witness for a `modify_existing` act with no other
  witness and settles it when a fresh read shows the start value. It admits the act's own control
  declaring `modify_existing` as `own`, and a no-class press on the act's page as a `step` that counts
  no attempt. After 2 landed undos that never bring the value back, it closes `gate_unsatisfiable`
  with `value_not_back`. Subject deletion no longer applies to an act that created nothing.
  Settle words follow the witness kind. An unrelated list never settles an act
  (`site-reset/undo-claims.ts`: a named list attaches only if it was read on the act's own
  page/resource or the act already named it).
- **Lead addition (leftovers match settlement).** `site-reset/leftover.ts` is the one decision:
  settled restored/unchanged -> not left; open or irreversible -> left; closed unsatisfiable ->
  possibly left with its `failed` reason (kept/possible -> possibly). The ledger accessors,
  `standing()`, `trialRan()`'s return and each project-ledger snapshot act (`left`, `failed`) all read
  it.

## Open questions for the lead

1. **Two defects outside t772 block the slot-2 shape end to end** (w11; the spec is marked `test.fail`):
   - Extension `record.ts` `nearestTitle`/`readRowTitle` takes a save control's subject from the first
     link beside it ("Apply on company site"), not the item's heading. `sanitize.ts` `pageSubject` reads
     only an h1. So every save on that page declares one shared subject, and no act owns its row until
     its undo lands.
   - Domain `press-effect/settled.ts` / `certain-no-effect.ts` (t513 press-again) pressed an undo under
     `undoes` a second time, because the list redraws only on load and the notice already showed. That
     re-did the act on the site. The fix (never re-press a lasting call under `undoes`, or never count an
     already-showing notice as "no change") changes a policy the social Post button's second press relies
     on. That needs your decision.
2. Per-act group settlement (w10) covers only acts whose own undo landed. An act never undone, on a list
   whose other rows still differ, stays open until a whole-list match. Settling it `unchanged` per act
   would need proof of a load after the act.
3. If a load read still shows the row a spent act's undo removed (as in 1, second bullet), that act stays
   open and its undo is refused `undo_already_done`. It is reported as left, which is true, but no call
   can clear it.
4. In one of w9's three headed `photo-dialog-act` runs, an undo press landed (`ok`, click validated) but the
   post stayed liked; the second press worked. It may be the same press-again behaviour. Not investigated.
5. The trial door's `trial_step_unwitnessed` refuses before `beforeTrial`, so it hides acts still to undo
   (w9). Joining them needs `service/**`; t775 may retire that path.
6. `undo-reach.unruled` does not count a value act's own control as a path for other acts' list reasons
   (w4b, open question 4).
