## 2. Is gateway tracing on?
No. SR never sets it. Trace capture is a Core process switch: env `FLUXIQ_CLIENT_GATEWAY_TRACE` = `1|true|on` (CS gateway-trace/environment.ts:7, from-environment.ts:20-27), read once when the runtime is built (CS programs/_shared/runtime.ts:79-80, `createAutomationStudioGatewayTraceHost({enabled: automationStudioClientGatewayTraceEnabled(process.env)})`). Unset = OFF (no capture source, no work). The Lab sets it to 1 for every Core it starts (packages/test-runner/src/environment.ts:72-73,140-142), which is why Lab runs trace and SR specs do not. With a project pool the store is the project's database, else in memory (wiring/host.ts:52-56).
To turn on in a spec: `process.env.FLUXIQ_CLIENT_GATEWAY_TRACE = "1"` BEFORE `startInstalledBuild` (so before `FluxIQ.create`, installed-build.ts:43-47); restore in `finally`. Each trial opens its own traced episode (CS service/candidate-trial/port.ts:23-28; wiring/trial.ts:37-38), so a live trial 1 leaves a trace in the project store once tracing is on.
Unverified: `pair()` stores `captureSnapshots:false` etc. (installed-build.ts, settings in `pair`); whether the extension must capture page snapshots for tier-2 offline reads needs a check of `apps/extension/src/background/trace-capture/` before relying on it.

## 3. Sequence and scenarios
Existing seam (before P6): a trial port has ONE `environmentKind`, fixed by `ports.environment` (CS service/candidate-trial/port.ts:65-66; project-build/subflow-trials.ts:113-114). `environmentKind` set and not `live` => no start hook, no site reset, yes is evidence only and never kept as the verdict (subflow-candidate/subflow-trial-gate.ts:221-225,498-506,553-556; result code `subflow.trial_offline_yes`, `ok:false`, `retestsLeft`, :559-573). Choosing offline per trial in test/repair phases is P6 (docs/working/trace-offline-trials-plan/reports/lane-t.md:284). The spec below assumes P6 provides the choice; the scripted builder only issues the same calls.
Scripted builder sequence (single-subflow plan, one build brief):
1. `core.submit_subflow` rev 1 (a Flow that really fails, repair-first.spec.ts:93 pattern) then `core.test_subflow` rev 1: LIVE (no trace yet; trace recorded). Expect `trialCode` = `no`, `trialRunId` set.
2. `core.submit_subflow` rev 2 (changed step) then `core.test_subflow` rev 2: expected OFFLINE against trial 1's trace (P6 rule). Expect `subflow.trial_offline_yes` (`ok:false`, no site reset), or an offline `no`.
3. `core.test_subflow` rev 2 again: LIVE (an offline yes asks for a live retest, `retestsLeft`, subflow-trial-gate.ts:559-570), preceded by a `NNNN-reset` step; `verify` answers yes.
4. Final judged whole run = that live test of the single-subflow plan (office-buy-now.spec.ts:176-178, photo-toggle.spec.ts:227). Then `turn.complete`, supervisor completes. A multi-subflow plan would add `project.assemble` and a supervisor `core.test_candidate` (CS supervisor/whole-trial.ts) for no extra value.
Best scenarios:
- job-board: `repair-first.spec.ts` and `job-unexplored-step.spec.ts` already script a failing Flow (HELD title link absent from TARGET page) then a repair; revision 2 clicks a link TARGET's page has. Read-only, `permittedActs: []`, 12 specs of support. First choice.
- photo-social: 9 specs (photo-toggle, photo-dialog-*, photo-page-order-limit), `bindDetectingRuntime` in photo-build.ts; a read-only task (page order/limit) gives a deterministic wrong-then-right revision.
Correction to the brief: the "office" specs use scenarios/everything-store (`openStoreDetail`), not company-website; no SR spec uses company-website. everything-store is a third fit but its specs mostly make lasting acts (cart), complicating the offline/reset story.

## 4. Command and prerequisites
- From `apps/extension`: `pnpm test:e2e e2e/site-reset/tests/<name>.spec.ts --workers=1` (package.json:12; extra args go to Playwright, `-c e2e/playwright.config.ts`). `--headed` is accepted but redundant. A direct Playwright run needs `NODE_OPTIONS=--no-experimental-strip-types` (playwright.config.ts:3-15; the script passes it).
- `pnpm test:e2e` itself runs `scripts/check/core-build.mjs` (fails if Core's dist is older than Core source; rebuild is `pnpm --filter ... build` in the sibling Core tree, `CORE_REBUILD_COMMAND`, scripts/check/core-build/freshness.mjs:28; or `pnpm build` at the Core root `fxwork/t769/!FluxIQ`), then the cached extension build (`build-extension.mjs`). Scenario Lab: `ui:e2e` builds it first (`pnpm --filter @fluxiq-web-extension/scenario-lab build`, root package.json); do the same if its dist is stale. So: build Core in `fxwork/t769/!FluxIQ` (needed after any Core edit, which P6 will make), then run the command; the extension build is automatic.
- Timeouts: default 30s, but each spec sets `test.setTimeout` 180-600s (job/office 300-420s); extension session budget 90s (extension-context.ts:44).
- Duration: recorded single-spec passes of `57.0s` and `2.8m` (reports/t748-u8-photo-dialog-step.md:81,94). Expect 1-3 min plus builds (Core build several minutes cold, seconds when cached).

## 5. Step log: where and how to assert
- Enabled by env `FLUXIQ_LLM_STEP_LOG_DIR` = ABSOLUTE directory (CS runtime/llm/step-log/directory.ts:3-14; unset or relative = off). Wrappers read `process.env` when built (tool-step.ts, default `env = process.env`), so set it before `projectBuild(...).run()`; safest before `startInstalledBuild`. Use `testInfo.outputPath("steps")` (absolute). SR sets it nowhere today; the Lab sets it from `paths.stepLogDirectory` (test-runner environment.ts:166) and files it under `~/FluxStuff/lab-runs/<date>/<runId>/steps/` for `--live-llm` runs only (docs/architecture/testing-facility.md:3757-3790).
- Layout (step-log/index.ts header; testing-facility.md:3764-3785): `steps/index.md` plus `NNNN-decide|judge|...` (model; scripted ones are logged too, at no cost), `NNNN-tool-<toolId>/` and `NNNN-test-<toolId>/` (call.json, result.json, page.txt, meta.json written last), `NNNN-answer-*`, `NNNN-reset/` (meta.json: kind reset, stage `start_hook|site_check`, trialToolId, outcome).
- Assertion approach (no SR helper exists; model on the Lab readers packages/test-runner/src/lab-runs/count-steps.ts and build-time/read-step-timings.ts): after `build.run()`, `readdir(stepsDir)`, filter `/^\d{4}-tool-core\.test_subflow$/`, parse each `result.json` (the `evidence` shown to the builder) and `meta.json` (result code). Offline = `subflow.trial_offline_yes` and no `NNNN-reset` in the trial's window; live = `subflow.trial_yes|no` preceded by a reset. Expected order: [live test no][offline test][reset][live test yes]. Gap: the step log does not name a trial's environment kind directly; P6 should add a field (for example `environment`) to the test tool's evidence or meta if the spec must assert it without inferring from code and reset folders. Also assert `resolved.status === "draft"` and the activity rows.
- Not in the step log: the trace itself (project store). Asserting "trial 2 read trial 1's trace" needs a Core evidence field from P6 or a trace-store read (not surveyed).
