## 1. What exists today, and what is reusable

- **Before-readings Core already holds.** `reset-settlement/observations.ts` keeps each list group's original
  (the first complete read, with `beforeAct`) and its latest read (subjects, row values, ledger clock, location).
  `reset-settlement/control-tracker.ts` keeps each control place's build-start counts and every page's latest
  control read. `site-reset/create-baselines.ts` issues the `destination-N` refs the model names. A trial step's
  own state diff already carries the act's before and after on its own page
  (`AutomationStudioSiteResetTrialActPlace.collections.before/after`, `controls.before/after`,
  `site-reset/contracts.ts:283`).
- **Where each lasting step's effect shows.** Each reversible plan step carries a witness stamp
  (`reset-admission/witness.ts`: `destination` ref, `own_list`, `control` place, `repeats` an explored act).
- **Core can look by itself.** `reset-settlement/judge.ts` `lookFirst` reloads a witness's location through
  `checks.lookAt` before a trial, at `ledger.ts` `beforeTrial`.
- **What the judge sees now.** `service/candidate-trial/summary.ts` builds the packet from the trial alone: record
  sets, graph, per-step attempts (what each step changed), start page, end view, `startedWith` (acts kept, start
  differences) and `earlierAdvice`. It carries **no before-reading of any list or control and no after-reading of
  a list on another page** (the cart behind a Buy Now).
- **Task semantics.** `project-agents/contracts/task-spec.ts:50` `AutomationStudioProjectTaskPart` has `goalFacts`,
  `lastingActs` and the t757/t764 `answer: { kind: "records"; columns }`; `notAsked` is task-level. Schema in
  `project-agents/supervisor/tools.ts:8-35`, parsed in `supervisor/plan-input.ts:123`, carried to judges by
  `service/project-build/task-checklist.ts`.
- **An idempotent toggle verb already exists downstream.** `domain/src/actions/schemas.ts:339` `web.dom.check`
  sets a checkbox, radio or `aria-pressed/checked/selected` control to a requested state, pressing only when it
  differs. Job-board's save heart and photo-social's like carry **no** such attribute (0 `aria-pressed` files in
  either fixture), so a second mechanism is needed for name-only toggles (section 4).
- **The Lab.** Oracles are absolute (`apps/scenario-lab/.../workflows/*.ts`, `scenario-assertions.ts:18-30`), but
  the Lab already judges them on its **own** playback after `resetScenarioLab` (`packages/test-runner/src/flow-lane/
  creation/lane.ts:454`, the chat path included) and on the zero-call replay after a reset

## 2. Before-state and the judge packet

New focused module **`flow-bootstrap/trial-change/`** (outside t772's directories), pure where possible:

| File | Responsibility |
| --- | --- |
| `contracts.ts` | `AutomationStudioTrialWitness`, `AutomationStudioTrialReading`, `AutomationStudioTrialSiteChange`, `AutomationStudioTrialPartProof` |
| `witnesses.ts` | Resolve a trial's witnesses from its lasting steps' stamps through a read-only ledger port |
| `readings.ts` | Take one before or after reading per witness: reuse the ledger's latest read when fresh at the current clock, else look (`lookAt`) |
| `delta.ts` | Pure: list delta by subject (added, removed, row value changed, unchanged) and control delta (from, to) |
| `proof.ts` | Pure: per part, from its typed effect and the deltas, `shown`, `no_change`, `already_in_end_state`, `carried`, `unproven` |
| `packet.ts` | The JSON the judge sees (bounded rows, screened like `build-test/observation.ts`) |
| `index.ts` | Barrel |

**Witness set of a trial.** Every lasting step of the graph that runs (subflow trial, candidate test, judged whole
run), each stamp resolved: `destination` and `own_list` to a list group and its location; `control` to a place and
its page location; `repeats` to the explored act's witnesses. A lasting step with no stamp keeps today's submission
refusal (`candidate.trial_step_unwitnessed`), reworded: "name where this step's change shows, so its trial can be
judged by the change". The witness no longer has to be an original read before the build's first act: a trial's
before is read at the trial's own start.

**When the readings are taken.**

1. Gate admits (no reset gate for in-place acts any more; section 5).
2. **Before:** for each witness, the ledger's latest read if no lasting call or trial landed since it
   (observations' `groupClock` / control tracker's page clock equal to the ledger clock); otherwise Core looks at its
   location (`lookAt`, the `lookFirst` port). Each reading records `source: "latest_read" | "core_look"`.
3. `prepareStart` navigates to the start page; the trial runs.
4. End view is read (unchanged), then **after:** Core looks at each witness location again. A witness on the page
   the run ended on is read from the end view's read, with no navigation.
5. The trial's per-act results come from the step diffs already recorded, with one addition: a step skipped because
   its control was already in the asked state (section 4) is listed per pass, with its row, as `already_in_state`.

**Packet** (new `siteChange` key on `AutomationStudioRunResultSummary`,
`result-verification/contracts/run-result-summary.ts`; placed before `earlierAdvice` so t752's cached prefix rule
holds):

```text
siteChange: {
  witnesses: [{ id, kind: "list"|"control", where, steps: [n], parts: [partId],
                before: { source, rows|state }, after: { rows|state },
                change: { added: [...], removed: [...], changed: [{ row, from, to }] } | { from, to } | "none" }],
  acts: [{ step, pass?, row?, outcome: "changed"|"already_in_state"|"no_change_seen" }],
  leftFromEarlier: [acts of this build in place at the start, with their did words],
  proofs: [{ part, effect, proof: "shown"|"no_change"|"already_in_end_state"|"carried"|"unproven", carriedFrom? }]
}
```

`startedWith` stays for kept acts; `differs` folds into `before`. Offline trials (P6) carry no `siteChange`: their
acts never happened (`whole-trials.ts` already skips the ledger for them).

## 3. Task semantics, typed in the plan (never parsed from words)

Add to `AutomationStudioProjectTaskPart` (`task-spec.ts`), beside `answer`:

```ts
effect?:
  | { kind: "change"; direction: "adds" | "removes"; count: number | "each_match"; what: string }
  | { kind: "end_state"; state: string };
```

and to `AutomationStudioProjectTaskSpec`: `unchanged?: string[]` (things that must show no change, judged
relative to before; `notAsked` stays for acts not to make).

- **Validation (mechanical, `task-spec.ts` `readPart`):** `change.adds` needs `create_new` or `modify_existing` in
  `lastingActs`; `removes` needs `delete` or `modify_existing`; `end_state` needs `modify_existing` or `create_new`; a
  part with lasting acts and no `effect` is accepted for one release with a warning, then refused (so old records
  still load). This also closes office's contradiction (round 6 cause 2: `lastingActs: ["create_new"]` while the
  goal facts set the address): an `end_state` part must list `modify_existing`.
- **Judged by delta:**
  - `change` is met when its witnesses show the declared change relative to before: N added subjects, or rows whose
    values moved by N units, or N removed. Cart 9 to 10 for "adds 1": met, no reset. Core's mechanical part: a
    `change` part whose every witness shows `change: none` is `no_change` (finding `result.change_not_seen`, a
    grounded no-reason, never a yes). The unit arithmetic on row values is the judge's (Core does not parse page
    quantities).
  - `end_state` is met when after shows the state. If before already showed it, the run is proof only as `carried`:
    the same step (same definition and control, `repeats`) was seen to make that change earlier in this build (an
    explored or trial act with `changeSeen`, `ledger.ts`). Otherwise `already_in_end_state`, which can never be a
    yes (section 5 says what then happens).
  - `unchanged` (and every witnessed row no act of the trial was attributed to) is met when before equals after,
    whatever the absolute state: a pinned post liked before the run and still liked after is no violation. A row
    that changed with no act attributed is `result.unasked_change`. A pass that **skipped** a row as
    `already_in_state` is still shown to the judge with its row, so a Flow that targets a row it must not touch is
    caught even when nothing changed (the photo pinned-post hole).
  - Records answers are judged against what the page showed during the run, which includes the before-state.
- **Agreement (`result-verification/agreement/`):** a yes on a part whose proof is `no_change`, `unproven` or
  `already_in_end_state` is not taken (verdict `unknown`, reason named); t771's refuted-no path gains one reason: a
  no whose only defect is an absolute count on a witness whose delta equals the declared change is refuted with
  Core's delta line.
- **Model guidance:** the PLAN_INPUT schema text and the judge instruction get generic wording, with examples from a
  kind of site none of the ten scenarios is (a library: "place holds on 2 books" adds 2; "set the reading-room
  alert to email" end state; "leave other holds as they are" unchanged). No cart, like, save, address or job words.

## 4. When a reset is still needed

| Situation | What happens |
| --- | --- |
| `change` part, any before-state | Runs. No reset. |
| `end_state` part, before differs from the state | Runs. No reset. |
| `end_state`, before already in the state, the step's change seen earlier in this build | Runs; the step skips or re-sets with no change; proof `carried`. No reset. |
| `end_state`, already in the state, put there by **this build's own act through another path** (the Flow's step was never seen to make it) | **Targeted reset:** before the trial, Core asks for an undo of exactly that act (new code `candidate.trial_starts_in_end_state`, listing only it). |
| Same, but the state existed **before the build began** | Never touched. The run is judged on leaving it as it is; the part says "already so before the build", `already_in_end_state`, and the build may finish only if the person's request is already met (the judge says so). |
| Toggle step written as a plain press | Refused at submission, not reset: `candidate.toggle_not_idempotent` ("a run on a site already in the asked state would flip it back; write the step so it only acts when the state differs"). |
| A targeted undo that no call can make (t743 unsettleable) | Never a deadlock: the trial runs with a disclosure, the part is `unproven`, the build may repair or end honestly. |

**Idempotent toggles (how the build is told, and how it runs).**

1. Controls that state their state (`aria-pressed/checked/selected`, checkbox, radio, option): the step uses
   `web.dom.check` with `checked: true|false`, which already presses only when it differs. The submission refusal
   above names it.
2. Controls that show their state only by name (a heart "Save" / "Unsave"): the domain derives a **toggle signature**
   from the explored press it just ran (the words its accessible name gained and lost, or the attribute it flipped)
   and returns it on the press result. Core stores it on the explored act; a plan step that repeats that act gets
   `ensureState: <signature>` on its node, attached by Core (no model words). The click node skips the press when the
   target already shows the signature, recording `skipped: { reason: "already_in_state" }` (a new executor step
   beside `executor/step-loop/already-done.ts`). Row-specific words in names are handled because only the gained and
   lost words are compared.
3. A press whose explored act showed no signature has no idempotent form: it stays a plain press and falls under the
   targeted-reset row.

**What the person is left with.** No automatic final reset. The ending row says per witness what the build changed
("held 9, now holds 11"), and the chat offers "put it back", which runs the existing reset brief only on request.
`project.completion_reset_first` stops holding completion. (Recommended default; the lead can choose a best-effort,
never-blocking cleanup brief instead.)
