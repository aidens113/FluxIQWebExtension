# FluxNode input-name boundary intake

Outcome: Done (read-only discovery; no implementation).

The minimal shared correction is lexical identifier parity, not permission to interpret every public schema property as a state path. Goal placeholders use /^[A-Za-z_][A-Za-z0-9_]*$/u, preserve case and have no per-name32-character cap (the whole goal has its separate4000-character bound). Ordinary Flow/FluxNode input schemas allow arbitrary own JSON property names: flow/interface.ts only checks object type, and type-schema/parse.ts deliberately defines __proto__ as an own property. Its existing parser test covers that behavior. Dotted, spaced, slash, empty or prototype-looking schema keys must not be silently reclassified as invalid public schemas.

Runtime draft binding-forms.ts and components/automation/processing-inputs.ts independently require lowercase-leading alphanumeric names of at most32 characters and exclude exact item. The draft constant is also consumed by answer-first/result-processing/inputs.ts, answer-first/flow-run/input-bound-steps.ts and bootstrap/authoring/script-binding.ts (whose refusal wording repeats the old limit). No lowercasing/canonicalization is performed; uppercase and underscore inputs currently remain fixed/unready rather than becoming equivalent identifiers. Draft flow-inputs.ts collects by Map using the exact name.

A neutral browser-safe contracts owner can provide one documented identifier rule: proposed packages/contracts/src/fluxnode/flow/input-identifier.ts exporting FLOW_INPUT_IDENTIFIER, reused by goal.ts and the binding/processing owners (retain an alias for the existing draft regex export if its consumers need compatibility). It describes single lexical identifiers only, not all possible input property keys. Keep exact item reserved by the runtime row context, not globally by generic schema/goal grammar. Preserve case, actual own-input membership, supported operand positions, current-value checks and refusal of row/step/raw-state forms. Do not add processing equality lifting.

The existing parameter resolver in components/automation/parameter-bindings.ts reads an OWN exact full key first, then longest dotted own prefixes, and also probes state.state and snapshot namespaces. Each walked segment must be own; inherited constructor/prototype properties do not resolve. Resolved state data is not recursively interpreted as new bindings. Thus direct own names constructor/prototype/__proto__ are not globally reserved by the public contract; prototype concerns belong to safe record construction and own checks. However permitting arbitrary dotted/raw state paths in processing would expand the binding boundary: explicit current input membership must remain mandatory. Supporting every arbitrary schema key unambiguously in general draft input bindings needs a dedicated exact-input representation/namespace, a larger change than this lexical parity fix. No such access widening is proposed here.

Secret inputs are a distinct compatibility decision: type-schema/parse.ts SECRET_INPUT_NAME repeats lowercase/alphanumeric32 plus item refusal, and spec/tests/secret-inputs.test.ts explicitly expects api_key to fail. Reusing the broader identifier there changes an existing public secret-input policy. spec/secret-inputs.ts currently assigns values[name] onto a normal object, so widening to __proto__ without safe own-property construction would lose that entry; follow the schema parser/canonicalizer's defineProperty pattern rather than inventing a blacklist. Do not silently broaden secrets in an unrelated processing fix; if approved, include that exact collector and its masking/collection owners in the same unit.
