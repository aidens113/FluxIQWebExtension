# Browser and managed-host audit

Audited repository commit: `28398c288ffbdffd150133dfb3f9355c17700ba8` (worktree `t913-hosted-platform-audit`, 2026-11-14). The launch-plan Current State is dated 2026-10-30 and is stale for extension hosting: it says there is no hosted extension code, while the current source has managed-browser enrollment.

## Findings

- **Implemented — local/remote gateway transport and managed enrollment.** The extension takes its gateway and Core API addresses from settings; defaults remain loopback (`apps/extension/src/shared/constants.ts:1-2`, `shared/browser.ts:4-13`). The settings UI accepts editable WS/WSS and HTTP/HTTPS addresses (`panel/settings/form-fields.ts:48-68`, `settings/save-plan.ts:21-60`). `GatewaySession` holds a managed-host enrollment ticket in memory (`background/connection/gateway-session.ts:105-118, 157-164`) and persists the resulting token with the gateway URL (`:248-257`). The browser-host package passes the host request's gateway/API URLs and enrollment ticket to the extension (`packages/browser-host/src/connect-host.ts:19-34`, `enrol/enrol-extension.ts:24-43`). This supports a remote gateway when configured by the launching engine; the extension has no first-party hosted server directory or hosted sign-in flow.
- **Implemented — managed Chromium lifecycle and profile persistence.** `packages/browser-host/src/launch-host.ts:14-25, 60-65` launches one isolated Chromium profile per host with the built extension and a configurable headed/headless mode. Named profiles are separate directories per host and persist across runs so the extension token resumes (`profile/named-profile.ts:5-17`); fresh profiles are temporary and removed (`profile/fresh-profile.ts:6-9`, `launch-host.ts:39-45`). The launcher can override the extension path (`launcher.ts:6-15`). This is a local Node/Playwright host seam, not evidence of a deployed managed-browser service.
- **Scaffolded — tenant separation.** A distinct profile directory per host is implemented, and `clean-environment.ts:1-10` strips variables whose names look credential-bearing from the browser process environment. I found no browser-host container, OS-user, filesystem, network, CPU/memory, or tenant sandbox policy in the inspected package. These per-host mechanics do not establish isolation between hosted customers or shared-compute tenants.
- **Partial — human takeover.** The extension has take-over/hand-back controls that pause and resume a runtime session (`apps/extension/src/shared/constants.ts:51-52`; `background/panel/run-control.ts:61-70`), and browser-host can launch headed (`packages/browser-host/src/browser-host-options.ts:3-13`; `launch-host.ts:64-65`). No remote display, authenticated browser viewer, or hosted human-to-browser control channel appears in the inspected host/deployment assets. Hosted human takeover is therefore missing/unverified; the run controls alone do not provide access to a remote browser.
- **Missing — production Linux deployment assets and hosted control plane wiring in this repository.** `rg --files` found no `deploy/` directory or deployment/Compose/Docker assets. `apps/product/package.json:6-11` describes a private product host module inert until a deployment lists it in `FLUXIQ_HOST_MODULE`; `src/host/platform.ts:11-15` only registers product metadata and a workspace-created hook. `packages/website-stand-in/server/start.mjs:1-16` starts a local HTTP server. These are integration seams, not production deployment, provisioning of browser workers, or a Linux managed-host service. Browser-host uses Playwright Chromium (`launch-host.ts:1-2, 64-69`), but Linux packaging/runtime setup is not present here.
- **Missing — extension server profiles and per-server login.** Current state is one `gatewayUrl`, one `coreApiUrl`, and one `fluxiq.session` storage key (`shared/browser.ts:4-13`, `shared/constants.ts:9-13`; settings fields `panel/settings/form-fields.ts:55-68`). There is no per-server profile collection or hosted account sign-in UI in these paths. A user can manually replace the endpoint; that is not a multi-server connection model.
- **Privacy gap to resolve before remote hosting.** On connection/heartbeat the extension sends state built from the active tab and all tabs (`background/connection/active-page.ts:92-94`; heartbeat wiring `background/connection.ts:179`). The public extension manifest still says it connects only to the runtime the person runs and pairs (`manifest.chrome.json:3-5`), which does not describe managed hosted execution.
