## Findings

**The shared dispatch result already exists.** `packages/fluxiq/src/io/index.ts:34` exports `OutputDispatchResult<TPayload>` with `ok`, `outputId`, optional `status`, typed `failure`, `clearedWait`, payload and metadata. Extend this public seam for CC10 rather than inventing another dispatch envelope. The wire failure owner is `packages/contracts/src/failure/record.ts:42`; gateway results already carry it (`packages/contracts/src/client-gateway.ts:197`). No typed transient or actionability field exists on those inspected seams.

**Readiness is not absent, but the existing readiness is a different fact.** `AS/runtime/executor/contracts.ts:496` has attempt `readiness: { ceilingMs, waitedMs, satisfied, checkedConditionCount, message? }`; `ladder-run.ts:216` evaluates recorded conditions through the host expectation evaluator. `recovery-ladder.ts:184` selects its wait rung using readiness availability, remaining attempts and `mayRepeat`. This reports a recorded-state wait, not whether the exact current target can accept an action. Reuse it for timing/history; do not rename it actionability or use a false readiness result as proof an act was unacted.

**Browser actionability already has a closed, reusable classification.** `apps/extension/src/content/action-runtime/actionability.ts:63-67` defines `ActionabilityRejectionCode = disabled | hidden | covered` and `ActionabilityReport = { actionable: true; point; detail } | { actionable: false; code; detail; point? }`. `checkActionability:73` measures connection/document, visibility, disabled state, then hit testing. Its success point can be elsewhere on the same control; a covering dialog remains a cover. The DOM point, element and prose are local browser evidence, not the portable Core type.

`action-runtime/results.ts:242` maps hidden to TARGET_NOT_SHOWN and disabled/covered to TARGET_NOT_ACTIONABLE. `actionRejected:274` embeds the reason into `failure.actual` as `reason: detail`; it may instead report BLOCKED_BY_DIALOG or USER_INTERVENTION_REQUIRED. `refusalRecord:340` sets `effect: unacted` only when `refusedBeforeDispatch` is present. That is essential: disabled/covered can also be observed after a verb acted. `recovery/fault.ts:135-205` documents and implements this distinction; a disabled word alone is explicitly insufficient. `domain/src/runtime/llm-evidence/action-failure/refusal.ts:203` distinguishes covered by `actual.startsWith("covered:")`; `node-run/retries/answer.ts` uses the same token to avoid replacing a genuine cover with an earlier rate-limit answer. These are direct CC10 typed consumers.

**Retryable is not transient.** Failure record retryable answers whether the same unchanged action can succeed, while `effect` answers whether repeating can repeat an act. Browser codes include retryable NO_EFFECT/PAGE_REPORTED_FAILURE with a one-extra-press certainty flag, and nonretryable disabled/covered state that can become usable after a page change. Do not mark every retryable code transient or every disabled/covered report transient. A cover can need a separate action; a disabled option can remain disabled indefinitely.

**The authoring retry-later inference is still English/code regex.** `AS/runtime/llm/repeat-guard/retry-later.ts:7` matches rate-limit/retry/disabled/busy/loading/timeout words. `outcomes.ts:487,528` exempts recorded calls and amendments; `decision-handlers/refusal-run.ts:151-154` exempts repeated refused mutation/proposal calls. `outcomes.ts` call/outcome/amendment types carry only resultCode/resultReason, not failure. `evidence-loop.ts:451,499` explicitly constructs both consumers' arguments. `decision-handlers/amendment.ts:267,271` constructs amended arguments separately. Merely extending failure does not reach any of these.

**Generic transport handling should remain Core-owned.** `executor/defensive/thrown-error.ts` reads aborted context before status, transport codes and bounded causes, then falls back to text. `defensive/assess.ts:125,142,172,205-226` keeps uncertain committing effects out of ordinary retry, interprets record retryable separately, and bounds the certain-no-effect extra press. CC8 must not turn authoring admission into permission to redispatch a committing act. Cancellation, policy/capability refusals and person-needed handling retain priority.

## CC10 follow-on shape

Prefer a shared portable contract exported from contracts, referenced by a **new optional `actionability` field on the existing `OutputDispatchResult` declaration**, gateway/runtime result types, and browser action result, rather than moving the DOM-rich ActionabilityReport into Core. The inspected declaration currently has no actionability field. Proposed shape (new design, not existing API):

```ts
type Actionability =
  | { actionable: true }
  | { actionable: false; cause: "hidden" | "disabled" | "covered" };
// Optional on dispatch/gateway/runtime/action results:
actionability?: Actionability;
```

The causes reuse the browser's existing closed classification and avoid a second synonym vocabulary. Core should inspect actionable as generic target readiness; web consumers interpret cause. Strict parser accepts plain exact objects, boolean discriminant, and the three literal false-branch causes; reject cause on true, missing/unknown cause on false, arbitrary keys, text, geometry and DOM references. Absence is unknown, not true. This says whether a target was usable when measured, not whether a verb was dispatched or landed. Keep failure.effect separate. A post-dispatch covered/disabled observation may be reported but must never be converted into unacted. Gate callers must state failure.effect only where they already know pre-dispatch refusal. Do not automatically combine actionable false with transient true.

CC10 touches the shared result declaration/protocol, browser result builder, `browser-result-mapping.ts`, `gateway-output-dispatcher.ts`, `adapter.ts` and typed consumers `refusal.ts`, `retries/answer.ts`, `recovery/fault.ts`. These overlap CC8 downstream files, so run this unit serially after CC8 rather than claiming disjoint producer work. It can replace leading-token reads without teaching Core web English. Core recorded readiness remains a separate contract.
