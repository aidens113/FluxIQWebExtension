## Outcome

Done (map complete; some corners listed under Not verified). Headline findings:

1. The model carries a lot of pure bookkeeping: copying `revision`+`digest` into `core.test_subflow`, `core.test_candidate` and then again into the completion; copying a `failingReceipt` whole into a repair brief; sending the `complete` object back whole. Core already holds the latest revision, the verdict and the digest for each.
2. The `where` grammar is per-row, per-field, literal: presence, number bounds (`atLeast/atMost/lessThan/greaterThan/equals`), text tests (`contains/startsWith/endsWith/matches/equals`, `not`). There is NO date bound, NO cross-field comparison, NO computed/sign field, NO set-membership against a named collection. A request defined by a relation ("books I have on loan", "people I follow") can only be written as literal value lists or text tests; Core only adds an advisory note (never a refusal) when listed values are not in the request.
3. The judge is one DeepSeek call family at `temperature: 0`, thinking disabled, JSON object mode, no seed, no `top_p`, no `max_tokens`. Identical temperature-0 prompts are measured to flip (Core's own comments say so). Core already compensates with 2 asks per check, converse re-ask for a first yes, and several Core-vs-judge overrides, but a lot of the judge prompt still asks the model to do arithmetic Core could do (row-vs-bound checks, count of rows, quote-the-exclusion).
4. Core already has strong deterministic machinery to build on (ensureState auto-written, layer handlers auto-written, stale-target re-find, trial change/proof computation, count-differs, requested-output hold). The plan should extend these, not add parallel paths.

## Grammar and save-time validation

The model writes a line script, not JSON (`flow-bootstrap/plan/flow-script-format.ts`): FORMAT L193, ACT_EXAMPLE L276, CONDITION_RULES L345, LOOP_FORMAT L414, STATE_FORMAT L533. Parsed by `flow-bootstrap/authoring/parse.ts` + `script-statements/`; assembled to a plan; validated by `flow-bootstrap/plan/validation.ts` (error codes `bootstrap.*`: unknown_parameter, invalid_parameter_value, missing_parameter, route_condition_*, cyclic/disconnected graph, ports, size limits) and `candidate/submission.ts` (`candidate.*`).

`where` / conditions
- Vocabulary: `contracts/processing-vocabulary.ts:20-29`: bounds `atLeast atMost lessThan greaterThan`, presence `is: present|absent`, texts `matches contains startsWith endsWith`, plus `equals` (number or text, one or list = any) and `not`. Parser `contracts/parse-condition.ts:17-60` accepts only these keys; semantics `contracts/condition-holds.ts` (number = first number in the cell via `read-number.ts`; text folded for case/layout; missing value fails every comparison; `not` inverts).
- Date: `contracts/read-date.ts` is used ONLY by `sort-value.ts` (`sort: [{field, order, as: date}]`). There is no date bound in a condition. "Due this week", "since 2015" as a date, "after Jan 3" must be a text/number trick (the format's own example reads a year column as a number, `atLeast: 2015`, LOOP_FORMAT example).
- Where applied: `extractList.where` filters at read time and decides the rows a `repeat over` visits; `recordOutput.process.where` only shapes the saved answer at run end (LOOP_FORMAT L~432-438). Order is where, dedupe, sort, limit, columns (`contracts/process-rows.ts` header).
- Model guidance on conditions is prose only: quantities "always compared with a bound, never a text test" (`flow-script-format.ts:345-350`); a refusal exists only for ordering in a lasting repeat (`script-statements/listing-order-in-repeat.ts`, `record-replace-in-repeat.ts`).
- Computed membership / sign fields: none. Closest: `script-statements/listed-values-advice.ts:1-60` (t785): a `where` whose `equals`/`in`/`oneOf`/`anyOf`/`values` literals are words the request never says gets ONE advisory note on the accepted revision ("These values are what the page shows today. Where each row itself shows what makes it one the request asks for, test that instead"). Never a refusal. (Only `equals` can actually carry a list in the real vocabulary; the other keys it scans are not accepted by the parser, harmless.) The judge instruction repeats the rule (`llm/diagnosis-instructions.ts:171`, "Where the request defines its set by the person's relation to each item ... advise that sign, never a literal list ... a library's 'books I have on loan' are kept by each row's Return button").
- Fact conditions (page facts for `when:`/`done when:`/handlers): `exists|absent|visible|enabled <handle>`, `text <handle> contains|is|matches`, `value <handle> is`, `count <handle> is N`, `dialog <kind> "name"` (STATE_FORMAT L~540); checked by `script-statements/fact-condition.ts`, `fact-locator.ts`. Route conditions: `<path> <test> [value]`, paths limited to `routing.paths`; tests list in FORMAT L~225.

What the judge decides by reading (and Core could settle or check from data it holds):

Core holds each cell value and the condition bound; it already marks rows as `leftOutSettled` (number fails the bound / no value / presence / text test), so the judge needs only a quote.
