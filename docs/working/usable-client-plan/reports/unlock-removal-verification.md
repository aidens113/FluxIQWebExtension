# Unlock removal verification (t914 committed tip)

Core tip `592a188a4` (unlock removal is `79f175d2a`); extension tip `ee9cacd68` (removal is `1285dd320`). Read via `git show HEAD:`; WIP ignored.

## Verdict

The claim is true for the production path, not for the code base. A connected panel session, paired extension or SDK session that goes through the runtime composition (`packages/fluxiq/src/programs/_shared/runtime.ts:278`) never meets an unlock or a "key locked" wait. That composition builds its key ports with `authenticatedModelKeyPorts` (`_shared/key-access/model-ports.ts:7-24`), which always supplies `createUseAuthorization`. With that port present:
- `releaseAutomationStudioSessionProviderKey` returns or throws a real error and never reaches the `AutomationStudioSecretsLockedError` throw (`runtime/models/secrets/session-key.ts:72-88,106`).
- `automationStudioSessionKeyLocked` returns false (`session-key.ts:122`), so the wait never starts (`locked-wait.ts:32-34`).
- Use authority is a per-call principal (`access/access.ts:16-48`, `_shared/key-access/authority.ts`). It needs no held session key: if none is held, `dataKeys.open` unwraps the data key from the host key (`access.ts:25`, `data-keys.ts:41-60`).

Nothing was deleted, though. The lock machinery is left as dead or compatibility code, and a custom `AutomationStudioSessionKeyPorts` without `createUseAuthorization` (the type is exported from `runtime/llm/index.ts:61`) revives the old wait. The user-visible leftovers are docs, the `model_key_locked` wait wording, and the legacy-key recovery message.

## Key storage at rest

- **Values**: each provider key stays sealed under a per-record data key derived by scrypt from the owner's password (`runtime/value-sealer.ts`). It is not re-sealed.
- **Data key**: new in this change. Each record also stores `hostProtection`, the data key wrapped with AES-256-GCM (`platform/custody/protection/aes-gcm.ts`) under the host keyring key, with AAD of storeId, ownerUserId, recordId and sealDigest, so it is bound to that record and value (`access/data-keys.ts:14-60`).
- **Host keyring** (`platform/custody/keyring/host-protection.ts`):
  - Windows local: `<root>/host-secrets/keyring.dpapi`, protected with DPAPI CurrentUser through `powershell.exe` (`windows-protection.ts`). Only the same OS account can read it.
  - Linux and macOS local: `<root>/host-secrets/keyring.json` in plaintext, mode 0600 and owner-checked. Symlinks and group- or world-accessible directories are refused (`private-file.ts`). Safety is only the file permissions, with no OS keystore.
  - Both: a `host-keyring-initialized` marker next to the root refuses to silently create a new keyring if the file is lost.
  - self-hosted: same as local, or a file named by `FLUXIQ_SECRET_KEYS_KEYRING_FILE`.
  - service (cloud): requires a mounted keyring file; `deploy/cloud/runtime/write-config.py:47-61` validates the `secret-keyring` secret. Without it, use fails with `host_protection_unavailable`.
  - In-memory (no `rootDir`): a random in-process keyring, so keys are lost on restart. Tests only.
- **Core restart**: the keyring is read again from disk, so a client keeps working. Authority is still checked per call: a panel session must still validate and a paired client must still be vouched for by the gateway (`authority.ts`, `vouchesForClient`).
- **Panel logout**: the panel session fails authority (`validateSession`), but a paired client uses its own `client` principal and is unaffected.
- **Key added after the client connected**: `createKey` seals and wraps in the same call (`service.ts:191-204`), so the next call can use it with no re-pairing. The chat sees it on its next availability read.
- **Residual risk**: anyone holding the host keyring plus the store can decrypt keys without the password. That is the accepted trade for password-free client use; it is stronger on Windows (DPAPI) than on Linux (file mode only).
