## Proposed bounded contract

Trusted server execution context contains original projectId, actual runId, actual owning graph Flow ID, node invocation identity, node attempt identity, effect ordinal and optional candidate identity/revision/digest/verification run when issued by that actual controller. Use original project IDs. A run-owned factory issues this from executor state, not action.metadata or API payload. Node invocation includes child call/loop/re-run identity; a repeated node attempt cannot reuse the same key accidentally. Prefer a monotonically allocated invocation ordinal in that actual run's execution context and persist the issued identity with its command claim. Restart never reruns a graph to guess the old ordinal; it reconciles the recorded command. Detached/controller run context missing means command evidence remains unsupported.

Stable command ID/claim key is derived from that trusted execution key, independent of payload digest; changing payload under the same key is a conflict. Random run identity supplies namespace entropy. Gateway binds the **selected actual ready clientId and sender sessionId** to the claim before send; neither is taken from echoed result metadata. Same command after reconnect/new session does not acquire a second claim or send: reconcile original binding as pending/unknown or committed. Session IDs are not bearer credentials and no pairing secrets are stored in ledger/logs.

Canonical request digest covers exact frozen original actionType/parameters/target/timeout/metadata + owner/client/session binding + protocol/issuer version. Compute from the actual dispatched payload before sending; do not hash withheld RuntimeStore diagnostics as if they were original payload. Store hashes and bounded content-free owner fields, not raw browser data/passwords/tokens. The command object used by send is a frozen clone of that digest input. A result receipt says `acknowledged_by_bound_client` and records trusted server receive/commit timing; it is not independent semantic outcome validation or a claim that an untrusted client cannot lie. Candidate controller must fetch/validate this receipt by actual owner/command key, never trust a receipt ID/status in model metadata or an unrelated event.

Generic gateway port: `claim(binding, commandDigest)`, `get(commandId)`, `settle(binding, validatedResultReceipt)`, `markUnknown(binding, reason)`, `reconcile(binding/requestDigest)`. Claimed record has immutable request/binding/digest and pending or committed/unknown disposition. Actual port owns transactions and validates corruption/duplicates/foreign owner joins. A fresh result commits receipt before authoritative promise resolution. A known committed replay may return only a safely retained usable result; pending/unknown never sends. No automatic retry under a fresh command ID or new session after uncertain send.

Client result may include sensitive or large extracted data. Persist a bounded validated receipt (status, command/client/session/run/attempt, safe failure classification/timestamps, original-result digest and redaction markers) using existing producer-redaction/withholding rules. Full payload is available to the first live caller after durable receipt commit, but restart reconciliation is receipt-only unless a separately approved protected dataset/object owner persisted the usable payload. Never return a fake succeeded extraction with a missing/withheld payload. Reconciled known effect with unavailable required result is explicitly `result_unavailable`/unknown for continuation, not permission to repeat the action. Exact retained-result policy must be approved before implementation; command receipt durability alone is not raw-result durability.

## Dispatch and completion ordering

1. Existing native/output permission/consequence/confirmation/target/session checks run normally. Receipt-required dispatch with no SQL port or no trusted run context refuses before any send; legacy non-receipt callers keep explicitly untrusted compatibility behavior. Revalidate selected ready session/client and AbortSignal after any awaited claim before sending.
2. Gateway uses stable server-issued command ID, persists immutable claim **before outbound queue/socket send**, and joins/compares an existing same-key record. Different payload/binding refuses. Pending from this or another process/restart returns unknown; committed reconciles and never sends. Only successful new claim owner can send once.
3. Install active pending-owner state and arm the client answer timer around the actual send after the claim. A failed/uncertain socket send leaves unknown, because it may have delivered. Proven cancellation before any send can record not_sent separately; do not infer this from a generic socket exception. No background rejected send promise can escape accounting.
4. Inbound obtains actual authenticated sender session/client, looks up the known active pending owner, parses result and asynchronously commits exact bound receipt. Only then clear timer, resolve caller and publish authoritative completion. Wrong client/session/command/request/duplicate conflicting result refuses without changing rightful pending owner. Client-supplied server receipt/provenance fields are discarded.
5. Timeout/cancel/disconnect/commit failure preserves pending or unknown truthful disposition; it never produces a performed/success receipt. Race settlement versus timeout is transactional: committed owner result wins exactly once, conflicting duplicates are refused. If COMMIT succeeded but acknowledgement was lost, reconciliation reads that exact committed receipt rather than recording a false rollback.
6. Unknown/late compatibility action_result events may remain observable for existing diagnostic clients, but have no authoritative command receipt and cannot settle a different command/run, complete a candidate stage, or drive normal RuntimeService attempts to succeeded. Runtime transport must distinguish/filter this event path from the awaited authoritative result rather than treating every forwarded event as a durable result.
7. Restart loads ledger on demand; pending/send-started records are outcome_unknown and never replay. New connections cannot reuse old sender sessions. No client-side durable result/resend protocol is assumed. A lost result before durable commit remains unknown until a separately trusted reconciliation mechanism proves it; do not manufacture certainty from the client reconnecting.

## Final precise executor discovery and implementation recommendation

`executor/graph-run.ts` already numbers attempts globally within each graph execution using `priorAttemptCount + attempts.length + 1`, including seed traces on resume. `node-execution.ts` derives the attempt ID from this number and adds `callFlowAttemptPath` for children. `composite-executor.ts` retries a child snapshot in its own loop with the same child options and resets the child's local attempts each time. Thus graph attempt numbers distinguish root loop/retry arrivals, but the current child call path alone does not distinguish the inner child retry. This is an actual collision seam, not a missing model metadata convention.

Recommended focused factory: a server-owned run context is constructed once from actual session.projectId/runId, retained across live repairs, and carried as a non-JSON options field. At real node attempt entry, allocate one opaque invocation identity from that run factory; its effect contexts share that identity plus the existing trace attempt ID, actual graph Flow ID, child path and the actual effect ordinal. A new real child attempt obtains a new identity even when its local trace number resets. Freeze the issued context and persist it with the pre-send claim. Repeated delivery of the same issued context reuses its command key; restarting does not reconstruct or mint an invocation to retry an uncertain effect. This needs no model-facing field and no native implementation access to privileged gateway authority. Native result effects continue through the existing executor dispatcher and permission policy. The pure run-state loops map can remain unchanged; its earlier proposed ownership is withdrawn.

For receipt-required execution, unknown delivery must also terminate that actual run's dispatch progression. Merely returning a generic retryable action failure would let a recovery ladder, child retry or resumed graph mint a fresh invocation and blindly resend. Add an explicit unknown-command disposition propagated through io-policy/runtime transport to the owning graph execution, with no retry/alternate recovery for that uncertain effect. Before reusing/resuming the same durable run, query the journal for unresolved owned commands and refuse further execution while any remain pending/unknown. A newly chosen explicit user run is a separate operation and does not silently reconcile the old effect. Exact graph/service stop and resume seams require approval together with the context owners; a ledger-only substep cannot claim this behavior.

Recommended result policy for the first slice: durable bounded receipt only, with a separate live usable-result branch. Reconcile returns a typed receipt plus `result_unavailable` for continuation; it never synthesizes a successful result with absent extracted values. A future protected result object can extend this without changing the command binding. Recommended event policy: existing compatibility event stays diagnostic; the awaited server-owned dispatch path carries an additive typed durable receipt result. No client wire receipt field is accepted. Required context/SQL port missing is an explicit pre-send refusal; legacy commands remain explicitly non-authoritative.

Exact new executor test owner should be `executor/tests/command-context.test.ts`; existing owning graph-run/retry/resume tests receive the narrow refusal regressions. Composite retry uniqueness belongs in the nearest runtime owning tests for `composite-executor.ts`. Generic gateway controller tests belong in its new focused `command-ledger/tests/`; real SQL tests belong in project `command-ledger/tests/`. This avoids adding another file to a crowded existing service tests directory and does not increase any structure baseline.
