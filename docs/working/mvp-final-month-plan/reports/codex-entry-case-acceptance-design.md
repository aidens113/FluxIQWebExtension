# Applicable entry-case acceptance design

Status: Read-only bounded design; not implemented or qualified
Owner: codex-t517
Date: 2026-10-13
Location: frozen t531 pair; parent owns integration and shared documents

Candidate acceptance currently proves one selected starting situation. The missing unit is an owner-declared set of applicable starting cases and exact receipts for those cases, not an obligation to execute every imaginable Router predicate. A simple task with one supported starting situation keeps one case. Required alternative cases come from the person's task and genuinely supportable starts, never the candidate builder's list of routes or a model's statement that coverage is complete.

## What the current path actually wires

Core paths below are relative to `packages/fluxiq/src/programs/automation-studio/runtime/`.

- `service.ts:1585-1589` mints one candidate ID and injects `service/candidate-trial/port.ts`, bound to project/Flow/instruction IDs, registry/resolution, current accepted-base digest, runtime-session/data/end-view owners, graph options and the build-test judge. `prepareStart` is the service's optional deployment hook. `service.ts:1603-1607` saves the draft and invokes promotion with one standing trial plus the port's in-memory records.
- `flow-bootstrap/candidate/contracts.ts` request/result identities are candidate ID, revision and digest; neither the request, start hook nor result contains a required case ID. `trial-gate.ts:227-239` calls prepareStart before its reset ledger, runs one frozen candidate, records lasting acts regardless of verdict and saves a verdict under revision+digest. The existing aggregate per-revision trial/retest allowance is three. Its no verdict closes that candidate digest; unjudged/transient results may be rechecked within existing bounds.
- `service/candidate-trial/port.ts:32-57` rejects mismatched candidate/revision/digest, keys prepared starts and retained unjudged evidence by revision+digest, and retains trial records in memory. Rejudging reruns no Flow and prepares no new start. Current draft `service/candidate-drafts/record.ts` has original instruction text/IDs, immutable candidate and base-settings revision but no durable case-set/receipt array.
- `service/candidate-trial/run.ts:58-74` opens a dedicated trial run and constructs verification identity from revision/digest/base and original-instructions digest when available. Its start receipt is synthesized from startLocation+reset status, with pageGeneration 0 and empty subjectStates. `requirementsDigest` uses a compatibility placeholder when original source binding is absent. This is an execution correlation receipt, not proof of an independently observed named starting state.
- `flow-bootstrap/verification/detached-execution.ts:51-72` revalidates exact candidate bytes, normalizes their complete topology without applying, routes on fresh host observations, requires observed state when Router predicates need it, and verifies selected graph ownership. It executes the selected entry graph; static rooted helper reachability does not establish applicability or result coverage for every entry. t529 helper execution and child evidence are a separate evolving dependency; this design does not claim them complete.
- `service/candidate-trial/run.ts` processes run-owned datasets and builds its summary from that trial's trace/graph/end view. The judge sees that summary rather than exploration success. The landed-act owner feeds reset accounting. `promotion.ts:56-86` requires one standing yes with matching recorded run, rereads authoritative draft, recomputes candidate fingerprint, checks current base/settings, then proposes through the legacy adaptation lock. Candidate/task edits already invalidate the candidate digest; that protection must extend to case declarations/receipts. The current promoter is explicitly a process-local legacy compare, not crash-atomic acceptance.
- `flow-bootstrap/candidate/digest.ts` hashes task text/base/plan for legacy candidates and owner-enumerated original sources for source-bound v2 candidates. `verification/contracts.ts` already defines verification identity, prepared-start and requirement/evidence shapes; reuse those identity concepts rather than minting an unrelated coverage authority. The existing production trial path does not fully populate that richer observed-start/requirement protocol.

## Actual reset boundary

`candidate-start-hook/from-environment.ts` defaults to no hook in the product. When configured, it POSTs an empty JSON object to a deployment endpoint, accepts an object response and returns it as the start result. It supplies no case declaration or condition-specific preparation. `programs/_shared/runtime.ts:69-77` installs that hook; the service otherwise records not_reset.

Downstream `packages/test-runner/src/environment.ts:161-166` points this hook at the current fixture's `/__control/reset` when fixture reset is enabled. `flow-lane/creation/readiness.ts` checks hook presence/reset configuration, not independently prepared case facts. This is a whole-fixture test reset, not proof that a production automation used site controls to undo exactly its own acts or preserved pre-existing user state.

`flow-bootstrap/site-reset/ledger.ts:276-289` trusts startReset: it marks this build's undoable acts undone without a comparison and records them as absorbed. Without that hook, `trial-policy.ts` can eventually admit residual/kept acts with startedWith after repeated reset refusal or cannotUndo. The judge receives that provenance, but it does not establish a clean baseline case. A residual-state trial must not satisfy a required clean case unless the declared case explicitly permits that independently verified residual state.

Keep three operations distinct: undo the build's own exploration/prior-trial acts; prepare the requested case through authorized controls; independently observe the resulting starting facts. A successful reset callback is a mechanism, not case-coverage evidence. Irreversible/uncertain lasting acts cannot be repeated simply to obtain another case receipt.

## Proposed contract and default behavior

Use one owner-controlled `candidate.acceptance_cases.v1` envelope, separate from model-authored graph annotations. It binds project/Flow, authoritative original-instructions/task digest, case-set digest/version and stable case IDs. Each required case contains its instruction source reference, authored task inputs, declared starting predicates, expected applicable entry binding for this exact candidate, and an owner-supported preparation reference or observed-current mode. The case declaration contains authored conditions; raw observations stay in their existing screened/object owners. Candidate builder fields cannot set required:false or waive a missing case.

Default is one `observed_start` case for an ordinary single-start task, with actual fresh starting observations. Additional cases are mandatory only when explicit task requirements describe those alternatives and the owner can actually prepare or observe them. Do not synthesize hypothetical page states from predicates, route count or generic labels. An explicit required alternative that cannot be prepared/observed remains unavailable and nonpromotable; it cannot silently become an excluded case. Preserve mutually exclusive route semantics by executing one independently selected entry per prepared case.

Do not equate undeclared alternative routes with tested routes. Bind each task case to the candidate-owned symbolic entry that a fresh Router actually selects. If the selection is inconsistent with that case's required behavior, record a mismatch; do not force-select the expected Subflow to make it pass. Case-to-entry mapping must be validated alongside declared target ownership, not granted by a builder yes.

Prepared-start receipt: exact candidate/task/case-set/case identity; conditions digest; preparation/reset ledger epoch; independent observation reference and generation when the case requires external state; preparedAt; authorized preparation result; reconciliation of this build's acts and preserved baseline. Core checks receipt identity/freshness and observes Router state again immediately before execution. Missing/unknown external generation or starting condition required by a case means unavailable, not a fabricated pageGeneration 0 proof. A genuinely input-only case can bind canonical authored inputs without inventing a browser observation requirement.

Trial receipt: same identity, start receipt ID, actual selected entry/rule/fallback, run ID, execution outcome, judge/result verdict, independent observed result references and run-owned effects/child evidence. Credit requires actual execution in that case, correct selected-entry identity, independently verified starting state and a yes for the exact trial run. A builder's completion or coverage words never credit a case. Rejudgement can improve that same run's verdict but creates no second entry execution.

Accumulate receipts by candidate/revision/digest/task/case-set/case ID. Store them durably under the candidate owner before they become eligible; current in-memory port history alone is insufficient for reloading an acceptance decision. Recompute the required set and reread receipts at promotion. All required cases need current successful evidence; missing, failed, stale, ambiguous or unreadable receipts leave a draft with closed per-case diagnostics. Candidate/task/case-set changes invalidate all prior credits. A semantic no still closes the candidate under existing policy; never judge repeatedly until yes. t525 deficient evidence recheck remains its own bounded correction.

Preserve the current aggregate trial/cost/cancellation purse. Do not multiply trial allowances by case count implicitly. Preparation and undo attempts use existing authorized controls, deadlines and cost accounting. More required cases than the available budget can establish means incomplete acceptance, not permission to omit cases or quietly buy extra calls. Per-case future allowances are a product policy choice, not this design's default.

Learned paces may come from multiple required trials. Accumulate the maximum validated pace by candidate Subflow/node identity and record every source receipt plus the exact promoted transformation. The existing promoter changes pace metadata after a judged candidate; preserve explicit original-versus-promoted identity/provenance and do not describe that transformed plan as byte-identical trial execution. Child pace/effect projection depends on t529's final contracts.

## Downstream realistic qualification design

Use one allowed realistic fixture whose existing controls can expose two authored task-relevant starts, such as company-website with and without its actual optional announcement. Declare both starts and the task's same desired extraction/result, prepare each with the site's owning controls, and independently verify initial observations and selected entry. Do not write a synthetic browser page or add a bespoke fixture state merely to guarantee a pass.

The task should contain an actual reusable operation over multiple existing rows so nested helpers and repeated calls receive different authored inputs and return the expected outputs. Verify relevant graph call edges/ownership and actual child execution/result records; avoid any minimum Subflow-count oracle. A flat correct task can remain a legitimate product answer where factoring is not required; structural qualification specifically tests a task that needs declared reusable behavior.

The free negative probe must withhold one required case receipt and prove no promotion/accepted-store write despite the other yes. Then execute/judge both cases and apply only after current complete receipts. Reset exactly build-owned effects between cases; independent oracle checks no duplicate/unrequested lasting consequences and preservation of pre-existing data. Close/reopen the saved automation and run each declared start with providers disabled; assert actual helper outputs, result datasets/goal and explicit zero provider/intervention counters. Separately validate Chrome/Edge and Firefox where appropriate. A fixture-hook reset pass cannot stand for the site-controls reset requirement.

## Concrete unresolved choices

- **Who declares task alternatives?** Recommend an explicit task/source-owner envelope carried by the existing task-save/generation API, defaulting to observed_start only for a genuine single-start task. A trusted independent interpretation can propose declarations linked to instruction spans, but an unresolved required condition must stay incomplete. A builder-controlled case array is rejected. Whether initial production UX authors these conditions or a trusted task interpreter derives them needs an explicit owner; current plain task text does not provide typed case declarations.
- **Unsupported required states?** Default to truthful incomplete draft with actionable named case preparation failure. Do not generate impossible states, omit the case, or demand every mathematically possible Router route.
- **Receipt persistence/lock?** Recommend candidate-owned versioned case receipts and recheck under the existing adaptation compare lock. Existing verification contract's stronger atomic/durable promoter is not currently the legacy production guarantee; adopting it would be a separate storage brief.
- **Residual/irreversible acts?** Default unavailable for clean-case credit. Permit only an explicitly declared, independently observed compatible starting case; never replay an uncertain lasting action to populate coverage.
