# Model/site-control reset readiness

Status: read-only discovery complete, 2026-10-13. No implementation, tests, builds, browser/provider calls, runtime-state changes or commits. Inspected main source and the frozen t529 Core pair; t529 child-act projection retains its invocation attribution but does not add undo ownership evidence. This report does not qualify production reset behavior.

## Finding

With the deployment start hook unset, the production candidate authoring loop really does offer model-directed undo through domain controls. It is not an absent mechanism. However, its current admission policy deliberately allows unknown restoration and acknowledged residual acts, trial feedback lacks the opaque ownership evidence needed to undo trial leftovers safely, and completion after a successful trial does not restore the baseline for the following whole run. The Lab's final wholesale fixture reset currently conceals that last gap, including in model-reset-only mode.

Owner-declared supported cases, reversal of this build's own acts, and independent observation of the selected starting case are three separate obligations. t532's declaration foundation creates none of the execution/preparation/restoration receipts. The t532 worker confirmed that observed-current declarations do not certify later restoration and prepared references currently have no production preparation provider.

## Implemented production chain

Core paths below are relative to `packages/fluxiq/src/programs/automation-studio/runtime/`.

- `service.ts` candidate generation constructs one `AutomationStudioSiteResetLedger`, shares it with `flow-bootstrap/action-permissions.ts`, and supplies it to `flow-bootstrap/candidate/authoring-loop.ts`. It passes the optional deployment preparation hook only to the candidate trial port. The ledger lives in this authoring invocation; it is not an independently persisted final-run preparation obligation.
- `flow-bootstrap/site-reset/start-check.ts` captures the initial opaque state once, after the initial opening tool call or before a later nonopening call. Failure does not silently recapture a later dirty baseline. The reader is passive and permission-denied. Comparing can navigate through the domain-owned arrival output, then read twice to filter transient changes. An unavailable arrival/reader, failed read, or absent baseline yields unknown comparison, not positive equality.
- `flow-bootstrap/site-reset/undoes-tool.ts` adds only an `undoes` reference to the ordinary action tool. The model sees build-owned act references and instructions to reverse them, preserve pre-existing state, and return to the original source. Core strips this field before passing the actual registered action to the domain.
- `flow-bootstrap/action-permissions.ts` checks the actual domain declaration before action. Positive opaque item/dialog identity fences undo targets. Only a positively newly created item gets the bounded unasked delete allowance; ordinary own-item actions still pass the existing permission gate. One related confirmation may follow; a different item is refused before dispatch. A missing token is not an equality match.
- `flow-bootstrap/site-reset/act-places.ts` captures exploration before/settled-after states, records same-location changes and newly appearing opaque item tokens, and checks undo effects independently. No-effect actions do not create undo obligations. Unknown reads and cross-location acts do not provide equivalent ownership proof.
- `flow-bootstrap/candidate/trial-gate.ts` asks the optional hook to prepare, then calls ledger `beforeTrial`, executes the trial, and records its lasting acts via `trialRan`. The model receives `leftOnSite`, reset-required feedback and, where admitted, truthful `startedWith` residual provenance. Semantic judgement of a trial is separate from clean-start proof.

Downstream `domain/src/runtime/llm-evidence/start-state/{observe,page-state,differences,state}.ts` supplies the opaque state/comparison. It uses existing secret-screened evidence, handle-free rendered lines, passive non-rendered state and opaque record tokens. Interruptions/focus are excluded; the pinned header's relevant hidden state is retained. `control-spot/{target,token}.ts` derives the same item/dialog digests for actual control declarations. This verifies captured page state; it is not a complete website-wide state reader. Absence of record evidence cannot prove item absence.

## Exact gaps and admission consequences

1. **Unknown or dirty comparison can admit.** `site-reset/trial-policy.ts` uses `comparison.differs ?? []`; kept acts, repeated unchanged refusal/no progress, and the refusal limit can admit residual state. `ledger.ts` can mark an attempted undo complete when `undoChanged` is unknown (`!== false`) and there is no usable per-act comparison. `cannotUndo` after an earlier ask preserves the act and admits a trial with it. These are explicit legacy liveness choices with provenance, not independent restoration proof. Clean-start/case qualification must not count these admissions as restored.
2. **A reset hook is trusted without observation.** `ledger.beforeTrial({startReset:true})` marks undoable acts undone without comparing. `candidate-start-hook/from-environment.ts` POSTs an empty request to a deployment endpoint and accepts a bounded object response; it does not prove this build alone was reversed or that pre-existing state survived. No configured hook correctly exercises the production undo loop. Missing hook must not itself make production unavailable once genuine preparation exists.
3. **Trial acts have words but not undo identity.** `site-reset/contracts.ts` trial-act shape contains step/definition/label/control/consequences. `service/candidate-trial/landed-acts.ts` filters skipped/state-held/no-effect attempts and, in t529, projects child frames without counting call containers. `ledger.trialRan` records these acts without `spot`, `place`, or positively created items. Moving to the right page can be admitted, but a later lasting removal/quantity control cannot demonstrate that it targets the trial's own item through this contract. Missing effect diff also still counts a succeeded action as a possible act; that should remain an obligation, not permission to undo an arbitrary item.
4. **Latest successful trial leaves its effects in place.** Trial gate completion accepts the current judged-yes revision. `authoring-loop.ts` has no post-success prepare/compare stage. The normal conversation `run.execute` calls `run-runtime-session`; service execution checks instruction authority and action permissions but has no creation-ledger final-start receipt or restore handoff. Do not reset every ordinary later user run: the missing obligation concerns the final verification run following build exploration/trials.
5. **Repair whole-run preparation is also unowned.** `service/runtime-adaptation/repair-rerun.ts` has no preparation port. The held-topology design correctly requires a fresh receipt immediately before the edited whole run and preservation of the original run's pre-act baseline, rather than adopting leftovers as a new baseline. This report does not implement the held adapter or reopen its execution owners.

The current lasting-act gates and uncertain-effect suppression remain necessary. Undo must never blindly retry a possibly landed lasting action, turn missing evidence into absence, remove pre-existing rows, or use a model's claim of success as a restoration receipt. A failed or irreversible own act may truthfully block clean qualification; it must not silently become a clean trial.

## What current Lab readiness proves

`packages/test-runner/src/flow-lane/creation/readiness.ts` normally requires the configured fixture preparation hook. `--model-reset-only` requires that hook to be absent, so candidate trial preparation then uses the production model loop. However, that mode still starts from an initial fixture seed and still unconditionally resets the fixture before playback.

`packages/test-runner/src/flow-lane/creation/lane.ts` calls `resetScenarioLab(...)`, then `prepareFlowPage("playback")`, then executes the final saved Flow. `environment.ts` normally points the Core hook at the scenario's reset endpoint. The final oracle may correctly prove the Flow's task result from this artificial start; it cannot prove baseline-preserving model undo or final-run preparation. Neither hook configuration readiness nor compilation is live reset qualification.

Both allowed cart sites already have real controls: crossborder `apps/scenario-lab/src/scenarios/crossborder-marketplace/client/cart-script.ts` binds per-line quantity and removal mutations followed by reload; everything-store `.../everything-store/client/cart-script.ts` binds per-line increment/decrement/delete and refresh. Tests should use those controls through the ordinary domain action path, not invoke their mutation endpoints directly. No fixture behavior change is needed to manufacture restoration.

## Smallest serial implementation partitions

1. **Generic clean preparation owner:** `flow-bootstrap/site-reset/{contracts,ledger,trial-policy,start-check,act-places}.ts` and adjacent tests, with a focused receipt owner. Preserve the existing residual provenance where useful for exploration, but distinguish it from verified restoration and from case observation. Missing compares, wrong target, no-progress, `cannotUndo`, stale reads and unknown effects cannot produce clean receipts. Receipts bind original baseline/ledger generation, task/candidate topology digest, case-set/selected-case identity and observation time. No model-authored receipt or browser identifiers in Core. Scope ordinary own-act reversal to exactly its positive before-state/item evidence; do not grant blanket delete/modify permission.
2. **Trial ownership evidence:** generic trial-act contract, `service/candidate-trial/{landed-acts,frame-evidence,run}.ts` and focused tests; forward per-invocation opaque domain-owned before/after/item evidence through an explicit trusted seam. Retain t529 graph/frame attribution, screens and single counting. Domain owns how a created row and restored quantity are recognized. If current retained snapshots cannot establish those facts, decline and add the narrow live producer/host seam instead of guessing from labels or graph parameters.
3. **Trial/final-run orchestration:** `flow-bootstrap/candidate/{authoring-loop,trial-gate}.ts`, candidate trial port and a focused creation-to-verification preparation handoff. Prepare/observe after the latest trial's acts and immediately before the final whole run. No unconditional reset on ordinary subsequent runs. Wire t532 owner declarations only after execution receipts exist; a dirty observed-current predicate is not original-baseline restoration. Held repair later consumes the same generic contract in its separately owned rerun port, preserving the original run baseline.
4. **Downstream observation and qualification:** bounded `domain/src/runtime/llm-evidence/start-state/` and `control-spot/` owners only if proof is insufficient; test-runner creation readiness/lane plus adjacent tests need an explicit production-control qualification mode that disables both trial and final wholesale resets. Initial isolated fixture seeding remains setup. Normal fixture-control measurements retain honest provenance. Do not remove or weaken task/final-state oracles.

These partitions require implementation briefs; no source ownership has been exercised here. Case parser, canonical executor and held-topology consumers remain separate from this investigation.

## Meaningful qualification

First provider-free regressions should drive the real permission/ledger/start-reader interfaces deterministically: positive own-new-item removal; restoring only a build-added quantity delta on a pre-existing row; preserving unrelated pre-existing rows and quantities; multiple acts sharing an item undone in reverse dependency order; nested/repeated helper invocation ownership; one confirmation lifetime; wrong/missing target identity refused before dispatch; unavailable/failed/stale observation never clean; unknown lasting effect never repeated; no-progress/cannotUndo residuals never count as clean; last-trial effects require fresh final preparation; new candidate/task/case/baseline invalidates receipt. Reading retained evidence for judge correction must not spend another site preparation or imply a new execution.

Then a separately authorized isolated live run on crossborder-marketplace or everything-store should establish a nonempty pre-existing baseline through its controls before the build baseline is captured, let exploration and a trial create own changes, and require model undo through the same registered controls before another trial and the final whole run. Privately compare authoritative fixture state for exact equality of original rows/quantities and absence of only build-created rows; publish booleans/counts, not page values. Record actual undo tool executions, permission decisions, opaque independent comparison, last-trial/final-dispatch ordering, selected declared-case observation and unchanged final task oracle. No reset endpoint between baseline capture and final run. Include a lasting uncertainty/no-effect case and an unundoable case with honest refusal. Setup seeding and ordinary deployment hooks must be explicitly excluded from model-controlled reset credit.
