## Minimal migration order and acceptance

1. **Fence false acceptance.** Modify existing verdict/agreement and promotion owners first. Confirming yes requires affirmative confirmation when a pair is required; missing required evidence remains unknown; no topology can persist a repair before judged success. Existing accepted Flow stays unchanged on unknown/no/cancelled/timed-out run. Add controlled negative unit/controller fixtures before paid live measurement.
2. **One bounded candidate operation.** Introduce a feature flag and candidate revision/receipt types in Core. Reuse accept + validator + existing graph representation. Discovery tool calls only append evidence; complete submission is an explicit operation that writes a candidate version, with diagnostics. Store base dependency identity, graph digest, source instruction fragments, locator-resolution provenance and required outcome brief. Keep one selected small task family first.
3. **Independent execution and evidence.** Downstream declares clean fixture start states and executes saved canonical candidate with normal runtime. Core consumes adapter-observed evidence with source/run/candidate identity. Trusted generic equality/count/member/all-of/existence checks run before semantic review. Builder labels/script-returned booleans are never observations by themselves. Distinguish create-new from ensure-already-true.
4. **Unify promotion, then repairs.** Bootstrap, reauthor, and runtime repair generate candidates through one validation/execution/verification/promotion contract. Retain strategy differences and user permission/policy. All topology shapes execute unapplied or are retained unverified; no apply-first exception. Persist version-to-verdict links using current Core graph/adaptation storage. For larger replacements, defer patch-language sophistication.
5. **Simplify and measure.** Delete obsolete retained/dropped/excused authoring grammar only when the flag's representative path works. Controller replay checks deterministic transitions and stops at observation divergence. Separate checkpoint model evaluations test understanding of the new interface; live headed A-D and zero-call runtime replay prove the complete loop. Measure false accepts and total cost per verified reusable Flow, respecting the existing user-mandated model/budget/live limits unless changed explicitly.

File ownership for execution briefs: one Core owner for verdict/agreement/evidence contract; one for candidate normalization/validation/submission; one serial owner for service/promotion/recovery wiring/storage joins. Downstream owners supply browser observations, reusable locators, fixture start-state/reset/oracles, build identity, and live operation. Parallelize only after identifying exact disjoint files. Create a paired Core working document before Core implementation.

## Consultant critiques and plan edits recommended

The consultant correctly reverses structural stages 2/6: separation of discovery from full candidate authoring should precede developing another small draft edit language. Avoid spending days simplifying machinery scheduled for deletion. Stage 4 direct evidence checks must move to the first acceptance fence, not wait behind broad tools.

Keep the user's fallback direction, but do not put general scripts/requests on the critical path to trustworthy A-D acceptance. Fallbacks must carry the same evidence, permissions, time/size bounds, candidate identity and promotion rules; successful fallback remains the required partial-success classification. Generic Core must not learn commerce facts; the adapter supplies semantic observation names and provenance.

The old Core authoring working document describes separated authoring as a historical cause of failures. That is a warning against testing one explored procedure while saving a different proposal, not evidence that discovery and persisted candidate must remain the same mutable object. Independent execution of the exact submitted candidate resolves the conflict.

No broad graph/runtime rewrite or new persistence store is supported by this audit. Full universal predicate language, sophisticated graph patches, broad service decomposition, and model strategy changes can wait. Small boundary extraction alongside implementation is justified; one wiring owner prevents service.ts conflicts.
