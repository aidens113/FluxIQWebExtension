## Authoritative evidence boundary

Core `runtime/durable-behavior/durable-behavior-changed.ts` owns retained-state semantics. A runtime patch or handler is durable only when a receipt matches a run adaptation ID and its promotion decision says applied; a kept reauthor is its own applied marker. `service/summaries/conversions.ts:71` and `api/handlers/runtime-execution.ts:119` use this same reading. An unread run detail makes the endpoint answer fail instead of manufacturing no-change success. The API/list layer intentionally returns booleans for available summaries; a UI must not reinterpret created IDs or requested autoApply as retention.

Legacy promotion decisions are deliberate: autoApply true with no applied field counts as historical automatic application, while applied false does not. This audit proposes no change to that compatibility rule, no new persistence logic and no domain-specific learning predicate. Missing UI payload data must remain distinct from an explicit server false.

## Source-backed gaps

1. **Chat's non-applied/unknown change wording overclaims review state.** `commands/run-flow.ts:150–176` reduces every readable adaptation to applied/not-applied and every unread adaptation to a fallback based on `answer.durableBehaviorChanged === true`. Thus rejected/disabled/reverted/superseded, held-back, missing-detail and genuinely pending cases all receive “waits for your review.” An unread record with unknown retention also receives that claim. Created/proposed changes are described as learned things even when none was kept. Existing tests explicitly expect this behavior for proposed/validated and unread cases; they do not cover rejected vs unknown distinctions. Typed retained patch/handler/re-author wording already works and should be preserved.

2. **Chat omits an authoritative durable change when no repair ID or explicit reauthor outcome accompanies it.** With durableBehaviorChanged true, no created IDs and no reauthored marker, `runLearned` has no entry and returns an empty sentence. With false and missing, the no-ID ending is identically silent. The normal endpoint usually supplies matching IDs/reauthor evidence, so this is an evidence-boundary gap, not a demonstrated live omission. A safe generic kept-change sentence may consume authoritative true; no kind should be guessed. Unknown must not be changed into none.

3. **Automations facts can override explicit no-change proof with current adaptation status.** `panel/automations/facts.ts:55–69` counts applied statuses whenever a detail map exists and computes futureRunsUpdated as durable true OR any applied status. The concrete input explicit durableBehaviorChanged false plus this run's ID currently reading applied produces learned 1/futureRunsUpdated true. This can arise after a later manual application; it is not proof that the run itself kept a change. Existing false tests omit the contradictory current status map. Where the server supplies the run's retained-state flag, that flag needs precedence for historical run attribution; current detail status can still explain later review/application separately. Unknown remains distinct rather than inferring from creation count.

4. **Automations pending copy does not identify unknown evidence.** With created IDs but incomplete/missing status proof, `summary-copy.ts:24` says Checking the change. Proposed, testing, validated and unread states are collapsed; explicit false plus a validated/unkept change can still read as ongoing checking after the run ended. This differs from Core web's explicit unknown/unkept post-run copy. Calling handlers and reauthor changes new page variations is also narrower than the actual capability; neutral kept-change wording would avoid inventing a page-specific kind.

5. **Core web's detailed metrics remain separate from its corrected post-run summary.** `RunDetailPanels.tsx:197` displays Durable yes only from `metrics.durableBehaviorChanged === true`, otherwise no, ignoring available summary.durableBehaviorChanged and treating missing as no. `run-detail-model.ts:32` likewise reads adaptiveMetrics for the durable story before considering created IDs. Raw adaptive metrics are derived from repair receipts and do not themselves include the separate kept-reauthor case; the summary does. A kept reauthor can therefore have a correct post-run message but an inconsistent detailed Durable metric/headline. This is a source-backed projection issue; no live screenshot is claimed.

The shared Run finished activity row is not, by itself, an inferred defect needing a broad event or persistence redesign. Normal Automations and chat already have richer response/thread projections. If future acceptance requires a detailed overlay ending too, its typed completion projection should reuse authoritative run-summary evidence, not duplicate promotion logic or infer from repair activity cards.
