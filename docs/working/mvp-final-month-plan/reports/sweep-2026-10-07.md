## What changed and why

### 1. Domain `recording/proposals/tests/record-output.test.ts`: a stale test (the code is right)

- **Failure:** "the rows one run keeps follow the request, held to Core's ceiling" expected `maxRecords` 200 for
  `maxItems: 200`, and got 1000.
- **Cause:** commit `3ac340bc` (t284, read-list S4+S5, worker s45-next-page) deliberately stopped deriving
  `maxRecords` from `maxItems`.
  - This follows `s45-next-page.md` §C3: "`maxRecords` is no longer set from `maxItems`". `maxItems` bounds every row
    the run collects, so dispatch declares it as `recordOutput.process.limit` (`output-nodes/extract-list/one-page-read.ts`).
  - `maxRecords` stays Core's default (1000) for one capture, which is one page's read.
  - The same commit updated the extract-list tests (`derived-record-output.test.ts`, `one-page-read.test.ts`), but
    not this test, which reaches the builder through the `recording/proposals` re-export.
- **Design note:** `read-list-collect-design.md` line 287 still reads "`maxRecords` (= `maxItems`) becomes a per-page
  cap". The later s45 decision (C3) superseded it, and the code and the other tests follow s45.
- **Fix:** I rewrote the test as "one capture keeps Core's default number of rows, whatever the request's maxItems".
  It asserts 1000 for no `maxItems`, for 200 and for 50,000, and that the builder adds no `process`, because that is
  dispatch's job. The routing of `maxItems` into `process.limit` is covered by
  `one-page-read.test.ts` ("dedupe, sort, maxItems and minItems leave the page…", and the reconciled-output case).

### 2. Core web `api/auth/login/tests/route.test.ts`: test timing plus a shared-state bleed (the code is right)

- **Alone:** 8/8 passed twice, in 13.6 s and 8.0 s. The whole-panel case took about 1.8 s.
- **In the full run** (`02-core-test.log`):
  - The 25-login cases took 5.5 to 7.5 s, about 250 ms per login against 18 ms alone.
  - The first whole-panel case (100 logins, so 600 locked read-modify-write cycles on disk) timed out at 60 s.
  - The second whole-panel case then failed with 429s before the 100th failure.
- **Cause, two parts:**
  1. **Timing.** 100 real logins through the durable store is too much disk work for a parallel suite on Windows.
  2. **Shared state.** vitest 2.1.9 does not stop a timed-out test body. The abandoned loop called the module-level
     `login()`, which reads the module-level `POST` that the next `beforeEach` had reassigned. So it kept adding
     failures to the next case's store, and called its shared `authenticate` mock.
- **Reproduced:** in a temporary copy, the first panel case was slowed by 100 ms per login and given a 5 s timeout.
  It failed exactly as the sweep did: case 1 timed out, and case 2 got `+ 429` entries before the end.
- **No regression:** the test last changed before 2026-10-01. `a466c972` (2026-10-01, the Windows EPERM lock retry
  in `lib/login-attempts.ts`) is the store's last change, and it adds retries only under contention, which a
  sequential case does not have.
- **Fix (test only):**
  - **`caseLogin()`.** Each case binds its login to the route module its `beforeEach` loaded. An `onTestFinished`
    hook refuses further logins once the case has ended, so an abandoned case can reach neither the next case's store
    nor its mocks.
  - **Seeded panel cases.** The whole-panel cases write 95 panel failures into the case's own store file, in the
    store's format (`{schemaVersion: 1, attempts: {panel: LoginAttemptState}}`). They then drive 5 failures through
    the route, each from its own address and username: the first 4 answer 401, the 5th 429, and a later correct
    login is still 429.
  - **Timeout.** The per-case `60_000` override is gone; the describe-level 60 s still applies.
- **Non-vacuity probe:** with the seed removed, both panel cases fail (`expected 401 to be 429`). So the seed is read,
  and a change to the store's format would fail this test rather than let it pass silently.
- **Isolation probe:** with the trusted case slowed (400 ms per login, 1 s timeout), it times out and the next case
  passes (1 failed, 7 passed, no unhandled rejection).

### 3. Downstream `pnpm -r --no-bail test`: one more stale fixture, in the extension

- **Run:** `pnpm.cmd -r --no-bail --workspace-concurrency=1 --filter '!@fluxiq-web-extension/domain' test` →
  `06-web-test-nobail.log`. Domain was excluded because it had already run in the sweep, with its 1 failure in item 1.
- **Packages that passed:**

  | boundary-audit | 6 |

  | test-contracts | 164 |
  | test-matrix | 17 |

- **Package that failed:** extension, 3 of 2558 tests, all in `content/extraction/tests/detect-pagination.test.ts`:
  - "a list with a pager above it and one below is named by the one above"
  - "a pager offering a labelled Next beside its numbers is proposed as Next"
  - "run muwansvz: …disabled text, is proposed as a list paged by Next"

  They also fail with the file run alone.
- **Cause:** commit `94f55df6` (t289, worker t289-fix-lab-process, "a 6,000-link page capture drops from 30.9 s to
  2.1 s").
  - It moved `selectorFor`'s `:nth-of-type` position (`selector/unique-selector.ts`) to `siblingPosition(element,
    element.parentNode, …)`, which reads the parent node's `children`.
  - The test page stand-in `extraction/tests/selector-page.ts` (`PageElement`) had `parentElement` and no
    `parentNode`. So every element looked alone, no `:nth-of-type` was written, and twin pagers and same-type
    siblings could no longer be told apart by selector.
  - A real DOM element always has `parentNode`, and the shadow-root case relies on it, so the product code is right
    and the stand-in was stale.
- **Fix:** `PageElement` gains `get parentNode()`, which returns `parentElement`. The root's is `null`, which the
  position reads as standing alone, as `html` does.
- **Other users of the stand-in:** `item-selector.test.ts` and `placeholder-run.test.ts` still pass.
- **`store-pager.ts` (`FakeElement`) was not changed:** it also lacks `parentNode`, but its tests use authored
  selectors and do not depend on `selectorFor`'s positions; all of them pass.
