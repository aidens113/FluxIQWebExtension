## 2026-10-27 Phase 0 findings (supervisor, read-only)

1. **The chat cannot attach a recording today.** The panel never sets `onScreen.recordingId` (thread-requests.ts sets
   only flowId/runId); the relay (`background/panel/conversation-relay.ts:149`) already forwards it to Core's
   `append-turn`; Core's `flow.createHere` (`runtime/conversations/commands/create-here.ts`) calls
   `save-flow-generation-instruction` without `linkedRecordingIds`. The panel never learns a stopped recording's id
   (stop reply is `{ok,status}`), and no panel code lists recordings although `fluxiq.listRecordings` exists in the
   background. So the chat attach step is in scope (units A and B below).
2. **How a linked recording reaches the model.** `service.ts:1521` reads linked recordings
   (`instruction-led/recordings.ts`) and every harness call of the build, project mode included (`runHarness`, passed
   to the project ports at :1585), carries them as `supplementaryRecordings`; the DeepSeek system prompt adds the
   "instructions outrank recordings" sentence when present.
3. **Finding for the lead (evidence is thin).** The projection the model sees is closed by design (t519): the
   recording's description plus a list of up to 100 output ids (action kinds such as a click or a select), with no
   targets, labels or values. A detour in the demonstration (a wrong sort then undone) is therefore visible to the
   model only as two extra action kinds. The no-detour-act oracle will hold almost by construction, so a pass proves
   the plumbing and that the description does not mislead, not that the model weighed a rich demonstration and
   rejected its detours. Enriching the projection (for example target labels, never typed values) is a Core
   model-facing and privacy change; not done here. See Open questions.
4. **Task choice** (accepted with exact oracle and zero-call replay in breadth-forty-tasks-plan, extraction only, so
   a demonstration leaves no lasting state): `crossborder-marketplace-free-hubs-under-ten`,
   `everything-store-coupon-earbuds-rated-four`, `job-board-remote-easy-apply`.
5. **Lab path.** Realistic live builds go through `run-lab` with `--instruction-task`, typing into the real chat
   (`run-scenario/chat-build/chat-entry.ts`, `flow-lane/creation/chat/`). The demo-workspace lanes the audit named use
   the Instructions library, not the chat, so the recorded-evidence lane belongs on the chat-build path instead.

## Open questions for the lead

1. **The evidence is thin (main finding).** The model sees only the recording's description and up to 100 action
   kinds, with no targets or values (t519's closed projection). A pass therefore proves the plumbing and that the
   description does not mislead. It does not prove that the model weighed the detours and rejected them.
   Recommendation: before the paid round, add the demonstrated controls' visible labels (never typed values or page
   data) to Core's projection, with a prompt-contract test, so the detours are actually visible to the model. That
   is a model-facing and privacy change, so it is the lead's or the user's call.
2. Core finalized the job-board recording at about one entry a second, so the lane now waits up to 300 s. Worth a
   Core look before paid runs.
3. Core's recordings list for the panel is not project-scoped (the newest 100 for the whole domain; the panel filters
   by project). A `projectId` filter in Core would close the gap.
4. If the chat model routes a message with an attachment to any command other than `flow.createHere` (or through the
   confirmed-ask path), the attachment is silently ignored. Acceptable for the MVP proof; noted.
5. A cheaper end-to-end check is possible but was not built: a provider-free chat send whose words-only reading picks
   create-here would show the attachment reaching the saved instruction without a model call.
