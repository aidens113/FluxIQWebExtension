## Finding and contract

t527 already removed worker-side row continuation. Preserve its Next-page transport; do not recreate or rediscover that work. The content reader still contains its paginating loop and checkpoint sender, while normal domain Flow dispatch refuses raw multipage requests and strips accepted one-page legacy paging. The remaining removal is a synchronized reader/public request/detection/compatibility unit, followed by browser-spec migration.

Detection metadata currently has an executable-read type dependency: `WebAutomationExtractionProposal.pagination` uses `WebAutomationExtractListPagination`; `extraction/structure-detection.ts` validates it by synthesizing an extraction request with `paginate`; `structure/packet.ts` stores it in `binding.extractList.paginate`; `plan-resolution/next-page-slot.ts` then reads that field to build the actual Next-page request. Removing the field from reads alone would erase Next-page binding. Move its capability first to a distinct bound way using the existing `WebAutomationNextPageWay` union, which already expresses next/loadMore/scroll/numbered without bounds.

Recommended new executable read shape has no `paginate`, page bound or carried checkpoint. New proposal/detection may retain the outward field name `pagination` but its value is a movement way, not a read request. The internal handle binding holds `extractList` (one-page read) and a separate `nextPage`/movement field owned by the structure boundary. Next-page resolver uses that field and keeps list item/fingerprint/frame identity; ownership, stale handles and control override checks remain unchanged. A detected absent way and a malformed present way remain distinct. Infinite-scroll signal continues to bind a scroll movement way; a lazy tail on a finite results page remains this page's completion work, not a new scroll page.

## Legacy boundary: explicit and raw first

Current `webAutomationExtractListPagesBeyondOne` only detects object scroll/maxScrolls or numeric maxPages>1; malformed/missing/wrongly typed values can instead be dropped by forgiving parsing. Do not silently broaden that into acceptance when retiring the parser. Define a closed compatibility outcome: absent; valid historical one-page; explicit beyond-one; malformed/ambiguous. Inspect the original raw value at both Flow preflight/dispatch and direct content action entry before unknown-key stripping.

- Recognized old next/loadMore/numbered with numeric integer maxPages exactly1 and valid own control fields can normalize to a current one-page read. Preserve frame/field/sensitivity/dataset facts; never execute the control. This keeps old picker evidence usable.
- Numeric maxPages>1, any scroll mode or any maxScrolls retains closed `web.extract_list.paginate_retired` and actionable Read → Next page → Repeat direction, even when another field is invalid.
- A present malformed value (unknown mode, null/array/scalar, missing/fractional/nonfinite/wrongly typed bound, missing required control, foreign mode key) is rejected as invalid/retired request, not dropped into successful one-page output. Agree exact closed code with the supervisor before source work; existing code need not be renamed to obtain this guarantee. The direct content boundary must return a classified failure rather than an unstructured success or leaking page data.
- New schema/catalog never offers paging; no graph synthesis, task synthesis or automatic multi-node migration. New authoring literal paginate retains the existing plan-resolution refusal and direction.
- Historical recorded definition decoder remains field-by-field and strict, with no unknown/sample values copied. A historical multipage definition may remain inspectable as legacy evidence only through an explicit nonexecutable compatibility shape/diagnostic; it must not masquerade as a current executable one-page request. If preserving its exact diagnostic requires a tagged compatibility result beyond the existing undefined return, brief that precise API expansion first. Existing recordings are supplemental, not execution authority.
- Historical run summary with multiple pages/stop words remains readable as historical evidence; current one-page outcome never claims those historical pages or invents list-end proof. No Core read-account/promotion changes in this unit; coordinate a separate historical summary isolation brief if removing an export would affect Core consumers.

The open compatibility decision is whether existing exported legacy pagination aliases remain deprecated during this release or are removed in a synchronized public version. Recommend retain alias only in explicit compatibility exports while the current read contract omits it; callers migrate to existing NextPageWay. No ambiguous malformed bound becomes a successful read.
