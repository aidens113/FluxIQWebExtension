# Original-project accepted authority cutover review

Status: concrete proposal; report only, not implementation, activation, or proof. Worker: p0_cancel_control. Date: 2026-10-07. Main Core/downstream source inspection only. No source/build/test/browser/provider/panel/git operations. The previous reserved `asql` namespace/new-project-only proposal remains unapproved and does not meet the original-project requirement.

## Recommended boundary

Explicitly adopt an existing supported project under its **original project, Flow, graph, router, subflow, instruction, binding, category and policy IDs**. Preserve original records, user files and history. Reuse t309's complete canonical-plus-resource snapshot representation and immutable project-SQL head/history; introduce no second graph schema. An auxiliary durable writer/adoption protocol is necessary because current authority spans project SQL, global canonical repositories and files.

The coherent activation unit is: all official writer fencing + trustworthy capture + atomic original-project adoption + pinned actual production reads + generation-bound normal execution + one transactional candidate acceptance owner. Foundation slices may land earlier, but none independently enables adoption or qualifies candidate acceptance. A new-project namespace must not substitute for this unit.

Initial supported scope can explicitly exclude code/JSON-owned, publication-dependent, cross-project/global-source and unresolved native dependencies, while accepting eligible existing local visual projects with complete Router/Subflow topology. The request must fail with the actual unsupported join; it cannot create a replacement project, renumber resources, silently ignore dependencies, or turn missing material into an empty accepted graph.

## Durable legacy-mutation guard

Proposed focused project-SQL owner: `storage/project/authority-guard/` with contracts, migration, store and barrel. The schema is coordination metadata, not graph representation. Store a project mode/revision row (`legacy`, `capturing`, `active`, `tombstoned`) and durable mutation claims carrying original project ID, protocol generation, operation/owner identities, request digest, status and result/evidence digest. Maintain a monotonic completed legacy revision. Exact numbered migration is allocated against current migrations at implementation time.

1. Every official legacy mutation acquires a claim in a short `BEGIN IMMEDIATE` transaction **before its first possible effect**. It compares project mode/protocol and atomically rejects capture/active/tombstone. Initially serialize topology mutations per project to avoid nested multi-store interleaving; an opaque ownership token lets nested helpers join the same claim rather than deadlock or create independently completed subclaims.
2. Commit the claim before file/global work begins. On normal completion, attest the full operation's observed resulting inventory, then complete the claim and increment legacy revision in another transaction. Only the owning wrapper can complete it. A helper returning early or swallowing an SQL failure is not full completion.
3. Any throw after possible effects, interruption, lost completion acknowledgement or failed reconciliation leaves pending/unknown. Conservative pending is already an adoption blocker. Do not auto-release in `finally`, by timeout, PID disappearance, lease expiry or elapsed time; none proves file/global effects stopped or a coherent result exists. A trusted reconciliation adapter must inspect and settle the exact operation, or adoption remains unavailable.
4. Adoption's transition `legacy -> capturing` is in the **same project transaction** that checks all claim states and compares the full completed revision. An earlier claimed writer prevents transition until it finishes; a later writer cannot claim. Hold the capturing mode during inventory/validation, without holding a SQL transaction across IO/compiler calls. Revalidate the capture token and revision in final commit. Aborted capture may return to legacy only when the capture itself performed no legacy mutation and no unresolved work remains.
5. A crash in capture leaves capturing/unknown; restart does not infer authority from files or install a fresh epoch. Reconcile the recorded adoption key/capture proof. A committed activation followed by lost acknowledgement replays the exact recorded binding without recapture or native replay.

This handles a writer beginning before adoption **only if it acquired the guard before effects**. Newly added SQL cannot stop an already running older binary, exported legacy object, external script or arbitrary file/SQL access that ignores the protocol. The one-time deployment gate must drain official uninstrumented processes/jobs and instantiate guarded owners before adoption becomes available; no panel management is authorized by this report. An operator assertion or database marker alone is not evidence that an old writer cannot finish. If this closed official-writer deployment cannot be established, original-project adoption remains blocked. After deployment, persistent claims provide normal cross-process operation rather than a recurring maintenance-only freeze.

All protocol-aware ingress must fail closed on unavailable guard storage. A missing mode row may initialize legacy only through authorized project admission; a reader must never create a missing project database as a fallback. Memory-only or arbitrary injected repository environments cannot promise durable adoption; refuse adoption there while preserving documented ordinary legacy behavior.

## Global writers, membership and deletion races

The project claim alone does not cover canonical mutations whose true project owner is unknown or dishonest. At canonical official ingress, use the original resource ID and existing durable ownership, not the supplied replacement's projectId. A missing canonical row after deletion cannot make an adopted resource writable by another project. Retain an ownership/tombstone association for global resource IDs through removal; serialize lookup and ownership changes under the canonical repository's own transaction/claim. Wrap service-injected repositories at the official boundary, and protect the default exported factories when they can mutate the same storage independently. Resource-owner remapping/rehome across projects is unsupported in the first cutover.

This stable routing requires a small canonical-owner companion protocol in the global canonical storage owner, **not** a second project/graph authority. Its exact persistence placement must be approved alongside repository owners before implementation: default SQLite can atomically store canonical resource-to-project claims/associations; an arbitrary custom repository with no equivalent atomic owner interface must refuse adoption. Never assume separate project SQL transactions atomically fence an uncooperative global repository. Global resource claim precedes project claim in a fixed order; multiple resource/project claims are sorted and partial acquisition is released only before effects. Adoption must freeze/verify the relevant resource ownership alongside the project capture token; crash leaves any held claims unresolved until trusted reconciliation.

Capture does not require global publications to become supported. It requires same-project canonical Flow resources to participate; publication/version/deprecation and external global dependencies remain explicitly unsupported. Guard a global publication write that targets a capturing/adopted project even when that operation is otherwise unsupported. Entirely unrelated projects must not be silently blocked, but a shared index batch must declare every affected project and acquire sorted claims. Read/modify/write of a stale whole project index cannot overwrite adopted discovery/manifest rows under the guise of editing another project.

Physical delete/removal is a special unsupported legacy operation during capture/active mode. Active deletion becomes an authority tombstone that retains the project database and original ID/history. Shared project discovery must retain durable active/tombstoned routing independent of stale index projections. Generation-tagged projection jobs may update compatibility index entries, but old legacy remove/recreate/seeding cannot erase authority or create a new database with the same original ID. If the existing discovery/index owner cannot provide that stable routing yet, activation is unavailable; directory presence alone is not existence proof.

## Trustworthy capture and original-ID activation

A new `runtime/service/project-authority/capture.ts` acquires the guard's capturing token and inventories **all** authoritative inputs without calling mutating load/ensure/materialize helpers. Read full project record, hierarchy/workspace, complete canonical Flow membership and real graph nodes/edges/partitions, ordered routers/groups/routes/fallbacks/subflows, all instruction bodies/scopes/status/priority/bindings, actual interpreted settings, categories/policies and file/index membership. Exhaust paging; no first100 truncation or maxRevision-only membership proof.

Record a canonical digest of exact file contents and complete sorted membership with absent entries represented explicitly, relevant index/global rows and per-resource revisions. Stat/mtime alone is insufficient. Read instruction bodies from original documents; compare SQL projections using the current representation rules. Preserve user IDs, ordering and timestamps; rebuild disposable compiled projections only through their owners. Re-run full enumeration/digests before final commit while the capture token and global resource guard remain held. Protocol writers are blocked throughout; this second observation detects contradictory inputs, not arbitrary hostile filesystem mutation.

Do not repair missing graphs as a side effect of capture. If an existing canonical document lacks a graph projection, either (a) deterministically derive a capture-only resource representation through the normal compiler with a declared validated mapping and commit it as part of the captured original topology, or (b) refuse `authority.missing_graph_projection`. Initial implementation should choose (b) until the derivation owner is explicitly included. Conflicting SQL/document graph, missing router graph owner, orphan/unlisted source, unsupported compiler transformation or ambiguous binding refuses and leaves original data intact.

Use actual loaded registry/normalizer/compiler and ordinary permission/scope checks, not supplied provenance strings. Known publication dependencies, code/JSON/global/cross-project sources, dynamic unresolved Call Flow targets, unknown native dependency declarations and category/hierarchy references outside captured ownership refuse. A dependencyScope caller literal `none` is not inspection. The foundation validator's explicit declarations alone cannot authorize original adoption.

Final activation uses transaction-bound primitives factored from accepted-state/store.ts: compare capture token/revision/resource-owner seal; insert the complete immutable snapshot under original projectId and a new adoption epoch; update accepted head and production-mode/binding pointer; commit durable adoption response/change feed/projection intent together with `context.sql`. Keep staged history intact. Do not sequentially stage then activate; an existing staged head is not production ownership and cannot be overwritten without its validated expected binding. Public staged mutations must acquire the legacy guard and refuse capture/active scopes, including previously opened staged stores.

Production state is a separate trusted marker/binding over the existing snapshot/head, not a new graph payload or a caller edit of `productionAuthority`. Normal complete-replacement CAS preserves original IDs/epoch, increments generation and validates compiler/settings/source/membership. Use existing file outbox through transaction-bound operations; add a narrow generation-bound companion intent for canonical/index projections where the current outbox fields are insufficient. No old projection becomes acceptance input or writes an accepted head. Native-effect uncertain claims also prevent incompatible authority edits/activation; execution freshness callbacks alone are not atomic dispatch fences.

## Pinned actual readers and execution

A focused `runtime/service/project-authority/view.ts` returns one immutable `{projectId, epoch, generation, digest}` view with full source/settings/membership and exact project record. A single-object request may acquire a fresh view. Multi-object instruction/dependency construction, graph API response, candidate execution and normal runtime admission must explicitly share one view; independent facade rereads can mix generations even when every individual read is SQL-backed.

Join original-ID active reads at `flows/store.ts`, `projects/store.ts`, `summaries/{store,sql-paging}.ts`, `indexes/store.ts`, `catalogue.ts`, and facade getFlow/router/subflow/full instruction set/settings/execution digest/graph viewport/binding/project hierarchy/discovery. Empty accepted membership stays empty. No file cache miss, summary repair, publication-history synthesis, global repository fallback or caller-supplied Flow can supply active topology. Public low-level readers of legacy graph/resource projection return explicit unsupported for adopted scope until routed to a pinned view.

`startRuntimeSession` must branch into authority before its catch-and-legacy-artifact fallback. `runRuntimeSession` parent/router/subflow/materialization/adaptation instruction/settings reads must consume the pinned view through a focused execution collaborator while reusing normal compiler/executor/permissions/consequences/cancellation. Read SQL settings as effective settings, not a diagnostic revision counter. Dispatch admission and mutation are serialized using durable claims, with exact generation compare inside SQL; do not hold transactions across browser actions. Unknown action completion remains unknown and blocks automatic replay. Legacy adaptive/recording/proposal/migration authoring can initially refuse adopted projects; candidate acceptance routes the exact original-project base binding and complete detached topology through the common gate only after its other interpreter/start/oracle/acknowledgement joins exist.

## Smallest coherent first implementation partition

Implement **durable original-project mutation/capture admission infrastructure with activation unavailable**:

- New `storage/project/authority-guard/{contracts,migration,validation,store,index}.ts` and owning tests: original IDs, short committed claim-before-effects, full-operation completion, unknown retention, monotonic revision, atomic beginCapture/CAS/reconcile and closed protocol envelopes.
- Add only the owning `storage/project/index.ts` export. Reuse current `database.ts`/UoW direct transaction primitives without broad changes; the guard must write its durable pre-effect claim in a committed transaction separate from the external operation. If storage budgets require extraction, request that exact owner before editing.
- Own downstream report and one scoped Core persistence architecture paragraph assigned by supervisor. No namespace, endpoint, automatic migration/adoption, service/UI flag, global repository wrapper, staged activation, or user-data mutation in this first partition.

This unit proves coordination behavior in real SQLite for existing original IDs; it does **not** claim all writers are covered. Tests use explicit wrapper calls and separate pools/processes: pending writer blocks capture; completed writer invalidates old revision; capture prevents a later claim; killed process after external sentinel write leaves durable pending/unknown; lost completion/activation acknowledgement reconciles exact key; no lease expiry clears unknown. The wrapper can be exercised around a synthetic multi-step legacy operation, with honest limits. Do not mistake that proof for actual official writer instrumentation.

Next serial work instruments SQL/global resource ownership and actual file/facade writers, then capture/view, then actual execution/acceptance. Shared service.ts wiring is serial. The first globally callable adoption endpoint remains absent until the combined gate below. This is smaller and safer to dispatch than inventing a reserved namespace, and directly supports the original-project requirement.

## Activation gate and honest unsupported joins

Supervisor must independently verify: all official ingress wrappers and nested/private/bypass operations; actual default SQLite and injected-compatible canonical owner routing; legacy writer delayed across beginCapture; wrong/absent global owner lookup; physical delete/recreate and cross-project forged resource IDs; two processes; literal kill before/after external writes and final commit; complete >100 membership plus source/settings edits; stale/cold/warm projections; and real normal execution from a single pinned original-ID view. No timestamp-only race test or observer marker substitutes for these checks.

One surviving official legacy writer blocks activation. Old uninstrumented processes must be drained through separately authorized operations before deployment qualification. Interrupted claims stay unresolved until trusted reconciliation. Missing/contradictory original graph/source/settings, uncooperative custom repositories, mutable publication/global/cross-project dependencies, unknown registry/native dependency interpretation, unsupported policy revocation atomicity, absent stable discovery/tombstone routing, and unjoined command/outbox outcomes all refuse explicitly. Candidate interpreter/start/reset/private oracle/trusted execution acknowledgement and common promotion gate remain independent prerequisites. Receipt/snapshot consistency alone cannot qualify them.

No source edits or executable validation were performed in this report. Exact canonical-owner companion storage and permission-revision fence require supervisor architecture approval before implementation; arbitrary external file/raw SQL mutation and SQL tamper resistance are outside this official API protocol. The design preserves original IDs/data and states where activation remains unavailable rather than substituting a new project.
