# P2 durable candidate promotion design investigation

Status: design proposal; production promotion remains unavailable. Worker: p0_acceptance. Date: 2026-10-06. Scope: read-only investigation in frozen paired t299 trees; only this report changed. No source, shared documents, providers, live runs, suites, or git mutations.

## Result

A transaction around the existing bootstrap apply method would not make promotion atomic. Accepted topology currently crosses multiple SQLite databases and JSON/generated files, and its readers combine those owners. A bounded receipt ledger is implementable independently; production promotion additionally requires an explicit authoritative accepted topology and transactional comparison of every mutable acceptance input. Do not wire an accepting promotion port until those prerequisites are implemented and tested.

Recommended sequence: durable receipt/run ledger and fail-closed preparation first; project-SQL transactional accepted topology and reader integration next; production interpreter/start/oracle/domain acknowledgement adapters separately. These are distinct tasks, not evidence that the current candidate can be accepted. JSON mode must remain draft-only until a real recoverable storage authority exists. The brief's real JSON tests should verify that refusal, unless the supervisor explicitly expands scope to implement JSON durability.

## Inspected current behavior

Core paths below are relative to `packages/fluxiq/src/programs/automation-studio/` unless stated otherwise.

- `runtime/service.ts:1801`, `:3445`: review holds a process-local bootstrap adaptation lock. Apply requires validated status, re-reads the permission ask, verifies bootstrap target/representation, dependency digest, recording restrictions, resolved handles, canonical compiler validation and exact normalized topology. It then saves each graph Flow, graph index, subflow, router, parent metadata, adaptation status and change feed sequentially. Catch compensation deletes newly created graph/subflow/router state and restores parent metadata. A process crash bypasses compensation. Extend mode needs special care: accepted prior topology cannot be restored merely by deleting newly written identifiers; existing revert refuses extend without saved before-graph state.
- `runtime/service/locks.ts`: generation, adaptation and recording have separate in-memory queues. They do not provide cross-process ownership, a durable commit or a generation/apply CAS.
- `runtime/service/bootstrap-adaptations.ts`: memory cache is updated before durable save. A failed write can leave cached status ahead of storage. A promotion path must not use cache as authority.
- `runtime/service/flows/writer.ts`: normal writer preserves project/scope ownership, expectedUpdatedAt, representation/publication/source-mode validation and compiler metadata, but writes global Flow repository, project document/index, canonical project graph, generated source/config, SQL metadata and change feed separately. The project database hold is a lease-lifetime mechanism, not an enclosing transaction.
- `runtime/service/flows/mutations.ts`: router writes document, SQL projection and summary index separately; subflow writes SQL, document and summary/index separately. Existing public methods must not be called from inside a project DB transaction and assumed to enlist: they acquire their own owners/queued transactions.
- `runtime/service/flows/store.ts:86`: Flow reads global repository/document then overlays project SQL graph nodes/edges. Router reads ProgramJsonStore. Subflow prefers ProgramJsonStore then SQL fallback. Metadata/summary APIs also read SQL projections and independent indexes. Thus committing only project SQL graph rows does not publish a coherent accepted Flow today.
- `runtime/service.ts:1315`: dependency digest includes parent, router, all paginated subflows, graphs, instructions, graph revisions and publication dependency state. A SQL graph revision check alone is weaker than the existing dependency check.
- `runtime/service/candidate-drafts/{record,store}.ts`: latest draft per Flow carries candidateId, canonical candidate revision/digest/base, original instruction text/IDs, baseSettingsRevision and accounting. Store accepts only draft/not_performed. Cached draft reads are insufficient for promotion freshness. No durable verification ledger, start claim, permission binding or promotion record exists.
- `runtime/service/flow-bootstrap-commands/permission-hold.ts`: normal apply follows the stored permission request to the actual conversation ask and demands its granted answer. Neither model-supplied permission nor a copied answer is equivalent. New candidate verification must retain trusted permission/consequence bindings; the current draft record does not retain a permission-request join for later promotion.
- `storage/project/database.ts:280`: real per-project SQLite transaction uses BEGIN IMMEDIATE/COMMIT/ROLLBACK. WAL synchronous NORMAL is not a proof of power-loss durability; test process-crash/reopen semantics and distinguish power loss guarantees.
- `storage/project/unit-of-work.ts`: real idempotent mutation record and change feed can share one SQL transaction. Request digest mismatch refuses replay; committed response replays; started/failed does not blindly retry. Its generic failure recording is unsuitable as proof that an uncertain COMMIT failed: reconciliation must first inspect durable committed state.
- `storage/project/adaptation-store.ts:180`: existing graph-patch adaptation path checks normal policy/gates/base, then commits graph patch separately from compiled/rollback/status/audit writes. Reusable validation concepts, not a ready-made atomic bootstrap topology transaction.
- `storage/project/graph-store.ts`: graph repository owns graph revision import/patch semantics, but its public patch uses its own unit of work. A promoted topology needs transaction-bound graph primitives rather than nested calls into this method.
- `programs/_shared/storage.ts` (outside automation-studio): ProgramJsonStore JSON uses per-file process lock plus temp write/rename; no multi-document journal/transaction/fsync guarantee. Its transaction API refuses non-layout-v2 storage and enforces one root/kind. Layout-v2 automation.state/program.state documents and project graph DB remain different owners. Ordinary writes do not automatically enlist in ProgramDocumentTransaction.
- `programs/database-manager/storage/sqlite-repository.ts`: repository transactions serialize one SQLite database path. They cannot make separate project DB writes or generated files part of that commit.

## Durable contract and trusted issuance

New internal ledger should retain immutable, bounded records keyed by project/flow/candidateId/revision, with payload digest and schema/version. Full receipts are internal; outward status carries IDs/digests and bounded summaries. Reject malformed/corrupt/mismatched persisted data rather than defaulting it to successful or absent.

Binding must include candidateId, candidate revision/digest, accepted dependency digest and explicit revision vector, base settings revision, original instruction text digest and instruction IDs/revisions/source spans, requirements digest, selected interpretation/version, compiler/registry/normalizer versions, owning scope/project/Flow identity, trusted permission/consequence bindings and actor/policy context. The original free-text request is immutable input; stored instructions additionally require comparison against current source revisions. No model may replace an explicit add/create instruction with ensure to satisfy a predicate.

The t300 verification identity currently omits candidateId and settings/instruction-source joins. Preserve its neutral evidence contract and add a durable envelope around it, with exact join validation at every stage. A plain packet.source string or accepting receipt JSON supplied through API/build tools must never mint trusted receipts. The internal orchestrator passes observer-produced receipts directly to a private issuance port; persisted records record issuer/version/provenance and integrity digests. This does not promise protection against a person editing local storage; no public acceptance/receipt issuance input is introduced.

Persist distinct requirement, start, execution and observation records with complete identity/run/start references. Quantified scope must be owned by the brief/interpreter or trusted enumeration, not a model-chosen subset. Commands/effects and outcome checks stay separate. Existing detached execution returns truthful empty command receipts; it cannot prove create. Domain acknowledgements and start reset remain unimplemented. Unsupported comparison/order/numeric interpretation and incomplete requirements remain unknown/refused.

Before invoking a start adapter or detached executor, commit a bounded `pending` attempt claim. Once claimed, a restart or duplicate must not automatically reset or execute it again. Record command execution and observation results as separate stages. Crash after side effects but before receipt persistence produces `outcome_unknown`; explicit reconciliation may recover trusted facts, but must not manufacture them from intent or rerun an irreversible action.

## Proposed ownership, staged before dispatch

First bounded unit, no accepting promoter:

- New `storage/project/candidate-verification/{contracts,migration,store,index}.ts` and owning `tests/`: project-SQL immutable candidate binding/receipt/run-claim/promotion-intent rows, bounded IDs/digests, insert-if-absent claims, strict read and reconciliation. Register only the focused migration/export needed by its opener, following existing project migration conventions.
- New `runtime/flow-bootstrap/verification/durable-session.ts` and owning test/barrel: trusted issuance/receipt persistence and run-claim orchestration around existing controller. Expose a fresh authoritative binding reader, never caller-provided acceptance. Current controller is edited only if a narrowly typed stage persistence hook is necessary; enumerate that ownership in the next brief.
- Narrow `runtime/service/candidate-drafts/store.ts` hook: uncached authoritative read for draft lookup, plus immutable copy into ledger before run claim. Reading a cached/latest draft remains normal UX behavior; it is not a promotion CAS.
- Real JSON/SQLite fixture tests: JSON promotion preparation explicitly unavailable; SQLite ledger restart, corrupt joins, duplicate/conflicting claim and uncertainty tests. No accepted graph changes.

Second unit, accepting promoter only after authority design is approved:

- New `runtime/service/candidate-promotion/{prepare,promote,reconcile,index}.ts` with owning tests: normal permission/policy/target/compiler validation, exact binding preparation, trusted receipt lookup and transaction invocation. Facade is a small call into this owner, preserving service budget.
- New `storage/project/candidate-promotion/{contracts,transaction,projection,index}.ts` and owning tests: one transaction-bound accepted-topology write, parent metadata/settings/instruction/version CAS, graph/router/subflow rows, promotion result, touched entities/change feed and projection outbox. No existing sequential apply reuse as commit.
- Narrow transaction-bound hooks owned in `storage/project/graph-store.ts` and `storage/project/flow-resource-repository.ts`: reuse graph invariants/mapping/revision creation without opening nested transactions. If their budgets require extraction, use cohesive subdirectories and move owning tests with the subject.
- Narrow authoritative-reader integration in `runtime/service/flows/store.ts`, relevant summary/index owners and execution/dependency read seam: accepted parent document/settings, router, subflows and graph must come from the same committed generation. Generated/global document projections must not override that generation. Exact additional summary/read files require investigation before dispatch; do not claim this is an already bounded two-file hook.
- Existing normal writer/policy/permission owners may need a focused extraction to share validation; preserve existing behavior and tests. Ordinary edits/settings/instructions/publication changes must participate in the same transactional authority/revision protocol or promotion must refuse those unsupported mutable dependencies.

This second unit has a real architectural prerequisite: current mutable accepted documents, instructions/settings and publication dependencies are not all transaction-owned in the project SQL database. An outer lease or preflight digest comparison does not close that race. Do not silently narrow the digest to graph revision. Choose authoritative migration/revision participation before writing an accepting port. A transaction that stores a promoted snapshot without synchronizing competing ordinary writers is also insufficient.

The publication mutation owner and all instruction deletion/update routes still need a bounded ownership discovery brief. Until identified and joined, accepting promotion must refuse that unsupported dependency scope. This is an explicit remaining design gap, not permission to omit it from the CAS.

JSON support is a separate storage design: one authoritative immutable-generation manifest with a recoverable journal and cross-process writer participation, or explicit migration to supported transactional storage. Per-file rename/compensation cannot satisfy the required atomic multi-owner CAS. Recommendation is explicit unsupported promotion for JSON in the first implementation; no automatic migration or data reset.

## Commit and recovery semantics

1. Prepare normal permission/policy/representation/registry/compiler checks and trusted receipt lookup; retain exact versions/results. Read authoritative originals and dependencies. Refuse missing interpreter/start/oracle/domain acknowledgements.
2. Begin transaction on the chosen single authoritative project storage owner. Compare latest candidate identity, all receipt joins, original instruction/source bindings, accepted base/settings/dependency revision vector and authorization binding. Cancellation checkpoint before durable mutation. If a comparison cannot be made under this owner, refuse promotion.
3. Derive deterministic bounded promotion key from complete binding, not run alone. Same key plus different request digest conflicts. Committed same key returns original accepted generation/result before checking a now-changed base; that base changed precisely because this promotion may already have committed.
4. Commit accepted topology, parent metadata, receipt acceptance/promotion result, change feed and projection outbox together. Create mode collision refuses. Extend mode needs retained prior generation/full inverse; do not delete old entities as recovery.
5. Generated source/config, global repository and JSON/index mirrors are recoverable projections from the committed generation. Reader/executor authority must not depend on a successfully completed mirror. Failure after commit retains committed result plus projection-pending status. Reconcile projections idempotently; never re-execute the detached Flow.
6. Lost COMMIT acknowledgement returns outcome_unknown while retaining its key. Reopen/re-read durable promotion record: committed means return the original result; proven rolled-back/no committed row allows a new *promotion-only* attempt after fresh validation, without rerunning execution. Storage unavailable remains unknown. Never label committed topology a cancelled/unapplied failure because a later signal or projection write failed.

## Required focused negative/real-storage checks

- Wrong project/Flow/candidate/run/start origin; superseded revision/digest; instruction text/source ID/source-span/settings change; changed accepted dependency/publication; stale host generation; conflicting enumeration or two required subjects with one observed; partial list and withheld command acknowledgement; fabricated builder/API success; unknown semantic mapper; explicit create existing-result/add-delta limitation.
- Permission ask missing/denied/revoked or reader error; person/policy changes; normal native authorization unchanged; registry/compiler/representation/version mismatch; normalization rewrite; duplicate IDs/ownership mismatch; target graph publication/extend rules.
- Real SQLite concurrent identical promotions yield one generation/change-feed group/result; same key altered binding refuses; competing ordinary graph/settings/source edit forces one winner; duplicate after accepted base changes returns committed result without new graph revision.
- Inject before each transactional write and immediately before COMMIT: no accepted partial topology on reopened DB. Inject after COMMIT/before response and during projections: reconciliation returns same result, no duplicate graph revisions, no action rerun. Reader/executor sees coherent old or new generation only.
- Real JSON draft/start receipt storage and unsupported promotion refusal preserve accepted files byte-for-byte. If JSON support is later implemented, repeat crash/concurrency checks against its real journal implementation rather than an in-memory store.
- Restart after pending start/run claim does not replay irreversible actions. Empty detached command receipts remain empty; no create promotion until trusted dispatcher acknowledgements exist.
