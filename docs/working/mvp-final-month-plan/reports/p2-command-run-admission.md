### Ticket authority and lifecycle

Introduce one nominal opaque outcome ticket, authenticated by private registration rather than constructor, prototype, copied JSON or supplied fields. Registration joins original command-run scope, its retained incarnation/root-session fingerprint, authentic per-effect gateway context, actual executor-entered graph/node invocation, original ordinal, complete frozen claim/request/client/session binding, exact actual committed receipt and the parsed frozen live acknowledgement. Do not serialize the ticket into command/result JSON, traces, metadata, saved attempts, evidence packets or domain outputs. Keep the live-result association in a server-only side channel; discard it on close. The ticket attests receipt accounting and live-result handling, not independent performed-subject or semantic outcome truth.

Only the trusted gateway post-COMMIT path can issue/register an outcome. Proposed generic leased resolver adds an internal observeCommittedOutcome callback, closed over the program run owner; dispatch invokes it only after existing controller returns completed with a matching re-read receipt and its exact parsed live result. Callback validates authentic effect context and privately reserved claim, re-reads the ledger and verifies the complete immutable receipt/result digest join before registering a ticket. It receives no model-selected consumed list and cannot be invoked through any remote API. Supplied receipt/result JSON or a builder success return cannot register a ticket. Storage still imports no runtime code.

Only the actual executor's private invocation port can consume that registered ticket. Mint an invocation UUID at executeNodeAttempt entry, once for that real entry, reused through native implementation and its returned effects. Legitimate node retries/loop entries/child retries get new UUIDs; record trace attempt IDs and existing child attempt paths remain compatible and do not establish uniqueness. The scope remains the original project/run/root owner; actual selected or published child graph identity/digest and parent-call lineage are separate registered invocation facts, never inferred from root flowId or model metadata. Child scope issuance must follow the actual router/composite-selected canonical document and existing compiler/permission gates; arbitrary child IDs refuse.

State machine: admitted → private effect issued/claim pending → matching committed live outcome → executor handling/capture complete → consumed. Unknown, receipt-only result_unavailable, conflicting/unregistered result, unaccounted issued context, escaped timeout/cancellation, failed capture or uncertain journal operation latches a terminal continuation block. A late truthful receipt can reconcile the exact claim but cannot clear this block. Each issued context/ticket is single-use; duplicate consumption, wrong invocation/ordinal/scope/incarnation/result and copied tickets refuse. No public consume(flag), consume(receiptJSON), successful model field or clearBlock method exists.

Actual per-effect consumption occurs in node-execution only after the awaited trusted dispatch result is checked, withCapturedRecords/record-output parsing and configured persistence complete, and that result's outputs/status/failure/declared route have merged into the node result. This point allows a next distinct effect in the same node without repeating the first effect. Before graph-run copies the attempt into values or publishes outputs/asks/routes, it checks that all issued effects of this invocation are accounted for; it checks again before leaving the node. Capture failure must retain unconsumed ticket/stop, not authorize retry of the already acknowledged action. An implementation/model returning success without a registered outcome never substitutes for this handling point. State mutation by arbitrary trusted Code/native implementations outside registered gateway effects remains unsupported for receipt-required execution; refuse before execution unless an approved owner supplies equivalent authoritative handling.

Storage continuation, if enabled later, takes only storage-owned opaque clearance issued by an injected trusted owner after this registered consume transition. Each atomically checked clearance is bound to exact original claim+receipt/request/client/session and the same in-process incarnation; callers cannot select subsets or arrays. claimForRun's UoW admission hook revalidates full history and accepts only complete privately consumed prior receipts of that incarnation, in the same transaction as the new claim/proof. Any pending/unknown/historical uncertainty or unmatched committed prior command refuses. A reconstructed scope has no durable consumed-result association and still refuses ANY prior claim, including committed ones. No restart consumption is inferred from a fresh connection or receipt status. Persisted consumption/result association would be a separate storage design, not part of this ticket slice.
