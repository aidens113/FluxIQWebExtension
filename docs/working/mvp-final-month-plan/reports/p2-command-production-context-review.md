# Durable command production context review

Status: review complete; implementation proposed, not implemented or verified. Worker inspected the frozen paired t313 Core/downstream sources on 2026-10-07. Only this report changed. No builds, tests, browser/panel operations, provider calls, generated edits, or git mutations. Supervisor verification of the ledger remains independent.

## Decision

Enable the existing generic ledger through a trusted, non-JSON command context carried on **both** policy-output paths. Mint ownership from the actual Automation Studio session and actual executor invocation; never from action metadata, client payloads, model-supplied IDs, or the generic RuntimeService's unrelated run map. Commit a matching receipt before exposing an authoritative result. Unknown delivery or missing reconstructed results must stop routing and every automatic retry/resume, not merely set a failure's `retryable` flag.

This is a serial Core/downstream production-integration unit, not an infrastructure-only gateway patch. Keep Core domain-neutral and preserve the existing wire schema/status vocabulary. `unknown` already exists in runtime and gateway action-result contracts. No new contract namespace, database schema, browser capability, or provider work is needed for the conservative initial fence below.

## Trusted API and injection

Proposed additive contract: a `ClientGatewayTrustedCommandContext` type exported through `fluxiq/client-gateway`, backed by an issuer-private identity registry/capability. A JSON object with matching field names is invalid. The Automation Studio run collaborator owns issuance; generic gateway code validates the capability, freezes ownership and request data, then combines it with actual selected session/client identity. Never accept binding fields from `ClientGatewayActionCommand.metadata` or inbound results.

Carry this optional context through `FluxIQRuntimeExecutionContext` (`runtime/contracts.ts:147`), graph effect context (`executor/contracts.ts:440`), and `OutputDispatchRequest` (`io/index.ts:24`). IO already depends on runtime result types, but the context itself should be a generic gateway type, not an Automation Studio implementation import. `IoRegistry.dispatchOutput` passes the request unchanged (`io/index.ts:266`), so this requires no new registry behavior. Keep the context outside serializable command/action records and withholding/evidence payloads.

Keep `ClientGatewayService.executeAction`'s synchronous response wrapper for existing callers: a separate optional trusted argument permits a deterministic response command ID and a result promise whose private implementation awaits claim/send/receipt. Legacy context-free callers retain their documented memory-only behavior; configured production Automation Studio receipt-required scopes must never silently downgrade when context or SQL is absent. Do not add durable fields to the browser wire contract. `ClientGatewayActionResult.status` already includes `unknown` (`packages/contracts/src/client-gateway.ts:101`). A server-generated unknown result may carry a bounded diagnostic reason, but only the trusted scope/journal controls the fence.

`programs/_shared/runtime.ts:64` constructs Automation Studio before gateway (`:72`) and binds generic runtime (`:121`). Automation Studio already owns the authoritative project database pool (`runtime/service.ts:341`, initialized `:416`, closed `:485`). Add a focused readonly collaborator/port backed by that pool, rather than exposing the pool or opening a parallel filesystem journal. Inject the generic ledger resolver through gateway options (`client-gateway/service/types.ts:18`) and constructor collaborator wiring (`client-gateway/service.ts:82`). Scope each store lease to its project and close it through the program-owned collaborator; cover close/error paths. Storage-less receipt-required runs fail closed; unrelated legacy tests/callers remain supported.

The current SQL port (`storage/project/command-ledger/store.ts:15`) is per-project and validates joins on every read (`:90`). Add a bounded run reconciliation operation to the existing port, implemented against existing claim/receipt tables. Initially scan bounded/paged rows and decode/validate each claim and proof before trusting its run ownership; do not let unvalidated `json_extract` values grant clearance. Reject incomplete/corrupt scans rather than declare a run clear. No migration is necessary for this conservative implementation; an indexed projection can be a later explicitly approved storage change. Claim admission must atomically reject unresolved other claims for the same run, so concurrent scopes cannot both pass a preflight then mint unrelated command IDs. The sequential policy executor supports this conservative per-run serialization; broader parallel command dispatch is a compatibility question for a future unit.

## Gateway-only first production partition

The first implementation task can ship A plus the composition/broker portion of B, without editing executor, policy dispatch, generic runtime bounds, or downstream propagation. This is the durable **gateway seam**, not a claim that existing Flow dispatches became durable. Trigger durable behavior only for validated explicit trusted contexts; leave legacy context-free calls unchanged until the later propagation/fence task enables receipt-required Flow execution.

Proposed generic option: `resolveCommandLedger(context): Promise<{ ledger: ClientGatewayCommandLedgerPort; close(): Promise<void> }>`. The gateway validates the opaque context before invoking this resolver and verifies that its frozen project binding agrees with the claim. The resolver returns a domain-neutral ledger lease; gateway code never imports Automation Studio or SQL storage. A program-owned `AutomationStudioCommandContext` collaborator receives the existing pool privately, issues contexts from a validated actual session, opens `AutomationStudioProjectCommandLedgerStore.open({ pool, projectId })`, and returns its generic port/close function. A minimal readonly field initialized next to other program collaborators is the only required Automation Studio facade/constructor change in the first task. `programs/_shared/runtime.ts` injects a closure delegating to that collaborator when constructing the gateway. Never expose the pool, let metadata select a database, or infer the project from a browser session.

Exact first-task subset: gateway/ledger `context.ts` and `dispatch.ts` plus existing contracts/controller/barrels; gateway commands/inbound/transport/types/service constructor and public barrel; new program `runtime/service/command-context/{contracts,controller,index}.ts`, narrow Automation Studio constructor/readonly-field wiring, and `_shared/runtime.ts`; owning tests only. The existing SQL store needs no new behavior for one explicit trusted command. Its complete run-scan/admission additions belong to the later run-fence task. A server-scoped issuer should validate session ownership through injected program ports (`getRuntimeSession`) before issuing a context; no caller-supplied JSON binding is trusted. Implement issuer contracts so B can add actual invocation allocation without a second competing authority.

First-task proof: use the real program pool and actual stored runtime session, acquire an explicit trusted command context from the program collaborator, dispatch through the actual gateway service and synthetic owned socket, then verify committed SQL receipt before awaited result resolution. Repeat missing/forged context, wrong project/sender, duplicate/conflicting result, failed send/commit, abort/timeout/disconnect and close paths. This establishes real production composition and gateway ordering only. No Flow-durability, recovery, restart-resume, runtime-event filtering, or browser execution claim until the later task. Gateway `client.action_result` stays diagnostic-compatible; authoritative Runtime event filtering can wait for the second task, which owns the runtime transport tests.

## Receipt ordering and asynchronous races

`commands.settle` currently deletes pending and resolves synchronously (`commands.ts:83`), then inbound emits compatibility evidence (`inbound.ts:91`). Adding SQL makes this asynchronous. Change inbound to await settlement. Reserve a pending entry's settlement state before any await; serialize duplicate receipt, timeout, cancellation, disconnect, and send-error decisions per command. Keep actual sender session/client binding stable across the await and validate it against the original claim. Do not replace the sender with whichever session reconnects later.

Use the existing controller (`command-ledger/controller.ts:100`): send callback waits for a private validated receipt/result; controller commits/re-reads before the public result promise completes (`:108` through `:117`). A private pending promise can settle before commit; an authoritative external result cannot. Receipt-commit lost acknowledgements re-read the journal. Matching committed receipt wins over a racing timeout; conflicting receipts never overwrite it. Late receipts may reconcile an unknown claim but cannot automatically restart a terminal run.

Observe existing gateway disconnection events to finish outstanding waits as unknown; no lifecycle source edit is needed if subscription wiring suffices. `service/transport.ts:34` currently queues and uses optional socket send, so no socket can look like successful delivery. Revalidate readiness/socket after asynchronous claim and before enqueue. Add a receipt-required checked send that does not silently queue without a live socket; do not change disposable activity publishing. A send that throws after effect delivery remains uncertain, never a safe resend. A synchronous throw proven before send can refuse without claiming execution, but the initial conservative controller may still return unknown.

Before result hashing, validate bounded plain JSON, known status/command ID, identity binding, supported timestamps, and existing parsed failure/cleared-wait fields. `receiveRaw` only parses/casts (`inbound.ts:40`); do not hash or commit arbitrary wire objects as successful receipts. Use the existing digest's plain-JSON limits and frozen clone; omit absent optional fields explicitly rather than feeding undefined into strict digesting. Server receipt `receivedAt` uses server time, not client-reported completion time. Wire `unknown` is not a completed affirmative receipt: mark uncertain outcome instead. Preserve outcome-specific failure evidence without promoting arbitrary client fields to ownership. Existing store decode bounds (`store.ts:127`) and historical mutation proof checks remain mandatory.

## Terminal, retry, and resume fence

Maintain one sticky trusted run guard shared by root, routed graph, children, and repair passes. It observes claim start and committed/unknown completion; bounds that escape while a claim is pending must close automatic progression. Unknown maps to existing failed/unknown diagnostic vocabulary with `retryable: false`, but the guard is authoritative, not a model/native result's failure flag.

Required checks:

1. At common graph entry and before each next node, including after a pause is released (`graph-run.ts:395`). The common runner covers `resumeAutomationStudioGraphRun`; public parked resume (`executor/resume.ts:65`) must carry the same scope, and missing scope at a receipt-required gateway refuses before sending.
2. Immediately after an attempt is captured (`graph-run.ts:456`), before outputs are published, ask/parking, state routes (`:548`), recovery ladder (`:573`), retry, or failure edge. A region timeout or cancellation can beat the private dispatch promise; inspect outstanding claims instead of trusting the synthesized timeout trace.
3. Before another composite child pass (`composite-executor.ts:68`) and before adopting its result (`:80`). Child bounds (`:101`) must not hide an unresolved issued effect.
4. At actual service admission, before changing the session to running (`service.ts:2583`), and before result-verification repair callbacks, recovery annotation, or automatic rerun on either routed/direct path. `repair-rerun.ts:127` must decline before candidate/promotion writes or `runCanonicalAutomationStudioFlow` (`:174`). Cover both `from: resume` and `from: start`; allocating a fresh invocation is not reconciliation.

Persisted pending or unknown claims block continuation of that actual project/run across process restart. Do not mistake receipt-only committed records for recoverable results: replay currently returns `result_unavailable` (`controller.ts:119`). **Smallest safe restart policy:** when reconstructing a run scope, prior claims whose consumption/result association cannot be proven refuse automatic restart/resume. With the current receipt-only schema there is no durable consumed-result association, so conservatively refuse reconstructed same-run scopes with prior claims, even committed ones. This intentionally limits restart of otherwise legitimate parked runs; it must be explicit in UI/diagnostics/tests. In-process known completed scopes may continue normally. Recoverable restart requires a later approved association/result-storage design, not invented extracted output or a new random command ID. An explicitly requested new run is a distinct operation; automatic repair or relaunch of the unresolved old run cannot disguise itself as one.

Cancellation still ends the run as cancelled where appropriate, while preserving unknown effect evidence and a durable continuation refusal. Permissions and confirmation remain before action dispatch. No command continues while receipt authority is absent, and sensitive values/results retain current withholding and redaction rules.

## Compatibility event conclusion

There is no runtime pending-completion table driven by compatibility events. `RuntimeService.emit` only invokes subscribers (`runtime/service.ts:245`); `dispatch` settles attempts from its awaited result (`:226`) then emits authoritative `command.result` (`:227`). The bridge ignores `client.action_result` (`bridge.ts:209`). Thus remove `client.action_result` forwarding as authoritative `command.result` in `runtime/client-gateway-transport.ts:98`, keeping the generic gateway compatibility event available to diagnostics. No new event namespace is needed.

Wrong sender already returns before event emission (`inbound.ts:93`); unknown command still emits legacy diagnostic evidence. Preserve that compatibility at the gateway, but it cannot resolve a runtime dispatch, update the journal, or count as executed proof. Narrow source search found no non-test Core subscribers relying on transport `command.result`; tests currently assert the old forwarding (`runtime/tests/client-gateway-transport.test.ts:78`, `:107`). Change those expectations and add an awaited dispatch completion test. External public subscribers may observe one fewer duplicate/out-of-band event: document this compatibility effect. Do not claim an external-consumer audit.
