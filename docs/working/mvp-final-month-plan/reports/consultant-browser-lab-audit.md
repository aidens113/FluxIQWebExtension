### Permissions, uncertain effects and fallback boundaries

1. **Pre-dispatch gates must survive the redesign.** `domain/.../permission.ts:100-138` calls Core with the declared consequence and a domain-owned observe/mutate effect. The declaration is model input; it is not independent proof of safety. Core must continue deciding grants from instruction/user authority. A page script can send a message before its page-change evidence is collected. Post-effect classification can audit the event; it cannot authorize the event before it happens.
2. **A concrete boundary mismatch needs a negative test.** `domain/.../plan-resolution/step-permission.ts:79,128` requires declarations for click/keypress/dialog but not type. `content/actions/type.ts:75-83` can submit via Enter when `submit: true`. Test a send/publish form with type-and-submit and no grant. This audit confirms the domain declaration mismatch; it does not prove the end-to-end Core permission gate is bypassed. Also inspect autosaving fields and GET endpoints with effects: HTTP method or verb name alone is insufficient consequence authority.
3. **Reconnect is implemented; exactly-once consequential effects are not established by it.** The socket backoff/watchdog and persisted outgoing event queue are documented at `extension-client.md:177-211`; `gateway-session.ts:215-240` sends/queues results and flushes the queue. Inbound `execute_action` is routed at `:313-322`, and `server-command-channel.ts:184-197` dispatches without a local command-ID duplicate journal. No end-to-end duplicate-write bug is claimed here: Core's admission, correlation and resend semantics require a paired audit. Add deterministic cases for disconnection before dispatch, after remote effect but before reply, and worker restart. Classify an uncertain write separately, reconcile it with fresh evidence, and never blindly resend it to get a clean response.
4. **Clicks already contain an automatic second press.** `content/actions/click.ts:176-189` retries an unanswered non-navigation press. A late response can duplicate a real irreversible effect. The new controller must distinguish rejected-before-dispatch, confirmed no effect and unknown outcome; page silence is not proof of no effect. Gate this case with delayed-server fixtures and permission-bound consequences.
5. **Script channel feasibility is a release gate.** Current Chrome minimum is 116 and manifest permissions include scripting, not userScripts or debugger (`apps/extension/manifest.chrome.json:6,17-26`). The supervisor checked official docs: userScripts is Chrome 120+, execute is 135+, and Chrome 138+ has per-extension Allow User Scripts (earlier Developer mode). `USER_SCRIPT` has its own world/CSP rules; MAIN shares the page world. `scripting.executeScript` takes packaged files/functions, not arbitrary source strings. Chrome store policy and Firefox parity require explicit implementation review; userScripts availability does not itself prove AI-generated-code store acceptance. Sources: [Chrome userScripts](https://developer.chrome.com/docs/extensions/reference/api/userScripts), [MV3 requirements](https://developer.chrome.com/docs/webstore/program-policies/mv3-requirements). No blanket claim that every script mechanism is forbidden is justified.
6. **Requests remain opt-in at both config and UI.** Capture/request origins, redirects, credential attachment, methods, body bounds and secret handling must be concrete. Do not expose authorization headers or session tokens in model arguments. Credentialed writes need the same pre-effect delete/money/send-or-publish authorization and uncertain-outcome rules as typed operations. Network capture debugger use is allowed only under the user's requests-toggle exception, never as a JS execution workaround.
