# w19-e4 — a replayed click that lands on an error page fails as `navigation_unexpected`

Worker report, 2026-09-13. Brief: `briefs/finish-week1.md` "w19-e4", built on
`w19-e3` (`1acea4c`). Design: `reports/i-w19-expectation.md` "Follow-up: W10
and W27", E4.

## Outcome

Done.

Before this change, `runActionInFrame` returned the frame's reply as it came,
so a click that led to a page the server refused still counted as a success.
That was the code at HEAD, `action-runner.ts:215`, so the item had not been
settled earlier.

Now, when a replayed `web.dom.click` takes its own tab's top frame to a
document served with HTTP 400 or above, the click fails:
- code `web.navigation.unexpected`, category `navigation_unexpected`;
- the record names the status and the path without its query or fragment.

The extension's current permissions are enough. No new permission was needed.

## What changed and why

### Permission check, done first, on a real browser

Setup:
- A scratch probe (`scratchpad/w19-e4-probe/probe.mjs`, outside the repo)
  loaded the built extension `apps/extension/dist/e2e-chromium` into
  Playwright 1.51.1 Chromium, headless.
- That build's manifest declares `scripting`, `tabs` and `webNavigation`, with
  host access to 127.0.0.1 and localhost. The Chrome manifest declares
  `<all_urls>`, which covers more.
- A local server imitated the two fixtures, each serving an HTML body with its
  error status, as `navigation/scenario.ts:84-86` and
  `failure-surfaces/scenario.ts:28-31` do.

What the extension's service worker observed:

| Case | Navigation events (tab's own) | Status read from the landed document |
| --- | --- | --- |
| Link, 302 then 404 | top frame starts `/second`, commits `/retired` with `server_redirect` | 404 (`name` `/retired`, `redirectCount` 1) |
| Button, 403 | top frame starts and commits `/blocked` | 403 |
| Link, 200 | top frame starts and commits `/fine` | 200 |
| Button that navigates nothing | none | — |
| Link inside an iframe, to a 404 | frame 7 only | top document still 200 |

Reading by the commit's `documentId`, from inside the `onCommitted` listener,
returned 404 in 10 ms, 403 in 3 ms and 200 in 3 ms.

The design's open edge was whether a click's reply reaches the background
before the page unloads. The probe sent the build's real content script an
`executeAction` click five times each:
- a button that sets `location.href` to the 403 page: `succeeded`, in 3 to 6 ms;
- a link to the 302 then 404: `succeeded`, in 3 to 4 ms;
- a button that does nothing: `succeeded`, in 2 to 3 ms.

So the reply won the race 15 of 15 times, which means the navigation usually
starts *after* the reply. That is why the start grace matters.

### `apps/extension/src/runtime/click-landing.ts` (new)

It exports one function, `sendClickCheckingLanding(action, tabId, send)`.

1. **Any other action type** is sent and returned untouched. No listeners are
   attached.
2. **For a click, listening starts before the send.** It attaches to
   `webNavigation.onBeforeNavigate`, `onCommitted` and `onErrorOccurred`, and
   counts only events for the click's own tab with `frameId === 0`. Another
   tab or a child frame is ignored.
3. **A reply that is not `succeeded`** is returned as it was.
4. **After a succeeded reply:**
   - **No top-frame navigation starts within 300 ms:** the click is returned
     as it was.
   - **One starts:** the watch waits up to 10 s for a commit. It stops early
     if every started navigation ends in an error, as a download does. It
     counts navigations still in flight, so a navigation the page replaces
     with another is judged by the one that commits.
5. **Reading the status.** The script runs inside the committed document,
   addressed by that commit's `documentId`, and returns
   `performance.getEntriesByType("navigation")[0].responseStatus`. When the
   commit carries no `documentId`, the read goes to frame 0 instead. The
   result is used only when it is a positive integer. A refused injection or a
   missing value leaves the click as it was: missing evidence never becomes a
   failure, and Firefox has no `responseStatus`.
6. **Status 400 or above.** The click fails:
   - `failure: navigationUnexpectedFailure(expected, actual)`;
   - `expected` is "the page the click leads to loads";
   - `actual` is "the server answered HTTP 404 for /scenarios/navigation/link-retired";
   - the message says the same in a sentence.
   - The frame's reply is kept, including `url`, element, resolution and
     snapshot. Only `status`, `message`, `validation`, `failure` and
     `finishedAt` are replaced.
7. **A lost reply.** If the send rejects, the same landing check runs. A
   refused landing becomes a worker-built failed result with the same record.
   Anything else rethrows the original error, so the command router's current
   behaviour is unchanged.

Listeners and timers are removed in `finally`.

**Deviation from the design, deliberate.** The design said to call
`waitForTabReady` after the commit and then read frame 0. I read the committed
document by `documentId` straight away instead. This is "that document" in the
brief's words, so a later document cannot answer for it. It also spares every
navigating click the extra stability wait of at least 1 s: the next step still
runs its own `waitForTabReady`, so the design's "the wait moves into the
click" would have added a wait, not moved one.

**The lost-reply branch** is the design's open question 3. It is defensive,
since the probe never saw a lost reply.

### `apps/extension/src/runtime/action-runner.ts`

The one call:
`const send = () => sendAction(action, tabId, message, targetFrameId);`
`return withTarget(await sendClickCheckingLanding(action, tabId, send), tabId, targetFrameId);`

Also an import, and one sentence in `runActionInFrame`'s doc comment.

### `apps/extension/src/runtime/tests/click-landing.test.ts` (new, 15 rows)

- 302 then 404 fails. The row checks:
  - the exact record, validation and message;
  - that Core's parser keeps the record;
  - that the reply's fields are kept;
  - that the injection is addressed by `documentIds`;
  - that the query and fragment appear nowhere;
  - that 3 listeners are attached during the send and 0 after.
- A 403 whose navigation starts 20 ms after the reply fails.
- A 200 landing is returned as the same object.
- Another tab, and a child frame: returned unchanged, with no injection.
- No commit: returned unchanged after the grace, with the wait measured.
- A navigation ending in an error with no commit is returned promptly.
- A replaced navigation is judged by the one that commits.
- A refused injection, and a missing status: unchanged.
- A commit with no `documentId` reads frame 0.
- A failed click is never judged.
- `web.dom.type` and `web.dom.assert` attach no listeners.
- A lost reply followed by a 403 landing gives the full worker-built failed
  result.
- A lost reply after no navigation, or after a 200, rethrows the same error
  object.

The injected function really runs, against a mocked
`performance.getEntriesByType`.

## Not verified

What a Lab run must show:
- **W10 `broken-link` and W27 `blocked-url`:** each reports
  `navigation_unexpected` / `web.navigation.unexpected` 3 of 3, with the
  `web.dom.click` attempt `failed`. They stop throwing at
  `run-flow-lane.ts:130` only once `g-negative-click-outcomes` declares that
  click `outcome: "failed"`.
- **W15, W16 and W28:** each keeps its verdict:
  - W15 navigates another tab;
  - W16's download ends without a commit, which was not seen live;
  - W28 navigates a child frame.
- **Every other week1 row** is unchanged. W19 still gets `auth_required` from
  D1 and E2, because its sign-in page is served 200.
- **Cost:** a click that navigates nothing takes at most about 300 ms longer
  (314 ms measured in a unit test). A navigating click adds only its time to
  commit plus the read (3 to 10 ms in the probe).

Other gaps:
- The probe used `dist/e2e-chromium` as built on 2026-09-12 17:35, not this
  change and possibly not HEAD. It proves the permissions, the events, the
  `documentId` read and the reply timing, but not `click-landing.ts` running
  inside the extension. That needs `pnpm build` and the Lab, both off-limits
  in this dispatch.
- Firefox was not exercised. Its commits carry no `documentId` and its pages
  no `responseStatus`, so a click there should be unchanged; that fallback is
  proven only by unit rows.
- The lost-reply branch was never triggered live; the reply won 15 of 15.
- The content harness was not run: the background worker is not loaded there,
  as the design says.
- A service-worker restart during a click's watch was not tested.

## Open questions or contradictions found

1. **Documentation I do not own.** `docs/architecture/failure-taxonomy.md:133-138`,
   the list of worker-side producers, should add `runtime/click-landing.ts`
   (`NAVIGATION_UNEXPECTED` for a click whose tab lands on a page served 400 or
   above). `docs/architecture/web-capabilities.md`'s click description probably
   needs the same sentence. These should have been in this brief's Owns or in
   the supervisor's integration.
2. **Path in the record.** The design said no URL text goes in the record; the
   brief says to name the path without its query. I followed the brief. A path
   can still carry an identifier, such as `/reset/<token>`. If that matters,
   name only the status.
3. **`waitForTabReady` dropped.** Reading by `documentId` at commit replaced
   the design's wait-then-read. Please confirm. The consequence is that a
   document the landed page replaces client-side is not what gets judged: the
   click's own commit is.
4. **Known gaps, as the design deferred:**
   - a sign-in page served 401 reads `navigation_unexpected`, not `auth_required`;
   - a soft 404, served 200, is not caught.
5. **`runtime/index.ts`** does not export `click-landing.ts`. It is internal to
   the runner, like `navigation-outcome.ts` and `command-options.ts`.
   `runtime/` now has 13 source files, under the 15-file advisory. No baseline
   entry needs to change.
