# w19-e1 — the recorder links a click to the navigation it caused

Worker `w19-e1`, brief in `briefs/finish-week1.md` ("Fifth dispatch", `w19-e1`),
design E1 in `reports/i-w19-expectation.md` §1. Read at `HEAD 5911011`; nothing
committed.

## Outcome

**Done.** A navigation that a click causes is now sent as its own recording
event. The conditions are: the tab's top frame commits a new document by
`link` or `form_submit`, in the same tab, within 5 s of an executable click.
The event is a non-executable `client.recording_event` (`web.page.navigated`),
with `metadata.transition: "explained"`. `metadata.explainedBy` is the click's
`sequence`. The URL is origin plus path, with no query and no hash. It carries
no input id and is not counted as an action. When and how the click itself is
sent did not change. A reload, a subframe's commit, and a link commit that no
click explains are still dropped.

I made one behaviour change beyond the literal design, and it needs the
supervisor's eye. **Every** subframe commit is now dropped, not only subframe
`link` and `form_submit` commits (see "What changed", item 3).

## What changed and why

1. **`navigation-recorder.ts`** (117 lines)
   - `shouldRecord` now takes a `NavigationOrigin` instead of a boolean:
     `"typed"`, `"page"` (a top-frame link or form-submit commit), or
     `"other"`. It returns a `NavigationVerdict`: `drop`, `navigation`, or
     `explained` with `explainedBy`.
   - A `page` commit is recorded only as `explained`: the tab's last
     explanatory action must lie inside the 5 s window and must name an
     executable click. Otherwise it is dropped.
   - An `explained` verdict does **not** claim `lastRecorded`. So a typed
     navigation to the same URL afterwards is recorded exactly as before
     (a test pins this).
   - The `typed` and `other` rules are unchanged, as are the
     before-recording-start check and the initial-URL grace check. Both
     checks still run first, so setup navigation stays dropped even when a
     click would explain it.
   - `noteExplanatoryAction(tabId, timestamp, explainer)` now takes either
     `{ kind: "click", sequence }` or `{ kind: "submit" }`:
     - A click replaces the named sequence. `sequence` is `undefined` for a
       click nothing can replay, so that click names nothing.
     - A submit extends the window and **keeps** the previous click's
       sequence, but only if that click was itself inside the submit's
       window. A submit 6 s after a click does not revive that click.
   - `clearRecordingTabs` also clears explanatory actions. Without this, a
     click from the previous recording could be named by a landing in the
     next one. Content-script sequences restart per document, so that
     number could even collide with a real click.
2. **`recorded-event-intake.ts`** (172 lines)
   - `noteNavigationCommitted` classifies each commit as `page`, `typed` or
     `other`, and returns early for `frameId !== 0` and for `reload`.
   - `recordNavigation` turns an `explained` verdict into a
     `browser.navigation` payload with URL `origin + pathname`, dropped if
     the URL does not parse or has an opaque origin. Its metadata is
     `{ transition: "explained", explainedBy }`. It re-enters through the
     facade's `recordEvent`, as every derived event does.
   - `processEvent` sends a non-executable explained navigation as
     `client.recording_event` through `gatewayRecordingEventFromPayload`,
     with the recording id, and then as evidence.
     - That function leaves `metadata` untouched when there is no `inputId`
       (`gateway-payloads.ts:75-76`).
     - The domain maps only `transition: "typed"` to an input
       (`domain/src/io/input-model.ts:111`), so no input id is added.
   - An explained navigation is not counted, and its activity reads
     "Evidence: Navigation".
   - The click path is untouched apart from computing
     `isExecutableRecordedAction` once, before `noteExplanatoryAction`, so
     the recorder can be told whether the click is executable.
3. **Why every subframe commit is dropped.** The brief says "a subframe commit
   … stay[s] dropped", and design §1.3 says "Subframe commits … still return
   early". At HEAD that was only true of subframe `link` and `form_submit`
   commits. `auto_subframe` and `manual_subframe` commits were scheduled.
   - The debounce is keyed per tab (`navigation-recorder.ts` `pending`).
   - An iframe that commits within 250 ms of the landing therefore
     **replaced** the pending top-frame landing. That iframe is an ad, an
     embed or a widget on the page reached.
   - The replacement would then be judged under the iframe's URL: dropped
     inside the window, or recorded as the tab's navigation outside it.
   - The same defect already lost typed navigations on pages with iframes.
   - The row "an iframe loading on the landing page does not displace the
     landing" pins the fix.
   - To revert only this part, change the guard to
     `if ((details.frameId !== 0 && (details.transitionType === "link" || details.transitionType === "form_submit")) || details.transitionType === "reload") return;`.
     The iframe row then fails.
4. **Tests.**
   - `tests/navigation-recorder.test.ts` is new, with 8 rows:
     - a landing names the click;
     - a page commit is dropped with no click, with an unreplayable click,
       before the click, after the window, or in another tab;
     - a submit keeps its click;
     - a submit with no click in its window names nothing, a later click
       replaces an earlier one, and an unreplayable later click names
       nothing;
     - a landing claims nothing, and typed and other navigations keep their
       rules;
     - setup navigation is dropped;
     - a new recording forgets the last one's click;
     - the debounce keeps only the last commit, using `t.mock.timers`.
   - `tests/recorded-event-intake.test.ts`:
     - The old assertion at `:150-160` ("a link navigation is explained by
       its click": never scheduled) is replaced. One row pins the
       classification: typed, link and form-submit as `page`, reload
       dropped, a subframe link or subframe auto commit dropped, a bookmark
       and a history-state update as `other`.
     - The re-entry row now covers typed navigation, history state and
       content-ready.
     - Three new rows use the real `NavigationRecorder`, mocked timers, and
       re-entry into the intake:
       - the auth-gate shape (pointerdown click 7, a submit, a `link` commit
         to `/account?session=secret-token#welcome`) sends the click, then
         one `web.page.navigated` with URL `https://shop.test/account`,
         `transition: "explained"`, `explainedBy: 7`, no `inputId`, the
         recording id, no `secret-token` and no `welcome` anywhere in what
         was sent, and the count stays 1;
       - an iframe does not displace the landing;
       - a subframe link, a reload, a link in a tab with no click, a link
         after the window, and a link after an unreplayable click all send
         nothing and derive nothing.
     - The harness gained an optional real recorder and a `reenter` option.
   - `tests/recorded-event.test.ts`: the executable-rows table gained "a
     click's landing" → not executable.
   - `tests/gateway-payloads.test.ts`:
     - the input-id table gained "a click's landing" → `undefined`;
     - a new row pins the wire shape: event type `web.page.navigated`,

## Open questions or contradictions found

1. **`explainedBy` is not unique within a recording.**
   - A click's `sequence` comes from the content script's own counter, which
     restarts in every document and frame (`content/recorder.ts:21`
     `let sequence = 0`, `:111` `sequence: ++sequence`).
   - Two clicks in one recording can therefore share a sequence, for example
     click 1 on the sign-in page and click 1 on the account page.
   - D1 and C2 should match `explainedBy` against the **nearest preceding**
     click in the same tab (`sourceId` `tab:<id>`), not the first click with
     that number.
   - The alternative is for E1 to also carry the click's gateway `eventId`
     (`web.<sequence>.<timestamp>`). The brief named only the sequence, so I
     did not add it.
2. **One click can have more than one landing.**
   - A client redirect that commits more than 250 ms after the first commit,
     but still inside the 5 s window, yields a second explained navigation
     naming the same click.
   - D1 should take the **last** one that follows the click. The design's
     "the second commit replaces the first" holds only inside the debounce.
3. **A landing that commits more than 5 s after its click is not explained.**
   This is the old window, kept as it was.
4. **Behaviour change beyond the design.** All subframe commits are now
   dropped (item 3 above). Before this change, an iframe's `auto_subframe`
   commit outside a click window was recorded as the tab's untyped navigation
   to the iframe's URL. As evidence only, that changes recording evidence on
   pages with iframes.
5. **Documentation.** No authored page under `docs/architecture/` describes
   navigation recording: a search for transition, link, debounce and
   explained near "navigation" found nothing. This paragraph belongs on the
   extension recording architecture page, whichever the supervisor assigns:

   > A committed top-frame navigation the page made itself (Chrome transition
   > `link` or `form_submit`, script navigation included) is recorded only
   > when an executable click in the same tab preceded it within 5 s. It is
   > sent as a non-executable `client.recording_event` (`web.page.navigated`)
   > with `metadata.transition: "explained"` and `metadata.explainedBy` set to
   > the click's recorded `sequence`, and its URL reduced to origin and path.
   > It maps to no input and never executes; Core's recording mapper reads it
   > as the landing of the click it names. A form submit extends the window
   > but never replaces the click. Reloads, subframe commits, and page
   > navigations no click explains are not recorded. Commits are debounced
   > per tab for 250 ms, so a fast client redirect records only where the
   > page settled.
6. **Structure baseline.** No entry needs changing.
