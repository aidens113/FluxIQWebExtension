## Outcome

**Partial.** Everything the brief asked for is built and green, with both
mutation proofs. But in a real recording the new claim is never made, because
of a gap in what reaches the mapper.

- **Done, as briefed.** A recorded click now proposes the path it landed on as
  its `expectedState`, exactly
  `{ conditions: [{ assert: { kind: "url", expected: <path> } }], mode: "all", timeoutMs: 5000 }`.
  Domain `check` and `test` pass, the structure audit passes unchanged, and both
  mutations fail named rows.
- **Why "Partial": the claim is inert on the live recording path.** I traced it
  in code, not in a browser. When the extension records a click, Core stores it
  as a `type: "action"` timeline entry, not as a click event. That entry holds
  only the replay parameters: no `sequence`, no event id, no `sourceId`. The web
  mapper maps no `"action"` entry, so it returns `null`, and Core then builds the
  click's candidate itself without an `expectedState`. The mapper change only
  fires for clicks that reach it as `domain_event` or `observation` entries. That
  is the shape the domain tests and Core's own proposal tests use, not the one a
  live recording produces. Evidence and the files the brief would need are in
  Open question 1. **A Lab run of W19 will not yet show the claim.**

## What changed and why

All paths are under `domain/src/`.

### New: `runtime/expectation/click-landing.ts` (100 lines, one exported value)

`webAutomationClickLandingExpectation(click, following)` returns the URL claim
or `undefined`.
- **Which landing.** It walks `following` and keeps the **last**
  `web.page.navigated` entry with `metadata.transition === "explained"` that
  names this click.
- **Naming by event id.** A landing names the click when
  `metadata.explainedByEventId` equals the click's event id. That id is rebuilt
  by `createWebAutomationRecordingEvent`, reached through the `client` barrel,
  from the click's `payload.sequence` and `observation.timestamp`, as the
  amendment says. The id's spelling stays in `client/gateway-mapping.ts`.
- **Fallback, no event id.** The landing names the nearest preceding click in
  the same tab whose `payload.sequence` equals `metadata.explainedBy`. The
  candidates are this click and any click between it and the landing in
  `following`.
  - **Same tab, not the same literal `sourceId`.** A deliberate reading of "the
    same `sourceId`": a click is sourced from its frame (`tab:7:frame:0`) and its
    landing from the tab (`tab:7`). `apps/extension/src/background/connection/tests/gateway-payloads.test.ts:50,73`
    pins both. Literal equality could never match a top-frame click.
  - **A missing source id matches nothing.** A wrong claim fails a correct run,
    so the fallback stays conservative. See Open question 2 for why this
    fallback is also inert live.
- **It emits nothing when:**
  - no landing names the click;
  - the landing's path equals the click page's own path, or is `/`;
  - the landing URL cannot be parsed;
  - the click's own URL cannot be parsed. Without it the same-path rule cannot
    be applied, so this case was added to section 2's list.
  - An opaque URL such as `about:blank` has no hierarchical path (its
    `pathname` does not start with `/`) and counts as unparseable.
- **Path only.** The claim is `new URL(url).pathname`: no query, no hash, no
  selector, text or value.
- **Why the shape of its input.** The builder takes plain
  `{ eventType, timestamp, payload, metadata }` steps, declared as a local
  (unexported) type. The mapper already knows how to unwrap Core's nested
  `domain_event` and `observation` payloads, so it hands the builder
  unwrapped steps rather than the builder repeating that logic.

## Open questions or contradictions found

1. **The claim never reaches a live-recorded click.** This is the brief defect
   the binding rules ask workers to report: ownership drawn around the mapper
   file rather than around the change. It is traced in code and not observed
   live.
   - **A live click becomes an `action` entry.**
     - The extension sends a click with `metadata.inputId`
       (`gateway-payloads.test.ts:51`).
     - The host registers every action input with an output binding
       (`web-panel-host.ts:41-53`; `io/manifest-definitions.ts:9`).
     - So Core's bridge records it through `recordGatewayInput`
       (`F:\!FluxIQ\packages\fluxiq\src\programs\automation-studio\client-gateway\bridge.ts:351-363, 588-614`).
     - That writes a `type: "action"` entry (`runtime/io-bridge.ts:31-49`).
   - **That entry carries no `sequence`, no event id and no `sourceId`.**
     - `parameters` is `binding.payload` (`src/io/index.ts:300`), which for a
       click is `selector`, `element`, `visualTarget` and `browserFrameId`
       (`domain/src/output-nodes/payloads.ts:31,46`).
     - Entry metadata is `domainId`, `inputId`, `inputRole`, `envelopeId` and
       `policyEligible` (`io-bridge.ts:24-29,47`). The envelope's own metadata,
       including `sourceId`, is not copied.
     - The top-level `sourceId` is `input.<inputId>`, and Core strips top-level
       fields from what a mapper sees
       (`runtime/service/recordings/proposal-candidates.ts:164-167`).
   - **The mapper returns `null` for it, and Core proposes the click itself.**
     - The mapper reads the event type as `"action"`, which maps to no input
       (`domain/src/io/input-model.ts:132-133`).
     - Core then falls back to `recordingActionEntryCandidate(entry)`
       (`service.ts:2411`, defined at `:5726-5749`), which has no
       `expectedState`.
   - **The landing does reach the mapper intact.** It has no input id, so it is
     appended as a `domain_event` (`bridge.ts:364-380`;
     `model/recording-domain.ts:186-203`), and its `transition`, `explainedBy`
     and `explainedByEventId` sit in the entry metadata the mapper sees. Only
     the click side is missing.
   - **What would close it.** Both halves are needed, and this is a supervisor
     decision.
     - **Core:** keep the recorded event's identity on the action entry. For
       example, `bridge.ts:611` puts `event.eventId` into the envelope metadata,
       and `io-bridge.ts:24-29` copies it, or the envelope metadata, onto the
       entry metadata. That is w19-e1's second option, plus the `io-bridge.ts`
       hop it did not mention.
     - **Domain, `web-panel-host.ts`:** map a `type: "action"` entry whose
       `outputId` is `web.dom.click` into a candidate carrying the claim, or let
       Core accept a mapper's `expectedState` for its fallback candidate.
     - **If an id is kept verbatim, the rule changes.** The match becomes
       "`explainedByEventId` equals the entry's stored id" rather than an id
       rebuilt from `sequence`.
     - **The builder mostly survives.** Its landing choice, exclusions and URL
       claim carry over; only `recordedClickEventId` would change.
2. **The no-event-id fallback is also inert live.**
   - A landing's `sourceId` is a top-level entry field (`recording-domain.ts:191`)
     that Core strips before the mapper sees it (`proposal-candidates.ts:165`).
     A live click's is too, as above.
   - With no tab on either side the fallback matches nothing, by design.
   - Every current landing carries `explainedByEventId`, so the fallback only
     matters for an older extension. Making it work would need `sourceId` in
     the entry metadata, which is a Core change.
3. **"Same `sourceId`" was implemented as "same tab".** The evidence is in the
   builder section above. If the supervisor wants literal equality, it is a
   one-line change to `tabOf`, but a top-frame click would then never match its
   landing.
4. **A small addition to section 2's list.** A click whose own URL cannot be
   parsed also claims nothing, because the same-path rule needs it.
5. **The mutation 2 failures are in the builder test only.** The
   `domain.test.ts` rows use one click and one landing, so an always-true match
   still passes there. The named failing rows are 169 and 175.
6. **Structure baseline.** No entry needs changing. `web-panel-host.ts` keeps its
   two baselined `imports`, and no new finding appeared.

### Paragraph for the recording architecture page

> A recorded click proposes where it landed. Core shows each recording mapper
> call the next 32 mapper-visible timeline entries (`following`). For a
> `web.dom.click` observation, the web mapper (`domain/src/web-panel-host.ts`,
> builder `domain/src/runtime/expectation/click-landing.ts`) looks in
> `following` for explained `web.page.navigated` entries
> (`metadata.transition: "explained"`) that name the click. A landing names the
> click when its `metadata.explainedByEventId` equals the click's own event id,
> rebuilt by `createWebAutomationRecordingEvent` from the click's
> `payload.sequence` and timestamp. A landing without that id names the nearest
> preceding click in the same tab whose sequence equals `metadata.explainedBy`.
> The **last** such landing wins, since a client redirect can commit twice. The
> candidate's `expectedState` is then
> `{ conditions: [{ assert: { kind: "url", expected: <path> } }], mode: "all", timeoutMs: 5000 }`:
> a path only, with no query, hash, selector, text or value, judged as a
> substring of the page URL within 5 s. No claim is made when no landing names
> the click, when the landing's path is the click page's own path or `/`, or
> when either URL has no parseable path. The landing itself maps to no input
> and proposes nothing. Core lifts the claim into the approved Flow node's
> `parameterValues.expectedState`, where the host's expectation evaluator checks
> it after the click. **Current limit:** a click recorded through a registered
> action input is stored by Core as an `action` entry without its sequence or
> event id, so that path does not yet carry the claim (see
> `reports/w19-d1.md`, Open question 1).
