# w19-e3 — an assert that meets a navigating tab is sent once more

Worker report for brief `w19-e3` in `briefs/finish-week1.md` (fifth dispatch,
design E3 of `reports/i-w19-expectation.md`). Written 2026-09-13.

## Outcome

Done. A `web.dom.assert` whose send to the page is refused because the page
went away mid-send (Chrome's "no receiver" or "channel/port closed" errors) now
waits for the tab to settle and is sent exactly one more time. Every other verb
is still sent once. Unit rows and three mutation proofs pass; the Lab proof is
still owed (see Not verified).

Re-verified at HEAD first: `runActionInFrame` (`apps/extension/src/runtime/action-runner.ts:197-220`
before the edit) sent once with no retry, so the item was not already settled.

## What changed and why

**`apps/extension/src/runtime/action-runner.ts`** (307 -> 337 lines)
- `runActionInFrame` now builds the `executeAction` message once and hands it to
  a new private `sendAction(action, tabId, message, frameId)` instead of calling
  `sendToTab` directly. The message body and delivery frame are unchanged.
- `sendAction` sends once. If the send rejects, it re-throws unless the action is
  `web.dom.assert` **and** the error matches `NAVIGATING_PAGE_ERRORS`; in that
  case it awaits `waitForTabReady(tabId)` and sends the same message once more.
  A second refusal propagates exactly as a first one did before, so
  `command-router.ts:32-33` still turns it into `web.action.failed`.
- `NAVIGATING_PAGE_ERRORS` matches `/Receiving end does not exist/i` (no
  receiver: the new document's script is not listening yet) and
  `/message (port|channel) closed before a response was received/i` (closed
  port: the old document unloaded mid-answer). The channel case is the likely
  one, because the content script answers `executeAction` asynchronously
  (`content/message-handler.ts:69-73` returns `true`).
- Why only the assert: it only reads. A click or type may already have acted
  before the channel closed, so re-sending it could act twice.
- No new import. `waitForTabReady` was already imported (`:15`); the
  baselined `imports` entry for this file stays at 1.
- The change is live, not inert: `runActionInFrame` is the only in-page send
  path, reached from `runBrowserActionCommand`, which `command-router.ts:30`
  calls for every action. No caller or barrel needed changing.
- Child frames get the same treatment. After a tab navigation a child frame id
  usually names nothing, so the second send is refused too and reported as
  before; the cost is one extra wait.

**`apps/extension/src/runtime/tests/action-runner.test.ts`** (352 -> 425 lines)
- The chrome stub gained `refusals` (errors successive `executeAction` sends
  meet, in order; a send past the list is answered) and a `timeline` recording
  each `waitForTabReady` (`onUpdated.addListener`) among the sends. Existing
  rows are untouched.
- New helper `runAgainstRefusals` keeps a rejection as the outcome.
- Nine new rows:
  - For each of Chrome's "Receiving end does not exist", "The message port
    closed…", and "A listener indicated an asynchronous response… message
    channel closed…": an assert is sent twice with a wait between
    (`["wait","send","wait","send"]`), both sends identical, one result
    (`{ result: FRAME_REPLY, tabId: 41, frameId: 0 }`).
  - For `web.dom.click`, `web.dom.type`, `web.dom.extract`,
    `web.dom.wait_for_selector` meeting the closed channel: sent once
    (`["wait","send"]`), and the refusal is what surfaces.
  - An assert refused for another reason (`No tab with id: 41.`) is sent once.
  - An assert refused on both sends is sent exactly twice, and the second
    refusal is reported.

## Not verified

- **Lab proof (owed to the supervisor's live campaign):** W18 auth-gate passes
  3 of 3 runs, with no `web.action.failed` / `action_failed` on the assert that
  follows the `sign-in` click. That shows the absence of the false failure, but
  not that a re-send happened: nothing logs a re-send (see Open questions).
- Live browser behaviour: the unit stub reproduces Chrome's documented error
  strings, but no loaded extension was driven through a real mid-assert
  navigation. The content harness does not cover the background worker.
- Firefox: "Receiving end does not exist" is the same wording there, but
  Firefox's wording for a channel that closed mid-answer was not checked and may
  not match the pattern. If it doesn't, an assert on Firefox that loses its
  document mid-answer is still sent only once.
- Extension `pnpm build`, root `pnpm check`/`pnpm test`, and the Lab were not
  run, per the dispatch rules.

## Open questions or contradictions found

- **No trace of a re-send.** The runner returns the second send's result with
  nothing marking that a retry happened, so a Lab run cannot tell "no race" from
  "race absorbed". If the supervisor wants that visible, a later brief would
  need an evidence or log field. That is outside this brief's two files.
- **Firefox closed-channel wording** (above). If Firefox parity matters for W18,
  a short live probe would confirm the string before Week 1 closes.
- **The test file is past the 400-line advisory threshold** (425). Not a
  failure; if it grows much more, the refusal rows could move to their own
  `tests/action-runner-resend.test.ts`.
- No contradiction with design E3 found. One small extension of it: the brief
  named "closed port or no receiver", and the pattern also covers Chrome's newer
  "message channel closed" wording for the same event, because that is the
  error an asynchronous `executeAction` answer actually gets.
