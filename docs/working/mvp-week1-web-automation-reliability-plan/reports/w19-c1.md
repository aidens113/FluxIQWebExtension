## What changed and why

### `runtime/executor/transition-comparison.ts`

`attemptWithHostExpectationEvaluation` used to replace only the comparison when
the host rejected the expected state. Now:

- **The host accepts:** only the comparison is replaced, as before.
- **The host rejects:** the attempt becomes:
  - `status: "failed"` and `route: "failed"`;
  - `message`: the host's message, or "The host reported that the expected
    state does not hold." That is the wording `builtin.policy.expectation` uses.
  - `failure`: the host's record, passed through
    `parseAutomationStudioFailureRecord`. When the host sent no record, or its
    record does not parse, it is Core's `expected_state_missing` record: code
    `core.policy.expectation_rejected`, retryable, stage `verification`.
  - `transitionComparison`: recomputed exactly as before, against the action's
    own succeeded outcome plus the host's verdict. The one difference is that
    it reads the same parsed record, so its status cannot disagree with
    `attempt.failure`.
- **Unchanged cases:**
  - an attempt that did not succeed;
  - a `builtin.policy.expectation` node (the gate, now at `:116`);
  - no evaluator bound;
  - an evaluator that throws.

Why the record is parsed: `attempt-trace.ts:21` parses a node result's record
where it becomes the attempt's. The host's verdict crosses the same kind of
boundary. Without the parse, a self-contradicting host record would land on the
attempt, and the comparison status would be derived from it.

Why Core's record is a local constant: the same record already exists as
`EXPECTATION_REJECTED_FAILURE` at `nodes/policy/expectation.ts:8`. It is not
exported, and neither `expectation.ts` nor the `nodes` barrel is mine, so the
four fields are duplicated. See Open questions 2.

Line 37 is unchanged. The generated framework reference cites
`transition-comparison.ts:37` for `compareAutomationStudioTransition` (both
`framework-reference.md:850`), so the import change replaced line 1 in place and
everything new sits below line 86. The file is now 215 lines; it has no
baseline entry.

### `runtime/executor/tests/node-execution.test.ts`

I replaced the old test at `:114-137`, which pinned a rejection leaving the
attempt `succeeded`, with a new `describe("a rejected expected state fails the
attempt")`. Its Flow is an action with `expectedState` whose `success` edge leads
to a second output, so a wrongly succeeded attempt would dispatch it. The rows:

1. **The host rejects with an `auth_required` record.**
   - The attempt is `failed`/`failed`, carries the host's message, and its
     `failure` equals the host's record.
   - The comparison is `blocked`, with `stateCheckCount 3`.
   - The run is `failed`, `dispatched` is only `["activate-element"]`, and there
     is one attempt.
   - The host was asked exactly what the old row pinned: source
     `transition_comparison`, node, attempt, and `stateRef`.
2. **The host rejects with no record.** The attempt's `failure` is Core's
   `expected_state_missing` record, its message is the default, the comparison
   is `missing_expected_state`, the run fails, and the second output is not
   dispatched.
3. **The host sends a record that does not parse** (`auth_required` marked
   `retryable: true`). The attempt gets Core's record, and the comparison is
   `missing_expected_state`, not `blocked`.
4. **The host accepts, and separately no evaluator is bound.** In both runs the
   attempt is `succeeded`/`success` with no `failure` and no `message`, the run
   succeeds, and both outputs are dispatched. With the evaluator bound, the
   comparison is `matched` with `stateCheckCount 3`.
5. **`failureRoute: "success"`.** A rejection and a failed dispatch are run with
   the same parameter. Compared field for field, both runs have the same run
   status, run message, attempt count, attempt status, attempt route, selected
   recovery candidate, and dispatch list.

### Compatibility effect

- **Who is affected:** every host that binds `expectationEvaluator`, for any
  node other than `builtin.policy.expectation` that carries `expectedState` and
  whose action succeeded.
- **What changes when that host rejects:**
  - the attempt now fails;
  - `attempt.failure` and `attempt.message` are now set;
  - the run takes the failure path: a `failed` edge if the Flow has one,
    otherwise recovery nodes, otherwise LLM diagnosis;
  - the next node is no longer dispatched.
- **Where it shows:**
  - A run with no failure edge now ends `failed`, with the message "Recovery
    ladder reached LLM diagnosis fallback before a configured provider was
    invoked."
  - The run detail copies `attempt.failure`, so the Flow lane will now see a
    category where before it saw none.
- **What does not change:**
  - a host that accepts, a host with no evaluator, and an evaluator that throws;
  - failed, waiting and cancelled attempts;
  - the expectation node;
  - the attempt's `outputs`: an action still reports `{ success: true, ok: true }`
    into run values after a rejection, and nobody asked for that to change.
- **This repository:** `i-w19-expectation` §3 found that nothing writes
  `expectedState` for web output nodes today
  (`domain/src/output-nodes/definitions.ts:22-25`), so no existing web Flow
  should change verdict until C2 and D1 land. I did not re-verify that.

## Open questions or contradictions found

1. **Nothing honours `failureRoute` at HEAD, so the brief's premise does not
   hold.**
   - **Where it goes.** `nodes/policy/action.ts:40` copies it into the dispatch
     payload. Neither Core dispatcher reads it: `runtime/io-policy.ts:59-73` and
     `:75-119` build the action from named keys and return `failedDispatchResult`.
   - **Where routing happens.**
     - The dispatch merge `node-execution.ts:154` uses `dispatched.route ?? "failed"`.
     - `graph-run.ts:126` routes on `attempt.route`.
     - Nothing in `domain/src`, `apps/extension/src` or `packages` of this
       repository reads it.
   - **The probe proves it:** with `failureRoute: "success"` a failed dispatch
     still routes `failed`, and the next node is not dispatched.
   - **The consequence.** For `failureRoute` to be honoured by every failure,
     rejections included, the change belongs where every failed attempt is
     routed. That is `graph-run.ts:126`, choosing the edge from the node's
     resolved `failureRoute`, or the dispatch merge in `node-execution.ts`. It
     does not belong in `transition-comparison.ts`, where it would make a
     rejection route differently from every other failure. Neither file was
     in this brief. Row 5 is written as an equivalence, so it stays green if
     that fix lands for all failures.
2. **Core's `expected_state_missing` record exists twice.**
   - One copy is `nodes/policy/expectation.ts:8`, not exported; the other is my
     constant in `transition-comparison.ts`.
   - To share one constant, a follow-up needs `expectation.ts` (or a small new
     file under `nodes/policy/`) to export it, and the `nodes` barrel to
     re-export it.
3. **The comparison's `actual` shows the action succeeded while the attempt says
   `failed`.** That is what "`transitionComparison` stays" asks for: the
   comparison is the host's verdict on the action's own outcome. Consumers that
   read `comparison.actual.status` rather than `attempt.status` will see
   `succeeded`.
