# w19-e2 — a failed URL claim on a sign-in gate reports `auth_required`

## Outcome

Done. Design E2 is in place. A `web.dom.assert` URL claim that names a URL and
fails on a page with a rendered sign-in form now reports `AUTH_REQUIRED`
(`web.auth.required`, category `auth_required`). The record quotes the Flow's
claim, never the page's address, a field value, or the demo password. A failed
URL claim on any other page is unchanged: it still reports `STATE_MISMATCH`.

Re-verified at HEAD before starting: the change had not landed. Both owned
files were clean in `git status`, `authGateFailure` still returned `undefined`
for any action without a selector, and neither file has a
`.structure-baseline.json` entry.

## What changed and why

**`apps/extension/src/content/action-runtime/results.ts`**

- `authGateFailure` now fires for two cases, and both still require the
  sign-in form to be on the page:
  - **Missing target (unchanged):** the named selector matches nothing.
    The record is exactly what it was before.
  - **Failed URL claim (new):** the action is a `web.dom.assert` whose
    claim is a URL and names one. The new helper `namedUrlClaim` makes
    that check.
- The new record's fields:
  - `expected` is the Flow's claim, for example
    `the page URL is /scenarios/auth-gate/account`.
  - `actual` is fixed text:
    `the page is not at the URL the Flow claimed; the document is a sign-in gate, so the session has probably expired`.
    It does not copy the verb's own `actual`, which is
    `the page URL is <full href>`. On a real sign-in page that address carries
    a return path or a token.
- **One deviation from the design's condition, and why.** The design's
  condition was `actionType === "web.dom.assert" && assert.kind === "url" &&
  signInGatePresent()`. I added "and the claim names a URL". A URL claim with
  no `expected` also leaves the assert verb as `STATE_MISMATCH`
  (`assertion-evaluation.ts:163-175` marks it malformed; `assert.ts:86-97`
  still sends it to `success`). Without the check, a broken Flow on a gate
  page would tell a person to sign in again. A harness control row guards
  this, with its own mutation proof.
- **Comments updated:** the module header (lines 29-34) and the
  `authGateFailure` doc. The sentence that said the modal refusal and this
  hook cannot meet now also says a URL claim is never refused.
- **Size:** 395 → 410 lines. This passes the 400-line advisory threshold,
  which only warns, and is under the 800-line limit, as the design predicted.

**`apps/extension/e2e/content/tests/failures.spec.ts`**

- New constant `ACCOUNT_PATH`.
- Two new rows under "on auth-gate":
  1. **`failures.spec.ts:144`:** a URL claim for the account page, made on
     the sign-in page, gives:
     - status `failed`;
     - category `auth_required`, code `web.auth.required`,
       `retryable: false`, stage `confirmation`;
     - `expected: "the page URL is /scenarios/auth-gate/account"`;
     - `actual` containing "sign-in gate".

     Neither the record nor the validation contains the demo password, and
     the record does not contain `harness.url`, the page's own address.
  2. **`failures.spec.ts:176`, control:** a URL claim with no `expected` on
     the gate page stays `web.validation.state_mismatch`, with `expected`
     "the assertion to name the expected URL".
- The non-gate control at `check-assert.spec.ts:296-313` was run, not
  edited.

## Open questions or contradictions found

- **Stale comment in a file I do not own.** The header of
  `apps/extension/src/content/actions/assert.ts`, lines 34-43, says the
  AUTH_REQUIRED edge for an assert is narrow: "a `url` claim carrying a stale
  selector on a page that has become a gate". That is out of date: any failed
  URL claim that names a URL now reports AUTH_REQUIRED on a gate, whatever
  its selector. The sentence should be updated by whoever owns `assert.ts`.
- **A known false positive of the heuristic, inherited from the design.** The
  gate is detected only by a rendered password control inside a `<form>`. A
  failed URL claim on a page that has one for another reason (a sign-up page,
  a change-password settings page, a header login box) will report
  AUTH_REQUIRED. No corpus row exercises that shape. The same limit already
  applies to the missing-target branch.
- **The result's validation still quotes the page's address.** A URL claim's
  `validation.actual` is `the page URL is <href>`, as it is for every URL
  claim today. The brief bounds the failure record, which is what changed
  here. Whether `validation.actual` should also drop the query is a separate
  question for whoever owns `assertion-evaluation.ts`.
