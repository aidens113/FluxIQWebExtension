### Compatibility effect

- **Importer SDK: both additions are optional.**
  - Existing mapper implementations still type-check, because a function that
    ignores `following` accepts the wider context.
  - Code that calls a mapper implementation directly with its own context object
    must now pass `following`. In Core only `service.ts` does that.
  - This repository's `mapWebRecordingObservation(observation)` takes no context
    (`domain/src/web-panel-host.ts:115`), and the domain tests call that
    function, so it is unaffected. I did not compile it against the new Core.
- **Stored proposals.** `RecordingFlowActionCandidate.expectedState` is optional,
  so proposals already on disk read as before.
- **Flows.**
  - A node gains `parameterValues.expectedState` only when its mapper proposed a
    plain object.
  - Together with `w19-c1`, a host that binds `expectationEvaluator` will now fail
    such a recorded action when it rejects the state.
  - Nothing in this repository proposes `expectedState` until D1 lands, so no
    existing web Flow changes.
- **Behaviour changes inside proposal generation.**
  - Observations are built before a mapper's first call rather than just before
    each call. So within one mapper's calls, an object in `following` is the same
    object that mapper is handed later. This is documented.
  - The payload clone now runs outside the per-entry `try`. An entry that could
    not be cloned would reject the whole generation instead of adding an issue.
    Timeline entries are JSON, so I expect none.
