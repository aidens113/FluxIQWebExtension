# w19-d1b — a linked click's action entry carries the landing claim (domain)

Worker report for brief `w19-d1b` in [finish-week1.md](../briefs/finish-week1.md)
("Fifteenth dispatch"). Worked in this repository on `dev` at `7263534`, against
FluxIQ Core built at `187f40d`. Nothing was committed. No `pnpm build`, no Lab
command, no Core edit.

## Outcome

**Done, with one pre-existing defect found and reported, not fixed.**

- A click the extension records through its action input reaches the recording
  mapper as Core's `action` entry. That covers every live click (w19-d1, open
  question 1). When a landing in `following` names the event id Core stored on
  that entry (`metadata.eventId`), the mapper now returns a candidate. It is the
  one Core's fallback proposes for that entry, with the landing claim added as
  `expectedState`.
- Every other `action` entry still maps to `null`, so Core's fallback is
  unchanged for it. That covers an unlinked click, a non-click, and an entry
  Core marks `policyEligible: false`.
- A permanent row records two clicks and a landing through Core's own service,
  IO recorder and domain-event call. It compares the web mapper's candidates
  with Core's real fallback candidates for the same entries. They are equal
  apart from the claim on the linked click.
- **Defect found:** a domain event that Core stores keeps its own payload one
  level deeper than the mapper reads. This was observed on built Core. As a
  result, the existing D1 path (a click arriving as a domain event) claims
  nothing on a real Core recording. The existing W25 check never sees a
  domain event's URL either. I worked around it on the new path only, because
  the dispatch said to change neither existing behaviour. See open question 1.

## What changed and why

### `domain/src/runtime/expectation/click-landing.ts` (100 → 124 lines, still one export)

`webAutomationClickLandingExpectation` now accepts a click step whose
`eventType` is `"action"`, which is Core's entry type for an IO-recorded click.
For such a step:
- **Its id is the stored one.** The click's id is `metadata.eventId`, kept
  verbatim and only as a non-blank string (new private `storedEventId`).
- **It cannot be rebuilt.** The entry has no `sequence`. Its `timestamp` is
  Core's append time, not the event's: the probe showed `1789291492919`
  against an envelope `timestampMs` of `900`.
- **It needs no page URL.** The entry carries none, so the "click page's own
  path" exclusion cannot apply to it. The `/` and unparseable-URL exclusions
  still apply.
- **It is named by that id alone.** The sequence-and-tab fallback only
  matches a click whose `eventType` is the element-clicked domain event, so it
  can never name an action entry. No extra guard was added; see "Not
  verified".

A domain-event click is unchanged: it still requires its URL, rebuilds its id,
and keeps the tab fallback.

### `domain/src/web-panel-host.ts`, the mapper only (171 → 222 lines)

- **`mapWebRecordingObservation`.** When no recorded action maps, it now tries
  `linkedClickEntry` before the W25 wait. The two cannot both apply: the wait
  needs an `input.event` observation. The doc comment now describes the
  action-entry case.
- **`linkedClickEntry` (new, private).** It mirrors Core's
  `recordingActionEntryCandidate` (`runtime/service.ts:5726-5749`), field by
  field:
  - `type` must be `"action"`, and `metadata.policyEligible === false` refuses;
  - `outputId` is the trimmed `outputId`, else the trimmed `actionType`, and
    must be `web.dom.click`;
  - `parameters` is `payload.parameters` when it is a plain object, else `{}`;
  - `sourceInputIds` is the trimmed `metadata.inputId`, else the trimmed
    `confirmationInputId`, and is omitted when neither exists;
  - `expectedConfirmation` is `{ inputId: confirmationInputId, timeoutMs: confirmationTimeoutMs ?? 5000 }`
    when `confirmationInputId` is set;
  - `confidence` is `0.95`, and `label` is `"Web Dom Click"`.

  It returns nothing unless the builder makes a claim.
- **The label.** `"Web Dom Click"` is Core's `readableTokenValue("web.dom.click")`.
  That helper is not publicly exported, so the domain holds a constant
  (`FALLBACK_CLICK_LABEL`), and the Core row pins it (mutation M7). A
  domain-event click is still labelled `"Click"`, as before.
- **`storedStep` (new, private).** It reads the entries after an action entry
  the way Core stores them. For a `domain_event`, the event's payload sits
  under `observation.payload.payload.payload`. Every other entry type goes
  through `recordedStep` unchanged.
- **`nonBlankString` (new, private).**
- **No new import.** `webAutomationClickLandingExpectation` was already
  imported, so the two baselined `imports` are unchanged.

**What the mapper can and cannot see for the entry.** Everything Core's
fallback reads is visible: `type`, `outputId`, `actionType`, `parameters`,
`confirmationInputId`, `confirmationTimeoutMs`, `metadata.inputId` and
`metadata.policyEligible`. The mapper cannot see:
- **The page the click was on.** The action entry has no `url`, and the
  element fingerprint drops `url` on purpose (`output-nodes/targets.ts:153-163`).
  Hence the missing same-path exclusion.
- **The event's own sequence and timestamp.** Hence the stored id.
- **The entry's top-level `sourceId` (`input.<inputId>`), `sequence` and
  `monotonicOffsetMs`.** Core strips these at `proposal-candidates.ts:170`. The
  fallback reads none of them.
- **The landing's top-level `sourceId`, its tab.** Hence no tab fallback, as
  the amendment says.

**Where the mirror differs from Core, on malformed entries only:**
- A non-number, non-null `confirmationTimeoutMs`: Core passes it through; the
  mapper uses 5000.
- A truthy value in `confirmationInputId` that is not a string: Core passes it
  through; the mapper refuses it.

`io-bridge.ts` writes neither.

### `domain/src/runtime/expectation/tests/click-landing.test.ts` (+2 rows, helper `storedClick`)

- **"a click's action entry claims the landing that names its stored event id".**
  It claims the landing's path. A landing on the click page's own path is still
  claimed, and this documents the limit. `/` claims nothing.
- **"a click's action entry is named by its stored event id alone".** Each of
  these claims nothing:
  - a landing naming another click's id;
  - an entry with no stored id;
  - a blank id on both sides;
  - a landing with no id but a matching sequence and tab.

## Open questions or contradictions found

1. **The mapper reads a Core-stored domain event one level too shallow.** This
   predates this change and was observed on built Core, probes 1 and 4.
   - **Where the payload sits.** `processRecordingDomainEvent` stores
     `payload: { target?, payload }` (`model/recording-domain.ts:193-196`). A
     mapper receives `observation.payload.payload = { payload: <event payload> }`.
     `recordedEventPayload` in `web-panel-host.ts` returns that wrapper, so
     `step.payload.url` is undefined.
   - **D1's domain-event path claims nothing on a real recording.** Neither the
     click's URL nor the landing's is read. Its rows pass only because they
     build domain events one level deep, which Core never produces.
   - **W25 misses a URL change.** `namesAnotherDocument` never sees a
     domain-event URL, so a navigation recorded between the addition and the
     click does not stop the wait.
   - **Navigation proposals are likely affected too.** A `web.browser.navigate`
     proposal from a domain-event navigation would read no `url`. This is
     inferred from code, not run.
   - **The fix is small but a supervisor decision.** Make
     `recordedEventPayload` read Core's `{ target?, payload }` wrapper, then
     rebuild those rows in Core's shape. It changes D1, W25 and navigation
     proposals on real recordings, which this dispatch said not to change. With
     it, `storedStep` folds back into `recordedStep`.
   - **Not checked:** which live events other than landings arrive without an
     input id.
2. **The same-path exclusion cannot apply to an action entry.** The field the
   rule needs is missing. Either of these would restore it, and both lie
   outside this brief:
   - Core copies a page URL from the envelope metadata. `io-bridge.ts` copies
     only `eventId` and `sourceId`.
   - The extension's landing carries the path of the page the click was on.
3. **The label.** `"Web Dom Click"` matches Core's fallback, so a linked
   click's node differs from today's only by the claim. The alternative is the
   domain's own `"Click"`. A linked and an unlinked click in one recording
   would then carry different labels.
4. **The domain now mirrors a Core function.** The Core row (M7) turns any
   drift into a failing test. The lasting alternative is w19-d1's other option:
   Core accepts a mapper's `expectedState` for its own fallback candidate.
5. **An `AutomationStudioService` without `dataDir` still writes relative to
   the working directory.** Item 3 wrote `recordings/` and `indexes/` into the
   repository root, even though the project was unknown. Other code that builds
   a service without `dataDir` should expect that.
6. **`domain.test.ts` is exactly at the 400-line advisory threshold.** One more
   line raises a warning.
7. **Structure baseline:** no entry needs changing.

### Paragraph for the recording architecture page

> A recorded click proposes where it landed. Core shows each recording mapper
> call the next 32 mapper-visible timeline entries (`following`). The web mapper
> (`domain/src/web-panel-host.ts`, builder
> `domain/src/runtime/expectation/click-landing.ts`) looks there for explained
> `web.page.navigated` entries (`metadata.transition: "explained"`) that name the
> click, and takes the **last** one, since a client redirect can commit twice.
> A click the extension sends with its action input id, which is how live clicks
> are recorded, reaches the mapper as Core's `action` entry. Core's IO recorder
> keeps the recording event's id on that entry as `metadata.eventId`, and a
> landing names the entry only when its `metadata.explainedByEventId` equals that
> stored id verbatim. The mapper reads the landing's URL where Core stores a
> domain event's payload, `payload.payload.payload`. For a linked click entry the
> mapper returns the candidate Core's fallback (`recordingActionEntryCandidate`)
> would propose, with the same output, parameters, source input, confirmation,
> confidence `0.95` and label, plus the claim. An action entry with no linked
> landing, one that is not a click, and one Core marks `policyEligible: false`
> all map to `null`, so Core's fallback stands for them. A click that arrives
> as a click domain event is instead named by an event id rebuilt from its sequence
> and timestamp, or, by a landing with no id, by its sequence within the same tab.
> The claim is
> `{ conditions: [{ assert: { kind: "url", expected: <path> } }], mode: "all", timeoutMs: 5000 }`:
> a path only, judged as a substring of the page URL within 5 s. No claim is made
> when no landing names the click, or when the landing's path is `/` or cannot be
> read. A domain-event click also claims nothing when the landing is on its own
> page's path. An action entry carries no page URL, so that rule cannot apply to
> it. The landing itself proposes nothing. Core lifts the claim into the approved
> Flow node's `parameterValues.expectedState`, where the host's expectation
> evaluator checks it after the click. **Current limit:** the domain-event path
> reads a Core-stored domain event's payload one level too shallow, so on a real
> recording only the action-entry path claims (`reports/w19-d1b.md`, open
> question 1).
