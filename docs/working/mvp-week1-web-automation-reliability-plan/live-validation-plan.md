# Week 1 live validation plan

Written 2026-09-12 by the senior supervisor agent, after Waves 1–3 landed and
before any live run. Its inputs are three read-only audits:
[v-facility](./reports/v-facility.md) (what the Lab can actually do),
[v-criteria](./reports/v-criteria.md) (how far each exit criterion really is),
and [v-inventory](./reports/v-inventory.md) (every unverified claim across
twenty-eight worker reports).

The plan's own rule governs this document: a phase is not closed on unit tests
or compilation alone. Everything below exists because something is currently
believed on the strength of a green gate rather than an observation.

---

## Safety rules, before anything else

These are not preferences. Each is a way to destroy the user's data or waste an
hour, and two of them were established the hard way this week.

1. **Never run `--target existing`.** It writes durable recordings and run
   history into `F:\!FluxIQWebExtension\.fluxiq\`, which is the user's real
   FluxIQ install, and it is documented as never validated live. Everything in
   this plan uses `isolated`.
2. **Never edit `.env.local`.** It configures the existing install. Because it
   sets `FLUXIQ_TEST_TARGET=existing`, every isolated command needs the prefix
   `FLUXIQ_TEST_ENV_FILES=none`, which skips both env files for one run. Without
   it a bare `pnpm lab run` throws on a missing project id, and
   `--target isolated` throws a conflict. That failure is fail-safe, but nothing
   runs until the prefix is set. `pnpm lab:interactive --target isolated` is the
   only exception.
3. **No two Lab, e2e or build commands may overlap.** Every `pnpm lab`
   invocation runs `extension test:e2e:build`, which does `rm -rf dist/` and
   `rm -rf build/`. A second command reading those directories mid-delete fails
   in ways that look like product defects. Lab runs are also headed and call
   `page.bringToFront()`, so they fight over the desktop.
4. **`domain/dist/host/web-panel-host.mjs` is not regenerated by the domain
   build.** Deleting `domain/dist` wholesale — which the fresh-clone proof in
   `repository-layout.md` tells you to do — destroys it, and `pnpm build` does
   not bring it back; it comes from `host:build`, which `pnpm dev` and the Lab
   run first. If you delete `domain/dist` for any reason, restore or rebuild the
   host module before starting a Lab run, or the panel will fail to load the
   domain.
   The earlier hazard here — `pnpm check` rewriting the `dist` a Lab run was
   loading — is **closed**. `packages/test-runner` now builds the domain only
   when `domain/dist` is absent, so a check during a Lab run finds a `dist` and
   leaves it alone. The guard's precondition is the negation of the hazard's.
5. **Preserve `test-runs/persistent-isolated/`.** It already holds
   `interactive-smoke`, `interactive-smoke-2` and `llm-dev`. There is no reset
   command; they are deleted only by hand. Do not clean them up.
6. **Capture every exit status by redirect, never through a pipe**, and run the
   content harness as
   `pnpm --filter @fluxiq-web-extension/extension run test:content --workers=4`.
   Note the `run` and the absent `--`: `test:content -- --workers=4` makes
   Playwright read the flag as a filename filter and silently run **zero**
   tests, reporting nothing wrong.

## Reading a failure on this machine

**This machine has faulty RAM. Confirmed by the user on 2026-09-12.**

The diagnosis: a build died inside pnpm's own installed code with
`SyntaxError: Unexpected identifier 'bunction'`, while the file on disk was
correct and contained no such string — so the corruption happened in memory
while reading a correct file, and `f` (0x66) to `b` (0x62) is a single flipped
bit. Every environmental failure catalogued below fits that one cause.

What this means for anything measured here: a rare, load-correlated failure that
does not reproduce on a quiet rerun is hardware. The tells are uniformity (every
test failing identically) or impossibility (an error inside a dependency's own
source that the file on disk does not contain). **A partial failure with real
assertion diffs is still a real failure and must be chased.**

It also means a long benchmark run can contain failures that are pure noise. A
single red row inside one is not evidence until it reproduces. When reporting
results from this machine, say which findings rest on a single observation.

The three shapes below are the same fault wearing different clothes. Mistaking
one for a regression cost hours before the cause was understood.

| Symptom | Cause | What to do |
| --- | --- | --- |
| `tsc` exits 3221225477 / segfault | Windows access violation under parallel load | Rerun alone once |
| Core vitest workers vanish; `Error: Worker exited unexpectedly` | A native SQLite module corrupts under parallel load | Run Core tests `--no-file-parallelism` |
| **All** content-harness tests fail, every one a 30 s timeout with no assertion diff | Playwright concurrency | Rerun at `--workers=4` |

The tell in every case is uniformity. A partial failure with real assertion
diffs is a real failure.

## What live validation can and cannot settle

**It can.** The real unpacked extension is loaded and driven today — this was
the open question the whole plan hinged on and the answer is yes. Two
independent drivers exist: `packages/test-runner/src/run-scenario.ts` launches a
persistent context with `--load-extension`, waits for the MV3 service worker,
opens the side panel as a control page and drives it with real
`chrome.runtime.sendMessage` and `chrome.tabs` calls; and
`apps/extension/e2e/fixtures/extension-context.ts` does the same without Core,
and is the only thing that proves MV3 worker restart. The "T3 tier" earlier
documents refer to is a label the plan invented, not a facility feature.

**It cannot, yet.** Four of the six exit criteria cannot be honestly proven by a
run today, for reasons that are code changes rather than longer runs. Those are
in flight; this plan assumes they land, and says at each step what to do if they
do not.

## Execution order

Ordered by diagnostic value per minute: cheapest and most localising first, so a
failure is attributed before the expensive steps run. Steps 1–3 are safe to run
concurrently with each other **after** one serialized warm-up build; from step 4
onward everything is strictly serial.

### Step 0 — warm-up build (serial, ~2 min)

`pnpm build` once, alone, so the later headless suites are not each racing to
produce `dist/` and `build/`. Nothing else may run during it.

### Steps 1–3 — headless suites (concurrent, ~5 min)

1. Root `pnpm test` — extension, domain, scenario-lab, test-runner, contracts.
2. `test:content --workers=4` — the content harness against the built bundle.
3. Scenario-lab `test:e2e`.

These prove page-side behaviour and nothing about the background worker, tab
routing or the gateway. Their value here is that they localise: if step 4 fails
and these passed, the fault is in the parts only step 4 exercises.

### Step 4 — the extension e2e fixture (serial, ~3 min)

`apps/extension/e2e/fixtures/extension-context.ts`, the real extension without
Core. This is the **first step that proves anything about the background
worker**, and it is the only thing in the repository that proves MV3 service
worker restart. Run it before involving Core, so a failure is attributed to the
extension rather than the gateway.

### Step 4b — reproduce the silently dropped recorded action (serial, ~30 min)

**This goes ahead of everything else that needs the Lab**, and it is the reason
the live sequence exists at all.

In one `basic-form` run of four during Wave 2, a click was recorded correctly —
`web.element.clicked`, one event — and then only four of five candidates were
proposed, so the Flow lost the action and nothing reported it. The rerun passed.
It has never been diagnosed, and nothing in Waves 2 or 3 touches it.

It is the only known defect where the product loses a user's action and reports
success. Every other failure in this plan announces itself; this one does not.
A benchmark run over a recording lane that can silently drop a step measures a
number it cannot explain, so this must be understood before step 7 means
anything.

Approach: run the `basic-form` recording lane repeatedly on `isolated` — the
observed rate is roughly one in four, so budget at least twenty runs — capturing
the recorded event stream and the proposed candidate set for every run, and diff
them on the failing one. The question to answer is not "does it still happen"
but **where the action is lost**: recorded and not proposed, or proposed and not
persisted. Those are different bugs in different modules.

If twenty runs do not reproduce it, that is a result worth recording, not a
clean bill of health — say what rate the sample rules out.

### Step 5 — one isolated element-targeted replay (serial, ~5 min)

The highest-value single run in this plan. `v-inventory` established that four
separate unverified claims hang off one chain, and one element-targeted replay
closes all of them:

- that `implicitRole` arriving actually improves a resolution (proved to arrive, never proved to help),
- that the reordered wire target's twelve signals reach the page,
- that the scoring calibration transfers from the harness to a Flow,
- and that the element-target confidence floor's new fast-fail on a missing fingerprint behaves as intended rather than refusing legitimate work.

That last one is a **behaviour change, not merely an unproven claim** — the
element-target floor now fails an action with no normalizable element signal
instead of letting it reach the page. If it is wrong it is a regression.

### Step 6 — the smoke corpus (serial, ~5 min)

`FLUXIQ_TEST_ENV_FILES=none pnpm lab bench --corpus smoke --target isolated`.
Eight historical smoke benches sit on disk, newest all-passing, so this is the
only step with a **baseline to compare against** rather than a first
observation. A regression here is unambiguous.

### Step 7 — the week1 corpus (serial, 70–110 min)

`FLUXIQ_TEST_ENV_FILES=none pnpm lab bench --corpus week1 --repeat 3 --target isolated`.

Do not start this until the bench honesty fixes have landed. Before them the
run is actively misleading: `initialExecutionSuccess` counts a run in which
FluxIQ executed **nothing** as a success, and sixteen of twenty-three runnable
rows are in exactly that state. Timing is extrapolated from eight historical
smoke benches (45–72 s per run, mean 57 s), not measured; the plan's earlier
45-minute estimate was wrong.

### Step 8 — the two behaviour changes, deliberately

Both are regressions if wrong and neither has been observed live:

- the element-target floor failing fast on a missing fingerprint (step 5 may
  already have covered it; confirm rather than assume),
- `web.dom.assert` reporting `TIMEOUT` with status `timed_out` where it
  previously reported `STATE_MISMATCH`.

## What to record

For every step: the browser and build target, the page, the extension state,
the exact command, the observed exit status captured by redirect, and the
counts. Distinguish verified behaviour from remaining assumption in the ledger
entry, and never paste a pairing token, bearer token, recorded page content or
anything from `.fluxiq` into a report.

## Known gaps this plan does not close

Recorded so nobody reads a green run as more than it is:

- **Level 2 target scoring cannot succeed as calibrated.** Reaching it requires
  losing the recorded identifiers, and their absence costs more than the floor
  allows; measured ceiling 0.270 against a floor of 0.35. Under investigation.
- **The recording lane executes at most two hard-coded probe actions and never
  the workflow.** Playwright drives the fixture while the extension records. A
  recording-lane pass is not evidence that FluxIQ drove anything, and the bench
  is being changed to report the executed-action count so that cannot be
  misread.
- **Firefox is untested throughout.** Every step above is Chromium.
- **`RunEvaluation` has no producer outside the bench**, and
  `lane-observation.ts` is populated by both lanes and read by nothing.
