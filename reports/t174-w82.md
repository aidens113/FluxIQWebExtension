## What changed and why

All paths are under `domain/src/runtime/llm-evidence/node-run/`.

- **Cause 5 (field lost its name).** `observed-control.ts`:
  - `webObservedControl` now names a control with `webLlmElementWords(element)`, which is the view line's own words function in `page-view/element/words.ts`, not a copy of it. The identity fallback also reads `label`.
  - New `webLabelledIdentity`. When the resolved `element` identity has no `accessibleName`, `visibleText` or `label`, and the look before acting shows the control with a whole label, it writes that label into `element.label`. It skips withheld text and controls that hold a secret, following the same rule as `element-identity.ts`.
  - `run.ts` wraps `ran` with it, so the dispatched command and `ranWith` (the stored node) both carry the label.
  - Why `label` and not `accessibleName`: the page computes a candidate's `accessibleName` only from labels the page associates with the field (`apps/extension/src/content/identity/accessible-name.ts`). It computes `label` from nearby text too (`identity/label.ts`), and that is the same reader that filled the packet's `label`.
  - In this run the packet's `name` was empty: 0024 had no `control`, and `webObservedControl` read `name ?? text`. So "Quantity" came from `label`.
  - If it were recorded as `accessibleName`, Core's scorer would give `-0.45` for "candidate is missing text" (`fingerprinting/element-fingerprint.ts:269`). The extension's veto (`identity/veto.ts` rules 1 and 2) would then refuse the field. Before this change the node had no name to compare, so nothing was refused.
  - I did not touch `element-identity.ts`. Adding `label` to `WebPlanElementIdentity` would break `present<>` in `plan-resolution/target-packets.ts` `agreedIdentity`, which is not my file.
- **Cause 14 (refusals name no notice).**
  - New `press-effect/notice.ts`. `webNodePageNotice(before, after)` returns the text lines that appeared or now read differently on the same page, at most 3, in the view's form (`t968 "Please select a Color."`). The words come from the view's line facts, so they are already screened.
  - `webNodeNoticedDetail` adds `detail.notice` to a `refused_by_page` refusal only. Busy (`RATE_LIMITED`) maps to the same code, so it gets the notice too, and its reason stays `page_busy_try_later`.
  - It is called from the `run.ts` catch block with `record.found` and the refusal's page. `resultReason` does not change.
  - New `press-effect/text-line.ts` holds the shared text-line rule, which `page-changes.ts` now imports instead of keeping a private copy.
- **Cause 1 (un-chose the pressed control).**
  - New `press-effect/choice.ts`. `webPressChoice` compares the pressed handle's line before and after, where chosen means the line has the token `marked`, `selected` or `checked`.
  - It produces `This press un-chose "Space Grey": it was chosen before.` or `This press chose "Silver": it was not chosen before.`
  - The new `WebNodeOutcome.choice` field (`outcome.ts`) sits ahead of `changed`. It is only information; the press still runs.
- **Cause 4 (test reads a refused press as replayed).** `replay.ts` and `replay-answer.ts`:
  - For a replayed in-place mutate step (press, type or select; not navigation, not read), the replay now takes a quiet look before dispatch. It restamps that page and does not mark it shown.
  - On failure, `failedOnPage` answers `core.replay.failed` on the page as before, plus `notice` when the refusal is `refused_by_page`. Busy semantics are unchanged: it is still failed, with reason `page_busy_try_later`.
  - On success, it takes a second quiet look and answers `core.replay.replayed` with `changed`, the F37 change lines, and still no page.
  - `WebNodeReplayAnswer` gains `notice?` and `changed?`. `webNodeReplayPage(run, shown = true)` gains its `shown` flag.
