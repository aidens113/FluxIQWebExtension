## What changed and why

### Item 1 (Cause 7): the judges get the page the run or test ended on

Where Core holds the page at judge time, and where it does not:
- **Build-test judge.** The test report's `observations[].evidence` holds whatever the domain answered for each step.
  The web domain sends the page view only with a failed, remembered or checked answer
  (`!FluxIQWebExtension/domain/src/runtime/llm-evidence/node-run/replay-answer.ts`, `webNodeReplayAnswerOnPage`).
  A passing replayed press sends no page (`replay.ts` header). So Core holds the end page only when the test's last
  answer carried one. In `run-murwd8le` the last step (Add to cart) answered `replayed` with no page, so nothing was held.
- **Post-run check.** Nothing in Core holds a page view. Attempt records, trace attempt outputs (url and title only, as in
  0085's `result.json`) and `stateRefs` (snapshot ids) all lack one.

What I built (all of it is screened and sent once, beside the summary):
- `result-verification/result-summary.ts`: a new summary field `endView: { after?, view }`.
  - Types `AutomationStudioResultEndView` and `AutomationStudioRunResultSummaryWithEndView`.
  - `automationStudioResultEndView()` screens the view. It sends nothing when no denied keys are declared. It sends
    nothing when the view holds a denied key or a credential-shaped value, so a page goes whole or not at all. Either case
    sets `withheld`.
  - `automationStudioResultEndViewRead()` reads the view through a port. A failed read is carried as the error's kind and
    sets `withheld`. It never ends the verification.
  - `summarizeAutomationStudioRunResult` gains the inputs `endView` and `endViewUnreadable`.
- `result-verification/build-test/summary.ts`:
  - It takes an optional `endView` that the caller captured after the test.
  - Without one, it uses the domain's view keys from the test's **last** observation, tagged `after: <step>`.
  - It never uses an earlier step's view, because a later step may have changed the page.
- `result-verification/run-outcome.ts`: a new optional port `readEndView({ projectId, runId, flowId })`. Its result is
  passed to the summary.
- Prompt (`llm/diagnosis-instructions.ts`): one sentence in the shared result-verification instruction says what
  `resultSummary.endView` is and how to read it ("do not suppose a step left undone what the view shows done").
- Token limits: the judge's reply cap is unchanged (`automationStudioLlmJudgeTokenLimits`). The input grows by exactly
  one page view. `build-test/tests/request-size.test.ts` was re-bounded with its arithmetic stated:
  - run 36's cut request is now 11,158 characters (8,113 before, plus one 2,962-character view);
  - the bound is 14,000, which a second view (at least 2,845) would break;
  - a new assertion checks that exactly one view appears in the whole request.

### Item 2 (Cause 8): the post-run `flowShape` follows the run's execution order

- `result-summary.ts` (`inRunOrder`, private) orders the nodes when edges are given:
  1. A depth-first walk numbers the nodes and finds each loop's return edge. A node's way on is walked before its
     `failed` way.
  2. A topological order is taken over the remaining edges, breaking ties by that numbering.
- Result: a merge comes after both of its branches, and a loop's return edge changes nothing.
- `run-outcome.ts` now passes `flowEdges: input.flow.edges`.
- I did not reuse the build-test judge's approach. Its order is right only because it reads the plan's nodes in authored
  order, and a stored Flow does not keep that order. The other existing walk, `orderedNodes` in
  `llm/node-tools/draft-from-flow.ts`, is private and outside my files.

     `this.llmEvidenceRuntime.executeTool(...)` — that is, the web domain's `web.output.dom-capture_snapshot`, the same look

     the whole check into "did not finish".

   - (a) `service/flow-bootstrap-commands/build-judge.ts` captures it at judge time, through the same binding look, and
     passes `endView` to `automationStudioBuildTestResultSummary`; or
   - (b) `llm/node-tools/replay-draft.ts` or `dry-run-gate.ts` captures it after the last step and puts it on
     `AutomationStudioFlowDraftTestReport`.
   - Either way, add `endView` to the call in `build-judge.ts`.
3. **Contract placement.** `endView` belongs on `AutomationStudioRunResultSummary` in `result-verification/contracts.ts`,
   which I did not own. It is declared as an intersection in `result-summary.ts`, with a TODO to move it. It is sent on the
